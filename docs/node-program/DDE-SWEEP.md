# DDE sweep: base-sdk decode domain against Dash Core (BS4a)

**Task:** BS4a (PLAN row; A1 §1.4 rule DDE, rows #1–#9; A1 §2.14 per-command decode policy; Opus m-17 sweep).
**Base-sdk branch:** `node/bsdk-bs4a-decode-domain` in `~/workspace/base-sdk` at 3c971b1 (after fix round 3), on `node/base-sdk` 098dafd (upstream `develop` 33fcc59 plus BS11a-t). 3c971b1 differs from 0c71f50 (fix round 2) only in a doc comment, so `dde-probe`'s `oracle/` and `bench/` keep their 0c71f50 pins and the round-2 measurements stand.
**Reference:** Dash Core v23.1.8 (mainnet pin) and v24.0.0-rc.3 (testnet pin). Every row below holds at both pins unless it names one.

Rule DDE: for every type the node decodes from untrusted bytes, base-sdk accepts exactly the byte strings Core's handler accepts, in the same handler state, with the same treatment of optional, trailing and empty input. Range, semantic and policy checks belong to rules, not decoders.

## 4. P2P: the per-command decode policy (A1 §2.14)

Line numbers are `v23.1.8 / v24.0.0-rc.3`; `np` is `src/net_processing.cpp`. "Verified" means the outcome was observed on regtest dashds of both pins (§6) and is asserted by the probe; "source-pinned" means `check_sources.py` asserts the cited code at both tags; every other statement is from Core source at both tags. A gate that runs before the read means Core never sees the payload, so no payload bytes change the outcome.

**What is settled.** The transport rules, the gates of §4.0, and in the tables the "Before the read", "Handler reads" and "Decode failure" columns, the **catch** marks and the trailing-byte rules are BS4a's normative decode policy: base-sdk's decoders and the `dashd-p2p::policy` mapping in §4.0.1 follow them. The "After the read" column is **informative**. The handler behaviour after a successful read (punishment tables, disconnect conditions, early returns, rate limits) is owned by `dashd-p2p` (P2a) and the overlay tasks (BS7–BS10, BS8, BS9a, BS9b), which re-derive it from Core source at both pins when they implement it. It records what the sweep found, with known gaps, and is not a specification.

### 4.0 Core's generic rule and the gates

**Transport.** Both run before any command is looked at.
- **V1.** A header length above 3 MiB (`MAX_PROTOCOL_MESSAGE_LENGTH`, below `MAX_SIZE`) disconnects before the command is checked (`net.cpp` 737 / 738). A bad checksum, or a command with bytes outside 0x20–0x7e or non-zero bytes after its first NUL, drops the message and keeps the peer (`reject_message`, `net.cpp` 795-806 / 796-807). A dropped message never reaches `ProcessMessage`, so no gate below counts it. The all-zero command is valid and reaches the handlers as the empty type. Verified with payload `010203`: commands with a non-zero byte after the NUL, 0x7f, 0x1f or 0x80 log "Header error: Invalid message type" and keep the peer; `pi ng` and the empty command log `Unknown command`.
- **V2.** The decrypted contents, type included, may be at most `1 + 12 + 3 MiB` = 3,145,741 bytes (`MAX_CONTENTS_LEN`). Core checks the decrypted length before the type and disconnects above it (`net.cpp` 1303-1310 / 1297-1304). A short-ID message may therefore carry a payload of 3 MiB + 12 bytes, a long-form one only 3 MiB. Empty contents, a short ID outside Core's slots (1–32 and 128–168, `IsValidV2ShortID`), a long-form type under 12 bytes, or a type with bytes outside 0x20–0x7f or non-zero after its first NUL drop the message and keep the peer (`GetMessageType`, `net.cpp` 1502 / 1496). The slots without a message, 5 and 29–32, give the empty type, which reaches the handlers as an unknown command. Verified: short-ID payloads of 3,145,728, 3,145,729 and 3,145,740 bytes are read; 3,145,741 disconnects; long-form 3,145,728 is read and 3,145,729 disconnects; short IDs 0xfe and 33 are dropped at 9 bytes of contents, and 0xfe disconnects at 3,145,742; short ID 5 logs `Unknown command ""`. Long-form types: a non-zero byte after the NUL, 0x1f or 0x80 are dropped; 0x7f, which V1 refuses, `pi ng` and the all-zero type log `Unknown command`.

**Gates before any handler reads, in this order** (`PeerManagerImpl::ProcessMessage`):
1. A second `version` is ignored (3907-3910 / 3936-3939). A `version` that failed to decode or disconnected leaves the peer pre-version.
2. Any other message before `version` is ignored (4147-4151 / 4178-4182).
3. Between `version` and `verack` only `verack`, `sendheaders`, `sendheaders2`, `sendcmpct`, `sendaddrv2` and `sendtxrcncl` are handled; anything else is ignored as "Unsupported message prior to verack" (4318-4321 / 4363-4366).
4. **Masternode probe connections:** the first message after `verack` must be `mnauth`, or the peer is disconnected (4323-4334 / 4368-4379). The check runs after the step-3 handlers, so `version`, `verack`, `sendheaders`, `sendheaders2`, `sendcmpct`, `sendaddrv2` and `sendtxrcncl` are handled without it; any other command, unknown ones included, counts.
5. **Blocks-only:** when `RejectIncomingTxs` holds, a command in `NetMessageViolatesBlocksOnly` disconnects before any read (4336-4341 / 4381-4386). `RejectIncomingTxs` holds for block-relay-only and feeler connections, and under `-blocksonly` for a peer without the `relay` permission (6127-6135 / 6273-6281). The set (`protocol.cpp:185-212`, the same at both tags) has 26 commands: `tx`, `dstx`, `dsa`, `dsc`, `dsf`, `dsi`, `dsq`, `dss`, `dssu`, `getqrinfo`, `qrinfo`, `platformban`, `qsendrecsigs`, `qsigrec`, `qsigsesann`, `qsigsinv`, `qgetsigs`, `qbsigs`, `qsigshare`, `qcontrib`, `qcomplaint`, `qjustify`, `qpcommit`, `qgetdata`, `qdata`, `qwatch`. Verified for `qsendrecsigs`, `tx`, `dsq` and `qwatch` with empty payloads under `-blocksonly=1`: "sent in violation of protocol", disconnect, no exception. On a default node the same payloads are not disconnected: `qsendrecsigs` throws and is logged, `qwatch` scores +10, and `tx` and `dsq` are not read (IBD, not synced).
6. **Loading blocks** (`fImporting || fReindex` at v23): `cmpctblock`, `blocktxn`, `headers`/`headers2` and `block` are ignored before the read (4978, 5221, 5234, 5274 / 5055, 5298, 5311, 5351).
7. **IBD:** `tx` and `dstx` return before the read (4815 / 4865).
8. The handler's own gates, in the "Before the read" column below.

**The exception rule.** A read past the end, a size above a `LIMITED_*` bound or `MAX_SIZE`, a non-canonical CompactSize and the other stream errors throw `std::ios_base::failure`. Unless the handler catches it (**catch** in the tables), `ProcessMessages` does (5794 / 5940): it logs "ProcessMessages(*cmd*, *n* bytes): Exception … caught" (category `net`, so only with `-debug=net`), without a peer id, and the peer is kept with no penalty. Handlers that catch and score: `filterload`, `filteradd`, `govsync` (the bloom filter only), `govobjvote`, `spork`, `getqrinfo` (v24), the sig-share messages, and the DKG messages' intake checks.

**Trailing bytes** after the handler's last read are ignored, with two exceptions, both v24 only: a DKG message must be consumed whole (+100, `llmq/net_dkg.cpp:600-603`, and again in the worker, `:372-383`), and a `qgetdata` longer than its 67-byte request is +100 (`llmq/net_quorum.cpp:90-93`).

**Unknown commands** are logged "Unknown command" and ignored (5684 / 5828; verified). `merkleblock`, `cfilter`, `cfheaders` and `cfcheckpt` are in `allNetMessageTypes` but have no reader; they are ignored without that log line.

**Penalties.** `Misbehaving` adds to a score. When the score crosses 100 the peer is marked for discouragement once (np 1933-1955 at v24), and `MaybeDiscourageAndDisconnect` (5689-5727 / 5833-5870) then disconnects it, unless it has `noban` or was connected manually. A local peer is disconnected but not discouraged; any other is discouraged and `DisconnectNode(addr)` drops every connection from its address. "+100" below therefore means a disconnect for an ordinary peer.

### 4.0.1 base-sdk API and the `dashd-p2p::policy` mapping

- `decode_v2_payload(cmd, payload, &ProtoCtx)` (BS7 r1) decodes a V2 payload kept apart from its type under V2 rules: the contents limit after the shortest type that carries `cmd` (a 1-byte short ID if Core maps one to it, else the 13-byte long form), and `is_valid_v2` (0x7f allowed in a long-form type). `decode_with_policy` is V1 only.
- `P2pMsg::decode_with_policy(cmd, payload, &ProtoCtx)` decodes a V1 message; it applies the V1 3 MiB bound (`PayloadTooLarge`), then Core's V1 command check (`InvalidCommand`, `CommandString::is_valid_v1`).
- `split_v2(contents)` applies the V2 bound to the whole contents (`ContentsTooLarge`), then types it as Core's `GetMessageType` does and returns a `V2Message`: a long-form type must pass `CommandString::is_valid_v2` (`InvalidCommand` otherwise), and a short ID without a message fails with `UnknownShortId`, including the slots Core reserves (5, 29–32), which Core types as the empty command and ignores: drop the message, keep the peer (BSX Q-26). `V2Message::decode(&ProtoCtx)` decodes its payload without the V1 bound; only `split_v2` builds a `V2Message`, so the payload is always within the V2 bound. `decode_v2(contents, &ProtoCtx)` does both; a policy that needs the command of a payload its handler rejects calls the two itself. Tests: `v2_contents_are_bound_as_core` and `v1_commands_are_checked_as_core` (Core-judged), `v2_type_errors_differ_from_payload_errors` (from source, short ID 32).
- An unknown command decodes to `P2pMsg::Unknown { command, payload }`.
- A command whose handler reads nothing ignores its payload (`consumed = 0`).
- A typed message decodes the handler's reads under the context (`MsgDecode`) and reports `consumed`.
- A raw stub keeps the payload (`consumed = len`) until its owner types it.
- A command Core knows but has no handler for (`merkleblock`, `cfilter`, `cfheaders`, `cfcheckpt`) is ignored unread by Core (verified: no log line, the peer stays). base-sdk decodes them to their typed variants in both directions, for SPV clients (BSX D-14); `dashd-p2p` ignores them before decoding (§5).
- V1 framing (BS7): `V1Header::check` is `readHeader`'s order (magic, then the 3 MiB length; both disconnect) and `V1Header::check_payload` is `GetReceivedMessage`'s (checksum, then the command bytes; both drop the message and keep the peer). `V1FrameError::disconnects` says which. Verified at both pins, with the dropped ping left unanswered.
- V2 send gate (BS7): `ShortId::for_send(cmd, common_version)` is `SetMessageToSend`'s: a slot of `V2MessageMap` (the empty type takes slot 5) from common version 70235, `platformban` from 70240, and the long form before the peer's `version` (`m_peer_version` starts at 209). `encode_v2` applies it. The table equals Core's at both tags (`bs7_short_ids.py`, base-sdk `short_ids.json5`).
- `ProtoCtx { version, bls }` carries the negotiated version and the BLS scheme. The scheme type is `dash_pkc::bls::BlsCtx` from BS11a-t (DEC-24 D2), merged into `node/base-sdk`; BS4a's placeholder was dropped in the rebase and BS4a uses only `BlsCtx`, `BlsCtx::BASIC` and its derives.

| base-sdk result | Core's outcome (`dashd-p2p::policy`) |
|---|---|
| `PayloadTooLarge` (V1), `ContentsTooLarge` (V2) | disconnect |
| `InvalidCommand` (V1 and V2), `UnknownShortId`, `EmptyV2Contents`, `TruncatedV2Type` | drop the message, keep the peer (verified for the command cases); it never reaches `ProcessMessage`, so it is not the first message of a probe connection (from source: `net.cpp` 664-671 / 665-672, gate 4) |
| `P2pMsg::Unknown`, including the empty type (an all-zero command, or a reserved V2 short ID) | log "Unknown command", ignore (verified); before `verack` the step-2 and step-3 gates apply, and on a probe connection gate 4 disconnects |
| `TooManyEntries` (`headers`, `headers2`) | +20, nothing more read |
| `VersionTail { head, .. }` | run the `version` checks on `head` (outbound services, obsolete version), then log and keep the peer pre-version |
| any other `decode_with_policy` error | the command's "Decode failure" cell: logged with no penalty unless marked **catch** |
| `Ok` with `consumed < payload.len()` | ignore the rest, except the two v24 trailing-byte rules above (owners BS8, BS9a) |

## 5. Open divergences by owner

Found by the sweep, outside BS4a's scope because the owning task reshapes the type. Each owner verifies with the `diff_*` target its PLAN row names.

**BS6a (payload shapes, BLS fields)**
- ProRegTx/ProUpServ/ProUpReg/ProUpRev: for `nVersion == 0` or above `GetMax`, Core reads only the version and returns. A 2-byte payload `0400` is a complete payload for Core (then `bad-protx-version`), but an end-of-data error for base-sdk (then `bad-protx-payload`).
- NetInfo v3 (ExtNetInfo): an entry of unknown type reads nothing in Core but is a decode error in base-sdk. v24 limits domain names to `LIMITED_STRING(253)`. A version of 0 or above the current one reads nothing more in Core (`netinfo.h` 413 / 425); base-sdk still reads the groups. A Service entry whose address fails to decode (e.g. IPv4 with length 5) is caught in Core and marked invalid, and the stream continues where the read stopped, at both pins (`netinfo.h` v23 244, v24 252); so is a Domain entry at v23 only (v23 250; v24 260 propagates the failure). base-sdk fails the whole payload, which changes the bytes consumed and the reject reason (`bad-protx-payload` instead of the NetInfo rule). BS4a r2 already makes the groups a map as Core's `std::map<NetInfoPurpose, NetInfoList>` is: a repeated purpose is read and dropped, and the groups come out in purpose order (Core-judged by `decoderawtransaction` at both pins, base-sdk test `net_info_groups_follow_cores_map`), so the groups, their order and the map framing re-encode as Core's do. That is not yet parity for the whole NetInfo, because the entry decoder still differs: Core marks an entry it cannot use invalid (`Clear()`) and re-serializes it as the one byte `ff` (`netinfo.h` `NetInfoEntry::Unserialize`/`Serialize`, 235/220 / 243/228). Likewise Core reads and discards the entries of a repeated purpose's group even when they are invalid, where base-sdk can still fail on one. Entry normalization belongs to BS6a, with the version and address decoders above.
- CbTx: v4 asset-unlock root (v24); `nHeight` is `int32_t`.

**BS9a, BS11a (DKG, IES)**

- DKG intake differs by pin (§4.2, source-pinned by `check_sources.py`): v23 decodes a copy with BLS, requires the complaint and premature-commitment bitsets to equal the quorum size and allows trailing bytes; v24 walks the framing without BLS, bounds the bitsets by the quorum size (the equalities come later, after the unrequested +10) and requires the whole payload. BS9a's typed decode must keep both shapes per pin. Sig-share `sessionId` is a `VARINT` (§2).

**BS10 (all commands typed)**
- `addrv2`: Core keeps BIP155 IPv6 `fc00::/8` as IPv6 (base-sdk makes it CJDNS, which re-encodes as network 6). IPv4- and TORv2-in-IPv6 become the invalid `::` address, and INTERNAL becomes NET_INTERNAL. Unknown network ids are skipped and stored as `::`.
- `addr`: a v1 TORv2-prefixed address becomes `::`.
- These change field values and re-encoding (relay), not decode verdicts.

**Rule layer (CS3, EV1, `dashd-p2p`)**
- BS7 after BSX (DEC-98): base-sdk is strict where Core is lenient, and `dashd-p2p` keeps Core's outcome where a peer can observe it. None of these is needed for interop: honest Core nodes never send the shapes involved.
  - `headers2` (D-07): Core's `Uncompress` rebuilds a first header with fields left off, and a version offset past the list, with zero fields; validation then rejects the header, and the peer gets `BLOCK_INVALID_HEADER`'s +100 (np 2000 / 3364) where base-sdk's decode error gets Core's "log, no penalty". A version-zero header is not always invalid: `bad-version` (`validation.cpp:4513-4518`) applies only once HEIGHTINCB, DERSIG and CLTV are active, so it is accepted on a chain with those postponed (regtest `-testactivationheight`; Sol BSX r1 M4). Reject reasons and penalty parity live node-side (BSX Q-1, DEC-98): if P2a needs them, `dashd-p2p` uncompresses leniently itself, parsing each `CompressedHeader` (base-sdk's wire parser) and rebuilding the fields as `Uncompress` does (~40 lines, a version list of 7). Not implemented; backlog for P2a.
  - `sendcmpct` (D-11): Core reads any non-zero flag as true and turns high-bandwidth mode on; base-sdk refuses it. `dashd-p2p` maps the decode error to Core's outcome or, accepting the deviation, ignores the message and keeps the peer. base-sdk reads the flag strictly in `p2p_core` until A-12 restores a strict `bool` codec in `dash-types`; then `SendCmpct` uses it.
  - `merkleblock`, `cfilter`, `cfheaders`, `cfcheckpt` (D-14): Core has no handler; "Core ignores this" moves to `dashd-p2p`, which ignores them before decoding, so a malformed payload costs nothing (backlog for P2a).
  - `headers`/`headers2` counts past the data (D-09) and `getblocktxn` (D-13): the verdict is Core's; nothing to do.
- The 10,000-byte payload rule, `bad-*-payload` on `!PayloadDecode::is_complete()`, every cap and penalty in §4, version-message disconnects, and the time clamp.
- base-sdk's `Checkable` is not normative (A1 R5), but BS4a keeps its size checks in Core's order (`bad-txns-oversize` before `bad-txns-payload-oversize`). It still treats a transaction as a coinbase when the first of several inputs has a null prevout; Core's `IsCoinBase` requires exactly one input (convergence-track fix).

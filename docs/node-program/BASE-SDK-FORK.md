# The base-sdk fork

How rust-dashcore consumes base-sdk during the node program (A1 §1.1 rule R1, §1.6; DEC-09).

## Layout

- **Fork repository:** `~/workspace/base-sdk`. Branch **`node/base-sdk`** sits on upstream `develop` and holds every fork change. Nothing is pushed.
- **Task branches:** `node/bsdk-<slug>`, cut from `node/base-sdk`, worktrees under `~/workspace/bsdk-wt/<slug>`. They follow base-sdk's CLAUDE.md/AGENTS.md (`namespace%type(scope):` commits, `just test lint`), are reviewed like any node task, and merge into `node/base-sdk` with `--no-ff`. Nothing node-specific and nothing embargoed goes into base-sdk.
- base-sdk's old empty `node/integration` branch is retired. `node/base-sdk` is the only fork branch.

## How rust-dashcore consumes it

The root `Cargo.toml` has two tables that list the same packages:

```toml
[workspace.dependencies]
dash-num = { git = "https://github.com/dashpay/base-sdk", rev = "<upstream>", default-features = false }

[patch."https://github.com/dashpay/base-sdk"]
dash-num = { git = "file:///work/home/agent/workspace/base-sdk", rev = "<fork>" }
```

- `<fork>` is a commit on `node/base-sdk`. Every build, in every worktree, uses exactly that commit, whatever is checked out in `~/workspace/base-sdk`.
- `<upstream>` is the newest upstream `develop` commit that `<fork>` contains (their merge base). Cargo still loads the upstream declaration, so it must exist on GitHub.
- Members depend on base-sdk only through `workspace = true`. The patch matches the upstream URL at any `rev`, so a member's own git pin would be silently replaced, and a path or other-URL pin would add a second copy. Both are rejected by the pin check.
- Both tables list exactly the base-sdk packages that members use directly. Packages reached only through other base-sdk packages (`dash-types-marker`, and `dash-pow`/`dash-script` under `dash-primitives`) are path dependencies inside the fork, so they come from the same pinned source without an entry. The tables do not list all eight library crates up front because Cargo warns about every unused patch on every command. To start using another base-sdk crate, add it to both tables at the current revs, then run `cargo metadata` and the pin check.
- `Cargo.lock` is committed. It records `git+file:///…/base-sdk?rev=<fork>#<fork>` for every base-sdk package.

**Overrides.** `Cargo.lock` names the source Cargo resolves, not the code it builds: a `paths` override or a source replacement in a Cargo config file builds other code while the lockfile keeps the pinned entry. So the pin check also requires, from `cargo metadata --locked --all-features`, that every base-sdk package comes from the pinned fork source and from a clean checkout of `<fork>` under `$CARGO_HOME/git/checkouts`. It reports base-sdk overrides (`paths`, a `[patch]` or `[source]` naming base-sdk, an alias passing `--config`, `include`) in every config file Cargo may load: `.cargo/config[.toml]` in the workspace root and its ancestors up to `/`, in any workspace directory other than `target/` and `.git/` (Cargo searches from the current directory), and in `$CARGO_HOME`. It reports `CARGO_PATHS`, `CARGO_PATCH*`, `CARGO_SOURCE_*`, `CARGO_UNSTABLE_*` and `__CARGO_*` variables, and `CARGO_ALIAS_*` variables that pass `--config`. Git is queried with replace refs off (`GIT_NO_REPLACE_OBJECTS=1`) and with explicit `git status` flags, so settings such as `status.showUntrackedFiles = no` cannot hide an untracked `build.rs`; a failing Git query fails the check. So does a fork workspace member that cannot be read at `<fork>`, such as a glob, which the fork does not use today.

**Threat model** (DEC-21). The pin check and the layer checks guard against accidental drift and misconfiguration on agentbox: a member that pins base-sdk itself, a second revision, a stale lockfile, a forgotten local `[patch]` or `paths` override, a stray Cargo config or environment variable, a hand-edited Cargo checkout, a new crate that reaches the dashcore stack. They do not guard against a local actor with write access to `~/.cargo`, the base-sdk fork repository or the toolchain, who already controls what gets built. Deliberately out of scope:
- forged Git objects or refs in Cargo's git database or checkouts (the replace-ref case is closed only because turning replace refs off is one environment variable);
- a one-off `--config` argument on a Cargo command line, which a separate check cannot see (the gate runs plain commands);
- toolchain wrappers and flags: `rustc-wrapper`, `RUSTC_WRAPPER`, `RUSTFLAGS` with `--extern`, a modified `cargo` or `rustc`.

Review findings in those classes are out of scope for these tools.

**Local development against a working tree.** While developing a base-sdk change, point the patch at a path in your worktree only, and never commit it:

```toml
[patch."https://github.com/dashpay/base-sdk"]
dash-num = { path = "/work/home/agent/workspace/bsdk-wt/<slug>/pkgs/num" }
```

After the base-sdk task merges into `node/base-sdk`, re-pin with `bump-base-sdk.sh`. The pin check rejects such a patch, so drop it before running the gate.

## Layer rules

SB0 §2.3 (DEC-81, DEC-119) withdrew rule R2 and its enforcement (the R2 entries of `deny.toml`, `r2_reach.py`, `check-r2.sh`). Every workspace crate now has exactly one layer in `contrib/node/layers.toml` (B base SDK, P pure, Pn pure node-only, S shared runtime, V dash-spv, N node, W the legacy dashcore and wallet stack, A products, T tests and tools), and the rules L1–L9 say which layers may depend on which.

Every package Cargo resolves is classified, member or not: from a `[b]` source (the upstream base SDK and the fork the root manifest pins) it is B, whatever its name; otherwise its `[crates]` entry; otherwise a `[patterns]` match (`dashd-*` is N). Names compare as crates.io compares them (case-insensitive, `-` and `_` alike), and sources after normalisation (scheme, user, case, `.git`, symlinks). Any other package is outside every layer. A copy of a listed crate from crates.io, git or a path has that crate's layer and is checked as a root of its own, like a member; a walk delegates to a package only when that package's allowed layers are a subset of the walker's. Every rule is keyed by package name and applies to every resolved package of that name (DEC-170), so each copy of a hot-path crate is walked like the member. A P, Pn or S copy from outside the workspace fails L1, because L4 and L5 lint workspace members only, and so does an outside copy of a name marked `pure = true`, whatever its layer. `allow_w` is a permission, not a rule: it names the workspace crates, so an outside package of the same name is plain N and fails closed when it reaches W. A ban walk passes only through layers the ban covers (and W, for bincode's exemption), so W does not hide what lies behind it. A declared dependency matches the package of its own path or source (after the root `[patch]`), not another package of the same name.
- `contrib/node/check-layers.py`: L1 (every member listed once; a listed crate that is not a member needs `pending`, and a member must not keep it; a listed name must agree with its pattern), L2 (normal and build edges, direct and transitive, point only to allowed layers: B depends on nothing of this repository, which replaces R2's ban on base SDK packages depending on W; nothing below V depends on W, V, N, A or T; N never on V; V never on N or Pn), L3 (N reaches W only through `allow_w = ["dashd-wallet", "dash-coreimport/wallet"]`; the feature-qualified entry is checked on `cargo tree -p dash-coreimport` with the feature off, which must hold no W; the hot path, every package named `dashd-chainstate`, `dashd-p2p`, `dashd-mempool` or `dashd-indexes`, reaches no W in the resolved workspace graph, walked through N and `allow_w` alike, so a feature another crate unifies onto its closure counts) and the `[bans]` (L8: no bincode, crates.io's or the workspace's `grovedb-bincode`, in the closure of a B, P, Pn, S or N package; no imbl in B, P, S or V). A row with `allocator = "own"` (`dash-spv-bench` with `heap-profile`, which installs jemalloc) must instead conflict, and the allocator must be the product package's own (DEC-188 (1)): rustc's diagnostic names a crate, which another package may share, so a second canary links every dependency the product unit is given, its own package's aside, and must link; failures name package ids (name, version, source) from cargo's own unit list. The canaries see what the product's rustc arguments name, so those arguments are allow-listed rather than parsed for known-bad shapes (DEC-188 am. 1; Sol r7 R7-1, r8 R8-1). The wrapper records every rustc unit the canary build compiles (a unit cargo finds fresh was built with the same rustflags, which its fingerprint holds and the product unit shows, and its crates reach both canaries through its rlib; an own row's own-package units, which the second canary leaves out, are recompiled every run (`cargo clean -p`), since cargo's fingerprint omits `RUSTC_WRAPPER`, and a fresh one fails the row), and cargo's `build-script-executed` records give every build script's linked paths, libraries and cfgs. One tokenizer reads all of them as rustc's getopts does (`--opt val`, `--opt=val`, `-Xval`, `-X val`, grouped short flags, long aliases). Each option must be allow-listed: the ones the registered products' units use, derived from a cold capture of all 30 (`--extern`, `-L`, `-l`, `--cfg`, `--check-cfg`, `--crate-name`, `--crate-type`, `--edition`, `--emit`, `--error-format`, `--json`, `--out-dir`, `--target`, `--cap-lints`, `-W`, `-A`, `-D`, the input file, and `-C` with the keys `opt-level`, `embed-bitcode`, `debuginfo`, `debug-assertions`, `codegen-units`, `strip`, `metadata`, `extra-filename`, `linker`, `link-arg` and `prefer-dynamic`), each with its rule. An `--extern` path must be a file cargo reported for a package of the unit graph, and a pathless one a sysroot crate's alone. `-L` takes `native` and `framework` paths, and a `dependency` path only to cargo's own `deps/`: a `crate` or `all` path, even into `deps/`, would let a bare `extern crate` load an allocator no `--extern` names. `--emit` may not name an output path, `--target` must be the row's triple, and `-C linker`/`link-arg` reach only the native linker, whose inputs are BL-92's residual. Any other option, `--sysroot`, `-Z`, an `@argfile` or `--` fails the row, naming the option and the unit or build script that gave it; one cargo itself trips on first (an `--emit` output path in rustflags breaks cargo's target-information query) fails it too, as cargo's error rather than this diagnostic (Sol r9 nit 2, left as is). Each canary keeps its units' arguments (`unit.json`, `units/`) and build-script records (`build-scripts.json`). Consumers outside the registry are out of scope: a shared or pure crate is proved only as the registered products link it (a downstream configuration that is not registered is not checked), the nested workspaces are harnesses rather than products, and the canary uses the workspace's cargo configuration, not RUSTFLAGS a product's build may add (cargo hfuzz's instrumentation); a C allocator that replaces malloc sets no `#[global_allocator]`, which `link-probe.py`'s `[[native]]` review covers for the shared and pure crates (above). A product's first build is a full release build of its closure; later runs recompile its own unit twice (the product and its rlib) and whatever dash-spv's build script finds stale when `.git` refs move: the 30 rows and triples took 32 min at load 150–190, 1–4 min per product and 2–5 s per further `dash-fuzz` target.
- `contrib/node/check-mobile.sh` (L6, L7): the default-feature normal closure of `dash-spv-ffi` and `key-wallet-ffi` on `aarch64-linux-android` and `aarch64-apple-ios` (`cargo tree -e normal`, no build needed) holds nothing `mobile-deny.toml` bans and no Pn or N package, by name, so an unlisted `dashd-*` from anywhere counts; the per-target graphs are Cargo's own (`cargo tree --target`, with edge kinds and conditions from `cargo metadata --filter-platform`, keeping only the declarations whose `cfg` holds for the target per `rustc --print cfg`), never the all-target graph mapped back; and the stripped `libdash_spv_ffi.so` for Android, built through `contrib/mobile/android-env.sh`, grows by at most min(2 %, 256 KiB) over a reference no change can move (DEC-170): the `contrib/node/mobile-size.txt` committed at the merge base with the local branch `refs/heads/node/integration`, which nothing in the change or its environment can redirect (HEAD's first parent when HEAD is `node/integration` itself, after a merge), or, while the base has none, the constant in `layers.toml`'s `[size]`, never HEAD or a record on the branch. The decision the constant cites must state each of its values (bytes, library, target, profile, NDK, API), its row on `node/integration` winning over the tree's, so a new constant needs a new decision that states it; once a merge base carries the constant, moving it also needs a decision new to the change. The record names the build environment (target, profile, NDK `Pkg.Revision`, API level), and a measurement in another environment fails until it is re-recorded. A PR that grows the library within the allowance records the new size with `--record`; re-recording does not move the reference, so the allowance holds for the PR's total growth. A larger total step or an environment change (a baseline migration) needs `--record --ruling DEC-…` with a ruling new to the PR (a row of `contrib/node/gate-rulings.toml`, in the tree or on `node/integration`, that the merge base does not have and, where the program's decision log is present, a verbatim copy of a log row newer than the merge base; DEC-987) that states the recorded bytes and any environment value it moves to, which then covers growth up to the recorded size. `--no-size` skips the build. cargo-deny is not used for L6 because it follows build dependencies too, and clap reaches the products as a build dependency of cbindgen;
- L9 (one owner per P2P command) is unit tests in the processors.

A violation is an offending edge: from, to (with version and source for a package outside the workspace), kind (normal or build) and target condition. `contrib/node/layers-baseline.toml` lists, per rule and root, every grandfathered edge with the row that closes it. It is a ratchet: an edge not listed fails, a new route to a listed package and a second source of it included, and so does a listed edge that no longer occurs, until its entry is removed. A crate joins `layers.toml` in the task that creates it, and the P, Pn and S crates also join the `node-pure` or `node-shared` CI group (`ci_config.py verify-groups` checks both directions).

What R2 enforced that the layer rules intentionally drop: R2 also restricted reachability through a crate's own dev-dependencies. The layer rules follow normal and build edges only (dev edges never reach a dependent), so an N crate may dev-depend on V in its tests. That loss is intentional (SB0 §2.3 scopes L2 to normal and build edges), not an oversight.

Known limits, accepted for SB1: the hot path and the `dash-coreimport/wallet` check read the resolved graph only, so an optional dependency of a non-member path or git crate that no build turns on is invisible to them (the general walk sees it through the widened graph); L5's dependency hygiene is a denylist (`shared-deny.toml`) plus clippy on the S crate's own call sites, so a registry crate that spawns or exits internally and is not on the list passes; and `wrappers` and ban `packages` match by name, so a renamed fork of a banned crate passes them.

The P and S lints build for the host and Android only. iOS and macOS bodies (`cfg(target_os = "ios" | "macos")`) cannot be built on agentbox and are unlinted until the Mac path runs the same `clippy-lib.sh` target matrix (BL-74).

## Pure crates

The pure crates (layers P and Pn of `contrib/node/layers.toml`: `dash-consensus`, `dash-sha256`, `dash-x11`, then `dash-evo`, `dash-dml`, `dash-filters`, `dash-llmq`, `dash-governance`, `dash-coinjoin` as they land, and any crate marked `pure = true`, such as P1's sans-io `dash-p2p-transport` in S; also the `node-pure` CI group) are ordinary `std` crates with no I/O, threads, clocks or globals (A1 §1.5, §2.1); globals are left to review, since `OnceLock` caches inside values are allowed. They are not `no_std`, and there is no `no_std` job (A1 X-1). `contrib/node/check-pure.sh` checks each of them:
- `cargo deny` with `contrib/node/pure-deny.toml`, rooted at that crate only, with all features and without dev-dependencies (build-dependencies count: a build-time clock or file helper makes the build non-reproducible), bans async runtimes (tokio, async-std, smol), sockets and network clients (mio, socket2, hyper, reqwest, zmq, …), storage engines and file helpers (rocksdb, rusqlite, sled, redb, memmap2, tempfile, …), clock crates (chrono, time, …) and thread pools (rayon, crossbeam-channel, …) anywhere in its graph. The root `deny.toml` cannot say "banned for these crates only", hence the separate file;
- clippy, with `contrib/node/pure-clippy.toml` appended to the root `clippy.toml` through `CLIPPY_CONF_DIR`, bans the std entry points to the file system (`std::fs` and the I/O methods of `Path`), sockets (`std::net`, Unix sockets, `to_socket_addrs`), processes (`Command`), threads (spawning, scoped threads and `Scope::spawn`, sleeping, the pools of threadpool, scoped_threadpool, futures' executor and crossbeam) and the clock (`SystemTime`, `Instant`, their `now` and `elapsed`; `Duration` stays allowed: the time is passed in as a value). Clippy cannot ban a whole module, so the lists name types and functions and are not exhaustive. It lints the crate's library and every workspace crate it depends on (Cargo applies clippy to all workspace members it compiles), with all features and with no default features, on the host and for `aarch64-linux-android` (the NDK through `contrib/mobile/android-env.sh`; the Apple targets need the Mac, BL-74). The lints are forbidden (`-F`), so an `#[allow]` or `#[expect]` cannot lift them;
- blst's thread pool (DEC-68/71/79). blst comes in through dash-pkc, and its build script compiles the pool on every hosted target, so `pure-deny.toml` allows `threadpool` through blst only and blst through dash-pkc only, and `pure-clippy.toml` bans blst's methods that run on the pool and the dash-pkc wrappers that reach them (dash-pkc re-exports blst, so the blst bans apply too). Clippy does not lint other crates' bodies, so the lists hold only for the blst release and base SDK revision they were audited against, which the file's `# audited:` stamp names. `check-pure.sh` fails when a pure crate links another blst or the base SDK pin moves, until the lists are re-audited (diff the base SDK between the two revisions for calls that reach the pool, in dash-pkc and every base SDK library a pure crate links) and the stamp is updated.

Tests and dev-dependencies are exempt, so tests can read fixtures. A crate joins layer P or Pn (and the group) in the task that creates it. To ban another crate or function, add it to the matching file and a selftest case.

## CI and leaving agentbox

The `file://` URL only exists on agentbox. Without the fork, Cargo cannot resolve any crate of the workspace, not just the node crates. Node branches are never pushed (DEC-09), and the integration gate (`PROCESS.md`) runs every check locally. The GitHub workflows still describe the jobs: a reusable `ci-plan.yml` reads the `[patch]` URL, and while it is a `file://` path every job that resolves the workspace is skipped with one notice instead of failing. `Verify Test Groups` and the pre-commit hooks other than clippy still run, since they need no dependency. The plan also drops test groups that have no crates yet from the matrix. Skipped jobs count as passing, so `rust.yml` also has a "Base SDK pin is local" job that fails on pull requests into `dev`, `main` or `master` and on pushes to `dev` or `main` (the branches the workflow's push trigger lists) while the pin is local; a change that still needs the fork can never look mergeable upstream.

Before anything from the node program goes upstream (pasta's decision), the pin must move to a source other machines can fetch:
- point the `[patch]` at a published fork or replace it with an upstream base-sdk revision that holds every fork change, then regenerate `Cargo.lock` and check the fork changes are all there;
- adapt `check-base-sdk-pins.sh`, which requires a `file://` fork;
- remember that crates depending on rust-dashcore do not inherit its `[patch]` or `Cargo.lock`: once a published crate needs fork-only base-sdk APIs, those need a release they can resolve.

A clean checkout elsewhere needs the fork repository, with the pinned commits, at the same absolute path.

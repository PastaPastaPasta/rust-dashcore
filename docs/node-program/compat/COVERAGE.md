# COVERAGE: consensus coverage matrix for M1–M4

Task O2a (A1 §4.4 "Coverage matrix", GPT F15; PLAN M1 exit 7). Written on 2026-10-08 from A1 rev1, PLAN rev1, DECISIONS up to DEC-60, the CS0, CS1, CS2, EV2, LQ1 and O17 designs, and the O2a header (`src/test/oracle/oracle.h`, ABI 6 since fix round 1). For the manager's review (O2a acceptance); rows change only through a reviewed edit.

## 0. Purpose and scope

Before any implementation gate depends on the oracle shim, every Rust consensus function or state transition of M1–M4 is mapped to six things:
- the Core function it ports at both pins (mainnet v23.1.8, other networks v24.0.0-rc.3; DEC-05);
- the oracle entry point that calls that Core function;
- the L0 vector source;
- the L1 differential target and its budget;
- the L2 replay window;
- the L3 mutation operator, or the L4 functional test or scenario.

A cell may say **none** only if it gives a reason that the manager accepts (§21). M1 exit 7 allows no unexplained "none" for an M1–M4 function. A1 §4.4 also fixes one mapping: EV1's special-tx checks are backed by `oracle_check_special_tx`, not by `oracle_dml_apply`.

Rules for the rows:
- **Which tasks.** Rows are the M1–M4 tasks of PLAN §1 and §4: BS*, CS*, EV*, LQ*, CH*, IX1, MN0 and O2b. A row for M5 or later appears only where an M1–M4 function calls it, for example the governance trigger back end or the IS runtime.
- **Rust names.** Where a design exists (CS0, CS1, CS2, EV2, LQ1), the Rust names are that design's. For tasks without a design yet (CS3, CS4, CS5a/b, EV1, EV3, EV4, LQ2, LQ3, CH*), the row gives the module path from A1 or the PLAN row, marked **(planned)**.
- **Pins.** Every L1 target runs once per pin through the CS0/O3 runner (DEC-30 N5). Values must agree three ways (Rust, v23.1.8, v24). Reject strings and classes are compared per pin, under that pin's `UngatedRules` (CS1 §7.4, O17 §4.1). §20 lists the rows that depend on the release.
- **L0 sources.** L0 files are O4's copies from v24.0.0-rc.3 (`test-vectors/core/0364ed626ec2/`). Among the consensus data files, v23.1.8's copies differ in one `trivially_invalid.json` row only, and only in its label: v23.1.8's test marks the payload failure `gettxpayload-fail`, where both releases' `CheckProUpRegTx()` return `bad-protx-payload` (checked through `oracle_check_special_tx` at both pins; dash-oracle-sys `tests/data/PROVENANCE.md`). All other v23.1.8 expectations come from the v23 oracle.
- **Quirk 1.** Quirk 1 (EMBARGO-1) is covered by PLAN §7's private tests and seeds (owner CS0; DEC-24 D6, DEC-30 N2). This matrix records nothing else about it.

**The O2a context.** All O2a contextual entries read one context, format 2, which holds:
- a window of headers;
- the BLS scheme flag;
- version-bits seeds;
- the adjusted time;
- the checkpoint setting and the best known header's height (the shim adds Core's checkpoints between the tip and that header to the block index);
- the tip's MN list (evodb bytes), or a flag saying the context holds none;
- a coins view, with a best-block flag;
- member lists per `(llmqType, quorumHash)`. Linked with `ld --wrap`, these replace `llmq::utils::GetAllQuorumMembers`.

Every field is explicit (`Context::new` has no defaults). A call that reads state the context does not hold (an absent or other block's MN list, missing members, headers below the window, the quorum manager behind MNHF signals and asset unlocks) fails with ORACLE_E_CONTEXT, not a verdict.

A result is an `oracle_validation`: the result class, the reject reason and the debug message, with their lengths so a truncated copy is flagged (oracle.h, ABI 6). dash-oracle-sys types the class per entry point (`ResultCode::{Tx, Block, Bool}`).

**O2a-LQ1 phase 1 (ABI 11).** Rows Q1–Q4 run in an LLMQ context (oracle.h "LLMQ contexts"): Core's quorum managers over a caller-seeded chain (headers, evodb lists, work-block coinbases, snapshot rows, mined commitments; `oracle_llmq_ctx_load` replays an `llmq-fixture v1`, which dash-oracle-sys `LlmqFixture` reads and writes byte for byte). Every computing call returns the record-only trace of Core's hooks (ROW, MEMBERS, GET_QUORUM, SCAN; `llmq_trace.h`), whose off-mode build is TU-identical to the pin's (F5). Context rules:
- One context per process, exclusive with peer sessions; `oracle_set_network` and every chain call fail while it lives. O2a's `GetAllQuorumMembers` seam stays off inside it (that seam serves only the chain contexts, which cannot run while an LLMQ context lives).
- Two link-level seams serve the context's state and forward to Core's function outside its calls: `node::ReadBlockFromDisk(block, index)` (work-block coinbases; a peer session's reorg reads through Core's, `tests/peer_session.rs`) and `CQuorumSnapshotManager::GetSnapshotForBlock` (llmq/utils.cpp's previous-cycle reads). The second wraps a member function with a free function taking `this` first. Its ABI-equivalence check compiles, with Core's `llmq/utils.cpp` flags (`-O2 -fPIE`, x86-64), one function calling `GetSnapshotForBlock` as a member and one calling the wrapper's declaration, then requires `g++ -S` to emit identical code for both, modulo the callee and local labels. That shows the same calling convention: the sret slot in `%rdi`, `this` in `%rsi`, then the arguments. The result is WRAP-ABI OK; evidence is in `/work/scratch/o2a-lq1/evidence/wrap-abi/` (`abi_probe.cpp`, `check.sh`, `check.log`).
- A read of a list, coinbase or below-first-header snapshot the context lacks is ORACLE_E_CONTEXT and poisons the context (ORACLE_E_POISONED, Rust `ContextPoisoned`). Rows and mined commitments are otherwise the context's database: a scan below the first header finds no commitments. So a fixture must reach the deepest window it scans. `LlmqFixture::check_scan_coverage` takes Core's `LLMQParams` (from `oracle_chainparams_json`) and simulates the scan from the fixture's own commitments (`scan_base_heights`: the store block, then the mined-commitment index newest first, rotated by quorum index and cycle, `max(count, keepOldConnections)` quorums). Unless the fixture starts at genesis, it refuses one that builds fewer of them, or (rotated) one where a quorum index runs out at a position where the walk would take an older commitment of it. It also refuses a fixture where any built quorum's member reads go below its first header (`WORK_DIFF_DEPTH` below the work block; rotated, below the cycle base and 3 cycles further). Demands are cold scans (fresh or restarted context, or the chain overload). `tests/llmq.rs` checks the simulation against Core's scan (commitments mined at the window start and mid-window, and a failed DKG) and against the regtest fixture's `quorum list`, and refuses the review's rotated counterexample (index 0 out of commitments above the first header). It also checks that every accepted fixture scans as the whole chain does, and that a depth-only floor would have admitted a fixture where Core silently finds a quorum fewer.
- Stateful calls run once (PendingOutput); `restart` rebuilds the managers and statics over the same evodb; `legacy_bls` is set per call and restored on every path.

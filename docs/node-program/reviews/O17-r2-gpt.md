## Decision standard

For consensus, “Platform normally issues small indexes,” “the code fixes a defect,” and “the reference can diverge” are not unreachability proofs. The node must reproduce the pinned release's decisions and relevant state for the same input and event history. Stateful behavior is reproducible by modeling that state; it need not be a pure function of the block alone.

For P2P/MN behavior, I distinguish interoperability from identification. Being more lenient can avoid penalizing an honest v23 peer while still providing an easy version oracle. A known, affordable malformed-message probe also matters to the UA-spoofing requirement. The retained exceptions below are actual resource/fault guards, require substantially stronger preconditions, or have no wire difference; retaining them does not mean that every adversarial trace is identical.

For RPC, fixes to stable authorization, balances, UTXO lists, index status, errors and startup options need a profile. Race elimination can remain common when its result is already a possible v23 result. Unspecified randomized coin selection and implementation-owned storage need not reproduce Core's allocator or disk layout. DEC-11's storage freedom does **not** authorize changing supported configurations or documented query results.

Each **→ `profile`** below disputes the current keying. A row covering several behaviors should be split: profile its externally relevant part and keep common implementation details or safe resource guards where possible. The retained parts should remain explicit, narrow exceptions, rather than becoming an unrestricted O10/O13/O14 allowed-difference category.

## 1. All eight consensus `v24-all` entries

### CONS-10 — ungated withdrawal-index membership: → `profile` (blocker)

`CAssetUnlockPayload::index` is a serialized `uint64_t` (23 `evo/assetlocktx.h:80,99,124`). Neither the payload check nor the credit-pool check enforces a small, monotonically increasing index. The signature authenticates the chosen index; it does not restrict its domain. Withdrawals are already enabled on mainnet at height 2,201,472, independently of V24 (`chainparams.cpp:197`). This fix is not behind V24.

There is a two-index witness, not a requirement to execute 2^64 withdrawals. Let `M = UINT64_MAX`. Add `M-1`, then `M`: the stored interval is `[M-1, 0)`, with zero denoting the wrapped end. Query `Contains(M)`. In 23, `lower_bound({M,M})` misses the interval start, and the final `prev->end > M` is false. In 24, `prev->end == 0` makes the result true. **Do not use a singleton `[M,0)` as the witness:** both releases' explicit `begin == value` fast path finds that singleton. The packet's “range is empty” wording is too broad.

Evidence: 23 `util/ranges_set.cpp:15-46,89-98`; 24 `:28-60,110-119`. Those membership results feed 23/24 `evo/assetlocktx.cpp:183/214` and `evo/creditpool.cpp:291/320`, giving different duplicate-index decisions. With suitable signed unlocks, spent prior outputs and the other credit-pool/window conditions satisfied, reuse is accepted only by the old index logic. Even a later multiply-invalid unlock can expose different reject precedence because membership is checked before quorum/signature verification. The same membership is visible to `getassetunlockstatuses`.

This is a conditional consensus divergence, not a claim that live mainnet already contains such an interval or that an unauthenticated peer can obtain the necessary quorum signatures. “A Platform quorum must sign” and today's Platform index policy do not prove that Core consensus makes the state unreachable.

Recommended home: a consensus-owned legacy/corrected range-membership rule, consumed by transaction checking, credit-pool updates/undo and the status RPC. Keep explicit unsigned wrapping as common code. Include the legacy writer/import implications of overlapping ranges after reuse; “Core never writes noncanonical ranges” is not justified for this edge state.

### DKG-08 — quorum-root caches after a reorg: → `profile` (blocker)

The packet itself identifies an acceptance difference, and the source confirms its mechanism. In 23, the outer cache is keyed by the active quorum **base-block pointers**, and its inner cache by base-block hash. Neither binds the hash to the particular mined commitment. Replacing a commitment on a branch while preserving its base block can therefore reuse the abandoned branch's commitment hash. A later coinbase carrying the correct root can fail `bad-cbtx-quorummerkleroot`, while a template can contain the stale root. In 24, mined-commitment writes/erases invalidate these caches.

Evidence: 23 `evo/cbtx.cpp:55-108,129`; 23 `llmq/blockprocessor.cpp:362-375,502-520`; 24 `llmq/blockprocessor.cpp:446,461-509,551`. There is no V24 gate on the invalidation. Different valid commitments for the same base can differ in their signer set; this does not require a new quorum base. A reorg in the not-yet-ChainLocked suffix is not excluded by mainnet checkpoints or by ordinary ChainLocks.

“Cannot be reproduced deterministically” is false: cache contents and the ordered calls that populate/invalidate them are state. A fresh v23 process and a v23 process that saw the old branch can disagree; that demonstrates process-history dependence, not equivalence to v24. Excluding every such reference result from O15 would exclude precisely the event history that needs review.

Recommended home: consensus/quorum-root cache semantics selected by the profile, with explicit state across connects, disconnects and template/proposal calls. Test both a fresh reference and an identically warmed reference. Common hash computation can remain shared.

### CONS-09 — BLS global scheme leakage: → `profile` (major)

The checkpoint argument is insufficient, and the row's “exactly at a failed connect/dry run” restriction misses a successful historical-verification path.

On an archival mainnet node with enough verification cache, call `verifychain` at **level 3**, with depth extending below V19. The RPC accepts this depth without a checkpoint cutoff (23 `rpc/blockchain.cpp:1421-1432`). `VerifyDB` calls `DisconnectBlock` on its temporary view (23 `validation.cpp:4715-4726`). That calls `UndoSpecialTxsInBlock` (23 `:2028`), which sets the process-global flag to legacy when it crosses below V19 (23 `evo/specialtxman.cpp:713-720`). Normal successful undo does not restore it. Level 3 never enters the level-4 reconnect loop (`validation.cpp:4745`), and the EvoDB rollback does not roll back this atomic. The current chain tip has not moved, but the BLS flag has.

In 24, `VerifyDB` saves/restores the flag with `ScopedBLSLegacyScheme` (`validation.cpp:5044`), including this return path. It also establishes the proper scheme inside `ConnectBlock` (`:2490`). Thus a normal mainnet RPC can leave different process state. This witness is conditional on retaining the block/undo history and completing the disconnect pass within the cache budget; it does not require a peer to mine a historical fork.

Moreover, `ContextualCheckBlockHeader`'s checkpoint check is not called by `ConnectBlock`, and `GetLastCheckpoint` means the last checkpoint **present in the block index**, not a permanent lower bound on every operation (23 `validation.cpp:4127-4137`; 24 `:2493-2497`). Do not remove the CS0/A1 BLS effect solely on the report's argument. Model the v23 flag transitions, failure/verification leakage and the v24 scoped variant.

### EVO-14 — v3 ProTx layout/DomainPort decoder: → `profile` (major)

Pre-V24 version rejection bounds the accepted transaction set, but it occurs **after payload decoding**. It does not make the different decoder unreachable. Version 3 bytes can fail `GetTxPayload` under one layout and finish decoding under the other; the latter then reaches `bad-protx-version`. Domain decode failures likewise become whole-payload failures only in 24. Therefore `bad-protx-payload` versus `bad-protx-version`, decode JSON and failure order are genuinely different on a mainnet node.

Evidence: 23 `evo/providertx.h:96-104,216-225`, `evo/netinfo.h:243-250`, `evo/specialtxman.cpp:869-887`; 24 `evo/providertx.h:176-213,343-361`, `evo/netinfo.h:253-262`, `evo/specialtxman.cpp:1098-1120`. `decoderawtransaction` does not require transaction activation. Policy R is an explicit rejection-parity waiver, not an unreachability argument.

Select the legacy/new payload layout and decode-error semantics in the consensus/codec rules; have RPC decoding follow those rules. Safe allocation bounds need not recreate the old allocation cost. No independently duplicated validation engine is required merely to choose between two serialized layouts.

### EVO-16 — multiply-invalid ProTx error precedence: → `profile` (major)

This is reachable with legacy/basic payload versions that are validly decoded on mainnet; V24 activation is irrelevant. A ProUpRegTx with an unknown `proTxHash` and payout equal to its voting key reaches `bad-protx-hash`/TX_CONSENSUS in 23, but the earlier trivial payout check gives `bad-protx-payee-reuse`/TX_BAD_SPECIAL in 24. Both reject, but the string, validation class and relayer score differ (100 versus zero). A ProRegTx combining payee reuse and wrong netinfo version similarly changes the first error.

Evidence: 23 `evo/providertx.cpp:210-228`, `evo/specialtxman.cpp:1150-1171`; 24 `evo/providertx.cpp:459-473`, `evo/specialtxman.cpp:1438-1482`. No signature forgery is needed to reach these earlier failures. Parameterize the order of the existing checks; calling this a “second pipeline” does not justify abandoning the reject-string/class contract.

### EVO-17 — special transaction before DIP3: → `profile` (major)

The old/new strings really differ: 23 `evo/specialtxman.cpp:111-113` versus 24 `:227-229`. A fully caught-up mainnet tip cannot reach this branch, but a mainnet node during initial synchronization or reindex can have an active tip below DIP3. Its RPC server can evaluate a funded, otherwise policy-valid special transaction with `testmempoolaccept`/`sendrawtransaction` against that tip. `ContextualCheckTransaction` performs its special-type checks only **when DIP3 is active** (23 `validation.cpp:319-342`); it does not rule this transaction out first. `CheckSpecialTx` is reached in ATMP at `:954` and rejects before payload-specific checks.

The last checkpoint is not an ATMP guard, and restricting the release override to regtest does not stop mainnet bootstrap. A one-string profile rule is enough. If the design instead intends to disable these RPCs until after DIP3, that would itself need to match v23; no such restriction is established here.

### MNO-12 — old-budget block-value checks: → `profile` (major)

The packet explicitly admits a mainnet `verifychain` difference. At historical budget-window heights, a synced v23 node insists on the ordinary block-reward bound even when the block is covered by a ChainLock. In 24, `NoCheck` permits the historical budget overpayment. Source: 23 `masternode/payments.cpp:156-175`; 24 `:276-294` and `evo/chainhelper.cpp:41-52`.

`verifychain 4 0` on an archival, synced node with sufficient cache reconnects historical blocks without advancing the active tip or resetting MN sync. The best current ChainLock covers those heights. The packet cites mainnet height 332,320 as an overpayment witness; I did not independently download that block, so the concrete historical amount remains packet evidence. The branch difference and the unrestricted reconnect path are independently verified (23 `validation.cpp:4663-4667,4745-4762`). Checkpoints protect header admission, not these canonical historical reconnects. Preserve the old/new check gate in the profile; do not mark this internal or assign it no verification consumer.

### EVO-18 — coinbase ChainLock diff guard: retain, with a bounded proof

For a valid parent in the mainnet history **after its first non-null coinbase ChainLock**, the stated equivalence is defensible. Let child height be `h` and parent diff be `d`. A validated parent has `d < h-1`. Both releases first enforce non-nullness and `child_diff <= d+1`; hence a surviving child has `child_diff < h`. The new out-of-range/ancestor guard cannot fire. Version/height checks newly added to `GetNonNullCoinbaseChainlock` also hold for that validated parent. Null signatures and too-old signatures retain their existing rejection order.

Evidence: 23 `evo/specialtxman.cpp:61-83`, `evo/cbtx.cpp:220-246`; 24 `evo/specialtxman.cpp:166-211`, `evo/cbtx.cpp:181-211`.

This proves equivalence for extensions/reorgs above that established history, not for arbitrary synthetic parents or the first historical ChainLock candidate. The first-candidate/corrupt-parent cases can expose the new null-ancestor crash guard; retaining that guard is a narrow fault/malformed-input exception, not Policy R's general permission to change rejection pipelines. State that scope explicitly, and keep historical valid-chain checks in O10. I do not recommend restoring a null dereference.

## 8. Required design follow-through

The release-profile architecture can accommodate these findings without changing DEC-24's layering. Add consensus-owned rules/state for legacy index membership, BLS effects, quorum-root cache behavior and the old-budget gate. Put codec layout/check order and validation-result mapping at the lowest relevant consensus/codec layer. Select observable download/DKG, recovery, startup and CoinJoin behavior in their owning runtime groups; project RPC status/balance semantics independently of Rust's physical storage.

Do not approve the proposed deletion of `Effect::BlsSchemeLeak` yet. The refutation of the purported MNHF-valid-bit difference can stand; these findings do not reinstate that field. The `V23_1` naming and regtest-only override remain sensible. Regtest-only selection does not make historical mainnet or debug-option behavior unreachable.

Update `decisions.json`, regenerate the report/profile-reader tables, and move the disputed rows out of the broad deviation partitions. Every new profile rule needs paired oracle cases. Prioritize source-derived witnesses for: the two-element wrapped range; warmed quorum caches across a changed-commitment reorg; archival level-3 BLS verification and level-4 old-budget verification; bootstrap pre-DIP3 RPC rejection; 4,097 duplicate QRINFO bases; QWATCH error probes; non-MN recsig subscription; raw OP_RETURN descriptor rescanning; wallet abandon/requery; and CoinJoin session replies/locks.

No new rows should be exempted merely because a reference run disagrees after a reorg, returns an inconvenient error, or needs process history. Those are exactly the traces this charter requires the implementation to account for.

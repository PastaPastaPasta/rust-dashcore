# DP4-01 independent review — 7c175a7e

## Findings

1. **Major — An ineligible authentication key can be selected for a profile write.** `rust/crates/dw-engine/src/platform/requests.rs:308` and `:383`; `rust/crates/dw-engine/src/platform/profiles.rs:290`. `auth_keys` checks purpose, HIGH/CRITICAL level, ECDSA_SECP256K1 type and disabled status, but it does not check contract/document-type bounds or V1 expiry. `flow_keys` selects the first held key and narrows the signer to it. For an identity whose lower-ID held key is bound to another contract (or has expired) and whose later key can sign DashPay `profile`, `update_profile` signs with the unusable key and Platform rejects an otherwise valid edit. A signed failure retains the call's credit quote. The pinned wallet library's `profile_signing_key` explicitly skips keys bound elsewhere and expired keys. **Fix:** apply the same eligibility rule to `ProfileEdit` in both the pre-redemption candidate check and final signer selection, preferring an unbounded key where possible; add a regression with an ineligible lower-ID key followed by a valid one, and one with no eligible key that refuses before redeeming the grant.

2. **Major — Full replacement lacks a contract-version safety check.** `rust/crates/dw-engine/src/platform/requests_net.rs:220` and `:250`; `rust/crates/dw-engine/src/platform/profiles.rs:229`. The writer fetches with the bundled DashPay contract, carries only the properties represented by that fetch, and replaces the entire document using the bundled document type. There is no check that Platform's active profile schema is the bundled schema. When a later DashPay contract adds a profile property, an older installed client can publish a v2-shaped replacement and lose a property written by a newer client if the older schema's decoding omits it. The design acknowledges this possibility in D21. **Fix:** before any replacement, verify the live contract/document version is one whose profile fields this binary can preserve, and refuse the edit before signing on a mismatch; alternatively demonstrate with a cross-version test that unknown properties round-trip unchanged. This guard matters before a contract upgrade can make the risk real.

## Risk disposition and checks

- **Current-schema data safety:** `merged` starts from Platform's fetched property map, so it preserves the avatar trio on `Keep` and the v2 payment-address fields; `Remove` drops the avatar trio together. The write uses the fetched document ID and revision plus one. Drive checks that the replacement revision is exactly one above the then-current revision (`rs-drive-abci/.../batch/transformer/v0/mod.rs:1460`), so another completed write between this fetch and broadcast makes this write fail instead of silently replacing it. The SDK reserves the identity-contract nonce for the transition. I found no current-pin lost-update path through that immediate read/write race.
- **Full-edit semantics:** the API has no baseline revision from the user's earlier `profile()` read. If device B changes `publicMessage`, then device A submits an older full edit changing only `displayName` but carrying B's old message, A's later call refetches B's document and deliberately writes the old message. This is last-submitted-full-profile behavior under the stated `ProfileEdit` contract. It is acceptable for 1.0 only as an explicit product choice; preserving independent edits across devices would require an expected revision/baseline in the API and a conflict response.
- **Contact freshness and cost:** expiry runs at session open, after loading a wallet, and from the changeset tap after a pass persists checked contact profiles. It is in memory, so the library's next plan fetches them again; reopening repeats expiry against persisted timestamps. The cost is proportional to established contacts and pending senders for every managed identity, one proved query per 100 targets per owner plus a persisted owner snapshot and signal each fetching pass. That is bounded per pass by the wallet's contact set, with the deliberately accepted repeated cost in D17. I found no missing expiry entry point in the reviewed lifecycle.
- **Validation and surface:** the bundled v2 schema states 25/140 `maxLength` with no `maxBytes` on these fields; Unicode scalar counting matches DPP's character semantics. Trimming, blank-to-clear, `profile.empty`, and `AvatarChange::Set` refusal match the stated contract. `ProfileEdit` is limited to its own flow in `prepare_signer`; the changed key-flow test correctly treats it as keyed. The dwcli grammar admits only aliases declared by clap and continues checking values under the canonical leaf command, so `profile get` does not open an unintended command path. Contract-Version 24, the IMPLEMENTED list, generated TS codes/data and dw-app mapping are aligned.

This was a read-only source review. I did not rebuild or write to testnet; the brief supplies the successful local gate and T2 evidence. The branch remained untouched.

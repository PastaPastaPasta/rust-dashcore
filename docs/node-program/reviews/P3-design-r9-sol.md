# P3 block-download rev9: narrow Sol review

**Verdict: CHANGES REQUIRED.** Reviewed `node/p3-design` at `ace4ffc1f` against Dash Core `v24.0.0-rc.3` (`0364ed626e`) in a detached Core worktree. This is a document review; I changed neither source branch nor Core. The D44–D47 mechanisms close the rev8 ordering defects. Two rev9 claims still need correction: S4-x (7) assigns one outcome to two distinct accepted-after-reply schedules, and the UA acceptance text lacks a test for the peer-visible timing residual that Q9 now admits.

## Findings

### F1 — Major: a wake before `ConnectTip` does not make the HB relay precede validation, and the UA evidence misses that timing

**Design:** P3 §3.6:1415–1453, Q9:1681, S4-x (6):2002, acceptance mapping:135, transcripts:2009–2024, R6:2219; D45. **Core:** `validation.cpp:4829–4837,4897–4901`, `net_processing.cpp:2228–2267`. PRD NFR-FP-02 at `PRD.md:784–792` includes packet timing in the UA classifier.

**Schedule:** An HB peer H knows A. A source sends B extending A. Core's `AcceptBlock` calls `NewPoWValidBlock` while holding `cs_main`; it enqueues `cmpctblock(B)` to H *before* `SaveBlockToDisk` and before ABC can check B's scripts. In rev9, V pushes N(B), writes B, publishes the accept, and rings at the first ABC C5 point. The OS then runs V through `ConnectTip(B)` and `BlockChecked(B)` while the woken net actor has not run. When the actor runs, it drains N then `BlockChecked` and enqueues `cmpctblock(B)` to H. The queue preserves frame order, but H receives the compact announcement only after the storage and possibly script-validation interval. The same race exists for an RPC-origin block while the actor is idle or busy with a message. No fairness or scheduling rule makes the C5 wake an acknowledgement.

Thus **M1's stated wake obligation holds**, and the residual is **wire-visible timing**. An adversary can use one connection to supply B and another HB connection to measure the distribution from B delivery to `cmpctblock(B)`; block size, disk pressure, and script cost can amplify the shift. This is a potential UA fingerprint, not proof that the held-out classifier exceeds AUC 0.55. Q9/R6 accurately acknowledge “alongside” instead of “before,” but the §1.3 UA row and §6.3 evidence only compare mocktime-scale transcript timing and do not exercise this boundary. S4-x (6) pauses V before `ConnectTip`, so it proves eventual relay *during an artificial pause*, not the production race above.

**Required change:** add a real-V differential timing probe around accept → HB `cmpctblock` for P2P and RPC origins, including a loaded/script-heavy case, to the UA evidence and state that Q9 remains subject to NFR-FP-02. If the design requires Core's before-validation guarantee for propagation, make the first C5 point wait for N(B)'s actor acknowledgement before `ConnectTip`; a wake alone cannot provide it. Do not claim the current ring establishes that order.

### F2 — Minor: S4-x (7)'s “accepted after the reply” expectation is not single-valued

**Design:** P3 §2.6:743–747, §3.6:1319–1327, S4-x (7):2002; D46. **Core:** `net_processing.cpp:3359–3362,3270,3380–3383`.

**Schedule:** Q's `headers(B)` computes `received_new_header = true` while tip is A. V returns an accepted `ProcessHeaders` reply. Before the actor executes `Redrain`, RPC V accepts and connects B, pushes N(B), and publishes tip B. The actor's post-reply drain now takes X′ showing B, applies N(B) before Q's continuation, and Q gets `cmpctblock(B)`; Q's announcement time is **not** set because B's work does not exceed X′'s tip. This is Core's schedule in which RPC `ProcessNewBlock(B)` runs after `ProcessNewBlockHeaders` releases `cs_main` but before `UpdatePeerStateForReceivedHeaders` acquires it. If B instead accepts **after the redrain/continuation**, Q's announcement time is set first and N(B) later skips Q. Both accepts are “after the reply” as the current test row phrases it.

**Required change:** split S4-x (7)'s last variant at the post-reply drain boundary. Specify “B publishes after the continuation's redrain” for the stated announcement-time/N-skips-Q expectation, and add or permit the before-redrain outcome above. This is a test-oracle correction; option (b) itself is sound.

## Requested narrow checks that pass

- **S4-x (1)–(4), (6):** P3 §3.6:1290–1352 and 1365–1388. If U(B,D) enters the moved cell before S, C6 makes S include D and I2 applies N(B) first; a late append waits for the next round. If S precedes N(C), N(C)'s stamp exceeds S and section 7 sends A first. A peer completing `VERACK` before N's applying drain is eligible exactly as Core can be when the synchronous callback runs after that `VERACK`. In (6), the forced pause lets the C5 wake run N(B) before the pause is released. That test does not establish an unpaused deadline (F1).
- **S4-x (5) and deviation 2:** P3 §3.6:1389–1413; D44. Core's `ForEachNode` checks `NodeFullyConnected` at each visit while iterating `m_nodes` in order (`net.h:1423–1440`, `net.cpp:4852–4855`); it does not snapshot all recipients at callback entry. With P before Q: U(A) visits P while P is not fully connected; `msghand` completes P's `VERACK`, then Q's section 7 takes S and Q's cell before U(A) reaches Q; U(A) blocks on Q's cell, so Q gets nothing at S and P can later get only `inv(B)`. With Q before P this particular combination cannot be formed. The owner is right that rev8.1's atomic recipient list excluded a Core-reachable outcome. P-before-Q is necessary, along with the stated interleaving.
- **M2 and I0:** P3 §2.6:807–822, §3.6:1319–1329; D46. Core releases `cs_main` after `ProcessNewBlockHeaders` and reacquires it for `UpdatePeerStateForReceivedHeaders`; direct fetch takes it again (`np:3362,3270,3206`). `Redrain(AfterHeaders)` maps to the Core schedule in which another origin's accept and synchronous N run in that gap. The reply contributes `last_accepted`/invalidity only, so the continuation never acts on an undrained newer snapshot. The same argument covers `cmpctblock` steps 6–13 after its header step. F2 only concerns the test's boundary wording.
- **I3 and DEC-236:** P3 §3.6:1308–1352; D44/D47. With the cell locked, the one `ChainView` load and list move observe every completed append before S; C6 puts its tip in S, and I2 drains its earlier N before section 7. An append contending after that lock goes to a later round, as Core's append contends on `m_block_inv_mutex` during section 7 (`np:2296–2305,6409`). No relay entry can sit behind `BlockChecked(B)`, so rev5's held-back U(A) outcome is gone. `RelayList` retains Core's >8 fallback to only its last hash. The changed S4-x (5) outcome is Core-reachable for P-before-Q, as above; no rejected r4–r7 outcome is reintroduced.

No P3 implementation exists at this revision, so validation was source and schedule comparison rather than a build or test run.

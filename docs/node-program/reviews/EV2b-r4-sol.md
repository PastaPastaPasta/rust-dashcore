# EV2b round 4 — checked DML block differential (D56)

Reviewed rust-dashcore `node/ev2b-dml-block` at `7c6865110` against the pinned Core v24.0.0-rc.3 oracle shim `f822bbcd74` (ABI 21). Scope was D56 only; the real-chain windows remain outside this review.

## Finding

1. **Nit — distinguish the old build-only mutant from the new shared-predicate mutant.** `docs/node-program/designs/EV2b-notes.md:66` calls D56 mutant A “Sol r3's,” and `node-l1/tests/l1_dml_block.rs:290-295` presents it as closing the old probe. I replanted the literal r3 change by bypassing `dash-dml/src/build/mod.rs:594-596`'s unknown-version guard. For raw input `5823c5cd43d2b4`, `compare_block` still returned `Ok(BothReject)`: Core and the new Rust check loop reject it first, and `node-l1/src/dml_block.rs:268-280` intentionally does not compare the later build reason. Changing the **shared** `unknown_pro_tx_version` predicate to return `None` instead made the same input return `Divergence(check layer: reason)`. The old build-only difference cannot change this block's checked consensus verdict, so this is an evidence-description issue, not an open parity defect. **Fix:** describe A as the shared check-predicate mutation and say explicitly that a build-only change behind an exact check rejection is unreachable and intentionally unobserved.

## D56 questions

- **Round-3 Major:** The reachable check-layer defect is now caught. `dml_checks::compare` matches Core's named transaction, label and reason, rejects an earlier Rust rejection, and treats an implemented step passed despite Core's reason as a divergence (`node-l1/src/dml_checks.rs:1034-1106`). On the pinned raw input, disabling the shared unknown-version predicate produced `Divergence(check layer: reason)`. Two independent scratch mutations in different steps also produced divergence through `compare_block`: make ProUpRevTx T2 pass an invalid revocation reason on checked seed `0d0c1406` → `passes a step Core's reason names`; make ProRegTx C14 pass a nonempty internal-collateral signature on checked seed `010c2000` → the same divergence. Baseline outcomes for all three inputs were `BothReject`.
- **Mutant E:** Making `entries_trivially_valid` always true left `compare_block` at `BothReject` for the pinned ProReg T11 and ProUpServ T7 inputs. The next network-fields step can reject the same invalid entry with `bad-protx-netinfo-bad`, so outcome matching alone cannot locate that rejection. The permanent `check_layer_mutant_inputs_compare_exactly` pin requires T11 and T7 (`node-l1/tests/l1_dml_block.rs:320-346`); under E it failed on the ProReg input because Rust reported C4 instead of T11. On an input where the later network-fields step passes or rejects for another reason, `compare` sees that the implemented T11/T7 step passed despite Core's reason and reports a divergence. The same-reason case remains a stated step-coverage limitation, with a directed pin, not evidence of full step-level equality for arbitrary inputs.
- **Ambiguous:** The bucket is bounded in the committed raw corpora by separate ceilings of 9/3, and the checked/probed corpora require zero (`node-l1/tests/l1_dml_block.rs:580-586,647-648,676-678,741-746`). The D56 report gives 63%/67% OutOfDomain among raw Core check rejections and 9/3 Ambiguous, all `bad-protx-payee-reuse`; the checked corpora have zero of either. The table test prevents a reason from being both implemented and owned along a type's walk (`:402-413`). A real divergence **can** be in Ambiguous: Core's reason may belong to a later owned payout-reuse step while Rust rejects earlier at another step, and Core's message does not identify the step. `compare` therefore returns `Ambiguous`/`OutOfDomain` (`node-l1/src/dml_checks.rs:1091-1106`). This is sound as an explicit exclusion with the stated corpus ceilings; it is not a parity verdict on those raw inputs or a global bound on future fuzz inputs.
- **Deferred lows:** The members-missing store-fault exception does not check which transaction faulted (`node-l1/src/dml_block.rs:273-280`), but it is reached only after Core has already rejected in its check loop; an exact Rust check rejection stops the node before the build, while a missing check is already out of domain. I found no in-domain false negative from this exception. ProReg C8 computes the internal collateral as `(txid, index)` and exempts only an entry whose existing owner's full collateral outpoint equals it (`node-l1/src/dml_checks.rs:864-875`), matching Core `specialtxman.cpp:1227-1241`. The checked generator can retain the old service on a replacement (`node-l1/src/dml_apply/checked.rs:712-745`). The absent dedicated exemption mutant is a test-strength issue, not evidence of an incorrect exemption or a hidden mismatch.

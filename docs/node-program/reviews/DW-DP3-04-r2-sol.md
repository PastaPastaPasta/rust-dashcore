# DP3-04 security review — Sol round 2

Reviewed detached head `5650d352` of `dw/dp3-04-trust-gate` against round 1 and the DP1-10 follow-merge.

**Verdict: CHANGES REQUIRED.** The displaced-account fix closes the round-1 race after the fallback latch, but an `Enforcing` payment can still use an account built from a superseded request before that latch has ever been set.

## Finding

1. **Major — a stale paying account is payable in no-latch `Enforcing` mode.** `rust/crates/dw-engine/src/platform/money_gate.rs:390-397` applies `paying_account_stale` only when `provenance.fallback_used()` is true. The new address check at `:419-424` asks whether the reserved address is in the *current managed pool*, not whether that pool was built from the current incoming request. `rust/crates/dw-engine/src/send/contact.rs:70-74` also allows an established contact whose channel is `SetupPending`; `rust/crates/dw-engine/src/platform/contacts_model.rs:251-264` gives a mismatched account marker that state. The existing `send/contact_tests.rs:1779-1787` explicitly proves that a mismatched marker passes `prepare` without the latch. A real state can arise if the process crashes after the library persists a rotated incoming request and clears its marker, but before its sweep removes the old immutable account and managed pool (pinned `platform-wallet` `contact_requests.rs:615-635`, then `:1617-1629`). On restart the deferred queue is gone and a contact payment can reserve from the old xpub; membership succeeds against that same old pool, no entity is considered unverified, and `prepare` signs a destination the current request no longer designates. This is a destination safety failure, even if the new request was SPV verified. It is narrower than the default degraded path, which normally sets the fallback latch, but affects the `Enforcing` path this gate is meant to support. **Fix:** make the request/account stamp check apply at least to every `Enforcing` re-check, irrespective of the latch; preferably refuse the stale account before grant redemption unless a matching queued rebuild can run. Invert the no-latch assertion in `a_stale_paying_account_is_not_paid` and add a rotated-request/old-account regression that refuses before signing, then succeeds after a rebuild.

## Round-1 findings

- **High displaced account after reservation: fixed for a rebuilt account.** `money_gate.rs:341-364` looks up the pair's managed paying account, and `:413-424` tests the reserved address under the same wallet-manager read lock as the current request and stamp. A new-xpub rebuild lacks the old address; `send/contact.rs:241-246` drops the reservation on refusal. `send/contact_tests.rs:1912-1930` covers a verifiable rotation to a new xpub, `:1936-1943` covers teardown with no latch, and `:1949-1962` covers a same-xpub rebuild that remains payable. The Major finding above is the remaining path where the account itself is stale and the stamp is skipped.
- **Low displaced fresh address regression: fixed.** `send/contact_tests.rs:1968-2011` pauses the second payment before reservation, lets the first claim its address, pauses the second after its fresh reservation, then gives the first address back unsent. The second returns `send.prepared_tx_spent`, and the returned address remains the kept one. `send/contact.rs:249-260` makes this refusal before signing.
- **Low contract wording: fixed.** `docs/contracts/m4-dashpay-engine.md:2820-2824` now says public signatures, record shapes and error codes are unchanged; it no longer says no code or record writes occurred. The DP1-10 merge owns item 54/version 28, and this gate is item 55/version 29.

## Path checks and residual note

- The library's `reserve_contact_payment_address` selects an address from the managed account and requires `mark_address_used` to find it in that pool before returning (`platform-wallet` `payments.rs:1074-1138`). This includes a gap-window extension, so an ordinary new reservation satisfies `contains_address`. A same-xpub rebuild pre-generates only its new gap window; an old high-index kept address can fail once, be dropped, and a retry reserves from the rebuilt pool. I found no permanent refusal from the new membership check.
- The library tears down the immutable account and managed pool under one wallet-manager write lock and registers them under one write lock (`platform-wallet` `contact_requests.rs:1617-1629`, `contacts.rs:557-586`). Its stamp compares the ciphertext actually built with the live incoming request before marking the account current (`contact_requests.rs:3236-3262`). These facts support the new-xpub and same-xpub cases when the stamp is enforced.
- The final check is a point-in-time read. After `money_gate.rs:253`, a sync rotation can run while `send/mod.rs:1134-1215` awaits change-address derivation or signing. This does not change the already chosen output, and D22 explicitly accepts that boundary. **Low documentation nit:** `docs/design/DP3-04-trust-gate.md:166` says the address was designated by the verified request “when it was signed”; the code guarantees designation at the last re-check instead. Say “at the last re-check” so a rotation between the check and signature is not mistaken for an atomic guarantee.
- Test-only `Point::Planned`, `Point::Reserved`, the pause storage and `reached` method are all behind `#[cfg(test)]` (`money_gate.rs:68-120`, `send/contact.rs:26-28,224-237`), so the hooks are absent from a release build.
- The `7402d6b1` merge adds DP1-10's read-only `stuck_top_up_fundings` query and renumbers the m4 items. It does not alter DP3-04's contact gate or `top_up`'s order: `topup.rs:423-470` still gates after the journal/identity checks and before the write lock, grant and funding call. I found no semantic conflict with DP1-10.

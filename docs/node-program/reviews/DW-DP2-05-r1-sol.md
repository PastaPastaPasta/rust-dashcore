## Findings

1. **Medium — `rust/crates/dw-engine/src/platform/notifications.rs:252` (with `journal.rs:669`).** An `events` consumer can call `mark_read(identity, u64::MAX)` while the wallet exists, then have its `appdb_op` blocking job delayed. `remove_wallet` can delete that wallet and a same-seed import can restore unread `dp_events` before the old job runs. The job reads the *new* epoch inside `ChangesetTap::mark_read` and updates the new wallet's rows, silently marking restored notifications read. The session operation guard does not serialize with wallet removal; the wallet lifecycle lock only covers the removal/import. Capture the generation at call admission, then serialize and validate it with the SQL mutation against removal (including the tombstone/reimport transition), or run this mutation under the wallet lifecycle fence. Add a held-job removal/reimport test with `up_to = u64::MAX`.

2. **Medium — `rust/crates/dw-appdb/src/dashpay_journal.rs:110`.** `journal_page` filters by `(wallet_id, identity)` and sorts on `id DESC`, but the schema has only the journal's unique key `(wallet_id, identity, kind, contact, ref)` and a partial unread index. SQLite's plan uses the unique index to find *all* identity rows and a temporary B-tree for `ORDER BY`; `LIMIT` is applied only in the Rust loop. A wallet with many historical payments or requests makes even a one-row page scan and sort its whole journal, with repeated cost on each page. Add an append-only migration for `(wallet_id, identity, id DESC)` and verify `EXPLAIN QUERY PLAN` uses it. Build an ignored-contact `HashSet` as well, so filtering a large muted list does not multiply per-row work.

3. **Low — `rust/crates/dw-engine/src/platform/notifications.rs:190`.** `event_page` holds `self.enter()` and calls `contacts_page`, which calls `self.try_enter()` again. If session close starts between those admissions, `try_enter` returns `network_not_open` even though the first operation was admitted and is still keeping close waiting. This is the same re-entry pattern addressed for `ignore`, although here it causes a spurious failure rather than a wait. Add a contacts read helper for callers already inside the gate, and use it here; test an admitted `events` call racing close.

4. **Low — `rust/crates/dw-engine/src/platform/journal.rs:628`.** `load_unread` schedules a blocking count without capturing the wallet epoch. If removal's `forget` runs before the job starts, `unread_moved` captures the *post-removal* epoch and puts an empty count map back into the cache after `WalletRemoved`. The normal removal test waits for the first count before removing, so it misses this interleaving. Capture the epoch when scheduling, pass it through the count, and avoid clearing a later generation's cache on failure; test a queued count held across removal.

## Claims checked

- **Inserted, unread, notifying:** `record_events` returns only rows inserted by its transaction; `ChangesetTap::added` excludes read rows and `notifies` excludes `UsernameRegistered`, `ContactEstablished`, and `PaymentReceived`. The unique journal key and once-per-relationship exclusions cover replays, restart, the two request paths, and key rotations. `Contest*` outcomes enter through the same journal writer. Unit tests cover these cases.
- **Catch-up and restore:** E0-06's authoritative-time boundary supplies `read_at` before insertion. Historic contact requests and accepted relationships are read; the T2 testnet log shows six restored rows, four contact rows read and two username rows unread, with zero news after a later pass. A `.dwbackup` import directly restores rows and calls `unread_moved`; the bundle test confirms the count. The declared `ContestWon` bundle residual remains.
- **Feed, count, mute:** SQL marks rows read atomically, counts unread with the partial index, and pages by stable row IDs. `ignore` marks the sender's rows read without re-entering the gate; the feed excludes ignored senders and retains hidden contacts. The declared late-ignored-row residual remains. Paging's missing ordered index is finding 2.
- **Removal and concurrency:** The epoch suppresses news from an in-flight journal write after `forget`, and `forget_news` clears queued batches; already-dequeued news has the declared residual. The stale `mark_read` mutation and delayed first count are findings 1 and 4.

Version 17, generated surface hash and item 43 agree. No new sender name, alias, note or amount logging was found; OS signal fields match the contract.
- **Test limits:** The T2 log proves a read-only testnet restore and later quiet pass, not a live received/accepted request or concurrent remove/reimport. The latter paths rely on unit fixtures; findings 1, 3 and 4 need targeted race tests. Review was from git objects at `d62666cf`; no build or edits in the implementer's tree.

# SB12a review, Sol r1

Scope: `0d0939b8a..1545af63f` (six commits), reviewed in a detached worktree. Design notes: `docs/node-program/designs/SB12a-notes.md` D1–D15.

## Findings

1. **HIGH — A mismatched header/hash pair can pass proof-of-work validation in a release build.** `dash-consensus/src/primitives/block.rs:43–52` exposes `Header::from_parts_hashed(raw, hash)` to every dependent and removes its only equality check with `debug_assert_eq!` in release. `dash-consensus/src/header.rs:63–66` then checks PoW against `header.hash()` without hashing `raw`; a supplied zero hash passes any otherwise valid positive target. This is reachable from untrusted bytes through the public `HashedBlockHeader::consensus_decode` (`dash-spv/src/types.rs:85–94`), which reads the header and hash independently, followed by public `bridge::headers::header_to_consensus` (`dash-spv/src/bridge/headers.rs:62–67`). Public `decompressed_to_consensus` (`headers.rs:77–80`) also accepts arbitrary pairs, and `HashedBlock::consensus_decode` (`types.rs:159–168`) plus `block_to_consensus` (`headers.rs:101–116`) does the same for blocks. The current network decoder's normal path supplies real X11 hashes, but neither this new consensus API nor these bridge entry points enforces that provenance. Make the accepted hash an invariant established by a verified decoder/type boundary, or verify the pair before it can enter consensus validation in release. A comment asking callers to vouch for it is insufficient for an untrusted byte path.

2. **MEDIUM — `x11-count` is available in production feature graphs.** `dash-spv/Cargo.toml:95`, `dash-consensus/Cargo.toml:21`, and `hashes/Cargo.toml:27` expose ordinary additive Cargo features. A dependent enabling `dash-spv/x11-count`, or a release `--all-features` build, compiles the thread-local counters and executes a counter update on every X11 call (`hashes/src/hash_x11.rs:39–41`; `dash-consensus/src/hash.rs:77–91`). That contradicts the stated test-only requirement and can silently change production performance. Keep instrumentation outside the public production feature graph, or explicitly change the requirement and treat this as a supported production feature.

3. **MEDIUM — Python optimization removes the mainnet height guard.** `contrib/node/sb12a-captures.py:154–157` implements the cap with `assert`. `python3 -O` or `PYTHONOPTIMIZE=1` strips that check, so `headers_replies`, `special_blocks`, `filters`, and `coinbase_clsig` can issue mainnet reads above 2,090,000. I imported the script under `python3 -O` and `under_cap('mainnet', 2090001)` returned normally. Use an explicit conditional and exception before each relevant read path.

## Requested checks

- **Hash call graph:** ordinary `headers` → `sync_manager::hashed_headers` → `HashedBlockHeader::from` → dashcore X11; `headers2` → `CompressionState::process_headers_with_hashes` / `decompress_with_hash` → dashcore X11 → `Message::new_headers` → `hashed_headers` using those cached hashes; blocks → `HashedBlock::from` → dashcore X11. The bridge maps the raw fields and calls `Header::from_parts_hashed` in all three cases (`dash-spv/src/bridge/headers.rs:62–116`). `dash-consensus::decode_header` uses the safe `Header::new` path. The public paths in finding 1 are the exception to the trusted-input assumption.
- **Byte-exact crossings:** `bridge_round_trips.rs:78–185,281–297` compares captured bytes after both sides encode for `headers`, `headers2`, blocks, `cfilter`, `cfheaders`, `mnlistdiff`, `qrinfo`, `clsig`, and `isdlock`. `headers2_to_base` decodes the original compressed wire bytes, supplies the prior hashes, then compares every restored header (`dash-spv/src/bridge/messages.rs:51–91`); base-sdk retains the flags and time delta on encode. The four `headers2` captures contain 32,000 headers, with full and offset timestamps and cached version positions 1, 2, 3, 4, 5, and 7. They do not exercise a negative time offset or version position 6. Mainnet `isdlock` and testnet `qrinfo` captures are absent as documented in D9.
- **Hashing extraction:** the body of `sync_manager::hashed_headers` (`dash-spv/src/sync/block_headers/sync_manager.rs:17–35`) is a direct extraction of the old `NetworkMessage::Headers` branch, preserving the length error, zip order, and `HashedBlockHeader::from` fallback. No SPV validation behavior changed in that diff.
- **Capture cap:** the normal `main()` call sites check the static mainnet height range before their RPC/P2P data requests, including `height + 8000` for `headers2` (`contrib/node/sb12a-captures.py:160–172,284–303`). Finding 3 is the guard failure under optimized Python.
- **Bench:** `dash-spv/benches/headers.rs:47–82` times a prehashed 2,000-header crossing, hashing plus crossing, and an 8,000-header decompression plus crossing, as the names say. Fixture decoding and `CompressionState::new` setup are outside the timed regions; the three PF0 IDs point at those names. These are bridge microbenchmarks, not the full network manager pipeline.

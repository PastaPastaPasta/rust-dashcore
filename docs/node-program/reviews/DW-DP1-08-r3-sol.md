# DP1-08 independent narrow review r3 — f2, aa9881c5

## Findings

1. **Major — The 20-second budget can starve later identities forever.** `rust/crates/dw-engine/src/platform/names_check.rs:365-395`. `ask_names` builds the same ordered list on every run, starts four questions at a time, and records every unanswered identity as `false`; the next run skips only `true` (nameless) answers. With at least nine identities and the first eight questions taking their full 10-second timeout, the ninth question cannot complete before the 20-second check timeout. Each minute's retry spends its budget on the same first eight. The ninth identity remains `Failed` (“Username not loaded”) even if Platform answers its question immediately, and may remain so after Platform recovers. Rotate or prioritize identities that did not get a completed question, while retaining the per-check budget; test repeated retries with a slow prefix and a responsive later identity.

2. **Minor — A retry can start a check after `stop_spv` has aborted the checks.** `rust/crates/dw-engine/src/platform/names_check.rs:193-215,243-250,300-318`. The retry task can return from `wallet_ids().await` and enter its synchronous loop over wallets. On another runtime worker, `deactivate(false)` can abort the retry and clear/abort the current `JoinSet` between two calls to `kick_names_check`. Abort is cooperative; the retry can make the next call before its next yield. `NamesRuns::start` rejects only `closed`, which `stop` does not set, so that call spawns a fresh check after `stop` and it can remain active when `stop_spv` returns. Give `stop` and `start` a shared active/epoch gate under the `Runs` lock, rearmed by the next start, and cover this interleaving. `close` does set `closed` and drains the set, so this finding concerns a nonclosing stop.

3. **Minor — The failed-restore rollback has a post-`forget` window for a new check.** `rust/crates/dw-engine/src/platform/names_check.rs:313-315,324-340`; `rust/crates/dw-engine/src/backup.rs:694-700`. For a newly registered wallet, rollback calls `platform.forget` **before** removing it from the manager. The independent minute retry does not consult the restore marker: during that gap it can start a check, capture the *new* generation, read the wallet still in the manager, and keep an `Arc` to it while rollback finishes. Its answer can then be inserted after rollback and inherited by a later import of the same wallet ID; the D28 generation comparison accepts it because the check began after the bump. Fence checks again after manager removal, or prevent checks from starting for a wallet being rolled back; exercise a retry held between `forget` and manager removal, then reimport.

## R2 closure and limits

- **R2 Major (supervisor stall):** Closed for ordinary name checks. The supervisor kicks per-wallet tasks without awaiting their Platform questions; questions run four at a time within the 20-second question-stream budget. The new held-check test covers another wallet's bring-up and a coalesced rerun. The budget does not enclose the preliminary appdb and wallet-manager reads; finding 1 concerns the bounded question stream itself.
- **R2 Minor (old answer after removal):** Closed for a check that began before normal removal or unload. `NamesChecks::forget` bumps the generation; `answered` compares it while holding the same mutex used for insertion. The held-answer test covers removal and reimport. Finding 3 is the separate case of a check **started after** `forget` in rollback.
- **D30 residuals:** The double-pass path can briefly expose `Failed`, but cannot turn a failed or timed-out question into `true` (nameless). A panicking question drops that check; a later trigger or the independent minute retry can run another. Neither alone creates a false “No username” or a permanent stuck state while the supervisor and retry remain active. Finding 1 does create a permanent neutral stuck state for identities behind a slow prefix.

Assumptions: a wallet may have nine or more managed identities; `wallet_managed_identities` retains its iteration order across unchanged retries; Tokio task abortion takes effect at an async yield.

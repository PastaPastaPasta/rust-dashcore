# DW DP4-02 independent security review, round 1

Reviewed detached `383d1c3f` against the DP4-02 design (D1–D32), DASHPAY §3.8, and m4 contract v29. The unrelated DP3-03b commits and merge-only changes were excluded from findings.

**Verdict: CHANGES REQUIRED.** The address and hash guards look sound, but disabling contact pictures is not an effective boundary for a read already in progress, and concurrent setting writes can leave the session enabled while the saved setting is off.

## Findings

1. **MAJOR — A read can fetch or return a contact picture after the toggle is off.** `rust/crates/dw-engine/src/platform/avatar.rs:269-290` snapshots `pictures` before awaiting the blocking cache lookup and uses that stale `network` value to decide whether to fetch. It also returns a verified cached thumbnail at lines 275–279 without checking the flag again, and a fetch already running at line 290 is neither cancelled nor suppressed before its result is returned at lines 291–294. Concrete scenario: a contact read observes `true`, pauses at `row()` while the DB is busy, `set_load_contact_pictures(false)` completes, then the missing row causes a new request to the contact's avatar host. With a cache hit or a fetch already running, the caller can receive the picture after the setting is off. `avatar_of` has a related window between its first check and the Platform read (`avatar.rs:616-629`). Recheck/cancel at each network boundary, and suppress any result whose read started before an off transition; exercise the boundaries with barriers in a regression test. The existing off test (`avatar_tests.rs:769-789`) changes the flag only between completed reads.

2. **MAJOR — Concurrent toggles can resurrect the in-memory `on` state after a durable `off`.** `rust/crates/dw-engine/src/platform/profile.rs:252-258` awaits a SQLite write, then stores the requested Boolean in the session. The operation gate is a shared read guard, so two calls are not serialized. Concrete schedule: call A writes `on` and is paused before its atomic store; call B writes `off`, stores `false`, and returns; A resumes and stores `true`. `app.sqlite` now says off, while this session allows new contact avatar fetches until reopen. Serialize setting transitions per session and make the memory flag reflect the last durable write; test overlapping `on`/`off` calls with a controlled pause.

## Boundary assessment and residual risks

- **SSRF:** `avatar_fetch.rs:73-150,183-199,211-268` canonicalizes URLs through `url`, refuses non-HTTPS/non-443/userinfo in production, checks literals and every DNS answer, gives reqwest only checked addresses, disables proxies and automatic redirects, and checks each manually followed hop. `prepare_url` bounds the published parsed URL to 2048 bytes (`avatar.rs:300-312`). The pinned `url` parser handles decimal, octal, hex, short dotted IPv4 and IDNA before the host check. The requested loopback, private, CGNAT, link-local, multicast, mapped/compatible IPv6, and metadata targets are refused, including private IPv4 embedded in mapped/compatible IPv6 and the well-known NAT64 prefix. The original URL remains with reqwest, so Host and TLS SNI remain tied to the checked name. I found no direct address-policy bypass. D28's public-address routing, globally addressed LAN hosts and non-standard NAT64 prefixes remain unavoidable with this policy. The local test seam does not exercise real TLS/SNI.
- **Size and decode:** `avatar_fetch.rs:239-287` applies a ten-second whole-fetch deadline and a five-MiB declared/streamed body cap. `avatar_image.rs:71-117` sniffs only PNG/JPEG/GIF, applies 4096-pixel side and 64-MiB decoded-output limits; `dw-engine` explicitly enables those three `image` features. The pinned GIF decoder reads the first frame only. Two decode jobs can run at once, but `avatar.rs:190-203` has no CPU deadline and dropped callers do not stop blocking work. A hostile valid image can occupy both decode slots for an unbounded wall-clock interval after the ten-second fetch deadline. This is the documented F7 residual, not a demonstrated bypass of the byte or output bounds. The 13 seeds and deterministic mutations are useful smoke tests, not a fuzz campaign or a CPU worst-case proof.
- **Cache, verification, and lifecycle:** `avatar.rs:256-294` requires well-formed hash/fingerprint fields before fetching and compares each URL row's content SHA-256 to the current profile before serving it; the fingerprint is not used as a verdict, per D32. The thumbnail stem includes content SHA and crop, and Unix reads/writes use a held directory descriptor with no-follow opens. The directory is owner checked; files are created 0600, and the created directory is 0700 under umask 002. A profile changing hash at the same URL may show initials for up to ten minutes while the old row is fresh, as D11 specifies. Failure rows are similarly bounded to ten minutes. Missing disk cache falls back to 64 thumbnail pairs in memory. Candidates are capped at 16 per wallet and checked against the publishing wallet (`avatar.rs:406-446`). A setting-read error at session open sets pictures off (`avatar.rs:565-597`), although the later toggle races above break that protection during an open session.
- **Platform amplification:** `avatar.rs:510-533` caches completed unknown-identity profile reads but has no in-flight single-flight or concurrency cap. Concurrent calls for one uncached identity can issue repeated Platform reads; errors are not cached. This is the documented F8 follow-up. It becomes more consequential when DP4-03 loads search-hit avatars in lists.
- **Windows and CLI:** Windows cache operations use a checked path followed by path I/O (`avatar_cache.rs:168-219`), leaving the acknowledged F4 reparse-point race; it could not be exercised on this Linux host. `dwcli profile prepare-avatar --gravatar EMAIL` does not log the address in the reviewed command path and `AvatarSource` redacts it in Debug, but the address remains visible in process arguments and often shell history. D31 explicitly accepts that developer-tool tradeoff.

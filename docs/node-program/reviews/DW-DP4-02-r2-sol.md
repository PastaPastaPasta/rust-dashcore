# DW DP4-02 independent security review, round 2

Reviewed detached `fb85d08c` against `383d1c3f` with `git diff 383d1c3f..fb85d08c -- rust ':!docs/generated'`. I excluded the DP3-04 merge-only changes. Scope was the D33–D35 picture toggle and unknown-identity read fixes.

**Verdict: CHANGES REQUIRED.** The epoch closes the ordinary on→off→on ABA, the transition mutex orders completed setting calls, and the per-identity Platform lock and four-permit cap are sound. Two cancellation windows still violate the stated off boundary.

## Findings

1. **MAJOR — An avatar or Platform request can start after a completed off.** `rust/crates/dw-engine/src/platform/avatar.rs:164-178` checks the ticket, subscribes to the watch channel, then uses `tokio::select!` to poll the revocation future before the network future. Another runtime worker can complete `set_load_contact_pictures(false)` (`profile.rs:254-261`) *after* the revocation branch reports `Pending` but *before* the network branch is polled. The latter can then begin `net.profile_document` (`avatar.rs:699-702`) or the HTTP fetch (`avatar.rs:446-448`) while the setting is already off. The next watch wake cancels the work and suppresses the answer, but cannot retract a request that started. The same fetch window exists for `Whose::Own`. Serialize each network-start boundary with the toggle's off publication, or narrow the promised guarantee, and test this exact interleaving. The final check for another user's cached picture at `avatar.rs:399-403` has no await before its inner return, but a concurrent off can also complete before the outer `avatar_of` returns at `avatar.rs:832-836`; an absolute return-time guarantee requires coordination at that boundary.

2. **MAJOR — A canceled setter can undo a later successful off on disk.** `profile.rs:254-261` holds the transition mutex only in the caller's future, but `NetworkSession::appdb_op` submits the SQLite write with `spawn_blocking` (`rust/crates/dw-engine/src/coins.rs:560-575`). Dropping the setter after submission releases the transition mutex without stopping the blocking write. Concrete schedule: an `on` call's blocking job pauses before deleting the setting row; its caller is dropped; a later `off` call writes `"0"`, updates memory, and returns; the old `on` job then deletes the row. `open_avatars` interprets that missing row as on (`avatar.rs:761-783`), so after reopening the session a contact avatar can be fetched despite the completed off. If the canceled job was `off` instead, it can leave the current session on while the DB says off, allowing a fetch in that session. Keep the write and memory publication in one serialized operation that survives caller cancellation, and add a cancellation regression with a held appdb job.

3. **NIT — The five-second failure cache survives a toggle epoch.** `avatar.rs:682-684,690-692,718-725` returns a cached `Err` by identity without considering the ticket's epoch. If Platform fails for Dave, recovers, and the user switches pictures off then on within five seconds, a fresh read still returns the old failure without trying Platform. If an off occurs after the initial `avatar_of` check and a cached failure is returned, `avatar_of` propagates that error at `avatar.rs:824` instead of answering `None`. This cannot return a picture or send a request while off, and it expires after five seconds, but scoping negative entries to the epoch would match the toggle semantics. The cache key is a full `Identifier`, so this failure cannot poison another identity.

## Boundary assessment

- **M1:** The epoch and revocation checks suppress the tested in-flight fetches and cache hits, including the own-identity fetch. There is no practical on→off→on ABA because every actual change increments the epoch. The network-start window in finding 1 keeps the strict M1 guarantee open.
- **M2:** Completed setter calls are serialized across SQLite and memory; a failed write leaves memory unchanged. The operation gate is a shared admission guard, and reads do not acquire the transition mutex, so I found no gate/read/transition lock cycle. Finding 2 keeps durable order open if a caller is canceled.
- **D35:** The weak-keyed lock holds one uncached Platform read per identity. A permit is held across each read; dropping the *inner* waiter removes it from the mutex/semaphore queue or releases its permit, so I found no permit leak and the four-read cap is enforceable per session. `DashPay::avatar` uses `on_wallet`, which spawns the inner task (`rust/crates/dw-engine/src/platform/names.rs:868-877`): dropping only the outer API future leaves that task and any permit active until its read ends. Completed failures are shared for five seconds and successes for ten minutes. There is no cap test or test of abandoning an active Platform read; those remain coverage gaps.
- **Recorded residuals:** A cache row write already running on a blocking thread can land after off. That write itself starts no network request, and the revocation/final check suppresses another user's result; I consider this residual acceptable. The dropped-setter residual is not acceptable: it can permit a contact-avatar request while durable off is stored, or make a later session on after a successful off (finding 2).

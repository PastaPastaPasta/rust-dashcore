# BL-155 narrow review, round 5

Scope: `afd99478d..16ffe9dbe`, the f4-to-f5 proposed gate delta, D34/D35, and the supplied f5 proofs. I made no branch or gate edits. I assume Linux permits arbitrary bytes, including newline, in a process's `comm` (verified with `PR_SET_NAME`), and that a check's foreground child may keep writing after its shard shell is killed.

## Findings

1. **Major — the session scan can miss a live writer after its shard leader dies.** `/work/scratch/bl155/gate.sh.new:125-138`. `shard_runs()` pipes concatenated `/proc/*/stat` files through line-oriented `sed`. A process name containing a newline splits one stat record into two lines; neither matches the expression. I created a private session whose leader exited and whose live child set its name to `writer\n`: the leader's `/proc/<sid>/stat` was absent, while the exact scanner emitted no row for that child. The second scan has the same failure. A possible kill sequence is: kill the whole step group (including supervisor and reaper), then `SIGKILL` a shard shell while its foreground child remains in the recorded session and writes. With that child name, `started(sid)` fails, both scans miss the member, and the next gate deletes the reservation and grants more shards. The r4 disk-safety invariant is therefore not closed for every kill pattern. **Fix:** parse each `/proc/<pid>/stat` as one complete record, using the last `)` to delimit `comm`, without treating newline as a record boundary. Add a regression with the leader gone, a live newline-named session member, and a later gate denied until that member exits.

2. **Rollout condition — replacing gate files does not replace readers already running.** `docs/node-program/designs/BL-155-notes.md:49`; `/work/scratch/bl155/gate.sh.new:169-178`. D34 correctly says that every gate copy sharing the ledger needs the f5 reader before the new shard code merges. That must include the canonical `/work/scratch/gate.sh` (currently an older, unreserved serial gate) and any gate processes already started from older copies. An active f4 reader can still delete a killed f5 step's `.res`; the next f5 reader then sweeps its `.sessions`. Re-copying private files alone does not drain those active readers. **Fix:** install the canonical f5 gate and replace private copies, then let every older gate process finish or stop it before merging the f5 shard code. A marker inside the same ledger cannot make an old reader safe: it cannot interpret the marker and can still remove or ignore the entry. This is a deployment prerequisite, not a request for a ledger version marker.

## Other checks

- Recording occurs before the shard's TERM trap and before any case starts (`selftest-checks.sh:24-39,533-575`). A shard killed before or during the append has no case writer yet. A failed append exits before cases. The real shard is its session leader, and the start-time field is correct. Whole-step-group and driver-only SIGKILL in `kill-group-final.log` kept reservations until the recorded sessions or group ended, with zero sampled violations; the proof does not cover the newline-name case above.
- PID/session-number reuse does not make an unrelated session retain an entry while an old session still has members: Linux cannot recycle that number until the session ends. Malformed `.sessions` rows are ignored. A stuck shard or unreaped zombie can retain an entry indefinitely, but each waiting gate's D33 admission loop has a finite default six-hour cap and then fails without starting selftest. This bounds each gate's wait, not the lifetime of the stale entry.
- The `.res` scan and orphan `.sessions` sweep run under the ledger lock. A normal shard cannot append before `.res` exists, since the gate writes `.res` before exporting the sessions path. The EXIT trap removes its own entry outside the lock only after checking its group and sessions; the supplied ledger proof covers the group and session branches. The fresh `/proc` re-read narrows an enumeration race, but it does not repair records split by newlines; a `/proc` enumeration is still not an atomic snapshot.
- `bash -n` passed for the proposed gate and `selftest-checks.sh`; `git diff --check afd99478d 16ffe9dbe` passed. The supplied `ledger-f5-final.log`, `kill-group-final.log`, and `j2-f5.log` report zero failures. I did not run the full selftest or modify the reviewed files.

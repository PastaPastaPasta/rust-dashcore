# BS11a design review, round 5 (narrow)

Target: `node/bs11a-design` at `5c52de0e1`; delta `839fc8a3c..5c52de0e1`. Source pin inspected: Dash Core `v24.0.0-rc.3`. The supplied static archive was inspected with `nm` and `objdump -drC`. No repository files were modified.

## Findings

### Major 1 — `SER` still omits a wrapper serialization call

The ABI-15 `SER r scheme` operation is specified as `ToBytes` **plus `GetHash`** (design `:374`), but its step row allows only one `ep*_write_bin` for a valid wrapper (design `:240`). `ToBytes` calls `impl.SerializeToArray` (`src/bls/bls.h:133-139`), which calls `g*_write_bin` (`src/dashbls/src/elements.cpp:178-198,400-436`). On the first `GetHash`, `cachedHash.IsNull()` is true and `SerializeHash(*this)` runs (`src/bls/bls.h:141-145`). The wrapper's `Serialize(Stream&)` calls `Serialize(Stream&, bls_legacy_scheme)` and then `ToBytes` again (`src/bls/bls.h:170-180`). Thus an ordinary valid, uncached `SER` has **two** `ep*_write_bin` calls; a later `SER` with a populated hash cache has one. Mutating operations clear `cachedHash` (`src/bls/bls.cpp:152,175,230,253`). The current row cannot match the real wrapper call log (D35(b)), and selftest (d) has no second write step to inject. Add the cache state and second call to the trace, or revise the ABI operation to omit `GetHash` if that is the intent.

### Major 2 — the supplied archive is not the v24 parity build

The design names `v24.0.0-rc.3` as its sole parity pin (`:7`) and says the symbol and constructor checks read the pinned objects that the shim links (`:213,249-251`). The supplied `/work/scratch/bs11a/relic/libdashbls.a` contains `libdashbls_la-legacy.o` identical to `/work/scratch/bs11a/relic/blssrc/libdashbls_la-legacy.o` (SHA-256 `608300d8…ffa74b0`). That directory's `legacy.cpp` and `schemes.cpp` hashes exactly match Dash Core `v23.1.8`, and both differ from `v24.0.0-rc.3`. In particular, the supplied `legacy.cpp:15-39` uses `static bool fInitialized`; v24 `src/dashbls/src/legacy.cpp:17-40` uses `std::call_once` (D44). Its `objdump -drC` call sites therefore cannot validate v24's first-call behavior, and the v23.1.8 bench constructor count cited by D43 cannot pin the future v24 Core `bls` object. No actual v24 shim-linked `libdashbls.a` or `libbitcoin_consensus_a-bls.o` was present in the supplied artifacts. Require the checker to read the exact v24 objects used on the shim link line (or validate matching hashes), then establish the per-path constructor count on that build. This is a build-evidence gap; it does not refute the source-derived legacy sequence below.

### Minor — D43's relocation count is only a site-count guard

D43 says the number of `ep*_set_infty` relocations **per wrapper function** must equal the constructor steps allowed **on its paths** (design `:251,485`). The span function has disjoint empty and nonempty paths (`src/bls/bls.cpp:155-176,233-255`); `objdump`'s total relocation count does not say which path executes a site. An equal total can coexist with one path missing a constructor and another having an extra one. Keep the total as a build drift check, but specify that D35(b) must exercise and match both paths (including the elision case) to establish the path-specific sequence. A v24 Core object was unavailable for checking the actual relocation totals.

### Minor — F8 still makes an absolute clear-before-throw claim

F8 says the listed operations, including `FromBytes` through `CheckValid`, clear a nonzero code before they return **or throw** (design `:68`). `G1Element::CheckValid` throws on `!IsValid()` before reaching `BLS::CheckRelicErrors` (`src/dashbls/src/elements.cpp:144-148`; G2 analogue `:367-371`). The trace row already recognizes this stop (`design :245`). Narrow F8 to paths that reach the clear point. The other round-4 F8 exceptions are now correctly named.

## Checks that matched

- **AGG source paths:** pair aggregation enters `CoreMPL::Aggregate` and constructs only its `aggregated` element before two in-place adds (`src/bls/bls.cpp:144-153,222-231`; `src/dashbls/src/schemes.cpp:176-192`). Empty span returns a default wrapper; nonempty span constructs `ret`, enters the same scheme constructor and adds in input order (`src/bls/bls.cpp:155-176,233-255`). The new pair/empty/nonempty rows (`design :234-236`) match those source paths. The move constructor can default-construct its `impl` (`src/bls/bls.h:61-66`), so its presence is indeed build dependent.
- **SwEnc and MulCof:** the expanded branch order (`design :224-226`) matches v24 `legacy.cpp:150-304,93-148,306-414`: `t=0` sets infinity; `w=0` gets the generator and conditionally negates; otherwise the two trial roots precede one selected root and the parity negation; cofactor multiplication has the listed `bn` setup, two muls, three subs, normalize/Frobenius/add/double sequence. The supplied v23 `legacy.o` confirms `ep2_sw_encode` is local (`t`), `ep2_mul_cof_b12` has no separate symbol, and all listed relic callees are undefined external (`U`) symbols. Its relocations show the two initial `fp2_is_zero` calls in `ep2_map_legacy`, the helper's second zero test, and the listed branch/call sites. This corroborates D41/D42 for the common source body, subject to Major 2's v24 build gap.
- **D45:** v24 `schemes.cpp:32-58` calls `Util::Hash256` once for all keys, then once per key before `bn_read_bin`; `src/dashbls/include/dashbls/util.hpp:61-64` maps each call to `md_map_sh256`. In the supplied archive's `libdashbls_la-schemes.o`, `nm` lists `U md_map_sh256`, and `objdump -drC` shows `CoreMPL::VerifySecure(...,bool)` call relocations at `0x415d` (all keys) and `0x41b9` (per-key loop), followed by `bn_read_bin` at `0x41c9` and `bn_mod_basic` at `0x41d7`. The source-derived D45 order matches.
- **D46 and most of D47:** the negative-scalar producer sentence is limited to the at-most-64-bit final-negation path and the longer `bn_mod` path (`design :122,488`), matching `relic_pc_exp.c:44-60,96-112`. The predicates, serializers, copies and both private-key products have no clear call (`elements.cpp:135-148,178-203,358-371,400-441`; `privatekey.cpp:184-205`), as rev5 now states apart from the throw wording above.
- **`core_get` and warmup scope:** `core_get` is only an accessor at the cited ordinary call sites; excluding it from `--wrap` does not hide a relic callee's sticky code, which is read after the wrapped call. In v24, the first `ep2_curve_get_s3/_s32` invocation performs `bn_make` and `bn_read_str` under `std::call_once` (`legacy.cpp:17-40`). A startup legacy map that reaches those helpers excludes those calls from the subsequent wrapper window and from injection selftest (d). With fixed valid radix-16 constants and successful allocation, `bn_read_str` has no input-driven error branch (`relic_bn_util.c:310-356`), but the cold-start calls are outside the dynamic fidelity proof. The shim should assert that both once initializers actually ran before opening any log window.

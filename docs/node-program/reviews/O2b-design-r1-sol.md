# O2b `diff_chain` rev1 design review

**Verdict: CHANGES REQUIRED.** Reviewed `docs/node-program/designs/O2b-diff-chain.md` at `6be658a82` against CH3 §7.8, CH3a D61, O8, PLAN, DEC-184/186, and Dash Core tag `v24.0.0-rc.3` (`da567d7dba945143eee4d2ce1621c21b32089989`). This was a read-only review of the repositories; no implementation or fuzz campaign was run. Core citations below were checked against that tag rather than the mutable `develop` checkout.

1. **BLOCKER — §7 P3b, §2.3 D32: the M3 persistence plant has no promised witness.** The plant removes dirty marking of *walked* entries in `InvalidateBlock`, but Core separately marks `to_mark_failed` dirty at `src/validation.cpp:4014-4016`. For the specified tip invalidation, that is the same entry, so the `FLUSH ALWAYS` still persists its failed flag. If an ancestor is invalidated, only descendant flags may be omitted; on reload, `LoadBlockIndexDB` sets `m_best_invalid` from persisted failures (`validation.cpp:5356-5358`) and `VerifyLoadedChainstate` calls `ResetBlockFailureFlags(nullptr)` at check level 3 (`node/chainstate.cpp:463-465`), clearing those descendant flags before the post-state comparison. The claimed post-restart `index`/tip difference therefore does not follow from this plant. **Fix:** replace P3b with a persistence effect that survives Core's load-time reset, or compare the persisted index image *before* `VerifyLoadedChainstate` on both sides. Provide a directed witness that fails on the planted build and passes on the unplanted build before using it as the M3 sensitivity proof.

2. **BLOCKER — §2.1, §9: the M4 `TEMPLATE` operation cannot use the proposed Core object graph.** The design excludes `CConnman` and a chainstate `CTxMemPool`, then says `TEMPLATE` runs Core's `getblocktemplate` template handler. That handler calls `EnsureConnman(node)` and `EnsureMemPool(node)` at `src/rpc/mining.cpp:739,757` (and builds with the mempool at `:826`). Proposal mode returns earlier (`:697-725`), so this does not affect M3 proposals, but M4 template calls fail before template creation. **Fix:** add a deterministic, detached `CConnman` and mempool with a documented setup/reset and compare regime, or invoke `BlockAssembler` through a dedicated test hook and state explicitly that the template RPC wrapper is not under comparison. Recheck the stock-`dashd` X-check mapping for this op.

3. **MAJOR — §2.3 D34, §2.9: `KILL` can silently persist sporks.** The design destroys and rebuilds `CSporkManager` on a killed restart but expects the spork map to revert to the last clean stop. Core's `CSporkManager::~CSporkManager()` stores a valid map to `sporks.dat` unconditionally (`src/spork.cpp:45-49`). Destruction is therefore a clean spork save unless a hook suppresses it; the listed “spork-map carry” hook does not say that it does. **Fix:** specify a kill-only suppression of that store, reopen from the last clean `sporks.dat` image, and test `SPORK → KILL` versus `SPORK → CLEAN` against `dashd` before admitting spork operations.

4. **MAJOR — §2.3, §5.1 D31/D32: the Rust restart comparison can exercise a test-only behavior instead of production.** `SutOpts::core_flush_causes_only` disables CH2's `THRESHOLD`, `DMAX`, and `LEFT_IBD` flushes, although `KILL` makes flush timing observable. The target can then report persistence parity while production Rust takes a different flush path. D32 is worded as a `NodeSut` load-path change, but Core's failure-flag reset is a production startup behavior (`src/node/chainstate.cpp:463-465`), not a harness option. **Fix:** put D32 in the production `open_chainstate`/CH1-node or CH5 path and test it there. For D31, either run a second leg with the production flush policy and compare the resulting durability, or explicitly narrow O2b's claim to the controlled Core-flush regime and make CH2's production `KILL` parity a separate named gate owned by CH2. Keep the test option inaccessible to the product path.

5. **MAJOR — §2.3, §6.5 D30: `declared-tie` is broader than the actual nondeterminism.** The Core comparator uses a pointer only after equal chainwork *and* equal sequence ID (`src/node/blockstorage.cpp:33-45`). Counting any comparator call that reaches that branch merely says such blocks were compared somewhere; it does not prove the later active-tip selection was decided by that call. Ending an input when both chosen tips are “among the tied candidates” could discard a real `PRECIOUS`, candidate-admission, or reorg bug that also selects an equal-work block, and it discards later steps. **Fix:** identify the exact maximal eligible candidate set at the selection point, require the differing choices to have equal work and sequence ID and to differ only by Core's pointer tie, and do not credit a declared-tie input toward the census or planted-bug search. A simpler safe rule is to discard and regenerate every tie-tainted input before scoring any subsequent op; record the discard rate.

6. **MAJOR — §4.2/§4.5 D16: the fallback and golden-key rationale overstate comparison coverage.** Moving the full UTXO digest to every fourth step can miss a transient wrong UTXO state that a later operation repairs, contrary to the per-step post-state claim. Moreover, O8's excluded `unspendable`, `bi`, and `stats` are per-block/cumulative accounting fields (`O8-statedigest-v1.md` §5.3); a UTXO MuHash, output count, and amount do not cover the same facts. **Fix:** retain an exact UTXO check after every op, using an incremental maintained digest if full scans are too costly, and describe the golden-only accounting fields as uncovered unless separate counters are added. Measure the full-scan cost before adopting any weaker schedule.

7. **MAJOR — §1.1, §6.4 D20: the CPU-hour wording conflicts with the controlling fuzz decisions.** The design says the 24/72 CPU-hour figures “must reach” their old PLAN numbers before closure. DEC-184(2) explicitly replaces every such gate with plateau and says a CPU-hour figure is reported **but is not a goal**; DEC-186 requires a passing `fuzzctl certify` at the gated head. The proposed 20,000-execution floor is a permissible per-target override under DEC-186, provided O2b-3 measures and justifies it, but S0/S1's predicted 5 execs per CPU-second is below the 5.56 needed for that floor in 3,600 CPU seconds. **Fix:** remove “must reach” from §1.1/§6.4/§9/§14, retain the CPU-hour report, and set each floor from measured gated-head throughput before the certification run. Treat insufficient progress as a target-design problem, not a reason to count more farm hours.

8. **MAJOR — §1.3 D29, §9, §14: M4 IS scope needs an explicit acceptance ruling.** Deferring IS at M3 is sound under CH3a D61: `NoEvo` refuses effects and the production IS store is LK1b. But PLAN's M4 exit text explicitly includes “CL/IS arrival,” while §9 lets M4 pass without `ISLOCK`, `conflict-tx-lock`, or `is_rm` until M5. **Fix:** either move a production-owned LK1b IS-store slice before O2b-5 and include those operators in the M4 gate, or obtain and record the PLAN/M4 acceptance amendment that defers IS. Do not present the current M4 gate as covering the full listed NFR-CEQ-08 CL/IS surface.

9. **MAJOR — §0, §10, §11, §14: the ABI allocation is stale.** The design labels 17 as O2a-SP, 19 as O2b-1, and 20 as O2b-5. The task's current allocation is 17 = train-14 bundle, 18 = O2a-GV, 19 = BS11a-2, 20 = CJ0. The “next free number at merge” sentence is correct, but the concrete tables, slice names, and pin/build steps still direct implementers to occupied numbers. **Fix:** replace the fixed 19/20 assignments throughout with symbolic “next free at each merge,” and update the ABI ledger, `pins.txt`, installs, and SB4 vectors only after reserving each actual number.

10. **MINOR — §0, §2.9: the Core tag identifier is incorrect.** The document calls `v24.0.0-rc.3` `0364ed626e`; the local tag resolves to `da567d7dba945143eee4d2ce1621c21b32089989`. **Fix:** correct the tag hash or name the different oracle pin explicitly, then recheck line citations against that stated revision.

**Verdict summary:** CHANGES REQUIRED. The overall session, per-step report, and slice plan are promising, and the M3 choice to defer IS is justified, but P3b currently cannot prove the claimed M3 persistence sensitivity and the M4 template path lacks objects Core requires. The restart model, tie exemption, post-state fallback, acceptance wording, IS milestone scope, and ABI ledger also need correction before implementation can use this document as a reliable gate specification.

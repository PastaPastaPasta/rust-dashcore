# EV2b consensus review — 77672a56c against Dash Core da567d7dba

**Verdict: CHANGES REQUIRED (verification gate; no confirmed code-level consensus mismatch).** I reviewed `c8ef13d32..77672a56c` in `dash-dml/` and `node-l1/` against Core v24.0.0-rc.3. The Rust build follows the ordering-sensitive Core operations I traced, but the supplied evidence does not yet exercise the real PoSe and activation paths required by the EV2 design, and the differential target is the raw rebuild helper rather than the checked block path. These are verification blockers for a consensus merge, not claims that the code currently computes a wrong list.

## Numbered findings

1. **Medium — The 50,000-block window stops before real quorum punishment and never crosses either payee activation.** `node-l1/src/dml_apply/window.rs:107-181` compares canonical bytes and payee per block, but the recorded run covers only heights 1,028,160–1,078,159 (`docs/node-program/designs/EV2b-notes.md:36`). The design identifies the first non-null commitments at 1,080,552–1,082,963 and requires the 100,000-block first window plus V19 and MN_RR windows (`docs/node-program/designs/EV2-dml.md:944-954`). Thus the 50,000-block result does not validate Core's non-null QcTx member punishment (`src/evo/specialtxman.cpp:702-726`, `:283-298`), the resulting PoSe decay/ban sequence (`src/evo/deterministicmns.cpp:281-334`), or the V19/MN_RR payment/streak transitions (`src/evo/deterministicmns.cpp:158-249`, `src/evo/specialtxman.cpp:759-790`) on a real chain. A quorum-height or member-order error at the first non-null commitment, or a streak error at either activation, would pass this window. **Fix:** complete the three design windows with recorded quorum members and per-block canonical bytes/payees, or provide an equivalent consecutive Core comparison across those events before treating the L2 gate as passed. The synthetic QcTx, payee and quirk tests are useful coverage but do not replace the stated L2 gate.

2. **Medium — The L1 comparison does not establish checked-block verdict parity.** `node-l1/src/dml_apply.rs:237-294` calls `oracle.dml_apply`, which runs Core's bare `RebuildListFromBlock`; `:225-230` deliberately counts a pre-V24 ProUpServ that Core's raw rebuild accepts but Rust cannot represent as out of domain. This exclusion is defensible for a validated block: Core's `GetValidatedPayload` rejects a V24-only version before the rebuild (`src/evo/specialtxman.cpp:1098-1120`, `:1323-1355`), whereas the raw rebuild's ProUpServ branch has no such check (`:454-517`). But this target cannot detect an orchestration error that lets such a transaction reach Rust's build, maps its refusal to a block verdict, or changes the stage/reason of a checked rejection. Nor does it compare `ProcessBlock` persistence/effects against Core's checked path (`src/evo/specialtxman.cpp:805-917`; `src/evo/deterministicmns.cpp:689-781`). **Fix:** add the design's `oracle_dml_block`/`diff_dml_block` validated-block target, comparing reject layer, class, reason, list, payee and observable effects; retain the raw-helper target for the reachable intersection. This is explicitly listed as a prerequisite in `EV2-dml.md:920-937`. Until then, describe the L1 result as raw-helper parity on its compared domain.

## Code comparison and residual risk

- **Build order and errors.** Rust `dash-dml/src/build/mod.rs:479-551` takes the payee from `prev_list`, confirms over the previous snapshot, decays PoSe, applies special transactions in block order, then handles collateral spends, the paid masternode and streak resets. This matches Core `src/evo/specialtxman.cpp:314-350`, `:731-795`. The previous-list mismatch is a `StoreError` at Rust `:479-482`; Core asserts parent hash or the exact default list at `:314-317`, whose equality includes the registration counter (`src/evo/deterministicmns.h:616-624`). That error mapping prevents a local wiring fault from being reported as a bad block. Rust's ProReg replacement precedes duplicate checks (`:670-718` versus Core `:389-448`), and the `internal_id` comes from the counter before `try_add` bumps it (Core `:365`, `src/evo/deterministicmns.cpp:512-515`). The ProUpServ type, network, hash and type-mismatch checks; registrar/revoke state-version paths; and both shared update handlers follow Core's branch order (`src/evo/specialtxman.cpp:454-701`). The spent-collateral check uses the raw transaction type as Core does (`:735-747`). I found no conflicting reject order in these paths.
- **Payee and PoSe.** `dash-dml/src/scan.rs:54-173` uses Core's effective pay height and `proTxHash` tie-break (`src/evo/deterministicmns.cpp:132-152`); its literal scan keeps the last continuing Evo in Core order (`:170-181`, `:212-245`). `payee.rs:30-123` uses the queue only under list-computed P1/P2 and otherwise falls back to that scan. The projection's length and weights follow Core's pre-MN_RR weighted count and post-MN_RR enabled count (`:196-249`), with bounded copies for malformed negative streaks. `pose.rs:12-61` uses the rebuilt list's current `max(100,total)`, caps punishment, bans at the threshold, and decays only non-banned positive scores, matching Core `:267-334`. The confirmation, decay and reset phases take fresh phase-start collision-bucket order; quorum punishment remains member-vector order (`dash-dml/src/build/mod.rs:399-445`, `:1012-1029`; Core `src/evo/specialtxman.cpp:283-298`). No seeded hash-table iteration was found on an output path: the unique map is only queried by key, while list order and diff serialization are explicit.
- **Shared masternodes.** The share-owner keys occupy the ordinary owner-key namespace in `dash-dml/src/list.rs:862-904`, as Core `src/evo/deterministicmns.cpp:478-494` does. Rust removes the collateral's old owner before probing replacement keys, matching Core `src/evo/specialtxman.cpp:389-425`. `ProUpShare` and `ProUpSharedReg` recheck the current share/voting separation and operator collision after earlier same-block transactions (`dash-dml/src/build/mod.rs:899-966`; Core `src/evo/specialtxman.cpp:619-701`). The 348 checked-in `diff_dml_apply` seeds include all eight named shared paths; the derived case actually holds a shared masternode from the prior block (`node-l1/tests/l1_dml_apply.rs:113-149`, `:205-227`). This is stronger than same-block-only coverage.
- **Evidence limits.** The L1 harness treats a Rust reader refusal against a Core success and any store fault as a divergence (`node-l1/src/dml_apply.rs:244-252`, `:219-225`); its remaining skips are either missing input list or declared invalid/undefined raw-helper cases. The 50,000-block comparison uses Core's canonical bytes, not merely a short digest (`node-l1/src/dml_apply/window.rs:148-153`). Core's canonical serializer covers the block hash, height, registration counter and every serialized masternode field (`src/evo/snapshot.h:228-247`; Rust `dash-dml/src/codec.rs:291-310`). It does **not** serialize the unique map or collision-bucket history. The Rust fast/twin `xcheck` compares those internal structures (`dash-dml/src/reference.rs:700-755`), but the twin shares the Rust transaction handlers and unique-key preimages, so it is not a second Core implementation. The supplied L0, 600 generated inputs, 348 seeds and quirk vectors are valuable checks; their agreement cannot by itself close findings 1–2. No attacker-controlled indexing panic or realistic integer overflow was established in the build paths inspected. The documented fuzz run remains uncertified (`EV2b-notes.md:41`).

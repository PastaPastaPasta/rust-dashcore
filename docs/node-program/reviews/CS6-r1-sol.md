# CS6 independent consensus-path review, round 1

Reviewed `node/cs6-sigcache` at `9c300f58a` against `b0d547b9a` and Dash Core v24's `sigcache.cpp`, `cuckoocache.h`, `checkqueue.h`, `validation.cpp`, and `init.cpp`. I assume a caller supplies the actual spent scripts and a distinct transaction-data slot for each transaction, as the current test callers do. The production block connector and mempool caller do not exist in this branch.

## Finding

**Major — A wrong prefilled transaction-data slot can accept and cache an invalid transaction.** `dashd-chainstate/src/checkqueue/script.rs:117-120,127-128,149-153` uses `txdata.tx()` for scriptSig and sighash while computing the script-execution cache key from the separate `tx` argument at line 111. The identity check is only a `debug_assert!`, so release builds omit it. Concrete scenario: transaction A is a correctly signed one-input P2PKH spend; B spends the same output but has a changed, invalid signature; the caller passes B with a `OnceLock` already filled by `TxSigData::new(A.raw())`. CS6 checks A and returns `Ok(())` for B, and with `cache_full_script_store=true` stores B's `(txid, flags)` as successful. A later correctly bound check of B then hits that entry and also accepts. Core's `CScriptCheck::operator()` (`validation.cpp:2107-2110`) constructs verification data from its own `ptxTo`, so it checks B and reports `mandatory-script-verify-flag-failed (Script evaluated without error but finished with a false/empty top stack element)` under the block flags. Parallel CS6 can likewise turn Core's `block-validation-failed` into success. This requires a caller slot mix-up; the current tests allocate slots correctly, but the planned per-block arena makes the mismatch a meaningful integration hazard. Bind the slot and transaction in one type or check their identity unconditionally before executing or inserting; add a regression that pre-fills a slot for A, checks B, and proves B cannot be accepted or cached in a release build.

## Other checks and evidence

- Under the stated slot assumption, the signature key is SHA-256 of the doubled 32-byte nonce, sighash, pubkey, then signature without its hash-type byte; the script-execution key uses txid and all four little-endian flag bytes. Both stores occur only after success, and the script-execution store is serial only. `cacheStore=false` soft-erases a hit and inserts nothing. These match the cited Core paths.
- Entries retain all 32 hash bytes. At the default 16 MiB per cache, the 259-byte buckets hold 518,144 entries versus Core's 524,288, or 0.988×. The different eviction order can remove a previous success but cannot manufacture one. Production constructors obtain fresh OS nonces; fixed nonces are exposed for tests and benchmarks.
- The queue uses Core's LIFO batches and 128-check cap, waits for helpers before returning its verdict, and returns the serial first-input reason or parallel generic reason in the expected paths. Its loom test exercises the actual `Shared::add`/`Shared::drain` implementation with loom locks and atomics; it does not model Rayon's scope or the control mutex, so it is evidence for the shared-state protocol rather than a proof of the entire adapter.
- The L1 differential test source covers 1,278 script rows, 149 transaction rows, and 14 signed multi-input rows across the named cache states. The ten L3 cases include multiple invalid inputs, different transaction orderings, a later non-script failure, 130 inputs, a mempool-warmed transaction, and a valid block. Synthetic vectors reset the script-execution cache when the same txid and flags refer to different spent scripts, consistent with Core's UTXO assumption; they do not exercise the finding above.

# BS11a design review, Sol round 1

Reviewed `node/bs11a-design` at `f15002d5c` (design rev1 `cddd85cc6`) against Dash Core `v24.0.0-rc.3`. The local `~/workspace/dash` checkout has no differences from that tag under `src/bls` or `src/dashbls`. I ran the supplied Core-linked probe; P1–P5 reproduced.

## Findings

### Major 1 — D16 must distinguish direct verification from arithmetic before verification

Design §0 lines 17–20, §2.2 S6, D16, and quirk 45 say that under the basic verify flag Core returns false on Exotic operands without computing. That is true of a *direct* `VerifyInsecure` or `VerifyInsecureAggregated` call on an Exotic wrapper (`src/bls/bls.cpp:296–335`; `src/dashbls/src/schemes.cpp:135–153,297–323`). It is not true of the S6 batch path: Core first aggregates public keys and signatures (`src/bls/bls_batchverifier.h:146–178,195–228`); both `AggregateInsecure` implementations call relic without a subgroup gate (`src/bls/bls.cpp:144–176,222–254`; `src/dashbls/src/schemes.cpp:176–191`). Only the resulting wrappers reach the basic validity gate. The design's own S6 cell says “F5 then F1”, but the summary, D16, A1 §1.4.1, and quirk 45 flatten that order.

Scope the claim to the three direct verify entry points. Add an ABI-15 script and differential seed that aggregates Exotic inputs and then verifies the **result** under the basic flag; testing `AGG` and `VERIFY` independently does not establish this composed path (§7, §8). This is also a reason for quirk 45's scaffold to describe the order of operations precisely.

### Major 2 — The ABI-15 error-code field cannot certify D8 as specified

Design §3.3/D8 and §7 lines 217–224 propose reading `core_get()->code` after each wrapper operation, “before any reset”, to prove it never becomes nonzero. The called dashbls methods already invoke `BLS::CheckRelicErrors`, which clears a nonzero code before returning or throwing (`src/dashbls/src/bls.cpp:81–91`; for arithmetic see `src/dashbls/src/elements.cpp:154–159,212–231,385–390,450–470`). `NativeVerify` also clears it on a failed check (`src/dashbls/src/schemes.cpp:326–349`). An ABI-15 shim that reads the code after these calls will usually report `RLC_OK` even if the operation set it. Thus `diff_bls_arith`/`diff_bls_verify` cannot validate D8 by the proposed field, and the PLAN risk row's “error code asserted per op” would be misleading.

Keep the wrapper result as the parity oracle, but specify a separate raw-relic probe or an observation point inside `CheckRelicErrors`/`NativeVerify` for D8. Record the pre-clear code there, including which operation set it. A post-wrapper code may still be useful as a state-leak check; label it that way. The explicit `ERR_NO_MEMORY` branches in the reachable normalization and pairing routines (`src/dashbls/depends/relic/src/ep/relic_ep_norm.c:112–119`; `src/dashbls/depends/relic/src/pp/relic_pp_map_k12.c:51–68,523–534`) also mean D8 should say “for normal, successfully allocated inputs”, not literally “never set”. I found no other input-driven `RLC_THROW` in the configured arithmetic paths I inspected; the `fp2_mul_nor` default error is unreachable for this field's `p mod 8 = 3` (`src/dashbls/depends/relic/src/fpx/relic_fp2_mul.c:117–150`).

### Minor 1 — State the Group-to-relic transition invariant and exercise it

Design §3.1/D4–D6 preserves coordinates for engine results, but an all-Usable `BlsElem::add` can retain only a blst `Group` point. Core's addition can leave a `PROJC` result (`src/dashbls/src/elements.cpp:212–224,450–461`; `src/dashbls/depends/relic/src/ep/relic_ep_add.c:265,432`; `src/dashbls/depends/relic/src/epx/relic_ep2_add.c:209–210,333`). If a later operand is Exotic, the engine must reconstruct a relic input, usually affine `BASIC`, rather than Core's literal intermediate. Relic selects mixed/general paths from the coordinate tag (`relic_ep_add.c:160–174,294–299`; `relic_ep2_add.c:147–169,259–261`). I found no counterexample to affine-equivalent conversion for a subgroup point, but Lemma U proves group-law equivalence only while all operands are Usable; it does not prove this transition on a later Exotic operation.

State the normalization/identity invariant that makes the transition observationally safe, or retain Core's coordinate representation across the transition. Add `Usable ADD/MUL → Exotic ADD/MUL → SER/ISVALID/VERIFY` scripts in both operand orders, including infinity and a zero-z engine result (§8's seed list currently names engine-result feedback but not this Group-to-engine boundary). `ep_norm` and `ep2_norm` have distinct coordinate rules (`src/dashbls/depends/relic/src/ep/relic_ep_norm.c:47–87`; `src/dashbls/depends/relic/src/epx/relic_ep2_norm.c:47–80`), so cover both groups.

### Minor 2 — Correct the G2 formula description

Design §2.2 R1 calls the G2 `ep2_add_projc`/`ep2_dbl_projc` forms “complete formulas for a = 0”. Core's G2 path is Jacobian addition with explicit `H = 0` branching and a separate doubling formula (`src/dashbls/depends/relic/src/epx/relic_ep2_add.c:147–183,259–301,390–407`; `src/dashbls/depends/relic/src/epx/relic_ep2_dbl.c:119–157`). The line-by-line port decision in §3.2 remains right, but R1 should describe G1 and G2 separately so implementers do not import the G1 formula assumption into G2.

### Minor 3 — Finish the docs commit's ownership and call-site updates

The `f15002d5c` edits correctly move BS11a's PLAN row, A1 D58, EV1 §2.5/D2, COVERAGE B1/B2 and register quirk 45. Two adjacent rows still contradict them: `docs/node-program/compat/COVERAGE.md:188` says the BS12 multi-op oracle is unassigned and BS11b L1 is blocked, while its new B2 row says the same oracle exists at ABI 14/15; `docs/node-program/designs/A1-architecture.md:468` still assigns secure-aggregation weights to BS11b although BS11a D10 and Core's `VerifySecure` require them in BS11a (`src/dashbls/src/schemes.cpp:231–253`). The §2.2 call-site inventory also omits `llmq/dkgsession.cpp:603–609` (quorum signature against a derived public-key share) and the explicitly-basic `llmq/quorumproofs.cpp:305–319` site. Add those to S7/S9 and S10 respectively. They do not change the engine boundary, but the inventory and cross-document ownership should be complete.

## Checks that matched

- **D1 / Lemma C:** For fresh canonical wrappers, the BS11a-t predicate and blst's on-curve result fix the relic `BASIC` point: on-curve coordinates agree; failed G1 unpack retains the sign digit as Montgomery y; failed G2 unpack with canonical sign 0 retains y = 0. The underlying paths are `src/dashbls/src/elements.cpp:24–86,245–311` and the relic decode/unpack functions. This is consistent with the earlier 305,176-input BS11a-t differential; I found no missing canonical byte class.
- **D16 direct calls / S1–S11:** The three direct Core-shaped verifies gate Exotic operands in basic mode and enter relic arithmetic in legacy mode (`src/dashbls/src/schemes.cpp:135–153,231–253,297–323,658–701`; `src/bls/bls.cpp:296–358`). S1–S5, S7, S9 and S10 use those gates; S8 uses DH without a scheme gate (`src/bls/bls.cpp:208–219`). S11 equality and serialization are separate wrapper behavior (`src/bls/bls.h:77–93,125–146`). S6 needs the order qualification in Major 1. The additional sites in Minor 3 fit existing groups.
- **D4–D6 arithmetic choice:** P2 reproduced `g1_mul` of the order-3 point returning the affine `(0,0)` artifact, and P3 found no error code for the sampled off-curve G1 multiplication/addition. Core's `g1_mul`/`g2_mul` select the 64-bit digit path before reduction and the large-scalar path after reduction (`src/dashbls/depends/relic/src/pc/relic_pc_exp.c:38–117`); using blst for Exotic arithmetic would diverge. The Group-to-engine transition remains Minor 1.
- **D7:** P4 reproduced `pp_exp_k12(0) = 0`; P5 reproduced a zero pairing result from an off-curve G2 operand with code 0. The Core B12 path runs the Miller loop, optional conjugation and `pp_exp_k12` (`src/dashbls/depends/relic/src/pp/relic_pp_map_k12.c:523–582`), whose B12 final exponentiation is the easy plus hard exponent chain (`src/dashbls/depends/relic/src/pp/relic_pp_exp_k12.c:134–203`). The proposed zero guard and product-of-chunks test are consistent. The planned symbolic/k proof and 10^6-input probe must run in slice 4 before this becomes an implementation claim.
- **D11:** Core's DH wrapper multiplies `sk * pk` (`src/bls/bls.cpp:208–219`), and all three IES paths take `ToByteVector(false)` then 32 bytes (`src/bls/bls_ies.cpp:40–51,74–86,89–108`). The current dash-pkc Chia KDF test encodes the scheme's own bytes, so the proposed basic-encoding fix is warranted.
- **D12:** `PrivateKey::FromBytes` reduces only with `modOrder`, while the non-reducing branch admits r (`src/dashbls/src/privatekey.cpp:52–71`); `GetG1Element`/`GetG2Element` use reduced generator multiplication (`:151–175`), and `g1_mul`/`g2_mul` have the ≤64-bit path (`relic_pc_exp.c:38–117`). The `sk = r` identity conclusion matches.
- **Oracle, fuzz, bench, slices:** ABI 15 extends BS12's single ABI-14 script as ruled. The decode-first slice is independent of the new oracle and unblocks EV1-2; slice 3's model work can begin before slice 2, and Core differential arithmetic waits for it. The class-aware seeds, zero-divergence DEC-184/186 certification, targeted low-ceiling branch review, and instruction-count decode bench gate are coherent. The error-code observation needs Major 2, and the mixed sequence needs Major 1/Minor 1.
- **Docs and quirk 45:** The new registry ID follows 44, names BS11a as owner, uses `scaffold`, and has a matching ignored test. The revised PLAN/A1/EV1/COVERAGE direction matches the Core direct-verification and IES paths, subject to Major 1 and Minor 3.

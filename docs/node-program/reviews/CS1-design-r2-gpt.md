For **FindAndDelete**, Core `src/script/interpreter.cpp:224–247` copies `[pc2, pc)` before matching, consumes adjacent matches by pattern length, sets `pc2` to the resulting cursor, and then calls `GetOp`. It does not update `pc2` to the failure cursor. On a failed parse the retained suffix therefore starts at the last `pc2` and is copied verbatim; a zero count leaves the original script untouched. The revised pseudocode preserves all of this. The narrower idempotence proof also holds: starting at an instruction boundary, removing exactly one complete instruction preserves alignment; every kept instruction and the failing tail reappear unchanged. The adjacent-match counterexample for arbitrary patterns does not refute that restricted proof.

For **sigops**, Core `src/script/script.cpp:154–199` and `src/consensus/tx_verify.cpp:118–162` agree with the revised contract. The boolean overload counts parsed opcodes until failure, uses only the immediately preceding parsed `OP_1..OP_16` for accurate multisig counting, and counts CHECKDATASIG as zero. The scriptSig overload returns the accurate scriptPubKey count immediately for non-P2SH, without parsing scriptSig. Its P2SH branch rejects failed parses and opcodes above `OP_16`, and uses the last successful parser call's data, including the empty data from a trailing small-integer/reserved opcode. The transaction aggregator filters spent outputs before calling this overload and skips the view entirely for coinbase. No non-P2SH fallback leaks into transaction-level P2SH accounting.

The **11-step CHECKMULTISIG order** in §4.5 matches `src/script/interpreter.cpp:1091–1198`. In particular:

- Steps 1–4 decode and range-check the key count, then add its charge and check 201 **before** testing stack sufficiency. The latter requires the key count, all keys, and the signature-count item: `nKeysCount + 2` items.
- Steps 5–6 decode/range-check the signature count and require `nKeysCount + nSigsCount + 2` items. They deliberately do not require the dummy yet.
- Step 7 deletes every declared signature, in Core's reverse stack order, before any pair's encoding checks. CONST_SCRIPTCODE can therefore fail before those checks.
- Step 8 traverses keys/signatures from the stack top downward, checks only reached pairs, and preserves the early exit when remaining signatures exceed remaining keys.
- Step 9 checks NULLFAIL while popping, using the original argument positions tracked by `ikey2`; unused nonempty signatures count too. Step 10 then checks dummy presence and NULLDUMMY before popping it.
- Step 11 pushes the result; successful VERIFY pops it, while failed VERIFY retains the false result and returns its error.

The probes again produce success at 201, OP_COUNT at 202 and before missing-key errors, and NULLFAIL before NULLDUMMY with the partial stack `[01][7f]`.

**The §6.2 per-pin argument is correct.** Core's two `CheckInputScripts` branches use the same first verification and always format that run's error. `SNM_v24` is a subset of `SNM_v23`; the v24 retry keeps a superset of the v23 retry's flags. For the valid flag combinations used here, removing restrictions preserves success. P2SH remains set in both retries, CLEANSTACK is removed with the other policy restrictions, and disabled CLTV/CSV break before DISCOURAGE_UPGRADABLE_NOPS can reject them. Thus a classification delta can only be v23 NonMandatory versus v24 Mandatory. The argument does not promise that all v23 failures of newly mandatory flags become non-mandatory: a surviving second failure keeps the classification mandatory. The paired CLTV/RETURN witness confirms this on both pins. Undefined bits remain inert.

**C2/C3 correctness and DEC-28**

C2's widening from a per-opcode multisig memo to a **per-input** memo is correct. A checker fixes an immutable transaction and input index. Core's digest then depends only on the exact scriptCode bytes and the signature's hash-type byte; amount is ignored. Flags influence checks and scriptCode construction before the checker, so they need no separate memo-key component. The memo must own its scriptCode keys, compare complete bytes, and remain local to that checker as designed. Different keys or missed/evicted entries can change cost, not the result. C2's byte key is appropriate because `CheckSig` reads an unsigned trailing byte; it does not truncate the public full-i32 sighash API.

C3's eligible regime is exactly Core's ALL-acting branch with ANYONECANPAY clear: `(ht & 0x1f)` is neither NONE nor SINGLE. Undefined base types, higher bits, and negative i32 types are covered without normalizing the appended hash type. Before input `i`, the plain preimage is precisely the blank transaction's `B[..o_i]`; after that input it is `B[o_{i+1}..]`. Replacing the one blank input with prevout, Core-serialized scriptCode, and sequence is byte-exact, even when malformed scriptCode's advertised size exceeds the emitted body. Suffix offsets refer to `B`, not to positions in the newly emitted preimage.

The checkpoint must copy the full streaming state, including buffered bytes and accumulated length, as §4.8 explicitly requires. Outputs, lock time and conditionally serialized payload remain in the suffix. NONE, SINGLE and ANYONECANPAY use the plain path, preserving zeroed other sequences, SINGLE's preceding null outputs, and ANYONECANPAY's input count of one. Out-of-range SINGLE returns ONE without a preimage; C2 may cache that digest, but C3 must never substitute a serialized transaction for it. No new consensus divergence was found in these algorithms.

An independent C++ model of C3 was compiled with each pin's actual `CTransactionSignatureSerializer`, including its malformed-scriptCode serializer. **Each pin passed 190,371 comparisons**: 84,912 accelerated cases compared exact preimage bytes and copied-midstate digests, 102,949 fallback cases checked Core preimages/digests, and 2,510 cases confirmed SINGLE's ONE result. The deterministic corpus includes all 256 hash-type bytes plus full-i32/high-bit/negative types; versions around the payload threshold; normal and special types; random sequences, values and payloads; malformed pushes and separators; input/output CompactSize boundaries; and 680-input transactions. It checks every input of small transactions and first/middle/last inputs of large ones. It also exercises 627 non-block-aligned checkpoint positions. This establishes the splice argument experimentally; the copied Core scriptCode serializer is not a substitute for CS1's planned independent serializer tests.

DEC-25's boundaries and DEC-28's required optimizations, API slots, SH1 prerequisite, Core-side benches and declared performance shortfall are represented correctly. This review makes no new performance claim.

**New minor findings**

**F7 — Narrow the new old-sighash twin's malformed-script assertion.** `designs/CS1-script.md:845–847` says the twins agree only for well-formed scriptCodes and asserts an expected difference for malformed ones. Malformed parsing alone does not imply different preimages. On **both pins**, a single-byte scriptCode `05`, `4c`, `4d` or `4e` fails `GetOp`, but its failure cursor is already at the end. The current serializer emits the whole byte string, so `SignatureHashOld` and `SignatureHash` agree under ALL. By contrast, `05 aa` and `4d 01` leave unconsumed tail bytes and the hashes differ. Out-of-range SINGLE also makes both return ONE irrespective of malformed scriptCode.

Fix the test contract to assert equality when the actual serializations agree, and an oracle-backed quirk-39 difference only for witnesses with unconsumed bytes and no ONE shortcut. Always compare the plain Rust result to Core; qualify the sentence that compares **both** twins to the same oracle for cases where the old twin is equivalent. This is a test-contract correction, not a defect in the proposed production serializer.

**F8 — State C3's single-input dispatch explicitly.** `designs/CS1-script.md:458–460,1064–1072` builds checkpoints only for `N >= 2`, but the usage steps select `checkpoint_i` based on the hash-type regime alone. The intended one-input behavior is evident from the benchmark discussion, but the normative dispatch needs an additional condition: use the plain path when checkpoint state was not built, including every single-input transaction. Preserve Core's input-index assertion before the SINGLE shortcut. Add a named one-input ALL regression and check every byte hashtype on that branch under `xcheck`. The review model used this explicit fallback; its successful results should not be read as evidence for an unspecified absent-checkpoint branch.

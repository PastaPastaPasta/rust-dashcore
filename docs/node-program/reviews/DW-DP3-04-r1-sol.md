# DP3-04 security review (Sol r1)

**Verdict: CHANGES REQUIRED.** The post-reservation check does not bind the address being signed to the account it has just accepted as current.

## Findings

1. **High — a verified re-check can approve an address from a displaced account.** `rust/crates/dw-engine/src/send/contact.rs:225` reserves or reuses an address, then `money_recheck` checks the payee at line 240; `rust/crates/dw-engine/src/platform/money_gate.rs:322` checks only `external_account_reference` against the *current* request. The wallet manager lock is released between reservation and re-check. A contact rotation and account rebuild can therefore replace the request and external account during that interval. If the new request verifies (including in the re-check's 10-second round), its marker matches and the re-check passes, but the signed output still uses the address from the old pool. The coin fence does not serialize the Platform sync or account rebuild. This can pay an address the current verified request no longer designates. **Fix before merge:** retain the reservation's account/request lineage and, after the final re-fetch, check the reserved address against the current external account pool and verified incoming request in one consistent wallet-manager read. Refuse and drop the reservation on a mismatch. Add a race test that rotates and rebuilds at `Point::Reserved`, verifies the new request, and proves the old address is not signed or kept. This is deferred Opus r3 **#7**, a real money-destination gap, not merely hardening.

2. **Low — the displaced-fresh-address fix lacks its own regression.** `rust/crates/dw-engine/src/send/contact.rs:247` now checks that a fresh address survived `keep`; this looks correct, but `rust/crates/dw-engine/src/send/contact_tests.rs:1836` exercises a *reused* address claimed by another broadcast. The 19 caught mutations do not exercise a fresh reservation displaced by a prior payment's give-back. **Fix:** add the interleaving with the first payment returning its address after the second has freshly reserved one, and assert `send.prepared_tx_spent` with no signing or keep of the displaced address.

3. **Low — item 54 overstates what stayed unchanged.** `docs/contracts/m4-dashpay-engine.md:2802` says “No signature, record or code changes,” although this patch adds code and writes `dp_trust_verified` records. The intended statement appears to be that public signatures, public record shapes, and error codes are unchanged. **Fix:** say that explicitly. Contract-Version 28 and the unchanged generated surface hash are otherwise consistent with a behavior-only contract update; m4 §4's error table did not change, so no Swift `engineCodes` update is needed.

## Requested rulings and checks

- **Deferred Opus r3 #6 (queued-operation ciphertext): hardening follow-up.** `money_gate.rs:327` exempts any queued `RegisterExternal` before reservation, even one carrying older ciphertext. The reservation drains it, and the strict post-reservation check at lines 450–455 refuses if the account marker is still stale. The platform-wallet stamp compares the ciphertext it actually built against the live request before stamping. A stale queued operation can waste a reservation or shorten the wait, but I found no independent path through it to a signed unverified address. Narrowing the exemption is still prudent and should be tested with an obsolete queued operation.
- **Deferred r2 #7 (`PreparedTx.contact` checked bit): hardening follow-up.** A failed first hand-off returns the address with `checked=false` (`send/contact.rs:326`, `:358`), so the next enforcing `prepare` skips an index. Carrying the bit would avoid that skip; the present behavior fails closed. A previously prepared transaction can broadcast after a developer-mode change without a new gate, as D14 explicitly allows. That policy boundary is separate from carrying this bit.
- **Deferred r1 #8 (gate before cheap refusals): hardening follow-up.** Watch-only, non-payee, and payment-lock refusals at `send/contact.rs:123`–`:127`, and top-up's funding/journal/ownership refusals at `platform/topup.rs:416`–`:432`, happen before the gate and before any Core funding or payment. Reordering changes latency/error precedence, not the destination safety property.
- **D7 degraded mode:** acceptable only under the stated degraded trust model: the trusted quorum service and proof-bearing Platform responses remain trusted while SPV verification is unavailable; a discovered disagreement is an additional refusal. `money_gate.rs:199`–`:202` makes one bounded probe and proceeds on absence, timeout, or an unverified result. An attacker able to control the trusted response can withhold/delay a comparison or supply a false quorum key when SPV has none, and can redirect funds. The probe is therefore not protection against a compromised fallback service. This risk should be explicit in the product/release decision for the default `Degraded` mode.
- **D15 overrun:** confirmed as a funds-safety claim. A blocking quorum/HTTPS lookup may extend the 60-second enforcing wait or 10-second re-check. During the initial contact gate, `prepare_contact` has not taken the coin fence, grant, address, or signature (`send/contact.rs:128`–`:134`); during the re-check it has reserved an address and charged a lease, but has not signed or broadcast (`:190`–`:203`, `:240`). Top-up has not reached its funding permit or `fund` (`platform/topup.rs:435`, `:467`–`:474`). No Core money moves during the overrun.
- **D17 precedence:** `money_gate.rs:289`–`:311` matches `contacts_model.rs:231`–`:277`: established, ignored, incoming, outgoing, with the same cached profile and shown username source. The tests compare the gate and row, and mutations removing profile/label checks fail. I found no material precedence divergence. A later change to either copy will need both updated.
- **Other bypass paths:** the gate runs before grant redemption and contact reservation; the payment lock is checked before the wait and again by `resolve`. The post-reservation check catches a newly shown name or unverified request. `PaymentLocks::claim_payment` checks the exact reserved address, so an old prepared transaction whose address was dropped gets `send.prepared_tx_spent`; the final address comparison also rejects a claimed reused address or a displaced fresh address. A signed prepared transaction is deliberately not re-gated at broadcast, so subsequent payee changes do not rewrite its output. `TxDraft::prepare` runs in a spawned runtime task (`send/mod.rs:975`–`:984`, `session.rs:659`–`:672`), making caller-future cancellation unable to strand an unchecked reservation. Top-up targets the fixed own identity ID and checks ownership again under its write lock before funding. Registration has no existing Platform payee and its funding hold includes `writes_wait`.
- **Tests and evidence:** the 19 effective mutations are meaningful for their named checks: `mut3.log` catches 18, and `mut-extra.log` catches the corrected claimed-slot mutation. The earlier claimed-address mutation survived because it could not fail by construction; its replacement is the one counted. They do not cover finding 1 or the fresh-address interleaving in finding 2. T2's successful unverified-B runs exercise a real degraded probe and a real enforcing `prepare`, without broadcast. Because that probe records B as verified first, the enforcing gate then takes its already-verified path; T2 does not demonstrate a live enforcing re-fetch. The identity-gate result is logged but not asserted by the test (`send/contact_tests.rs:2041`–`:2045`), although the recorded runs show `Ok(Ok(()))`. T0 covers the enforcing wait/refetch behavior.
- **Gate and flakes:** `git diff --name-only 1aa8beda..26da1de7 -- rust` is empty; the last two commits are a main merge and design-doc update. The full Rust run on 1aa8beda reported 2 failures among 2050 tests, both in untouched `platform/lease/call_tests.rs`. Their 100–300 ms stall and 5-second polling assertions are load-sensitive. Both pass when I run them alone from the same test binary, so a load flake is plausible; I did not independently reproduce the reported 20/20 reruns. The full gate itself remained red, so the branch should also receive a clean gate run or a documented CI rerun after finding 1 is fixed.

## Lock order and false-fence audit

- The new path is **appdb connection → tap epochs** only during `record_events_if`'s admission callback. `delete_wallet` releases the connection when it returns, and removal then calls `tap.forget`, taking **epochs → catch-up cache → unread → pump**; no connection is taken under its epoch guard (`wallets.rs:253-265`, `journal.rs:601-606`). Readmission takes the connection only after the removal lifecycle lock is available.
- `refresh_unread` holds `refreshing` while it queries appdb, then obtains `epochs` only after `unread_counts` returns and its connection guard is dropped (`journal.rs:642-665`). `load_unread` holds `epochs → unread` but takes no connection. `mark_read` reads the epoch and releases that guard before its appdb mutation (`journal.rs:755-775`). `ignore` releases its identity write lock when `set_ignored` returns, then obtains the mark-read write fence (`contacts.rs:299-314`, `requests.rs:635-657`). That fence is acquired before the blocking SQL job; removal waits for it before manager removal, not while holding appdb (`private_details.rs:703-725`, `runtime.rs:449-457`). The session gate is an outer admission; its close waits for calls and does not acquire appdb while holding an epoch guard. I found no cycle involving these paths.
- An ordinary live-wallet write reads an unchanged epoch and is admitted. The only bumps are `tap.forget` during completed removal and restore rollback (`wallets.rs:264`, `backup.rs:719-723`). Import/readmit cannot overtake a successful removal because both hold the wallet lifecycle lock. Rollback that retains a watch-only wallet is the one explicit false-fence case, judged below; the watch-only registration has accounts but no DashPay identities (`multiwallet.rs:512-528`).

## Residual rulings

- **(a) Acceptable.** A failed restore can call `tap.forget` while keeping an existing watch-only wallet (`backup.rs:689-724`). That can fence a concurrent journal callback, but a watch-only wallet has no DashPay identities to produce one through the normal application flow. Item 43 now states the outcome. This is a narrow documented loss of an in-flight row, not evidence of a normal live-wallet false fence.
- **(b) Must fix.** This is pre-existing, but it leaves the newly claimed writer-generation guarantee false for a committed partial removal. See finding 1. A failed appdb delete occurs after the wallet has left the manager and its seed has been wiped, yet bypasses `tap.forget`; a same-session reimport can readmit before an old callback runs. The error does not restore the old wallet.
- **(c) Acceptable nit.** `mark_read` can mark `Events` after `unread_moved_since` already marked it (`journal.rs:763-773`). A `BTreeSet` coalesces them when they share a pump window; across windows there can be two harmless refresh hints. It writes no extra rows or news.

## New findings

1. **Major — `rust/crates/dw-engine/src/wallets.rs:259-264` and `rust/crates/dw-engine/src/platform/journal.rs:901`.** If `persister.delete_wallet` succeeds but `appdb.delete_wallet` fails, removal has already removed the wallet from the manager and wiped its seed, yet returns before `tap.forget`. The tap epoch stays unchanged. A same-session import of the same seed may call `readmit_wallet`, and a pre-removal `WalletStore::store` callback delayed before `record_events_if` passes the old epoch check and inserts its event into the reimported wallet. A scratch-only test installed a SQLite trigger that fails deletion of an existing `dp_events` row, held a writer at `pause_journal`, observed removal return an error, dropped the trigger, reimported the backup, then released the writer. The test **failed** because the old writer's contact appeared as journal row 2. The proof patch is `/work/scratch/dw-dp205-r3-sol/failed-delete-proof.patch`. This is the residual (b) the implementer reported; being pre-existing does not close the new journal-generation contract under partial removal. Bump/invalidate the generation when manager removal commits even on later delete failure, and require completion of the failed appdb cleanup before that wallet id is readmitted. Add the injected-delete-failure and delayed-writer test to the branch.
2. **Minor — `rust/crates/dw-engine/src/platform/journal_tests.rs:1256-1271`.** The test waits for emitted events but never arranges a pump flush between the old recount mark and row mark. With only the `ef4e2b6b` one-mark change reverted in the scratch copy, the test passed 15 of 20 isolated runs and failed 5. It therefore does not reliably catch the bug, even though the production change is correct. Add a test hook that pauses after the old first mark and forces or observes a pump flush before the row mark, or an equivalent deterministic assertion on the pending mark sequence. Keep a bounded timeout for the test hook.

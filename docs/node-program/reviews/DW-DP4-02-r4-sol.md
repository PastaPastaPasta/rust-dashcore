# DW DP4-02 independent security review, round 4

Reviewed detached `14f0a041` (r4 fix `9ca1e34a` against r3 `b14573e7`) using the requested `rust`, `docs/design`, and `docs/contracts` diff. The merge of `main` was checked only for the m4 contract and its test.

**Verdict: CHANGES REQUIRED.** D39 closes the avatar-URL resolver race, and D40 closes the avoidable post-join delivery gap. The avatar-triggered Platform profile read can still start a TCP connect or DNS lookup outside the off drain.

## Findings

1. **MAJOR — An avatar-triggered Platform connect can start after off returns.** The remote-profile step is dropped on revocation at `rust/crates/dw-engine/src/platform/avatar.rs:939-942`, but D39's admission is passed only to the avatar HTTP fetch (`avatar.rs:657-659`), not to the Platform SDK (`rust/crates/dw-engine/src/platform/requests_net.rs:240`). Concrete schedule: on a cold SDK connection, an unknown user's `avatar` polls `Document::fetch_many`; the DAPI client creates a pooled Tonic `connect_lazy` channel (`rs-dapi-client/src/transport/grpc.rs:38-63`, `transport/tonic_channel.rs:72`) and queues the request. Tonic's separate channel worker dequeues it and verifies that its response receiver is still open (locked `tower` 0.5.3 `buffer/worker.rs:71-97`). The OS deschedules the worker before its next `service.poll_ready` (`worker.rs:147-170`; the engine has a multi-thread runtime at `rust/crates/dw-engine/src/engine.rs:79-86`). Off publishes, `unless_revoked` drops the SDK future and the avatar ticket, and `Pictures::drained` sees no registered read, so `set_load_contact_pictures(false)` returns. The worker resumes; it does not recheck cancellation before `poll_ready`, which makes Tonic's lazy connector start a TCP connect to the DAPI address. This applies to the default IP-literal seed addresses. With a configured hostname (accepted at `rust/crates/dw-engine/src/session.rs:919-921`), Hyper's default GAI resolver can also start a detached `spawn_blocking` lookup (`hyper-util` 0.1.20 `client/legacy/connect/dns.rs:109-125`) that runs after off. Tonic's channel worker and that resolver are outside the ticket registration; D39's `Admission` never reaches this transport. Add a cancellation/drain boundary for avatar-attributed Platform transport work, or narrow the documented guarantee explicitly if Platform traffic is allowed to continue.

2. **NIT — D39's 30-second figure is not a worst-case bound.** `docs/design/DP4-02-avatar-pipeline.md:172` calls a system lookup the off's “worst case” and gives glibc's 5 s × 2 × 3 = 30 s calculation. A concrete schedule is: an avatar DNS worker registers and enters `getaddrinfo`; off publishes its epoch and waits in `Pictures::drained` (`rust/crates/dw-engine/src/platform/avatar.rs:205-210`); the resolver tries multiple search-suffix candidates, or an NSS module stalls, so the worker does not drop its admission and off (then a session close waiting behind it) cannot finish. The 30-second calculation is a common default single-name estimate, not an upper bound even on glibc. The design already notes longer NSS and OS waits; it should say explicitly that the application has no finite drain bound.
3. **NIT — The contract states a stronger return guarantee than D40 can give.** `docs/contracts/m4-dashpay-engine.md:503` says no avatar call still pending when off returns will return a contact picture, then excepts a value already past the last check. A concrete schedule is: a cached contact answer passes `Answer::deliver` (`avatar.rs:1121-1125`); its thread is descheduled before the Rust return or Tauri's response serialization (`rust/crates/dw-app/src/api/social.rs:329`); off completes; the held value is then returned. This is the deliberately recorded D40 residual, so the contract should describe the guarantee at the final epoch check rather than at physical response delivery.

## Boundary assessment

- **R3 finding 1 closes for avatar URL lookups, but the whole network boundary remains open.** `Admission::admit` checks the stamp and increments the read count under one watch write lock (`avatar.rs:380-392`). The blocking worker holds that registration across `getaddrinfo` (`avatar_fetch.rs:211-220`), including when its awaiting fetch is dropped. If off wins the lock, the worker refuses the lookup; if admission wins, off's drain waits for its drop. `Checked::resolve` gets an admission only inside the task-local `Fetcher::fetch` scope (`avatar_fetch.rs:233-243,298-306`); the blocking task receives an explicit clone, so it does not rely on task-local inheritance. The production pipeline has only this `BlockingResolver`; `prepare_avatar` deliberately uses `Admission::any` (`avatar.rs:681-694`). In the locked reqwest 0.12.28 / hyper-util 0.1.20 source, the configured resolver overrides default GAI or Hickory. Redirects stay inside `follow`, and `pool_max_idle_per_host(0)` disables Hyper's pool, including its detached background connect path; Happy Eyeballs stays in the connector future. A fetch cancelled by off therefore cannot start a later avatar TCP connect. The Platform SDK uses a separate client and resolver, as finding 1 explains.
- **R3 finding 2 closes at `DashPay::avatar`.** The inner answer carries the original stamp and whether the identity is another user (`avatar.rs:1048-1055,1111-1125`). After the runtime task joins, `DashPay::avatar_through` performs the final check immediately before returning (`profile.rs:250-259`), suppressing contact pictures and contact-read errors after an intervening off. Argument and wallet errors that occur before own/other classification remain ordinary API errors. The own-identity classification comes from the wallet's summaries (`avatar.rs:1071-1082`), and only own cached pictures remain available off. `dw-app` calls this public method and converts its result without another await (`rust/crates/dw-app/src/api/social.rs:321-329`); no event carries thumbnail bytes. A result already past that final check can still be delayed by thread scheduling or bridge serialization until after off, exactly D40's recorded in-memory residual. The desktop's React Query cache (`apps/desktop/src/dashpay/profileQueries.ts:63-72`) will need invalidation or gating when the setting is exposed in the UI; it is outside this engine fix.
- **No new drain deadlock found.** Admission registration and deregistration take only the watch lock. The off transition holds the separate transition turn while waiting for earlier read counts, but neither DNS workers nor reads need that turn to finish. Session close waits for the operation gate and then the transition turn (`session.rs:749-751`). A stalled OS resolver, cache row or thumbnail job can extend both waits; this is a liveness residual, not a lock cycle.
- **Tests and merge.** The D39 test pauses inside the admitted avatar-URL worker before the lookup and checks both the drain and a worker started after off; the D40 test pauses after the task join and before the public check. The matching-avatar test reaches the custom resolver through the task-local scope. None exercises a cold Platform SDK channel or its worker, so the mutation checks do not cover finding 1. The m4 contract is version 31, retains DP5-01 as item 56 and DP4-02 as item 57 (`docs/contracts/m4-dashpay-engine.md:3,2905-2924`); `m4_dashpay_contract.rs` retains both implemented sets.

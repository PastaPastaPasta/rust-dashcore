CHANGES-REQUESTED

## Findings — real defects

1. **Medium — `apps/desktop/src/api/lockReport.ts:137`.** `reconcileLockReport` fetches `lockStatus` but does not use it when deciding `settled`. With `walletsWithSecretsOmitted > 0`, a `lockStatus` response that no longer accounts for the report's wallets (or says the vault is unlocked) still leads to “Every action the lock stopped has ended” as soon as the listed artifacts settle and no lease reports an in-flight call. This does not reconcile the omitted wallet count as ROADMAP U-07/E0-13 D3 require. Verify the current lock state and the full wallet set against the report before treating a wallet omission as settled; keep the report unresolved if that check cannot establish the omitted wallets' state. Add a test in which the returned `lockStatus` disagrees with the report.

2. **Medium — `apps/desktop/src/fixture/wallet.ts:193`.** The fixture's `historyPage` implements only category and text filters and uses decimal offset cursors (`:203–205`). The engine applies type, status, date, minimum amount and watch-only filters, validates limits, and uses query-tagged keyset cursors (`rust/crates/dw-engine/src/history.rs:834–874, 986–1014`). For example, a UI test that filters to `statuses: ["unconfirmed"]` still receives confirmed rows from the fixture, while the real app does not; an invalid or stale cursor silently produces an empty fixture page but fails in the engine. Implement the same filtering, sort tie-breaks, validation and cursor behavior, with shared vectors from the engine, so paging and filter UI tests exercise real responses.

3. **Medium — `apps/desktop/src/fixture/handlers.ts:158`.** `dashpay_accept_request` returns `req-${username}` and succeeds for any supplied grant. The engine's `request_ref` returns the request's decimal millisecond `created_at` (`rust/crates/dw-engine/src/platform/journal.rs:99–104`), and `accept` redeems an authorised grant before it sends (`requests.rs:611–627`). A UI can pass fixture tests while storing a non-engine request reference or omitting the grant flow, then fail against the real facade. Use a numeric request reference and exercise grant rejection/acceptance at this IPC boundary; add a contract test against a real engine response.

4. **Medium — `.github/workflows/tauri-selftest.yml:154`.** The judge accepts whatever screen keys are present; it does not require four screens. With its default fresh empty wallet, `collectReport` records only Overview and Transactions: there is no transaction to open, and a real vault supplies no passphrase, so `txDetail` and `unlock` are skipped (`apps/desktop/src/app/selftest.ts:198–213`). Thus macOS/Windows CI can pass even if the detail or lock screen never renders. Require the expected screen set and seed/open a real transaction and a lock/unlock path, or explicitly split these into separate mandatory real-engine checks. Keep the missing-history selector exception limited to the empty-wallet checks.

5. **Low — `apps/desktop/src/fixture/handlers.ts:190`.** The fixture returns notification pages, unread counts and successful `dashpay_mark_read` mutations while the corresponding engine methods still return `platform.not_implemented` (`rust/crates/dw-engine/src/platform/notifications.rs:47–64`). A future bell UI can be green in fixture tests yet always fail in the current packaged app. Until DP2-05 lands, make these handlers return the engine's stub error, or mark the scenarios as future-contract examples and require a real-engine integration test before treating their UI tests as release evidence.

6. **Low — `apps/desktop/src/api/events.test.ts:41`.** The test called “shows a lock's report with its done” has no `lastLockReport` request in flight. Removing `cancelQueries` from the implementation would leave this test green, so it does not prove the claimed slow-fetch race. Start a deferred report query, emit `done` with a newer report, then resolve the old query and assert the newer cache value and screen remain.

7. **Low — `rust/crates/dw-app/src/api/app.rs:75`.** The pre-existing test-only `ipc_bench_rows` command is granted to the packaged main window (`capabilities/app.json`) and lacks the `selftest_path()` gate used by adjacent selftest commands. It returns at most 200 synthetic rows, so this is a production-surface hygiene issue rather than a data leak, but it means the claim that test-only IPC paths cannot be enabled in production is too broad. Gate this command on `--selftest` or remove its release permission, and cover the refusal without that flag.

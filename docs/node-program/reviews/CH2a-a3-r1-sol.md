## Findings

### S1 — major: a logging panic lets `CoreAbortSink::read_failed` unwind instead of aborting

**Location:** `dashd-chainstate/src/store/abort.rs:45`, also `:48`; constructor at `:25`.

Both supplied `log` closures run before `std::process::abort()`, with no protection against unwinding. Replacing `eprintln!` with a fallible stderr write fixes that one output failure, but does not make the fatal path non-unwinding. The constructor accepts any safe `Fn(&str)`, and the existing child test itself supplies a `println!` logger.

**Concrete failure:** a stored-coin error trips the latch and calls this sink. If the logger panics—for example, `println!` writes to a pipe whose reader has exited—the storage call unwinds past the intended abort. A worker panic can leave the process alive; a caller can also catch the unwind. The result is no longer Core's immediate fatal read path, and application destructors can run before termination. The node-wide latch still prevents subsequently admitted writes; this finding does not claim that the latch is cleared or that an invalid verdict was observed.

**Independent proof:** `abort-probe.rs` compiles the reviewed production `abort.rs` unchanged, supplying only its parent trait declarations. With an outer `catch_unwind`, a panic on either the first or second log call returns control and exits **0**, printing `read_failed unwound: true`. A `println!` logger with a broken stdout pipe does the same. The controls, with a returning logger and with stderr closed, both terminate with **SIGABRT**. See `abort-probe.log`.

**Fix:** establish an abort-on-unwind guard before formatting or calling the logger, or catch logging panics locally and unconditionally abort afterwards. Add child-process checks for a panic at each logging call and a broken logging pipe, with an outer catch to prove that the fatal call cannot escape. This is the a3 requirement to never unwind, rather than a new shutdown invariant. Core's reference path is `coins.cpp:355-371` (`ExecuteBackedWrapper`), with the user callback at `init.cpp:2087-2091`.

### S2 — minor: the cache fixtures fail on the correctly capped 32-bit implementation

**Location:** `dashd-chainstate/src/caches.rs:165` and `:203`; `tests/data/cache_sizes_v24.txt` and `cache_log_v24.txt`.

`MAX_DB_CACHE` correctly selects 1,024 MiB on a 32-bit build, matching Core `txdb.h:35`. Both tests nevertheless compare against fixtures generated by 64-bit Core. For example, the `dbcache=2048`, indexes-off row expects 2,136,997,888 coins bytes, while the correct 32-bit result is 1,063,256,064. The `dbcache=16384` log section likewise expects the 64-bit shares.

**Proof:** compiling a scratch copy of `caches.rs` with only the pointer-width condition selecting the 1,024 MiB branch makes the grid and log tests fail; the default split passes. See `cache-32-cap-sim.rs` and `.log`. I also attempted an actual i686 test build of the unchanged source; the installed Rust target lacks the system's 32-bit C startup objects/libraries, so it could not link (`cache-32-build.log`). The executed negative control is a cap simulation, not a claimed native i686 run.

**Fix:** retain separate pinned-Core fixtures for the two pointer widths, or select platform-appropriate expected rows/log sections while keeping a direct test of the 32-bit cap. The calculation is correct today; this is a portability failure in the tests.

### S3 — minor: the indirect RocksDB assertions do not cover non-strict cache behavior or `allow_stall`

**Location:** `dashd-chainstate/src/tuning.rs:359-374`; construction at `dashd-store/src/rocks.rs:172-183`.

The test observes the cache capacity, WBM size and the WBM's charge to the cache. Its OPTIONS checks also cover per-CF buffers, `manual_wal_flush=false` and no L0 pinning. Those are useful, discriminating assertions: the recorded uncharged-WBM mutation fails the usage assertion at `tuning.rs:374`.

However, the same usage/capacity assertions do not distinguish `allow_stall=true` from false or a non-strict LRU from a strict one. The write is far below the 37 MiB WBM threshold and the 74 MiB cache capacity; neither behavior is exercised. The OPTIONS file does not serialize these two settings. Thus the a3 row's assertion requirement is only partly evidenced.

The implementation values are correct by inspection through RocksDB 11.8.1's binding: `Cache::new_lru_cache` reaches `NewLRUCache(capacity)` with its non-strict default; the WBM constructor forwards the explicit `true` to `WriteBufferManager`, whose `ShouldStall()` checks it. I did not plant these two additional mutations or claim a failing current configuration.

**Fix:** add small native/behavioral checks that distinguish the two settings: exercise a retained cache charge beyond capacity and a WBM above its threshold, with controls selecting strict capacity and no stalling. Keep the existing charge test; it proves a different property.

### S4 — minor: snapshot `multi_get` coherence is not tested across a later write

**Location:** `dashd-chainstate/src/coins/tests/table.rs:57-58`; `coins/model.rs:1193-1195`; the engine path is `dashd-store/src/rocks.rs:667-672`.

The new snapshot `multi_get` test performs no write after taking its snapshot. The model's producer takes a snapshot and reads it in the same atomic model operation. Consequently a realistic regression—snapshot `multi_get` reads the current engine instead—cannot be distinguished there. `dashd-store`'s model has snapshot point reads and scans, but no snapshot `multi_get` operation.

**Independent negative control:** a scratch engine wrapper changes only snapshot `multi_get` to read its live engine; snapshot `get` and iteration remain correct. All **64** inputs/configurations from the cross-engine test's schedule pass the model with identical Stats to the correct Memory model, with the tagging allocator active. A directed overwrite after snapshot creation then shows the bad result: snapshot `get` returns `old`, while its `multi_get` returns `new`. See `store-probes.rs` and `store-probes.log`. This wrapper mutation is outside the reviewed branch; I did not modify `RocksSnapshot` in place.

The reviewed RocksDB code correctly sets the snapshot in `read_options()`. This is a coverage finding, not a current snapshot defect.

**Fix:** on both engines, snapshot several coins, then overwrite, erase and create keys before querying snapshot `multi_get`; compare with that snapshot's point reads, including duplicates and absent keys. Retain a live-read negative control. The previously reported reversed-results mutation proves key ordering, not snapshot isolation.

## Wipe, crash recovery and CH5

The three Durable batches are correct against the atomic multi-CF engine contract:

1. Before the marker batch survives, the old state remains and the original requested wipe can restart.
2. Once the marker survives, `wiping=true`, tips and the transition marker are absent. Whether the delete batch survives or not, repeating it is safe.
3. Once the final clear survives, the delete batch necessarily survives too. A failure reported after a batch applied has the same recoverable states. Repeated crashes during retries do not change the argument.

The committed crash test covers failures before each write, both reindex flag states, preservation of block files/index records and final marker clearing. My independent probe adds failures before **and after** all three atomic writes, further crashes in every retry position and both reindex flag states: **48 schedules pass**. This exercises the real `wipe_chainstate` through an external wrapper, with Memory power-loss/restart behavior. Actual open-time recovery is absent from this branch and remains CH2b's obligation; the design's recovery step 2 resumes `wiping` before examining a flush marker.

The new marker correctly stays separate from Core's `-reindex` flag. Core destroys the coins/evo databases for either reindex mode (`node/chainstate.cpp:149-160,233-236`; `dbwrapper.cpp:144-146`), but destroys the block-tree DB only for full `-reindex` (`node/chainstate.cpp:153-157`). Keeping the block index here is therefore correct for this chainstate-only primitive; CH5 owns the additional full-reindex index reset.

**Range completeness:** for every schema-v1 key, `[empty, 0xff × 1024)` is complete. A1 §2.9 gives evo keys of 32, 33 or 7 bytes; coins keys are at most 37 bytes. Even an all-ff key of those lengths sorts before the proper extension used as the upper bound. The range also includes an empty key. It is not a mathematically unbounded deletion: an arbitrarily malformed key equal to or above the sentinel would remain. That limitation is outside the valid-key schema proof and should not be represented by CH5 as a general repair of every form of database corruption.

**Physical deletion deviation:** accept it for a3. Range tombstones give the required logical wipe and replay safety while keeping the shared index/file CFs. They do not free old SST bytes as `DestroyDB` does; the design records this. CH5 must retain that caveat and test low-space reindex behavior/reclamation, as well as disk-size reporting after its copy point. A3 supplies no CLI reindex driver and does not establish that the future CLI needs only Core's post-destruction disk space.

## Custom tuning and mutation strength

**Custom-tuning ruling:** acceptable for a3. No production `FlushMachine`, `ThreadDriver`, `InlineDriver` or subscriber driver exists in the reviewed source. They are expressly b1/b3 content in §7.2. Implementing stubs solely to satisfy this one earlier acceptance sentence would not demonstrate their future behavior. A3 actually tests `CoinsBudget::for_engine` with a reserve distinct from both shipped tunings and counts one `after_bk` call per successful model release. The custom journal value has no consumer yet and is not evidenced by a vacuous assertion. This is a deliberate partial acceptance, not a claim that the original sentence has been fulfilled in full.

**CH2b must carry forward:** use that custom reserve in the real flush machine's batching/accounting, assert the real step-11 hook and driver behavior, and use the custom journal budget/deletion span in its subscriber driver. Likewise `GlobalFailStop::check`/`wait_tripped` must arrive with the first consumer that needs those APIs.

I read the complete implementer report and inspected the available five explicit mutation-failure records (`implementer-mutations.log`): reversed snapshot epoch order, reserve reduced to S, omitted after_bk, wipe using reindexing, and uncharged WBM. Each fails the intended test assertion. For the reported empty-range mutation, the direct cross-engine test's `len()==3` and expected rows discriminate an extra empty operation; I did not independently repeat the source mutation. For reversed snapshot multi_get results, repeated/absent/non-ordered model keys give a real semantic discriminator; I did not find a separate run record proving that historical mutation and do not count it as independently replayed.

The Memory/Rocks model runs use actual shipped reserves as well as a shared ModelTuning reserve, so engine mapping/order errors and different reserve policies are exercised. The after_bk counter detects an omitted call, not the complete durability protocol. These are no-crash cache models: they cannot establish b1 recovery, real threaded interleavings, journaling or flush-driver ordering. S3 and S4 identify two realistic divergence classes outside the claimed mutation evidence. The prior a1+a2 membership/best-block findings were read for continuity; a3's baseline already carries the subsequent tests and fence changes, and this review does not reopen those approved transitions.

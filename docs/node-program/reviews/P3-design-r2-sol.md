## Finding

### F1 — Major — the residual Q9 window can change the wire message, not just its debug line

Design: `P3-block-download.md:1147-1158`, `:1368`, `:1815`; Core: `net_processing.cpp:2228-2266`, `:2273-2305`, `:6411-6479`. Existing port section 7: `dashd-p2p/src/processing/sync.rs:423-497`.

The head-of-`send_messages` drain closes Opus m-1's common case, but a signal can arrive **after** that drain and before section 7. The design says section 7 then sends the same cached compact block, and only the log line differs. That holds when the pending announcement list contains just the newly accepted block. It does not hold when the new block unlocks an already stored descendant:

1. A fully connected peer requests high-bandwidth compact blocks and also sends `sendheaders` (or `sendheaders2`); these are independent peer flags. It knows the current tip P. A valid descendant D of B is stored, awaiting B.
2. The actor drains at the head of `send_messages`. Before it takes its section-6–12 chain snapshot (`logic.rs:794-799`), an RPC submits B, extending P. `AcceptBlock` emits `NewPoWValidBlock(B)` under Core's v:4831 guard. Core's synchronous callback sends `cmpctblock(B)` and sets `best_header_sent = B`; rev3 queues that per-peer half after setting `recent`.
3. ABC connects B and D. `UpdatedBlockTip` appends both hashes to `headers_relay` (Core np:2281-2305; the port's `peerman.rs:141-145`) before the actor takes that snapshot and reaches section 7.
4. Core's section 7 skips B because the peer was already sent its header, then sends one `cmpctblock(D)` (np:6458-6479). Rev3's section 7 sees **two** unsent headers and sends `headers(B,D)` or `headers2(B,D)` (np:6473-6522; port `sync.rs:469-497`). It records D as `best_header_sent`. The later per-peer drain then skips B as an ancestor of D. The peer sees different message types and a different compact-block nonce draw, not merely a different debug line.

With neither headers preference set, the two-entry list falls back to `inv(D)` before the queued `cmpctblock(B)`, whereas Core sends `cmpctblock(B)` before `inv(D)`. Thus the broader problem is the per-peer callback crossing section 7, with the multi-header case giving a direct wire difference. `Shared::recent` preserves B's cached bytes but cannot restore the callback's earlier update of `best_header_sent`. The S4 differential row tests a single RPC block; it does not force the stored-descendant case.

**Fix:** Make the per-peer update and section 7 mutually ordered at their shared peer-state boundary, including a signal arriving after the head drain; or explicitly seek a manager ruling for this wider wire deviation, revise Q9/R6 and the parity claim, and add a differential case with B plus a stored descendant and both header-preference settings. The current “same frame, only log line” bound cannot stand.

### F2 — Minor — the performance gate mixes instruction-count mechanisms

Design: `P3-block-download.md:1437-1456`. The text says every gate counts `instructions:u`, and the Rust actor is read by `perf stat -e instructions:u`, but its Core reference is Callgrind's inclusive `Ir` count, subtracting another inclusive count. Callgrind's instrumented guest-instruction estimate is not the PMU's retired user-instruction event. A strict `≤ Core` READY gate can fail or pass because the counters differ, even for identical machine code. Also, subtracting all of Core's `ProcessNewBlock` removes its synchronous `NewPoWValidBlock` work, while the Rust actor retains the delayed per-peer half.

**Fix:** Measure both sides with the same counter and workload boundary. If Callgrind is used for function attribution, label that comparison as such and do not call it an `instructions:u` gate; account for `NewPoWValidBlock` on both sides. Keep the separate real-V merkle-pass gate.

## Requested dispositions

- **PreStart discard: exact under A-12's startup order.** `BlockChecked` (`net_processing.cpp:2314-2343`) has no peer punishment, HB-list change, map erase, or log without a `mapBlockSource` entry; the only Core insertion sites are the P2P block/compact handlers (`:3804`, `:5271`, `:5383`). Before the actor's first drain, none has run. The invalid and valid/IBD branches both reduce to no action; a missing node state cannot create an effect without that map hit. `NewPoWValidBlock`'s per-peer half iterates `FullyConnectedOnly` (`net.h:1438-1441`), and `VERACK` sets `fSuccessfullyConnected` only in the actor's message handling (`net_processing.cpp:4257`), after its first drain. Its peerless half, including the nonce draw before the height check, the highest-height update, and the most-recent block/encoding, runs on V at push in rev3. I find no pre-start wire, peer-state, or log effect from the discarded entries. Therefore a literal unbounded pre-start queue is not needed for **behavioral** parity. DEC-229 literally offers actor-start registration or an unbounded queue, so the manager should record this equivalent discard optimization as an amendment or choose the literal fallback; the design already flags the deviation in D26.
- **My M1, M3, m4–m6: closed as ruled.** D19 gives P3 ownership of the extra ring, an explicit temporary empty-ring deviation, P5/MP1a insertion owners, and an orphan-then-compact acceptance row. E4 and the compact differential are required for S3/S4 READY, with the release-toolchain oracle rule. The sweep covers 0..=65,535 and a real GCC 13.3.0 `std::unordered_map` probe, with 305 table entries including the sentinel. The IBD direct-fetch case and `merkle_checked` handoff are stated and tested in the plan.
- **My M2 and Opus MJ-1/MJ-2: closed at design level, subject to A-1b's implementation checks.** C5 forbids queue-space waits while `holding` or `PreStart`, and inside an existing wait. The idle-point mode defers class C without calling `release_point()` outside a composite. The bound is restated as the queue bound plus Q × (one compact encoding and two entries) plus C `BlockChecked` entries, carried to §5.1 and A-9; cost is released per processed entry. Q = 6 is correctly identified as the default **assumption**, with CH1-node asked to confirm one outstanding `ProcessBlock` per sender and no marked-lane producer. The tests cover N = 1, 4 and 16, hold, pre-start, nesting and per-entry release.
- **D27/D28:** The peerless split preserves Core's early `recent` state, including a pre-connman import after IBD has latched false. The carried `EntryFacts` are the in-scope immutable fields needed for a new header's one-entry overlay; the previous header has already been accepted, and `ProcessBlockAvailability`/`PeerHasHeader` can use the carried identity and chain work without waiting for publication. The remaining Q9 window is **not** correctly bounded, as F1 shows.
- **D30–D33 and DEC-229:** D31's smoke, certification floor, READY/PENDING distinction, oracle validity rule and binary pin are mechanical; D32's drop guard covers panic; D33's listed nits are fixed. §3.8.1 states DEC-229 as a binding rule for current and future actor waits, covers the hold, startup, reorg, RPC, ChainLock, import and shutdown origins, and classifies `Activated` as a draining wait and `ProcessHeaders` as R/M-complete. F2 qualifies the instruction budget, and the literal DEC-229 wording should be updated for PreStart.

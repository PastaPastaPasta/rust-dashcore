**Verdict: ACCEPT WITH NITS.** Reviewed `node/p2a-net-wire` at `e9ef589a9` against `a5d2a9c59` in a detached worktree. Core reference: Dash Core `v24.0.0-rc.3` (`0364ed626e`). No branch source was edited.

## Findings

1. **Low — the new certify floors measure throughput, not relay-path exercise.** `node-fuzz/targets.toml:520,532,544` sets plausible floors at about half the measured 3600 CPU-second execution count, but `node-fuzz/fuzzctl.py:1650-1668` can certify a flat corpus after those counts without requiring an address to be sent to another peer or a `getaddr` reply. **Schedule:** repeatedly execute scripts that handshake but send no qualifying fresh address to an enabled second peer, or ask `getaddr` only from outbound peers. Core then skips relay under `src/net_processing.cpp:4460-4463` and skips outbound `getaddr` under `:5389-5397`; a stable run can still cross 53,000/48,000 executions. The deterministic `scripts_reach_core_address_paths` test (`node-l1/tests/p2p_addr.rs:268-299`) separately proves Core actually relays in at least 16 of 64 scripts per target and replies in at least 32 of 64 getaddr scripts, so this does not block un-parking. Treat the floors as throughput evidence, or require a replayed path witness if a certificate is meant to prove relay coverage.

2. **Low — the session module's description still says all sessions install the stand-in.** `node-l1/src/p2p_node.rs:14` says this branch installs `addr_send_timer`, while `node-l1/src/p2p_addr.rs:967,975` and `node-l1/src/p2p.rs:383` now install `NodeAddressRelay` for the address and multi sessions. **Schedule:** handshake an inbound source and an address-relay-enabled destination, deliver a fresh routable `addr`, then send a pass: Core calls `RelayAddress` (`src/net_processing.cpp:4460-4463,2686-2734`) and `MaybeSendAddr` (`:6186-6252`); the node does likewise, rather than running the documented timer-only stand-in. Update the module comment to name the remaining stand-in users (`p2p_single` and relevant tests).

3. **Low — D33 overstates when the virtual clock moves.** `docs/node-program/designs/P2a-net-notes.md:39` says only `run_for` advances the clock. **Schedule:** `DialSim::run` executes a `DialPlan::Sleep` through `SimExec::wait` (`dashd-net/src/sim.rs:272-277`), or a `connman_sched` step 5 directly advances it (`dashd-net/src/sched.rs:222`), without calling `run_for`; the new `close` also advances it. Core's linger is measured on its steady clock (`src/net.cpp:2121-2145`). The accurate D33 point is that the virtual clock did not advance *while `close` waited* on a lingering peer.

## Checks and risk assessment

- **Wiring and Core parity:** `Session::addr_relay` is built over the node leg's own chain (`node-l1/src/p2p_node.rs:832-845`). The existing `NodeAddressRelay` matches Core's one-or-two-peer SipHash fan-out (`dashd-net/src/relay.rs:157-217`; Core `net_processing.cpp:2686-2734`), `MaybeSendAddr` timer/queue order (`relay.rs:261-325`; Core `:6186-6252`), and network/bind-keyed 21–27 h getaddr cache (`relay.rs:74-101`; Core `net.cpp:4265-4306`). The intake token bucket is in `dash-p2p/src/addr.rs:193-259` and matches Core `net_processing.cpp:4416-4469`. The one-line multi-session switch introduces no address command into the handshake or headers vocabularies.
- **D30 domain:** all three un-parked targets construct BIP155 entries through `Entry::encode_v2` (`node-l1/src/p2p_addr.rs:278-303,497-554`); the byte stream can mutate the address template but cannot bypass that encoder. Its ID-2 `fc` to `fd` rewrite is harness-local. Both prefixes remain RFC 4193 and unroutable to Core (`netaddress.cpp:371-374`); the pinned base-sdk misreads only ID-2 `fc` as CJDNS. V1 IPv6 and BIP155 ID-6 CJDNS can still contain `fc`, correctly. `diff_p2p_multi_relay` accepts raw payloads, remains parked, and its ignored regression still diverges as documented.
- **D33 schedule:** a far-end close can race the socket writer. If send reports a hard error before the reader records EOF, the peer is marked without `other_side_disconnected`; the sweep sets `steady + 100 ms` (`dash-p2p/src/netcore.rs:1257-1286`). Core takes the same 100 ms path after a locally initiated disconnect (`net.cpp:2121-2145`). Advancing to that deadline lets this legitimate schedule complete; after a direct EOF, the extra 100 ms is simply a valid idle interval before the next simulated dial step. `connman_sched` checks connection invariants at the next step, so this creates no state Core could not reach. Draining the peer's send queue first is optional, but would remove one valid send-error ordering from the simulation. The harness copies `LINGER`, but its `until <= end` assertion fails loudly if production extends the linger.
- **Coverage limit:** these sessions stay in IBD, so self-announcement is not compared. D29 records that gap. No production address-relay code changed in this branch; `dashd-net/src/sim.rs` is the only dashd-net edit.

# DW DP5-01 independent security review (Sol, round 1)

Reviewed detached `a08c2ce3` against `5b90e25b`, with the DP5-01 D1–D25 design, m4 v29 contract, ROADMAP DP5-01, and DASHPAY §2.9/§3.8. The unrelated DP3-03b merge was not reassessed. Only planted, fake secrets were used.

## Findings

1. **High — successful vault creation can leave invitation text in plaintext indefinitely.** `rust/crates/dw-vault/src/vault/links.rs:706-715` swallows a reseal error, and `rust/crates/dw-vault/src/vault.rs:823-828` returns successful creation anyway. If `links/<id>.tmp` is a directory, `write_replacing` cannot remove it; the existing test at `rust/crates/dw-vault/src/vault/links_tests.rs:531-550` confirms `create(Some(...))` succeeds while the entry still contains `cPlantedSecretKey`. A crash after the vault file is committed and before reseal has the same exposure until another key-bearing stash operation completes. If `stash.pub` is absent and the vault is later locked, `links.rs:855-864` also writes *new* bearer links as plaintext. The 0600/0700 modes limit other-user access, but this violates the stated post-creation sealing boundary and extends recoverable plaintext lifetime beyond onboarding. Make the post-key reseal outcome visible to creation/recovery/unlock and fail closed for new links when a vault exists but no usable stash public key is available; provide a reliable retry state for pre-vault entries. A crash before any seal can complete remains an explicit recovery limitation.

2. **Medium — an oversized entry can exhaust process memory before its size limit helps.** `rust/crates/dw-vault/src/vault/links.rs:460-467` rejects an entry file over 16 KiB, but `links.rs:600-605` then calls `scrub`, which allocates `vec![0; meta.len() as usize]` at `links.rs:384-396`. The temporary-file cleanup (`links.rs:592-595`) and destroy (`links.rs:736-745`) use the same unbounded scrub. A local actor able to write the stash directory can make a sparse `<32-hex>.dwl` or `.tmp` of many GiB; the next `stashed_links`/stash operation can abort on allocation rather than deleting it unread as D7 promises. Scrub in fixed-size chunks and bound or unlink malformed oversized files without allocating their length.

3. **Medium — multiline link text defeats the new stderr redactor.** `rust/crates/dw-uri/src/redact.rs:155-175` cuts only the line containing a recognized scheme/marker. `rust/crates/dw-app/src/launch.rs:194` includes an unknown option verbatim in an error, and `rust/crates/dw-app/src/lib.rs:188-192` redacts then prints that error. An argv value such as `--bad=dashpay://invite?pk=FakeKeyFirst\nFakeKeySuffix` prints `unknown option <link>\nFakeKeySuffix` to stderr. I compiled the exact `redact.rs` module into an isolated scratch reproducer and observed that output. D12's control-character refusal prevents such a string from being **stashed**, but it does not protect logging before or outside the stash. Redact the whole untrusted value before formatting errors, or make a recognized link consume the remainder of the log event, including subsequent lines; add a multiline regression case to `link_redaction`.

## Threat-model observations and remaining limits

- The stash key derivation is domain separated (`links.rs:179-202`); a fresh ephemeral ECDH key and random XChaCha20 nonce are used for each seal (`links.rs:324-344`, `crypto.rs:49-65`). AAD binds the filename id, kind, times, network, vault id and key identifiers (`links.rs:288-300`). Copying ciphertext under another filename or editing those fields fails authentication. **An actor with write access to the 0700 stash directory can still replay an intact file under its original id after it was taken, and can forge a new sealed entry using public `stash.pub` or inject a well-formed `plain` entry** (`links.rs:212-280`, `359-381`, `855-864`); ECIES gives confidentiality, not sender authentication or anti-replay. This is outside the stated local-disk-writer threat model (D19), but the limitation should be explicit when describing tamper resistance. Replaying a payment can present the same offer again; it never sends automatically.
- Before any vault exists, a JSON `plain` field holds the **complete trimmed link**, including invitation `pk`, in a 0600 file under a 0700 directory (`links.rs:224-238`, `438-445`, `547-550`, `860-864`). Umask 002 cannot widen those explicit modes. Expiry is lazy, on a later read (`links.rs:570-614`); an idle pre-vault profile can retain the plaintext past its nominal TTL. A failed plaintext write or rename leaves a partially written 0600 `.tmp` until a later `load_entries` sweep (`links.rs:436-450`, `592-595`), even if the stash call reported failure. Zero overwrite before unlink is best effort on copy-on-write/journaled storage (`links.rs:384-396`, `448-455`). A crash between rename and scrubbing the old open inode can leave historical plaintext recoverable at the filesystem layer.
- `stash_invitation` uses `normalize_invitation` alone (`rust/crates/dw-engine/src/platform/invitations.rs:227-236`), and the OS intake does not send invitation text in its `LinkRoute::Invitation` IPC variant (`rust/crates/dw-app/src/shell/links.rs:228-232`, `362-370`). The separate `stash_invitation` command accepts a link pasted by the renderer (`rust/crates/dw-app/src/api/identity.rs:445-449`); that user-input path necessarily holds the text before calling Rust. Normal OneLink parsing still creates percent-decoded `String`s in `rust/crates/dw-uri/src/deeplink.rs:108-115,493-500` without zeroizing them, as D24 concedes. Separately, the generic app intake and `stash_link` still invoke the payment classifier (`shell/links.rs:403-425`; `invitations.rs:124-139`); `rust/crates/dw-uri/src/ext.rs:140-155` copies even unknown query values, then drops them unzeroized. For example `dash:?invite=FakeKey` leaves a parser copy in freed heap. This is a crash-dump/memory-residue limit, not an observed log or IPC leak; continue moving parser temporaries to `Zeroizing` when hardening bearer input.
- The 16-entry cap is global (`links.rs:831-844`). A user opening 17 distinct invitation links can evict an older invitation, as the existing test confirms (`links_tests.rs:275-315`). Each intake requires a separate opening, and no payment is sent automatically, so I do not treat F3's per-kind cap as a blocker here. A second wallet on the same network does not restash payment/contact links because D2 checks for *any* wallet (`shell/links.rs:371-385`); this is the disclosed F1 scope gap. On Windows, a failed replace returns an error with the original plaintext entry still present; Windows ACL and rename behavior were not run on Linux.
- I found no further writer-order race: create, unlock and recovery call reseal before releasing their writer (`vault.rs:823-827`, `896-912`, `2619-2622`); destroy holds writer and stash mutex through removal and key deletion (`vault.rs:2632-2669`). Take checks kind before decryption and deletes before returning text (`links.rs:903-944`); the engine returns an invitation id without opening it (`invitations.rs:194-210`). Forget deletes while locked (`links.rs:951-968`). The tests cover these normal paths, though the error paths above weaken the overall guarantee.

## Validation

- `cargo test -p dw-vault` — attempted: first build aborted when the shared `sccache` server reset during `blst`; the direct-compiler retry reached a pre-existing `platform-wallet`/`dpp` feature-unification error (`dpp::ed25519_dalek` compiled out). Building `dw-vault` together with `dw-engine` supplied the workspace feature; I ran that exact compiled `dw_vault` unit binary directly: **98 passed, 1 ignored**. The combined broad `dw-engine --lib` run made progress through the unrelated lease suite but was interrupted after a prolonged test under load; it has no final pass claim.
- `cargo test -p dw-engine --test m4_dashpay_contract` — **9 passed**; its DP5-01 cases cover rejected stash inputs and contract surface. The app IPC test below covers the successful engine stash path; there is no dedicated `dw-engine` stash test module.
- `cargo test -p dw-app --test link_redaction` — **1 passed**. `cargo test -p dw-app --lib ipc_tests::links_opened_before_a_wallet_survive_onboarding` — **1 passed** (167 filtered out; the test took 66 seconds under load).
- `cargo test -p dw-uri --test link_fuzz` — **4 passed** (seed corpus and bounded generated cases).
- Isolated `rustc` reproducer importing the exact `dw-uri/src/redact.rs` — passed; printed the fake secret suffix after a newline.

## Verdict

**CHANGES REQUIRED.** The successful-creation plaintext state, unbounded scrub allocation, and stderr leak need fixes or an explicit change to the security contract before this can ship.

## New findings

1. **Major (Medium impact) — `rust/crates/dw-engine/src/platform/journal.rs:670-673`: a failed first count can erase a valid same-epoch recount.** `load_unread` inserts an empty placeholder and queues the first count. While that job waits, an E0-06 journal write calls `unread_moved_since` and replaces the placeholder with a real count, say 1, at the same epoch (`journal.rs:604-627,845-850`). If the queued count then fails, `count_later` checks only the epoch and removes the entire wallet count map. `unread_count` next answers 0 and queues another count, despite a successful journal count and its event signal. Preserve a distinct pending-count token or generation and clear the placeholder on failure only if it is still the job's own; epoch equality alone does not establish that. The added scratch proof test, `review_proof_failed_first_count_keeps_same_epoch_recount`, sets this exact order and **failed as expected**: `left: None`, `right: Some(1)` (1 test, 816 filtered out).

2. **Minor (Low impact) — `rust/crates/dw-engine/src/platform/notifications.rs:135-139`: removal can finish before `load_unread` schedules.** A concurrent `remove_wallet` can run after `require_wallet` returns but before the synchronous `unread_count` call reaches `tap.load_unread`. Removal deletes rows and calls `tap.forget`; the delayed call then sees `tap.unread == None`, installs a placeholder at the *new* epoch, and its job can repopulate the cache after `WalletRemoved`. Capture the tap epoch before the wallet check and require it to be unchanged when `load_unread` installs its placeholder; or serialize the check and schedule with removal. The scratch pause proof `review_proof_unread_count_check_then_removal_recreates_cache` failed as expected after removal returned: `left: Some(0)`, `right: None` (1 test, 817 filtered out).

3. **Minor (Low impact) — `rust/crates/dw-engine/src/platform/journal_tests.rs:1535-1552`: the held-count tests do not release on assertion failure.** `a_held_count` pauses a runtime blocking worker, then runs `assert_eq!` and the `between` closure before `pause.release.notify_one()`. A panic there unwinds into a runtime with its worker still waiting. Add `ReleaseOnDrop` (as the new notification race tests do in `notifications_tests.rs:381-388`) and bound both wait loops. The notification pause tests do release on failure.

## Fence, lifecycle, contract, and test checks

- `on_wallet` captures the object, not just the wallet id. Removal can interleave before the fence, but `WriteFences::enter` detects the changed object after acquiring it; once the mark holds the fence, removal waits. The order is gate → optional lifecycle/removal barrier → write fence → manager lookup or appdb write (`gate.rs:27-40`, `wallets.rs:217-265`). The mark takes no lifecycle lock, revoke barrier, discovery hold, or identity write lock. Removal takes no appdb connection lock before waiting on this fence, so this path has no lock cycle. `ignore` drops its identity write lock when `set_ignored` returns (`requests.rs:635-657`), then uses the captured wallet for the fenced mark (`contacts.rs:292-315`); a stale mark is logged and does not affect a reimport.
- `.dwbackup` restores its rows and awaits `tap.unread_moved` while holding the restore lifecycle lock (`backup.rs:573-610,669-677`), excluding a simultaneous removal. Rollback removes the newly created wallet and rows and calls `tap.forget` (`backup.rs:684-723`), invalidating a queued count. The detached bring-up count also captures its epoch when scheduled (`journal.rs:980-988`); a failure there does not clear an existing cache. The new finding concerns `load_unread`'s failure cleanup.
- M4 Contract-Version 17 §2.6 and item 43 now describe `wallet_not_found` for a stale `mark_read` (`m4-dashpay-engine.md:479,2249-2261`). The code already exists in `PlatformError`'s listed error codes. `dwcli` propagates the error (`dwcli/src/dashpay.rs:1370-1372`); `dw-app`/generated TypeScript return a rejected command, with no caller in `apps/desktop/src` requiring success; `dw-ffi` withholds the engine-only event surface (`dw-ffi/src/api/engine.rs:263`). I found no existing caller broken by this outcome.
- Mutation proof: commenting out the migration index made the plan test fail with `sqlite_autoindex_dp_events_1` and `USE TEMP B-TREE FOR ORDER BY` (1 test, 97 filtered out). The new index-plan test therefore detects finding 2. With production behavior reversed in the scratch worktree while preserving test hooks, the admitted-events test failed with `Err(NetworkNotOpen)` (finding 3), the queued-count removal test failed with `Some(1)` instead of `None` (finding 4), and the stale admitted-mark test returned `Ok(())` instead of `WalletNotFound` when the object comparison was bypassed (finding 1). The first mark test also detects removal of the fence: with its pause hook preserved, it failed promptly at `the job holds no fence` (and its drop guard released the worker). These are behavior-sensitive assertions. The same-epoch failed-count order is untested in the reviewed branch.

## E0-06 `record_events` gap (outside this fix range)

**Real — Medium impact, outside DP2-05's fix range.** `WalletStore::store` commits the library changeset, then calls `tap.record` (`store.rs:95-115`). `ChangesetTap::journal` can be delayed before `appdb.record_events` (`journal.rs:837-845`) without holding the per-wallet write fence. Removal can delete rows and set the `removed_wallets` tombstone, and a same-id import can clear that tombstone through `readmit_wallet` (`dw-appdb/src/lib.rs:490-518`). The old callback can then insert journal rows into the new wallet; because it captures the epoch at its late journal call, the current epoch does not suppress its resulting signal/news (`journal.rs:844-858`). Fence the journal writer to the original wallet generation or provide an equivalent generation check at the SQL mutation in E0-06. This does not reopen R1 finding 1: the `mark_read` mutation in this diff is fenced.

# O2a-CJ1 CoinJoin oracle and `diff_coinjoin` — Sol review, round 1

**Verdict: ACCEPT WITH NITS.** I found no Core/Rust verdict mismatch in the reviewed rules. The one finding is a differential seed coverage gap; a pre-existing crate unit test covers the same boundary.

## Finding

1. **Low — the differential's DSTX structure rows omit the pool-size boundary.** `node-l1/tests/l1_coinjoin.rs:237-253` uses only `(inputs, outputs)` of `(3,3)`, `(10,1)`, `(1,10)`, `(2,3)`, and `(19,1)`; `node-l1/src/coinjoin.rs:1144-1171` seeds only the first three. Core rc.3 `src/coinjoin/coinjoin.cpp:100-154`, especially `:127-142`, accepts a balanced 180-input/180-output DSTX before V24 and rejects 181/181; after V24 it permits at most 200 per side. **Concrete input:** a DSTX with a non-null ProRegTx hash, 180 inputs and 180 standard-denomination P2PKH outputs, on mainnet with a tip at height 4030 and V24 `DEFINED` (mainnet V24 is `NEVER_ACTIVE` at this pin). Changing Rust's `is_balanced_within` in `dash-coinjoin/src/dstx.rs:328-330` from `<= max_pool_in_outs()` to `< max_pool_in_outs()` made Rust reject that input, yet all nine `l1_coinjoin` tests still passed. The existing `dash-coinjoin/tests/core_ports.rs:417-428` boundary test caught the mutant. Add 180/181 and 200/201 structure rows to the differential seeds for each network and relevant V24 state. **Schedule note:** this is a narrow O2a-CJ1 seed improvement before relying on its fuzz corpus as boundary evidence; the existing unit test prevents this particular regression from silently shipping, so it does not block CJ1.

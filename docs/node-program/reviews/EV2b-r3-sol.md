# EV2b round 3 — checked DML block differential

Reviewed rust-dashcore `node/ev2b-dml-block` at `118ac6482` against the pinned Core v24.0.0-rc.3 oracle shim `f822bbcd74` (ABI 21). This is the narrow D53–D55 review. The real-chain windows from round 1 remain outside this review.

## Findings

1. **Major — Round 2's check-layer parity gate remains open; the fuzz entry misses a planted wrong Rust reason.** At `node-l1/src/dml_block.rs:285-305`, every Rust build/process rejection after a Core `DmlStage::Check` rejection becomes `BothRejectStageDiffers`, without matching the Core-named transaction, class, or reason. `compare_block` returns only that outcome (`:459-467`). I disabled the unknown-provider-version guard in `dash-dml/src/build/mod.rs:579-582`. For a raw generated input Core still reported `bad-protx-version`, while Rust's recorded reason changed from its unknown-version refusal to `bad-protx-payload`; `compare_block` returned `BothRejectStageDiffers` before and after. The dedicated L0 test and `run_inputs`' D2 assertion failed, so these are useful regression guards, but the fuzz target itself did not catch this mutation. A different Rust rejection in the same block can likewise mask acceptance of the transaction Core named; the baseline generated corpus already has cross-reason pairs such as `bad-protx-inputs-hash | bad-qc-payload`. D53 explicitly calls this *post-check DML parity* and defers exact EV1/CH7a check parity. That is an honest scope statement, but it does not close round 2 Major 1 or meet this round's target mutation gate. **Fix:** retain the check-layer gate as open until Rust's EV1 checks run on the same block and compare the rejecting transaction, stage, class, and reason. Treat `BothRejectStageDiffers` as coverage only in the meantime; do not count it as evidence that the fuzz entry catches missing or wrong checks.

2. **Minor — The generated raw-mode tally does not describe the target for 314 of its 600 inputs.** `node-l1/tests/l1_dml_block.rs:285-299,330-336` always calls `generate` and the one-block comparator, but `node-l1/src/dml_block.rs:459-467` routes any input with byte 1's `FLAG_CHECKED` bit to the sequence generator. Reproducing the fixed splitmix stream showed that **314/600** generated inputs have that bit. Of the two raw-generator `bad-protx-version` inputs used by the D2 assertion, one has flag 36; the real target returns `BothAccept` on that checked sequence, whereas the test counts a raw `BothRejectStageDiffers`. This does not invalidate the separate checked-sequence test, but it overstates raw fuzz-entry coverage and makes its mutation evidence ambiguous. **Fix:** clear `FLAG_CHECKED` for the raw generated corpus, then run `compare_block` on every such input; keep the checked corpus and its per-block tally separate.

## Other questions in the brief

- **Round 2 Major 2 closes for post-check paths.** The checked corpus reaches 412 accepted, 439 build-rejected, and 34 process-rejected blocks, including 0–50 transaction blocks and five build reasons. Changing `BAD_PROTX_DUP_NETINFO_ENTRY` to `bad-protx-dup-key` made `checked_sequences_match` fail at round 2 with `Divergence(reason)`; the same input made the actual `compare_block` entry return that divergence. Stage and reason comparison after Core's check loop is effective for this same-block conflict.
- **The carried-list residual closes.** `replay_carried` builds from its own `MnList` and reference twin; `xcheck` invokes `MnList::check_invariants`, whose I-U recomputes the unique map from the masternodes (`dash-dml/src/testkit/replay.rs:191-220`, `dash-dml/src/list.rs:791-800`). Thus a map-only error in an accepted block cannot pass this comparator with I-U enabled. To isolate the carry, I retained a changed address in both maps and disabled I-U: on the permanent two-block regression input, block 1 accepted, block 2 gave `Divergence(layer)` with the carried list, and block 2 gave `BothAccept` when our list was decoded afresh from Core's bytes. This verifies a block N+1 duplicate-key verdict caused by block N's map state.
- **D53 and D55 deferrals:** D53's unrelated-rejection masking can hide a missing or wrong check-layer verdict, as finding 1 shows. Its members-missing refusal can turn a Core check rejection into `OutOfDomain`, but Core never reaches DML build on that input; checked mode supplies members. D55 R2's first-tip rules can lose post-check coverage at an activation crossing, and R3's last-block outcome loses per-block coverage counts. Neither R2 nor R3 suppresses an encountered divergence: `compare_sequence` propagates its first error. They are acceptable only as coverage limits, not evidence of exact check-layer parity.
- **Out-of-domain accounting:** Beyond the oracle's own `Argument`/`Context` refusals, the comparator intentionally permits only absent supplied lists, pre-DIP3/no-list cases, the `(reason, rejected transaction type)` entries in `MISSING_CHECKS`, and the `MEMBERS_MISSING` prefix on a Core check rejection (`node-l1/src/dml_block.rs:217-269,285-305,343-354,388-390`). Short inputs and unsupported pins are target-format exclusions. I found no additional opaque escape path on a Core post-check build/process verdict. `run_inputs` asserts its generated raw inputs' out-of-domain outcomes; that assertion should not be read as a statement about every possible target input.

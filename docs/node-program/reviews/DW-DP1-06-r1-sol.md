# DW-DP1-06 round 1 review (Sol)

Range: `1bb0225a..5aee23d2` on `dw/dp1-06-credits`. Read-only review of the branch; scratch experiments are separate.

## Findings

### Major — a consumption-unknown lock disappears from the pending and double-funding gates

**`rust/crates/dw-engine/src/platform/topup.rs:232-252`** (`untaken`, `open_locks`), with `:455` (`TakenTopUps::record`). `RecoveredFromChain` is expressly *not* proof of Platform consumption: the pinned platform-wallet library uses it when a chain scan finds an unconsumed finalized lock and when it durably records an unauthenticated “already consumed” response. `untaken` excludes this status. Thus a crash-stranded lock that advances from `Broadcast` to `RecoveredFromChain`, or a false code-24 response that induces that state, vanishes from `pending_top_ups()` and from `check()`'s `credits.top_up_pending` refusal. A user can authorize a second top-up while the first lock is still usable, paying two asset locks. The process-local taken set also reports `AlreadyApplied` and suppresses Finish for the rest of that process; after restart the set clears, but `RecoveredFromChain` stays excluded, so the normal pending UI does not recover the first lock. Explicit Finish can still find it if Platform later answers honestly, but the claimed no-loss/no-double-fund path fails. Fix: retain a durable consumption-unknown state for a lock that this top-up funded and keep it visible/blocking until authenticated consumption or an explicit user resolution; historical recovered locks need a separate settled classification so they do not block forever. Do not turn an unauthenticated code-24 response into a durable `AlreadyApplied` conclusion; add a false-response/restart test.

### Major — document prices are estimates, not upper bounds

**`rust/crates/dw-engine/src/platform/credit_costs.rs:173-189`**. `CostAssumptions::new` uses 1,000 existing documents and zero user fee increase. Drive's `write_processing` grows with the depth of the document and index trees; once a type's tree exceeds the assumed size, an otherwise identical write can cost more than the published table. The table is used for “about N requests” and low/empty thresholds, and m4 §5 calls these prices upper bounds. The PV13 path also substitutes PV14 insert methods; DashPay's simple indexes make the layout substitution plausible, but the current tests do not compare a PV13 server charge or prove no underpricing. Fix: publish these as estimates with a separate conservative upper bound, or price with a documented maximum for state-dependent processing and verify it against PV13 Drive charges. Keep the existing larger write-grant caps until such a bound is proved.

### Major — the displayed credit level can stay stale after spending

**`rust/crates/dw-engine/src/platform/recovery.rs:500-503`** and **`rust/crates/dw-engine/src/platform/identity.rs:115-121`**. `credit_level` is computed from the managed identity's cached balance, but this branch schedules no balance refresh after contact/name/private-details writes or in the DashPay pass. Those writes fetch live balance for their own spending check, without persisting it to the identity summary. After repeated requests, a profile can continue to show an old high balance and `Ok` even when Platform would classify it `Low` or `Empty`; the warning can remain absent across restarts until the host explicitly calls `refresh_balance`. The live pre-spend check prevents an over-budget write, but does not make the displayed balance current. Fix: perform the plan's best-effort refresh after each credit-spending write once its write lock is released, and refresh old balances in the pass; expose an as-of/stale marker if refresh fails.

### Minor — an undersized top-up grant is redeemed before its cap refusal

**`rust/crates/dw-engine/src/platform/topup.rs:366-381`**. `authority()` consumes a vault grant before `available(Funding)` and `plan.total_duffs > remaining` refuse it. A grant capped at the top-up amount but missing the fee receives `platform.grant_exceeded` and funds nothing, yet the same grant cannot be retried. `a_grant_below_the_quote_funds_nothing` checks only the funding count. A scratch regression first refuses a 5,000,000-duff grant for a 5,000,000-duff top-up, then retries a smaller valid top-up with it; the second call fails `GrantInvalid`. Fix: inspect the vault grant's cap without redeeming it (as registration already does), or make cap validation and redemption atomic; assert the grant remains usable after this refusal.

### Minor — restart tests preserve the fake library's state in memory

**`rust/crates/dw-engine/src/platform/topup_tests.rs:249-299`**. The four scripted kills copy/reopen the dispatch journal, but preserve the `World` `Arc<Mutex<_>>`, including its tracked locks and Platform-consumed set. They exercise journal states, not whether a `Built`/broadcast lock and its identity index actually survive the wallet.sqlite restart. There is no kill before the funding marker, and no test of an unauthenticated false code-24 response followed by restart. Fix: add a storage-backed restart test around the real asset-lock persister (including `RecoveredFromChain`), plus a false-response test; keep the fake tests for dispatch-state coverage.

## Checks and observations

- An unreachable Platform leaves a proved lock tracked as `NotApplied` and eligible for explicit Resume or Finish. An unauthenticated, outpoint-matched code-24 answer is different: the pinned library durably marks a ChainLocked lock `RecoveredFromChain` (consumption unknown), and this branch also adds it to the process-life taken set.
- The funding call uses a Mode B `topup/<index>-<k>/funding` step. The marker and signed-lock provenance are used by `matches_step`; a `MaybeSent` or `WillBeSent` step refuses another funding call. The step's signed-lock records survive journal reload and avoid attributing an earlier top-up's row to a later step. The initial grant is `max_duffs = duffs + fee_bound_worst`, `max_credits = 0`. Apply uses the exact existing outpoint, so Platform's one-consumption rule prevents crediting one lock twice.
- The four scripted restart points are marker-without-signature (`NotSent`, next step), signed/tracked `Built` (`WillBeSent`, pending), proved before apply (`Sent`, Finish applies), and Platform-consumed before local mark (`already consumed`, balance added once). The fake covers these journal transitions; the caveats above limit the persistence claim. A vault lock before funding prevents the call; after funding the lock remains tracked for a fresh-grant resume. Finish takes the identity write lock and re-reads each lock. A journal not yet loaded maps the next-step lookup to `broadcast_unknown` (L5); this fails closed but needs a retry after load.
- `refresh_identity_balance` uses `IdentityBalance::fetch_with_metadata` through the session SDK and the layered trust provider. The library's height watermark rejects older/equal-height snapshots, preserving the newer balance. m4 §5 explicitly excludes the balance from `IdentitySummary.unverified`'s content provenance; the flag covers keys, shown profile and names. Thus a fallback-served balance can coexist with `unverified=false`. This is a documented limit, contrary to the plan's broader wording.
- `top_up_fee` is dpp's minimum, while Platform meters the actual fee; the quote's `credits` is an upper bound on credits received, as the implementation now states. Android's `CreditBalanceInfo` uses empty below one maximum operation and low at or below ten; the new thresholds match that ratio. The table's maximum of contact request/profile update intentionally differs from Android's fixed 100,000,000 credits.
- m4 Contract-Version 17, dw-app commands and DTOs, generated TS, CLI commands and error-code mapping agree on the implemented surface. The implementation does not include the plan's `CostTable.fee_version`/`source` or `TopUpOutcome.top_up`, and m4 has been re-blessed to the smaller implemented shape. DP2-05 may require a version-18 re-blessing on integration.
- `cargo fmt --all -- --check`: passed. `git diff --check 1bb0225a..5aee23d2`: reports trailing spaces in generated TS files only.
- `nice -n 10 CARGO_BUILD_JOBS=8 cargo test -p dw-engine -p dw-app` with the private target: `dw-app` 116/116 passed; `dw-engine` 813 passed, 8 ignored, one 1-second hand-off deadline test failed under load. The exact failed test passed alone (1/1). The separately invoked m4 contract binary passed 9/9.
- A scratch-only regression that changes a funded lock to `RecoveredFromChain` without consuming it fails: `pending_top_ups()` returns 0 instead of 1. A Drive estimator check at PV13 layout and fees showed the **max-field** contact-request table price rising from 99,314,660 credits at its 1,000-document assumption to 103,642,860 at one million; this directly exceeds the published table. Three scratch-only mutants each made an existing test fail: reverting signed-lock attribution made the restarted step read `Sent` instead of `MaybeSent`; suppressing pending locks made the IS-timeout test see zero pending; redeeming the grant before refusal checks made the unknown-funding retry return `GrantInvalid` rather than `broadcast_unknown`. Each corresponding test passed with its mutant disabled. The extra scratch cap-refusal regression failed with `GrantInvalid` as described above. T2 fixture and T3 live top-up were not run; no testnet writes were made.

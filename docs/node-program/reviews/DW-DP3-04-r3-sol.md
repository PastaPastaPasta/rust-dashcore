# DP3-04 security review — Sol round 3

Reviewed detached `43516c6a` of `dw/dp3-04-trust-gate` against `5650d352`, the D25–D27 design, and the pinned Platform/SQLite dependencies. I did not edit, commit, or push the branch under review.

**Verdict: CHANGES REQUIRED.** The round-2 `Enforce` gate gap is closed in the engine, but the pinned SQLite writer prevents a rotated contact with a *new xpub* from rebuilding its paying account. The next sweep removes the old in-memory account but cannot install the new one, so legitimate payments remain impossible; each restart reloads the old account and reopens D26's degraded stale-address window until another sweep.

## Finding

1. **High — new-xpub contact rotation cannot replace its persisted address pool.** The engine's `money_gate.rs:352-356,403-415` deliberately permits an unstamped account in `Probe`/`Off` and relies on a sync pass to rebuild and stamp it. The engine opens the pinned SQLite persister (`session.rs:335-339`). In the pinned `platform-wallet`, `contact_requests.rs:1617-1629` removes the old account and pool **in memory** and queues the new registration; `contacts.rs:529-555` persists an `account_registrations` upsert plus a new pool snapshot before inserting that account in memory. The pinned `rs-platform-wallet-storage` writes those in one transaction (`sqlite/persister.rs:2163-2185`), but `sqlite/schema/core_pool.rs:71-78,157-176` rejects a row for the same account, pool and address index when its typed public key changes. Every DashPay external account generates typed ECDSA pool entries from its xpub at registration (`key-wallet/src/managed_account/managed_account_type.rs:745-756`; `address_pool.rs:408-413,559-564`), and neither the account upsert nor the pool upsert deletes the prior pool rows (`sqlite/schema/accounts.rs:215-222`; `sqlite/schema/core_pool.rs:55-69`). **Failure scenario:** Bob's old account and pool are stored, then Bob rotates to a different xpub. The sweep removes the old account in memory; the queued `RegisterExternal` reaches the SQLite store, where index 0's new public key conflicts with index 0's old public key. The transaction rolls back, the registration stays queued (`platform-wallet/contact_requests.rs:2548-2555,2618-2622`), and every retry hits the same conflict. `Enforce` keeps refusing; `Probe`/`Off` cannot reserve once the sweep has removed the old in-memory account. After every relaunch SQLite restores the old account and `external_account_reference: None` (`sqlite/schema/contacts.rs:403-420`), briefly allowing `Probe`/`Off` to sign to Bob's old address again before the next sweep. No successful online pass can repair the contact. **Fix:** make the pinned storage layer replace/version the pool rows atomically with a changed DashPay external xpub, preserving old used-address history separately; then add a SQLite-backed new-xpub rotation/relaunch test that proves the new pool and matching stamp can be reached. The in-memory `send/contact_tests.rs:276-303,1506-1518` rebuild fixture bypasses this persistence path.

## Narrow path checks

- **Round-2 `Enforce` finding:** closed at the engine layer. `money_gate.rs:471-481` checks payability on the first gate read, independent of the fallback latch; an absent or mismatched stamp refuses under `Enforce` (`:337-356,403-415`). A queued `RegisterExternal` may pass the first read, but the post-reservation read is strict (`:556-577`), so a crash before the sweep, a restart before the first pass, or a drain racing a rotation cannot sign from an unstamped/old account under `Enforce`. A successful same-xpub rebuild can retain the reserved address; a successful new-xpub rebuild drops a displaced address. The finding above prevents the latter rebuild on the SQLite backend.
- **D26 in `Probe`/`Off`:** the documented missing-stamp exposure is real: SQLite always restores `None`; it does not persist a `Some(old)` stamp. A corrupt established contact row is rejected or skipped rather than silently assigned a matching stamp (`sqlite/schema/contacts.rs:283-333,391-425`). A live `Some(old)` marker refuses in every mode (`money_gate.rs:352-356`). The stale-address window still ends at an in-process sweep, but the SQLite conflict reopens it after each restart and prevents the promised recovery payment to the new account.
- **Address binding:** the re-check reads the current stamp/request and managed pool under the same wallet-manager read guard (`money_gate.rs:403-415,471-481`); `Probe`/`Off` also perform this destination-only read (`:567-572`). A reserved address absent from the current pool refuses and is dropped (`send/contact.rs:241-246`). The pinned storage rehydrates pools by deriving against the current account xpub, not by admitting an old stored script verbatim (`sqlite/rehydrate.rs:535-617`), so I found no second path for an old address to pass after a *successful* new-xpub rebuild.
- **Refusal kicks:** `NotPayable` calls `kick_dashpay_sync` (`money_gate.rs:524-540,573-575`). The library's `sync_now` admits one pass at a time (`platform-wallet/manager/dashpay_sync.rs:337-355`), so concurrent kicks do not queue full sync passes. Every refusal still spawns a short task and asks for a balance pass (`dw-engine/platform/runtime.rs:723-736`); repeated local prepares can cause task churn. More importantly, no number of kicks resolves the SQLite conflict above. Test pause/refetch hooks and `Point` are behind `#[cfg(test)]` (`money_gate.rs:69-117`, `send/contact.rs:224-237`). The shared `managed` lookup preserves the same wallet/owner selection for stamp and provenance reads (`money_gate.rs:431-467`).

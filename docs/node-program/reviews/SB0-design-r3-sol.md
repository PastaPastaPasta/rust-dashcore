## Major findings

### M1 — KGW's exit guard exceeds the proposed context

**Severity:** major. **Refs:** §4.1.1, `docs/node-program/designs/SB0-shared-base.md:445`, `:450`, `:455`; SB4 `:1278`. **Related:** r2 F2.

`PastBlocksMax = 4,032` bounds the entries contributing to KGW's average. It does not bound every ancestry API read in the unchanged function. In `dash-consensus/src/pow/kgw.rs:64–68`, iteration 4,032 advances `reading` to its predecessor. The next iteration calls **`chain.header(reading)` before checking `i > past_blocks_max`** (`:34–37`). Both Core pins have the corresponding predecessor advance and height read in the loop condition (`pow.cpp:35–36`, `:64–65`). Complete node ancestry answers this normally.

**Concrete failure:** take a mainnet-shaped chain with parent height **19,999**, uniform 150-second spacing and constant valid-range target bits. The event horizon does not stop the walk before the maximum. Rev2's R=4,032 context contains **15,968…19,999**. The unchanged Rust function then reads **15,967** to exit the loop. The proposed adapter panics in debug or rejects the legitimate header batch with an internal error in release. A resident arena containing the record does not help if `RuleContext` expressly exposes only its R-entry range. The disposable Rust probe reproduced the read with parameters for both pins; a 4,033-entry context returned the same target as complete ancestry. BTC 576 and DGW 25 passed as positive controls.

**Fix:** distinguish the contributing window from the context's full API-read envelope. With the functions unchanged, load **KGW's `PastBlocksMax + 1` entries**, clipped at genesis, including its loop-exit predecessor. Alternatively, change the pure loop to test the mass bound before the additional ancestry read, with a separately verified equivalence change. Keep DEC-105's BTC 576 and KGW 4,032 arithmetic; neither number needs to be reinterpreted as Bitcoin's interval or an extra contributing KGW sample. Add a **maximum-length KGW walk**, with both resident and cold guard reads, to SB4's gate; the current beyond-25-entry case is insufficient.

### M2 — Rebuild preservation breaks the MN locator/state contract and has no recoverable subscriber transition

**Severity:** major. **Refs:** §4.3.1, `docs/node-program/designs/SB0-shared-base.md:586–590`; §6.1 `:872`; §9.5 `:1074–1075`, `:1087`, `:1089–1097`. **CH2:** `CH2-coins-flush.md:1233–1239`, `:1269–1285`, F1/F8/F9/F10/F11 `:1335–1345`.

`dash-mnlist` is explicitly a subscriber with a durable locator. The rebuild clears its `mn_lists`, `mn_quorums` and `mn_snapshots` while keeping **all subscriber locators**. That commits a locator at L with no MN state at L, contradicting the data-plus-own-locator contract in §9.5 and CH2's locator-target state invariant. Merely recovering L's header hash does not recover the discarded list/quorum state.

**Concrete failure:** the MN subscriber and filter subscriber have durable locator **A200**. Re-anchor to C50. The Durable transaction deletes the header/MN records but preserves both locators and filter data. After a crash immediately following that transaction, normal open's rule says an unknown locator rewinds to the anchor (`:1092`), whereas the rebuild rule says it waits (`:1097`). No durable rebuild phase or equivalent restart invariant is specified to distinguish those paths. Even granting the intended wait, same-branch forward sync eventually restores A200 under a new header id, and the stated resumption condition is now met; the MN subscriber still has **no state at A200**. A disk-backed SQLite witness confirms this committed state survives reopen. Transaction atomicity alone does not make it a valid subscriber checkpoint.

A steady-state reorg adds another necessary case: a lagging subscriber's locator can name the losing branch. Clearing every branch record means that forward sync of the winning branch may never restore that hash. The “rewinds as above” fallback then has no specified old-branch ancestry or state-reset procedure. CH2's ordinary rewind needs that path and `stage_disconnected`, rather than just moving a locator. A full client restart can address old feed/snapshot lifetimes, but it must quiesce writers and invalidate the old feeds before deletion; otherwise a late subscriber `WriteSet` can reinstall data/locators whose header dependency was deleted, and retained cold snapshot reads can trip the corruption latch. F1/F8/F10/F11 cannot span this reset as an ordinary tip change.

**Fix:** specify a restartable rebuild state machine, recorded durably or inferred through an equally explicit invariant on every open. Before the deletion, quiesce subscriber/header tasks and the store writer, retire old feeds/snapshots and outstanding writes, and define the new stream's sequence/id lifetime. Preserve each retained subscriber's data together with its locator, wait through the rebuild across crashes, and define an atomic data/state/locator reset for a locator whose branch is not recovered. **The cleared MN state needs either a reset locator and fresh bootstrap, or restoration of its state at the retained locator before resumption.** It cannot follow the generic “keep data and locator” rule while its data is deleted. Keep `next_id` monotone or make an explicit generation boundary; never let a retained reference alias a new header.

Gate SB13/SB15 on crashes before/after the rebuild transaction and during forward sync, including a second restart, an MN locator at the old tip, same-branch recovery, an absent losing-branch locator, pending fanout, and an old queued write. Check F1/F2/F3/F8/F9/F10/F11 at the old/new stream boundary and verify subscriber rows equal their declared locator state. This preserves the controlled-rebuild choice and requires no backfill.

### M3 — Clearing the lock rows can erase already established ChainLock finality

**Severity:** major. **Refs:** §4.1, `docs/node-program/designs/SB0-shared-base.md:396`; §4.2 `:473–483`; §9.5 `:1074`, `:1096`.

The table grouped with MN state includes **`locks`, with the best and pending CL**. The rebuild deletes the MN tables and every header record, including conflict statuses. The listed `meta` fields (`:1067`) contain no surviving finality pin. No exception preserves the applied best ChainLock or its constraint while its `BlockId` is unavailable.

**Concrete failure:** the client has verified a ChainLock at A[h]. A later permitted reorg **above h** restores an older active commitment and triggers re-anchoring for its history. The rebuild clears the applied CL and header/conflict records. During the ensuing forward sync, a peer supplies a higher-work header branch B that agrees with every shipped checkpoint but forks **above the old checkpoint and below h**, so B[h] differs from A[h]. With `cl_floor = None`, the written best-work rule can select it. The client has reversed finality it had already authenticated, simply to obtain more history. The peer needs valid header work, not a forged ChainLock. Hiding the old certificate is enough once the client deletes its copy.

Core's enabled ChainLock check rejects a conflicting hash at or below its known locked block (`v24 chainlock/chainlock.cpp:73–95`; `validation.cpp:4693–4698`). This scenario has **no spork disable/re-enable transition**, the explicit reset case in `chainlock/handler.cpp:209–220`. The finding is about the proposed SPV rebuild's loss of its persisted verified constraint, not a claim about Core restart persistence.

**Fix:** retain the strongest already verified ChainLock constraint outside the disposable MN/header state, addressed by **height/hash and verification provenance**, not the deleted id. The rebuilt chain must pass that pin before it can publish a conflicting suffix or resume subscribers; receiving its header later must not turn the constraint into an optional pending lock that a peer can suppress forever. If “MN tables” was intended to exclude the applied best-CL row, make that exception and enforcement rule explicit. Test a rebuild and interrupted rebuild while CL remains enabled: a higher-work branch crossing the retained lock must never become active. This does not change the anchor/backfill ruling.

### M4 — The old-set lock rule has no boundary protecting valid recent locks

**Severity:** major. **Refs:** §4.3.1, `docs/node-program/designs/SB0-shared-base.md:592–599`, `:617`; §5.2 `:754`, `:758–760`; SB11 `:1285`.

Not letting arbitrary old lock messages trigger header resync is sound: returning unavailable neither substitutes a key nor authorizes another quorum. But “older active set than the one SPV holds” is not a staleness bound. Active sets can change between the production and delivery of a useful lock. Rev2 specifies neither a supported recent-lock horizon nor retention/acquisition of historical authenticated scans within it. Its stale-cycle negative test does not cover that transition.

**Concrete failure:** a CL-type commitment is mined at cycle base **s=2,500,128 plus 20**, height **2,500,148**, replacing the oldest of the four active CL quorums. A valid ChainLock for height **H=2,500,155** selects from **H−8=2,500,147**, the set immediately before the mine. It is delivered when the local header tip reaches **H+1**, whose current selection start is **2,500,148**. The request's scoring winner can be the removed old quorum; the deterministic scoring witness constructs such a set. If the engine holds only its latest authenticated set, the explicit old-set rule reports this **one-block-late, otherwise useful lock** unavailable. It triggers neither re-anchor nor any specified historical-set request/retry. Repeated normal commitment transitions, or startup just after one, can therefore lose CL liveness even with all required headers already present and correct keys obtainable.

Core selects a ChainLock using its **own signed height**, not the latest held set (`v24 chainlock/clsig.cpp:253–269`; `llmq/quorumsman.cpp:711–721`, `:849–854`). The chosen height matters for ISLocks too: both pins derive a prior-cycle `nSignHeight = cycleHeight + interval − 1` when appropriate (`v23 instantsend/net_instantsend.cpp:106–122`; v24 `:136–152`). An ISLock delivered just across a cycle boundary need not be useless or hostile.

**Fix:** define the finite recent-lock/cycle history the client supports, chosen from local chain progress rather than a peer-provided arbitrary height. Retain or acquire the **authenticated canonical set for that signed height** and its required histories within that horizon, then use the already correct select-once/status rule. If supporting that local horizon needs an earlier anchor, include it in proactive coverage as headers advance, rather than granting stale messages a resync trigger. Missing inputs within the supported horizon need a bounded acquisition and retry path. Outside it, unavailable with no re-anchor remains reasonable. Add delayed CL tests immediately before/after a commitment mine, ISLock delivery across a cycle boundary, and fresh startup on the new side of each boundary. Do not restore filtered selection or unbounded old-lock resyncs.

## Minor findings

### m1 — CH1-node's coding-float definition still contradicts its dates

**Severity:** minor. **Refs:** `docs/node-program/designs/SB0-shared-base.md:1389`, `:1394`, `:1398`. **Related:** r2 f2.

The design defines coding float as the gap between coding completion and the interface-constrained merge. It gives CH1-node coding completion **11.0** and merge **11.5**, a gap of **0.5**, then calls that gap **2.0**. The 2.0 is instead the allowance from completion 11.0 to its **latest M2-safe merge 13.0**. P2a-node's corresponding earliest-merge gap really is 2.0 (11.5→13.5).

**Scenario/fix:** dispatch using the same defined metric for both rows overstates CH1-node's interface wait by 1.5 weeks. Keep the corrected merge slack at 1.5 and the milestone dates. Either quote CH1-node's earliest-merge gap as **0.5**, or label its **2.0** as coding slack against the latest permitted merge and change the definition consistently. The defect is terminological/arithmetic in this paragraph, not a changed critical path.

### m2 — Repeated destructive re-anchoring does more than one forward sync

**Severity:** minor. **Refs:** `docs/node-program/designs/SB0-shared-base.md:585–590`, `:1200`.

For an unknown base below 2,450,000, a client first steps from 2,500,000 to 2,450,000, downloads forward to the old anchor, discovers that the base is still unknown, then steps to 2,400,000. The next transaction clears the just-downloaded header records. The successful final sync must download that discarded range again. This contradicts “the whole re-anchor therefore costs one forward sync of tip−c′ headers” (`:590`), even granting the intended reuse of the already authenticated T for intermediate coverage checks.

**Fix:** state the cost as the sum of attempted forward ranges plus the final sync, with a bound from the finite checkpoint ladder. Alternatively, revise the target/rebuild procedure to achieve the advertised single traversal, still without backfill. The simpler text correction is sufficient. Measure a multi-checkpoint unknown-base case, not only a one-step recovery.

## Assessment of the four requested probes

1. **Controlled rebuild:** one Durable SQLite transaction gives an all-or-nothing table reset, but subscriber correctness is not implied by atomicity. **M2** covers the locator/state, crash, stale-branch and stream-generation gaps; **M3** covers the finality constraint. The node's separate B1/P10 path is unaffected. The SPV reset must be specified outside the uninterrupted F1–F11 stream, with a fresh F10 handoff once state is reconciled.
2. **Old locks:** no peer-driven re-anchor is a useful resource/liveness boundary and is fail-closed. It needs the recent-lock distinction in **M4**; neither an old quorum surviving failed DKG nor a recently delayed lock is equivalent to an arbitrarily stale message.
3. **`BelowAnchor`:** **no separate finding**. An anchor is a trusted checkpoint hash, its pack is hash-linked, and accepted extensions follow full header rules. A branch genuinely diverging below that checkpoint cannot contain the same trusted anchor without a hash collision. Rejecting that branch without blaming a peer changes peer handling, not fork eligibility. Core's checkpoint rule likewise refuses pre-checkpoint forks (`v24 validation.cpp:4492–4501`). A valid weaker branch *sharing* the anchor remains an ordinary eclipse/availability exposure of header-based SPV; `BelowAnchor` adds no new authority to it. Do distinguish the anchor floor from the resident-window floor: stale branches below the latter but above the anchor remain eligible and must resolve through cold records, as SB5 specifies. The rebuild's loss of a later verified CL is the distinct **M3** problem.
4. **CPM:** **the arithmetic is credible as a conditional sensitivity model; the unchanged SB11/SB15 effort estimates are not independently established by rerunning it**. The overlay still reproduces baseline/A/B/C M2 **18.0/18.5/18.5/21.5** and REL11 **30.0/30.0/30.0/31.0**. A stress run adding **3.0 coding weeks to SB11** and growing **SB15 from M to L (+1.5 weeks)** gives A: SB11 **24.5**, SB15 **28.5**, SB18 **31.0**, while REL11 stays **30.0**, M2 **18.5**, and M5 **41.5**. The node milestone claims therefore tolerate substantial growth in these two product rows. The narrower “SPV rows end by week 27” claim does not survive that growth. Re-estimate SB15's rebuild/recovery work after M2–M4's contracts are settled; retain the explicit stub-overlap, approval-date and external-#902 assumptions. No new major dependency/CPM finding is warranted merely because scope grew.

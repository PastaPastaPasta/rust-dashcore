### R3-01 — blocker: migration preserves R2-01's unsafe self-spend as definite negative evidence

**Locations:** `rust/crates/dw-appdb/src/dispatch.rs:699` (1–3 → 4 migration), `:614` (`standing_calls` retains legacy self-spends); `rust/crates/dw-engine/src/platform/lease/fence.rs:1746` (loads them without provenance classification); `rust/crates/dw-engine/src/platform/lease/mode_b.rs:584` and `:475` (any recorded ChainLocked self-spend derives `NotSent`). **Scenario:**

1. A schema-3 build at the reviewed r2 head executes the already demonstrated R2-01 trace. The real lock A reaches proof, but its untrusted index-0 row is not journaled `Sent` and disappears. Unrelated pending lock B survives. The old tap attributed B to this call, so Repair admits a self-spend S conflicting only with B and records S against the standing funding marker. A's inputs are already spent; S does not invalidate A.
2. The wallet retains S's ChainLock and the schema-3 journal's funding marker and `self_spend` row. This is ordinary output of the old vulnerable path, not a malformed journal. No `signed_lock` table existed in that build. Upgrade to `11bbb1f`.
3. Migration adds an empty `signed_lock` table and preserves the old self-spend. `load_journal_with` installs it. B still matches the step's index-0 funding key, so it does not trigger the *nonmatching* unattributed-row veto. With recovery incomplete and no durable `Sent`, the step reads **`NotSent`** solely from S. Nothing rechecks whether S conflicted with A or whether the old row was admitted using exact ownership.
4. Consumers treating `NotSent` as permission to discard and create a new funding draft can fund again after A already paid—the same money-safety consequence as R2-01. A new attempt to Repair would be refused by the new guard, but the migrated negative resolution has already escaped that guard.

**Evidence:** `review_r3_schema3_heuristic_repair_must_not_survive_as_negative_evidence` uses a real on-disk `DispatchJournal`. It constructs the schema-3 layout and normal marker/self-spend rows corresponding to the r2 trace, opens it through the current migration, loads the resulting rows into the real `LeaseTable`, and supplies the same partial wallet evidence through `FakeTracked`. It observes zero signed locks, incomplete recovery, and **`Some(NotSent)`**. The assertion requiring a conservative result fails. The fresh suite is **5 passed / 1 failed**, exit 101; the migration probe rerun alone fails identically, exit 101. Logs: `/work/scratch/p2b-r3-sol/fresh-r3-probes.log` and `migration-probe-alone.log`; source: `migration-probe.rs`.

This is a supported historical-state reproduction. It does not claim that the new Repair admission creates this row, or that a live mined wallet was exercised. The old producer's unsafe admission and persisted false-NotSent trace were independently demonstrated in the r2 report; this round verifies that the new schema upgrade and recovery still accept that durable output.

## Ownership assessment

The mechanism is sound for the pinned builder's transaction shape. `CountingFundingSigner::sign_ecdsa` records a digest only after the vault successfully signs it and before returning the signature. `StoredLock::of` recomputes every input's digest from the complete stored transaction, insists on exactly two pushes, insists on the literal hash-type byte `0x01`, parses the key and DER signature, normalizes S, and verifies ECDSA. `signed_all` requires a nonempty digest list and membership of **every** digest in **one** running call of the same wallet. The key is committed through the P2PKH script code; an accidental signature under a different key does not authenticate the same digest/template.

- **SIGHASH types and ANYONECANPAY:** no `NONE`, `SINGLE`, ANYONECANPAY, or nonstandard synonym is admitted. The fresh probe signs real type-8 transactions under flags `0`, `2`, `3`, `0x41`, `0x81`, `0x82`, `0x83`, and `0xff`; every such input is rejected. This goes beyond relabeling an ALL signature.
- **Special payload and other commitments:** key-wallet's `TransactionSigner` uses `legacy_signature_hash` over the input UTXO's P2PKH script and `All`; the checker reconstructs that same script. At rust-dashcore `40268cc`, `legacy_encode_signing_data_to` copies the special payload and consensus-encodes it into the signing transaction. The fresh probe changes the asset-lock credit payload, adds/removes/reorders inputs, changes sequence, locktime and version; unchanged signatures fail provenance in every case. The built-in real-session test also signs a type-8 lock through key-wallet's actual `TransactionSigner` and the vault counting signer, then verifies the durable signed record before the wallet persister takes it—even when that persister refuses its store.
- **Same key or inputs across calls; re-signing:** the test with two calls signing the identical transaction records that transaction for both. The digests prove authorization of a transaction template, not exclusive authorship of a particular signature byte string. That is safe for Repair: both records name the same conflicting input set. Changing outputs, payload or a distinct input set changes the digest. A different signature nonce or a high-S/signature-push malleation can change the txid without changing that economic input/output template; such copies still share the inputs the self-spend must consume.
- **An extra input signed by another call:** the fresh two-input transaction has one digest recorded by each call. Neither owns it; Repair refuses `NoKnownLock`, including after reload. An ALL signature from a smaller transaction cannot be transplanted onto the enlarged input set. The implementation's matching regression also covers missing, mixed, empty and absent digests, another wallet, and storage after the call ended.
- **False negatives:** the pinned P2PKH builder is covered by the actual-signing integration test. Other hash types/scripts, mixed-call signing, or a store arriving after the permit ended cannot be authenticated by this mechanism and may park funding. With no signed record and incomplete recovery, newly requested Repair refuses; those cases do not supply negative evidence. A malleated row first observed after the call ended may lose durable positive attribution, but the original recorded input set remains a Repair obligation; if the lock confirmed, `LockInputsSpent` prevents a misleading self-spend. These are conservative liveness limits, subject to the legacy exception above.

## One lock per funding call

**True of the inspected pinned entry point; not enforced by the desktop permit.** At platform `bc41f1b`, `create_funded_asset_lock_proof_pooled` calls the broadcast half once, then waits for that outpoint's proof. The broadcast half calls `build_asset_lock_transaction_fenced` once, tracks that one transaction as `Built`, synchronously queues its changeset through `WalletStore::store`, then invokes the broadcaster. The pooled key-wallet builder also returns one signed transaction; its loops collect inputs/credit-output bookkeeping, not additional broadcasts. I found no internal retry that builds another lock. The standing-marker gate prevents another **permit** for the same step; it does not limit the number of builder invocations made with one permit's reusable signer.

Multiple durably recorded locks are correctly retained and all must be conflicted with. The implementation's two-lock test passed. I also deliberately violated the one-build contract: A's signed-lock write lands, distinct-input B's fails, both disappear from the wallet snapshot, then the table restarts. Before restart Repair names both; afterwards it admits based only on A. A ChainLocked self-spend of A then reads `NotSent` even if missing B already confirmed. The boundary probe documents exactly the risk stated in §2a.6; it is not a reachable second-build path found in the pinned one-call implementation.

Therefore this assumption is substantive, not a general fail-closed property of “at least one signed-lock row.” DP1-02's call site must invoke the one-build entry point once per permit, and every pin change must recheck this. If reusable/multiple-build funding is introduced, enforce that restriction at the API boundary or persist an obligation for every released signing template before the second build can escape; merely recording whichever locks successfully reach the journal is insufficient. This conditional boundary is not an additional current-pin blocker.

## Failed writes and migration mechanics

For one lock, a failed signed-lock write leaves exact txid/inputs in memory with `durable = false`; a subsequent store **while that call runs** retries it. No later store is guaranteed, and journal close retries owed positive `Sent` bundles, not an unconditional lost signed-lock write. If there is no next store and the process dies, the standing FULL funding marker remains and no signed-lock row is manufactured. The implementation's failed-write/retry, no-next-store/restart, closed-journal and no-standing-marker cases passed. The fresh crash-before-call-finish probe also reloads durable state before finishing the old permit, leaves a trusted unrelated pending row, and confirms that neither Repair admission nor self-spend recording succeeds, nor can a sighting of the attempted self-spend produce `NotSent`. Within the original process, Repair must conflict with the exact in-memory lock. The real-session regression refuses `LockInputsSpent` when that lock's inputs are gone even if an unrelated matching row has a spendable input.

The SQLite migrations are transactional, additive, and keep WAL/`synchronous = FULL`. Versions 1 and 2 retain their prior markers/resolutions; version 3 retains its Mode B rows and gains an empty signed-lock table. Signed locks are linked to the standing marker by its sequence, wallet, artifact and step; they compact with the artifact, and old/mismatched/superseded markers do not make a signed record stand. Input encoding is fixed-width txid plus little-endian vout, and malformed input lengths fail decoding. These structural checks passed. They do not cure R3-01's semantic authority of legacy self-spends.

`standing_calls`' fourth argument is supplied by both in-repository callers: `DispatchJournal::load_calls` reads the actual signed-lock rows, and `FakeJournal::load_calls` supplies its signed-lock vector. The workspace builds against the changed signature. No caller silently supplies an empty placeholder for a populated current journal. Loaded signed locks survive wallet close/reopen; the guessing map has no replacement in-memory ownership heuristic.

## Findings

1. **Major — an old won outcome can become unread news on restore** (`rust/crates/dw-engine/src/platform/journal.rs:1019-1028`, `contest_watch.rs:598-621`). The tap's pre-existing name path emits `ContestWon` whenever a watched label appears in the library name list. It derives the event age from `name_time`, and uses `Age::Unknown` if the marketplace name-state row is not yet stored. At the pin, `sync_dpns_marketplace` calls `add_dpns_label_if_missing` before `record_dpns_name_states` (`rs-platform-wallet/.../dpns_marketplace.rs:1680-1695,1784-1788`); the first call persists the identity snapshot and invokes the tap synchronously. Thus a restore can journal the old win unread before the watch sees the poll's resolving block time. The later watch insert is deduped and cannot change that row's read state. A scratch-only regression probe set a catch-up boundary 60 s in the future, listed the name before the watch, and expected a read win; it failed with `contest_won` unread and `username_registered` read (`catchup-probe.log`, `catchup-proof.patch`). Let the watch's block-timed outcome own the `ContestWon` insert, including when the name snapshot arrives first; retain the companion username as read.

2. **Major — a full first contender page is mistaken for proof of participation** (`rust/crates/dw-engine/src/platform/contest_watch.rs:154-170`). `verdict` defines `placed = contains(me) || truncated()`. For a resolved poll whose 100-entry first page omits `me`, it therefore returns `Lost` or `Locked`, journals that outcome and deletes the watch row. The pin permits 1,000 contenders per contest (`rs-platform-version/.../system_limits/v4.rs:154`), while this SDK query defaults to 100 (`rs-drive-abci/.../contested_resource_vote_state/v0/mod.rs:130-150`), so the omitted identity may be on a later page or may never have joined. D2 calls this Open-unknown. The current test at `contest_watch_tests.rs:301-312` explicitly expects `Lost` for the full-page case, so it protects the wrong behavior. Keep a watched row unresolved until a page proves the identity is present, or page to find it; preserve the direct `WonByIdentity(me)` case because the winner itself proves participation.

3. **Major — the claimed end-date request budget is not bounded** (`rust/crates/dw-engine/src/platform/contest_watch.rs:259-268,454-464`). `SdkContests::ends` calls `get_current_dpns_contests(..., None)`. At the pin this helper contains its own fetch loop and can make another DAPI request for each full last timestamp group (`rs-sdk/.../contested_queries.rs:432-499`). One call to `ends()` is therefore not one end-date request; a network with many such groups can consume many requests during the 20 s pass. The outer timeout bounds the awaited pass in time, but not its request count. Use one explicitly bounded end-date page/query in the watch, or impose a strict page/request limit in the SDK call path, and test it with a multi-page fake.

4. **Minor — a `Contests` signal bypasses the one-pass-per-second floor** (`rust/crates/dw-engine/src/platform/bringup.rs:277-299`). The floor is installed only after a timer-fired pass. A queued `PlatformSignal::Contests` resets `contests_at` to `Instant::now()`, so a second pass can start immediately after the first. Re-arm through the same floor for signals. Due-row checks still suppress repeated queries of existing rows, limiting impact.

5. **Minor — the numeric cap test does not guard 16** (`rust/crates/dw-engine/src/platform/contest_watch_tests.rs:591-608`). Changing `PASS_CAP` from 16 to 17 in scratch left `a_pass_asks_about_sixteen_rows_at_most` green: its expected count is computed from the changed constant. Assert the literal 16 (and the next-pass remainder) so the budget contract is tested independently. The mapping and fence mutants were killed, as below.

## Other axes

- **D2/D3:** For a listed contender, the pin's `WonByIdentity`, `Locked`, `NoWinner`, and unresolved states map as planned. The outcome time is `BlockInfo.time_ms` and is passed as `Age::At` to `ChangesetTap::journal`; lost and locked rows go through that sole news writer. The ordinary watch-first won path reuses the row label and stored end, so the later name snapshot dedups `ContestWon` and stores `UsernameRegistered` read. Finding 1 covers the name-first order.
- **D4:** Persistent writes in adoption, `start_watching`, outcome application and row deletion take the write fence for the wallet object read. The fence prevents a pass held in a network query from writing after removal/reimport; the parent `72d61af9` already contains the DP2-05 r4 fix that calls `tap.forget` even after an appdb delete failure and cleans residual metadata at readmission. `watch_contest_once` serializes normalized-label adoption and `register_name` in one SQLite transaction. Concurrent outcome insertions dedup in the journal. No new D4 finding.
- **D1:** The supervisor gives a wallet pass a 20 s `tokio::time::timeout`; network reads hold no write fence, so an indefinitely pending async query is cancelled and does not itself block removal or vault locking. A wallet with no watched rows has no recurring contest timer after the initial startup pass. The per-row due times and 16 vote-state query cap work in the baseline. Findings 3–5 qualify the request and pass guarantees.
- **D6:** `contest_status` rejects malformed identity/label inputs, an identity absent from the wallet, and a complete unplaced poll with no watch row. A watched but currently unplaced label is shown Open. Watched resolved outcomes call `apply_contest`, the same function as the watch. Finding 2 also affects this on-demand path for a full first page.
- **M4:** Contract-Version is 18 and the surface SHA-256 remains `524c6fadd69a02d8606a6e111d53bbd0b868e6d1c4561fb86707b6bac83169ad`; the contract test passed. DP1-06 independently uses version 18 with a different surface hash (`6246593e...`), so the second of DP1-04 and DP1-06 to land must rebase and bless version 19 or the next free number. U-07 remains at 17 with the base hash and creates no version collision by itself. This is follow-merge coordination, not a separate defect in the current branch.
- **L3/L5/L8:** The requested implementer follow-up list was not present in `plan.md`, `T2-evidence.md`, the two commit messages, or the branch's contract diff. I requested its location and cannot give an evidence-based per-item ruling without its text. The concrete major findings above independently require changes before merge.

CHANGES-REQUIRED

1. **MAJOR — Deferred lifecycle actions outlive the view and can restart resources after cleanup.**

   **Where:** `Vendor/swift-cross-ui/Sources/SwiftCrossUI/Views/Modifiers/Lifecycle/OnAppearModifier.swift:27` and `Vendor/swift-cross-ui/Sources/SwiftCrossUI/Views/Modifiers/Handlers/OnChangeModifier.swift:70`. The interacting cleanup is `Views/Modifiers/Lifecycle/OnDisappearModifier.swift:104`.

   **Failure scenario:** Create a conditional view, queue its `.onAppear`, then remove it before the backend dispatches that action. Removal schedules `.onDisappear` through a main-actor `Task`; the queued appear action uses the backend queue instead. There is no lifetime check or cancellation. Cleanup can therefore run first, followed by the appear action for the already removed view. A subscription or task started by that late action has no subsequent disappearance to clean it up. The same defect affects a non-initial `.onChange`: commit a changed value, remove the view before its queued action runs, then the old action executes after cleanup and can overwrite shared state or reactivate a resource.

   **Independent evidence:** Real vendored `ViewGraph` code over the fake backend, in `/work/scratch/dw-d4-r2-gpt/mini/Tests/SwiftCrossUIPatchTests/Round2Tests.swift`:

   - `deferredHooksAfterRemoval`: before draining the backend, events are `["disappear"]`, resource inactive; afterward they are `["disappear", "appear", "change"]`, resource active.
   - `changedHookAfterRemoval`: after an actual value change on an already appeared view, events are `["disappear", "change"]`, resource active.
   - `taskCreatedByLateAppearLeaks`: events are `["disappear", "appear", "resource-start"]`; the stored task has `isCancelled == false`. The probe explicitly cancels it afterward.

   These three regression assertions fail in both `round2-final-tests.log` and `round2-repeat.log`. The backend queue is intentionally held while the view is synchronously removed and the actor cleanup runs; this is an allowed ordering between the two scheduling mechanisms. On GTK, higher-priority events can also remove a view before its idle callback is dispatched. This finding does not require a duplicate action or a broken observation queue.

   **Fix:** Associate queued hook actions with the actual node lifetime. Invalidate a per-node lifetime token synchronously when the node is removed, and check it before running a deferred action. A children-owned token is one possible implementation; ensure the captured action cannot keep the lifetime artificially valid. Coordinate lifecycle delivery so cleanup cannot be followed by resource-starting actions from the removed lifetime. Keep actions outside observation/layout scopes to preserve the original M1 fix. Add the three disappearing-view regressions to the repository suite. Do not merely put `.task` back on the deferred queue: its cancellation probe currently passes, and deferring its start reintroduces the previously identified task-start-after-cleanup hazard. Document the changed ordering and lifetime guarantees in P8.

   **Impact:** A framework lifecycle regression. I found no `.onAppear` use in the current CrossUI app; the observed send flow still succeeds. Paired appear/disappear resource management is nevertheless supported public API and is now unsafe.

## Ordering, starvation, and the send flow

The five independent lifecycle probes isolate the unsafe hook lifetimes from ordinary `.task` behavior. `taskCancellationAfterImmediateRemoval` passes with `["task-start", "task-cancelled"]`. `taskVersusAppearOrdering` observes `["task-unready", "appear"]`: the task body can execute before deferred `.onAppear` initializes resources. That is a real ordering change to account for, but I do not treat an undocumented task/appear ordering assumption as a separate blocker. The concrete resource leak is covered by finding 1. The repository's once-per-change test passes; I found no inherent duplicate invocation for one committed value on one surviving node.

The depth queue snapshots and clears its pending batch before dispatching updates (`ModelObserver.swift:128`). It does not keep processing newly enqueued items inside the same flush. New work schedules a later flush, and renewed descendants are skipped by observation ID. For a finite batch, sorting does not intrinsically starve deeper nodes or create a livelock. A continuous stream of higher-priority GTK events can starve idle sources, and a hook that continually mutates its own input can schedule endless successive batches. Those are distinct from the fixed ancestor-update multiplication. P8 also does not coalesce the separate legacy `@State`/Publisher path into this observation queue.

I rebuilt `dash-wallet` from the fresh reviewed source copy, using isolated build files and existing engine artifacts. The focused real-GTK/Xvfb demo send completed all **11 checks with zero hard failures**, including listing the sent payment on Transactions. The main thread then measured **0%, 0%, 0% demand** over the harness's three two-second windows; an additional completed five-second sample measured **0.46%**. Log: `/work/scratch/dw-d4-r2-gpt/send-probe.log`. This directly corroborates the supplied m2 rerun, which includes the same send flow and passed 179 checks. The supplied m1 and ux logs total 103 and 242 checks respectively, with zero hard failures; the headless rerun reports 539 passing tests. I inspected those broader runs rather than rerunning all of them.

The original send-induced sustained busy condition is gone in the exercised flow. It could recur with a genuine application feedback loop, continuously arriving model changes faster than whole-window layout, many legacy Publisher updates, backend work that writes observed state during layout, or constraints whose reported/requested size pair continually changes and therefore never matches P10's refusal memory. The remaining whole-window observation scope also means a finite update can still be expensive. None of those possibilities invalidates the demonstrated coalescing improvement.

## GTK C allocation and memory-safety review

My actual-C probe, compiled with AddressSanitizer and UBSan and run under isolated Xvfb display 91, passes matching-report-once, repeated equal allocation suppression, two independent roots, refused-then-honoured allocation, multiple preempts, and a pending request followed by a same-sized allocation. Files: `root-widget-probe.c` and `root-widget-probe.log`. Leak detection was disabled for the GTK process; this is not a whole-framework leak audit.

The flag is an initialized field of each `GtkCustomRootWidget`, so windows do not share it. GTK sheets use ordinary `Gtk.Window` content instead of this root-wrapper allocation/request protocol; there is no shared sheet flag. It is cleared before callback invocation. The callback receives `CustomWidgetSize` by value, and the Swift wrapper copies its integer dimensions into the queued closure, so this change introduces no borrowed stack pointer. GObject allocates the updated struct size. I found no new memory-safety defect in the C delta. The pre-existing retained callback-box ownership is outside this change.

The flag **can stick without an allocation**: changing a mapped window's default size to an unchanged value need not cause GTK to allocate. P10 documents this accurately. A later unrelated allocation can then answer that pending request as a refusal. Multiple outstanding requests also have no generation identifier, so a delayed report is interpreted against the most recent outstanding request. Later size changes clear refusal memory and cause ordinary relayout, including a refused-then-honoured request. I found no demonstrated new endless loop or supported-window minimum clipping from these cases. The corrected GTK minimum blocks the original user-drag failure; without a window manager, forced undersizing can still persist. AppKit's absence of honoured-request reports is separately documented. The protocol is best-effort resize correlation, not an acknowledgement tied to a request ID.

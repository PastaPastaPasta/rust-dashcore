# BS13 base-sdk perf helpers — Sol round 1

Revision: `73d2407` (13 commits over `8382b76`). Reviewed in a detached worktree.

## Findings

1. **Blocker — v24 asset-unlock txids disagree with Dash Core.** `pkgs/primitives/src/transaction.rs:388` hashes the complete transaction encoding for every `Transaction`. In Dash Core `v24.0.0-rc.3`, `CTransaction::ComputeHash` uses `ComputeStableUnlockHash` when the transaction is a type-9 asset unlock with a 145-byte payload whose first byte is at least 2. That hash zeroes the final 132 bytes (requested height, quorum hash, quorum signature) before SHA256d; Core retains the full hash separately as `GetInstanceHash`. The Rust method returns the *instance hash* as `TxHash`, so changing only a v2 unlock's quorum signing fields changes its Rust txid while Core's txid stays fixed. `Block::merkle` at `pkgs/primitives/src/block.rs:273` uses those Rust txids, producing a different merkle root and failing valid v24 blocks. This behavior existed before BS13, but the new streaming path retains it. The new `check_digests` assertion at `pkgs/dev/src/parity.rs:127` expects full-wire SHA256d for every tx and thus cannot detect it. **Fix:** implement Core's exact stable-unlock txid predicate and zeroed-tail hashing, expose the full instance hash separately, and test both against Core v24 vectors; adjust the parity checker so this exception is expected.

2. **Major — provider-payload `Hashable` hashes signatures that Core's signing hash excludes.** `pkgs/primitives/src/codec.rs:19` streams the complete `BaseCodec` image for every `hash_impl!` type. For `ProRegTx`, `ProUpServTx`, `ProUpRegTx`, `ProUpRevTx`, `ProUpShareTx`, and `ProUpSharedRegTx`, the Rust wire encoders include their final signature field (for example `pkgs/primitives/src/payload/proregtx.rs:220`), while Core's matching payload serializers omit those fields under `SER_GETHASH` (`src/evo/providertx.h:224,299,363,417,500,536`; `SerializeHash` defaults to `SER_GETHASH`). A signed `ProRegTx` therefore has a Rust `Hashable::hash` that changes with `vch_sig`, while Core's `SerializeHash(proTx)` signing digest does not. The mismatch also predates BS13; this change preserves it and the new parity checker does not cover these types. **Fix:** give these payloads a Core-specific signing-hash API (or make `Hashable` use that serialization if that is its intended contract), with tests against Core's `SerializeHash`; keep full wire encoding available for transport.

## Validation

- `cargo test -p dash-primitives --all-features --test parity --test encoded_len`: 8 passed, including corpus, mutated corpus, generated images, and the in-test planted mutant.
- Built the `hash_parity` target with the README's sanitizer coverage flags. The `planted-mutant` build exited 77 on a generated block seed, reporting `the sink's block SHA256d is not the buffered one`. The real build completed 126 seconds and 33,565 executions with no crash.
- Independently checked Core `v24.0.0-rc.3`'s stable-unlock predicate and hash. Changing an existing 190-byte asset-unlock corpus transaction to payload version 2 gives full-wire SHA256d `8ea9e7d5e50042e743ec91e286fa869923e4ddd22b55fd2636e807fd7f54f3e5`, versus Core's zeroed-tail hash `2b3ff94b9041aff5b77c42631894290a6f9993c645c935e2ebe27a62b17bc20b` (display byte order).
- Inspected the changed `encoded_len` overrides at CompactSize boundaries, transaction version/type and payload conditions, and the default counting buffer. No arithmetic mismatch found. The `decode_with_ranges` paths use the same field decoders and shared `decode_seq` logic as plain decode; the parity tests compare values, errors, cursor positions, and range slices. The public sequence decoder retains both the `MAX_SER_SIZE` CompactSize limit and the remaining-byte count bound; its caller-provided reader must still consume correctly.
- Inspected the `hash_impl!` expansion and its p2p_core callers: both buffered and streamed paths invoke the same `BaseCodec::encode`, so I found no type-specific byte-stream divergence. Core-specific hash serialization remains a separate contract, as above. The added non-optional dash-dev dependencies create no new dependency cycle or `std` requirement (`dash-pow` is `no_std`).
- Built the `primitives` release benchmark locally and ran `perf stat -e instructions:u` with `RUSTC_WRAPPER` unset. For `block_decode_txids`, the 200- and 1200-sample counts were 4,718,117,434 and 12,011,810,688; the difference is 7,293,693 instructions per added iteration, consistent with the owner's 7,294,410 (and below the stated 7,405,172 baseline).

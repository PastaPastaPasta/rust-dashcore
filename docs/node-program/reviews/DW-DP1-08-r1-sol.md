# DP1-08 independent review — ece905c5 over 53a78fb1

## Findings

1. **Major — The 10-second hold can still assert that a named wallet has no username.** `apps/desktop/src/api/queries.ts:216-229`; `apps/desktop/src/dashpay/status.ts:272-274`; `apps/desktop/src/components/shell.tsx:142,148-150`. The engine reports a newly discovered identity as live and nameless before its first names pass (D21), but that pass has a 20-second budget (`rust/crates/dw-engine/src/platform/recovery.rs:96,663-695`). If it takes 11–20 seconds, or a user switches away before it completes and returns after 10 seconds, the timer expires and Home shows “Finish username registration” while the chip says “No username” for an identity that already owns a name. A later names result repairs the display, but the false state is the regression D21 was meant to prevent. The timer itself re-arms and cleans up correctly; its expiry is not evidence that names were fetched. Keep the state at “Updating…” until the engine exposes completion of the first names pass, including a failed/unknown outcome, or use neutral copy that does not assert the identity is nameless. Add a delayed names-pass regression test.

2. **Minor — A failed refresh can leave an old card or chip indefinitely.** `apps/desktop/src/dashpay/queries.ts:50-64`; `apps/desktop/src/api/queries.ts:238-266`. After a successful status read, `useQuery` retains `data` if an invalidated read fails. `statusError` is then false because `data` exists, and the shell also passes that old `status.data` directly to the chip. For example, after a wallet reload or restore changes `noIdentity` to `ready`, a failed status refresh leaves the enabled “Join DashPay” card and chip until another invalidation succeeds; the reverse can leave a joined chip. Treat a failed current read as unknown/error on both surfaces, or explicitly mark cached data stale and prevent affirmative actions. Cover a successful read followed by an invalidation and failed refetch; the current error test covers only an initial failure.

3. **Minor — Status transitions omit their key information from live announcements.** `apps/desktop/src/screens/dashpay/DashPayCard.tsx:71-84`. Only the message lines are inside `role="status"`; the changing title and `(n/3)` step are outside it. When a registration row arrives or advances, a screen reader may hear the wait line but not the username or new stage. Include the title and step in the polite live region, or add an equivalent concise live announcement. `aria-labelledby` names the section for navigation but does not announce its later changes.

4. **Nit — The parity record claims a CoinJoin tip that is deliberately absent.** `docs/parity.md:291`. IOS-065 lists “the CoinJoin tip” among the Join page contents, while DP1-08 D9 explicitly omits it because this engine cannot fund registration from mixed coins. Remove that phrase so the parity row does not claim an implemented or recommended flow that the UI does not provide.

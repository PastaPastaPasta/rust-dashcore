## Numbered findings

### 1. Major — a concurrent row-less Resend can outlive a definite refusal and released inputs

**Locations:** design `:473`, `:520`, `:580–591`, `:597–600`; model `e0_04_design_model.py:237`, `:336`, `:487`, `:650`.

The set records admission immediately, and a repeat gets an unrestricted `Resend` with no permit or completion handle. The original permit's `NotSent` removes the id and refunds its charge unless a previous attempt has already finished Sent/MaybeSent. That test does not account for a concurrent repeat that is admitted but still running. Neither the API nor an obligation serializes all identical-byte SDK calls; sequential `TxDraft` serialization is insufficient for the general fence.

**Interleaving:** O admits a leased row-less artifact and pauses in transport. R presents the identical bytes and gets Resend. O is definitely rejected before its own send, so `finish(NotSent)` forgets the id and refunds. Lock revokes the lease and returns; R has no permit in its snapshot. A repeat by O now gets Refused/Cancelled and, for a Core payment, releases its inputs. R then sends the original bytes. A new build can now compete for inputs of a live transaction. For state transitions, the same trace gives a false Cancelled and an unjustified budget refund.

**Proof:** `adversarial_model_checks.py::concurrent_rowless` replays this using the **unmodified model's transitions**, changing only the initial state to allow an independent row-less caller R. It ends with O Cancelled, inputs released, and R sent; the model flags the late first send. The shipped `rowless` scenario fixes `r="done"` and permits only O's sequential repeat, so it cannot explore the trace.

**Fix:** give every attempt, including a Resend, an artifact-scoped completion guard and track active attempts under J. An artifact may become definitely unsent, be forgotten, or refund only when all admitted attempts are definitely unsent and none remain capable of sending. Dropped/ambiguous attempts retain possible-send provenance. Alternatively defer concurrent identical-byte repeats until the first attempt settles, without awaiting another caller under J. The library must derive the error/release decision from that aggregate result. Add simultaneous repeat/reject/lock tests for Core transactions and state transitions.

### 2. Major — waiting for old permits does not close the interval before the vault gate runs

**Locations:** design `:220–229`, `:831–839`, `:886–894`; model `e0_04_design_model.py:952–971`.

`lock_gen` excludes creators that started **before** the freeze. A creator that starts immediately **after** it reads the new generation and passes. Its only additional wait is for pre-freeze permits, which can already be empty while the detached `spawn_blocking(vault.lock())` has not executed. The design assumes “the vault was locked in step 2”; spawning that operation does not establish this.

**Interleaving:** a grant G exists before Lock, in epoch E. Lock freezes an empty permit table, increments the generation and queues its vault operation. Before that operation runs, B begins a lease, reads the new generation, redeems G in E, inserts Active and signs a transaction. B pauses before admit. The vault operation then ends E and Lock returns. B was absent from the freeze and remains Active: `live(B)` checks lease state, not signer epoch. B now obtains its **first** dispatch permit and sends after Lock returned, using authorization issued before Lock. An own-key B also retains its KeyHold because the freeze never dropped it. A second Lock can see this new lease, contrary to the claim that it only joins a subset of the first snapshot.

**Proof:** `adversarial_model_checks.py::lock_gate_window` implements the stated generation/permit conditions and reproduces the post-return First. Part 2's creation check only asks whether a creator with `b < 0` survives; it does not check this post-freeze/pre-gate interval.

**Fix:** maintain a table-owned lock-operation barrier covering both vault-gate completion and the old permit drain. Recheck that barrier and generation atomically at insertion. Unlock/grant handling must establish the ordering of the vault lock before using its new epoch; lease creation cannot reopen merely because the permit table is empty. A detached coordinator must finish and clear the barrier when the caller is dropped. Concurrent Locks should join that coordinator. Test zero permits, delayed blocking-pool execution, a gate wait longer than H, dropped callers and double Locks. Retain the max(H, gate completion) bound without allowing this bypass.

### 3. Major — cross-process row-less refusal depends on a marker with no write-ahead rule

**Locations:** design `:592–596`, H10 at `:640`, `:809–814`, Q18 at `:1304`; `SDK/platform/transition/broadcast.rs:125`, `:156`, `:172`; `PW/wallet/identity/network/registration.rs:227`, `:276`.

H10 converts a later Refused/Cancelled into MaybeSent **if** the flow's durable state records an earlier hand-off of that step. There is no requirement to make such a marker durable before the row-less commit. The per-process set disappears at restart. A phase written after the library returns is too late: the SDK broadcasts before waiting for execution, and registration bookkeeping occurs after submission succeeds.

**Interleaving:** an existing funded lock is used to sign and broadcast identity transition S. Kill the process after S reaches a node, before the response or `IdentityRegistered`/step-marker write. Durable flow state remains FundingSent/ProofWaiting and contains no earlier identity-submission marker. After reload, the flow signs the same S again, then Lock wins before its new admit. The new set has no S, so it is Refused; H10 has no marker to consult and allows Cancelled, while the original S can still execute. Power loss can lose a marker acknowledged from a NORMAL database too.

**Proof:** the scratch `rowless_crash_marker` check demonstrates the permitted trace. The pinned broadcast-before-wait and later bookkeeping establish the real suspension window. The shipped model explicitly excludes row-less crashes (`crash_steps:529–530`), so its refusal invariant cannot establish the cross-process claim.

**Fix:** require a durable write-ahead possible-dispatch marker for each resumable row-less flow step, tied to the artifact hash and step identity, before First admission/transport. It must use a durability barrier sufficient for the claimed crash/power-loss behavior. Consume that marker when interpreting later refusals, independently of whether a success phase was recorded. This can be a small journal extension; it need not persist the entire process set. Add kills before/after broadcast, before response and before phase persistence. This supplies the prerequisite assumed by accepted Q18 rather than reversing that decision.

### 4. Major — the proposed own-key split still contains an invisible ChainLock fallback

**Locations:** design `:315–323`, `:341–345`, `:1108–1114`, Q19/Q20 at `:1305–1306`; `PW/wallet/asset_lock/orchestration.rs:227`, `:665–717`; `PW/wallet/identity/network/registration.rs:169–197`, `:240–259` and top-up `:479–502`.

The first `create_funded_asset_lock_proof` call does return `FinalityTimeout` at its 300-second wait; its nearby comments are misleading, but its executable path matches that part of the design. The **second** call is not a submission of a supplied proof: pinned `FromExistingAssetLock` takes an outpoint and an invitation-authorization flag, with no proof argument. It resumes proof resolution internally. Registration/top-up also catch an invalid InstantSend proof from Platform and call `upgrade_to_chain_lock_proof(..., None)` inside the submission call.

**Counterexample:** the own-key split obtains an IS proof and enters step 2. Platform rejects that proof 20 seconds into the window. The library enters an unbounded ChainLock wait; the engine receives neither the claimed timeout nor a fallback notification. The KeyHold remains usable until its old window timer, rather than dropping when CL waiting begins. If CL arrives after that timer, the library's internal retry signs with a dead held signer, rather than executing the designed park/new-grant continuation. The row's host phase cannot be advanced at the actual fallback boundary either.

**Proof:** exact-pin source check `hidden_chainlock_fallback` verifies both the enum's missing proof argument and the hidden `None` fallback. The new `proof_wait_started` callback names only the build proof wait; it does not observe this later fallback.

**Fix:** add an explicit opt-in submission/funding API that surfaces **every** CL fallback to the host, or a fallback callback plus a continuation requiring fresh authority. Define how a proof already obtained by step 1 enters step 2. Park/drop the hold at the fallback itself and resume signing only with the intended new grant/lease. Add these requirements and tests to P3/L1–L15: the currently listed Q1 PR content does not provide them. Accepted Q19's split remains reasonable, but needs this additional platform behavior.

### 5. Major — the FULL journal can preserve a possible send that load catch-up cannot fence or resume

**Locations:** schema `:693–701`, H6 at `:637`, `:798–800`, `:986–991`; DASHPAY `:981–989`; `PW/wallet/core/generation.rs:107–165`, `:242–252`.

Accepted Q11 allows loss of a NORMAL `wallet.sqlite` row while its FULL dispatch entry survives. H6 iterates **tracked rows**, and the journal has neither signed bytes nor input outpoints. An orphan Dispatching entry therefore supplies no way to reserve its inputs or resume its committed transaction. Reconstruction from the chain can recover a finalized asset lock; it cannot discover a transaction that has not reached the chain, or resend bytes that were lost before enqueue.

**Interleaving:** register T, store its Built row in NORMAL mode and durably commit Dispatching. T is handed to a peer, which withholds it. Power loss loses the Built row and the local pending-spend fence but preserves Dispatching. On reload there is no row for H6 to re-reserve; chain reconstruction finds nothing. A user builds a conflicting payment using T's selectable inputs. The peer can later release T, so either payment can win. In the variant killed between the durable journal write and enqueue, T is never resent at all despite the liveness claim. This requires no manual journal rollback/deletion.

**Proof:** `normal_power_loss_orphan` constructs the recovery state expressly permitted by Q11. Catch-up does “nothing to resume,” reserves nothing and produces no model violation. Pinned pending-spend fences are process-only, and their source explicitly warns that an elapsed time/height or restart does not prove an earlier transaction is unsendable.

**Fix:** preserve NORMAL for ordinary wallet changesets, as DEC-65 requires, but add a dispatch-specific durable recovery payload: signed transaction, input outpoints and enough funding metadata to rebuild its row. Load must reconcile Dispatching/PreFence journal entries **without** rows and fence their inputs before spending opens, with a defined resume/reconstruction path. An equivalent narrow durable barrier for dispatch-critical row data also works. Add power-loss recovery tests distinct from the kill-only matrix; DP1-05's finalized-chain reconstruction alone does not establish this invariant.

### 6. Major — rebind can restore signing above the new grant's cap

**Locations:** design `:166–170`, `:236–258`, `:297`, `:406`, H8 at `:639`.

`rebind` takes fresh authority but keeps the old budgets. The vault refuses a funding signer whose requested cap exceeds its token, but a PlatformIdentity token is checked only for `max_credits != 0`. No rebind rule checks that the fresh grant covers the remaining purposes and budget, or limits **newly signed** artifacts to its smaller cap.

**Counterexample:** a lease has Credits cap 1,000 and zero spent. An epoch change moves it to NeedsGrant. The user issues a fresh `PlatformOp{max_duffs:0,max_credits:1}` for rebind. It may yield PlatformIdentity because 1 is nonzero, and rebind preserves the 1,000-credit budget. A newly signed 100-credit transition passes the fence, exceeding its fresh grant by 99. The analogous Spend path is vulnerable if prepare consults only the retained lease budget. Already-signed artifacts continuing under Q5 do not authorize new signatures above a replacement token's scope.

**Proof:** the scratch `rebind_credit_cap` check follows the documented tests and budget retention and admits 100 against the new cap of 1. This is an underspecified authorization rule, not a claim that the absent rebind implementation already contains it.

**Fix:** validate wallet, purpose set and remaining caps under J when rebinding. Reject a grant that does not cover the remaining authority, or explicitly constrain new signing/admission to the intersection of old remaining authority and fresh grant caps while preserving previous charges/permits. Define mixed grant-set rebind behavior. Test smaller, zero, wrong-purpose and partial replacements, including checked accounting around outstanding artifacts.

### 7. Major — “nothing in flight” is not evidence that a flow was cancelled

**Locations:** design `:488–489`, `:598–603`, `:898–912`, `:1263–1264`.

The outcome rule says a revoked flow reports definite Cancelled if “it had nothing in flight.” A permit ends at hand-off, before the much longer proof wait. Thus every successfully funded registration waiting for proof can satisfy that condition. LockReport retains only the freeze's in-flight permits; neither it nor the stated classification rule requires consulting completed artifact history.

**Interleaving:** funding T is durably Dispatching, enqueued, and its permit finishes Sent. The flow waits for IS/CL with no permit. Lock takes an empty snapshot and revokes the flow. The literal §8.4 rule yields Cancelled although T is already on the network and cannot be cleaned up. The §12 test expecting Sent/MaybeSent during an IS wait contradicts the rule. Likewise a registered permit's attempt-level NotSent must not imply cancellable funds: Q13 intentionally retains Dispatching and later resends it.

**Proof:** `snapshot_only_outcome` uses the original model's transitions to reach an empty snapshot with a successful send and Dispatching. The model checks O's previous verdict, not the flow outcome that §8.4 derives at Lock, so it does not test this error.

**Fix:** retain monotone per-artifact/flow dispatch history after permits finish. “No permit” only means nothing to drain. A flow with any committed possibly-sent artifact must report Sent/MaybeSent, including definitely rejected attempts whose registered artifact remains committed. Cancelled requires proof that all relevant artifacts were never committed and cannot send. Define partial multi-artifact outcomes explicitly and test completed funding plus an uncommitted identity submission.

### 8. Minor — the model's safety oracle can forget a successful send, and its coverage wording is too broad

**Locations:** `e0_04_design_model.py:6–8`, `:336–351`, `:529–545`, `:590–606`, `:650`, `:952–971`; design `:999–1039`.

The documented single-artifact limits are useful, and the r4 replay really works. However, `may_send` ignores the immutable `sends` history, `rl_out`, and active row-less Resends. Its input flags can be cleared by a later rejection. This lets a broken implementation pass even the existing sequential scenario.

**Mutation:** `forget-rowless-history` makes any row-less rejected repeat forget all earlier hand-offs and report NotSent. All **seven original scenario explorations** still report zero violations. The explicit trace First → Sent → identical repeat → Resend → Rejected ends with `o_verdict="NotSent"` and `sends=(("O",0),)`, yet `violations(...)` is empty. The mutation source and log are retained in scratch.

**Fix:** judge definite outcomes from immutable actual-send history and all still-sendable attempts, independently of the bookkeeping being tested. Include the concurrent caller from finding 1, row-less restart/marker crashes, and post-freeze/pre-gate creation. Power loss must be separate from the process-crash transition, which currently retains every acknowledged wallet row. Model lock-outcome aggregation as well as the original caller verdict. Narrow the header's “every safety and timing property” claim to the state space actually explored. Require the new mutation to fail before claiming coverage.

## Closure checks and pinned dependencies

- **The registered-artifact commit point is materially improved.** The one-J CAS, Committing exclusion, spawned writer, durable Dispatching before transport, dead origins after reload, and CAS-winner cleanup block the original r4 unsent-Built/resume trace. I replayed it under r3 and under this design: r3 sends after Lock; the design ends Cancelled, no send, row removed and one reservation release. The earlier split/CAS models and their mutation probes also ran. Process-kill traces with a surviving wallet row support this part of the design; they do not prove the power-loss case in finding 5.
- **No separate old-epoch vault signing bypass was found.** The merged gate covers key use and release (`dw-vault/src/vault.rs:533–556`, `:856–862`; `signer.rs:236–250`). A Weak own-key upgrade inside that gate is compatible with Lock waiting for ongoing operations. The host-table race in finding 2 is a different gap. The unrestricted scan master remains a documented engine-only export whose already-resolved copy cannot be revoked; E0-05 must cancel/drop the actual scan before claiming key disposal. IdentityScan separates that exceptional export from capped PlatformOp; QuickUnlock remains limited to Spend/SignMessage. Wallet/issuing-vault/epoch binding from E0-03 must survive the new held-signer and authorize_set paths. I found no additional grant escalation beyond the rebind rule above.
- **M1 bypass is deliberate until P5.** Existing `TxDraft::prepare` checks a Spend grant before signing (`send/mod.rs:819–829`), but broadcast retains signed bytes and reaches the old unleased routes at `:1072–1080`. Lock can therefore lose to a prepared M1 payment in P1–P4. That matches accepted Q2; P5 must actually route both mixed and finalized paths through the lease and must remain part of completion of the accepted plan. CoinJoin, external PSBT and genuine rebroadcast exemptions match Q3.
- **The r4 stress barrier is fixed.** The merged `lock_race_tests.rs:398–490`, `:530–556` use a timeout-aware rendezvous and AbortOnPanic; a worker error wakes peers. I inspected that fix; I did not rerun the unchanged Rust stress suite.
- **Core choke point and SPV facts verified:** the listed production Core sites reach TransactionBroadcaster. The pin has a single broadcast-and-acceptance wait holding `client.read()` (`PW/spv/runtime.rs:323–336`); dash-spv subscribes before enqueue but starts its acceptance deadline only afterwards (`client/transactions.rs:85–91`). Local broadcast membership and repeated-txid idempotence are in `sync/mempool/manager.rs:363–377`, `:465–520`, with later rebroadcast at `:677`. PSBT constructs a separate broadcaster. Readiness, the permit/acceptance split and PSBT wiring are **new Q1/P4 work**, not behavior available from the pin. Also, DapiBroadcaster's “one request” is one SDK call with internal retries (`PW/broadcaster.rs:132–149`); deadline enforcement must include those retries.
- **Persistence/recovery facts verified:** Built is tracked before broadcast (`PW/wallet/asset_lock/build.rs:1098–1142`); `queue_asset_lock_changeset` logs and continues on storage error (`PW/wallet/asset_lock/manager.rs:220–235`). The desktop uses Immediate/WAL/NORMAL; SQLite load returns empty unconfirmed outgoing transactions (`PWS/sqlite/persister.rs:1861`). The merge/upsert protect Consumed, with other lifecycle writes last-write-wins (`PWS/sqlite/schema/asset_locks.rs:125–150`). Resume takes claims and the pin refuses cleanup under them; the new override, stored reservation ownership, drop guard, error propagation and load re-reservation must all be implemented in P3. Re-reservation must also install protection that survives key-wallet's reservation expiry, through positive terminal/spend evidence, not merely another expiring token. No current desktop resume call/catch-up was found.
- **SDK facts verified:** StateTransition broadcast is the common send path and precedes response waiting; retries use the same serialized request. Default request retries are three, accounted across lower-level retries (`SDK/sdk.rs:89–95`, `SDK/sync.rs:89–200`); DPNS imposes its smaller budget. A higher user_fee_increase changes signed bytes (`PW/wallet/asset_lock/orchestration.rs:353–410`); deterministic identity signing supports identical-byte repeats where the other inputs also match. Shielded persisted redrives remain a 1.1 registered-artifact requirement. SdkBuilder has no host request-executor injection; `Sdk::execute` dispatches to its private implementation (`sdk.rs:309`, `:778–789`). Thus the rs-sdk hook is a real prerequisite, not replaceable by wrapping the platform-wallet broadcaster alone.
- **Q1 status:** neither pinned library provides DispatchFence/DispatchScope, registration/abandon integration, deadline clamping, re-reservation or proof-wait notifications. P1/P2 can proceed against fakes after design closure, but library-driven Lock-to-cancel cannot be claimed until P3/P4 carry the platform changes. Finding 4 expands the required upstream behavior. I did not open a PR or infer pasta's approval.

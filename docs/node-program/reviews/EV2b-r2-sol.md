# EV2b round 2 — checked DML block differential

**Verdict: CHANGES REQUIRED (verification gate; no confirmed DML implementation mismatch).** Reviewed rust-dashcore `54f146358` and the pinned Core shim `f822bbcd74` against Core v24.0.0-rc.3. Round-1 finding 2 remains open: the oracle reaches Core's checked layer, but the differential does not compare that layer. ## Findings

1. **Major — Checked rejection parity is still untested.** `node-l1/src/dml_block.rs:143-155` returns `OutOfDomain` as soon as Core reports `DmlStage::Check`, before running Rust or comparing the rejection class, reason, payee or effects. This is broader than the shim's argument/context refusals: the shim returns an actual block verdict here. Core's pinned `src/test/oracle/oracle.cpp:3523-3532` calls `DmlBlockCheckLoop` first, and `src/evo/specialtxman.cpp:1107-1115,1323-1355` rejects a pre-V24 ProUpServ with a V24-only payload version at that layer as `bad-protx-version`. A missing or wrong Rust EV1 check, or an orchestration path that lets that transaction reach the DML builder, is invisible to this target. The generated baseline included two `bad-protx-version` check rejections, both skipped. Disabling Rust's unknown-provider-version guard at `dash-dml/src/build/mod.rs:579-582` left the generated checked-block test passing with exactly the same 44 accepts and 556 skips. **Fix:** when EV1/CH7a is available, execute its check on the same block and compare Core's check-layer stage, class and reason before deciding to build. Until then, report this as post-check DML parity and keep finding 2 open.

2. **Major — The generated corpus does not exercise post-check rejection ordering.** `node-l1/src/dml_apply/input.rs:55-56,441-449,738-790` reuses the raw-helper generator, caps additions at 16 transactions, and usually emits payloads that Core's check loop rejects before DML build. `node-l1/tests/l1_dml_block.rs:223-240` requires only 30 accepted inputs and verifies that skips equal check rejections; it does not require generated build or process rejections. In the baseline, 600 generated inputs gave 44 `BothAccept`, 556 check skips and **zero** `BothReject`; 348 public seeds gave 48 accepts, 300 check skips and **zero** `BothReject`. Six post-check rejections came only from the fixed crafted cases. A wrong reason or precedence in a same-block registration/update/replacement path absent from those cases can survive the fuzz target. **Fix:** add checked-mode generation that preserves valid input hashes, required share signatures and QcTx heights while varying DML conflicts and 0–50 transaction sequences; assert stage-specific generated rejection coverage and complete the prescribed profile campaign.

## Checked path and effects assessment

- The pinned shim does run Core's `CheckSpecialTxInner` loop, followed by `BuildNewListFromBlock` and `CDeterministicMNManager::ProcessBlock` when DIP3 is active (`src/test/oracle/oracle.cpp:3387-3415,3521-3566`). Its check loop is the DML-relevant portion of `ProcessSpecialTxsInBlock`; the header explicitly excludes the CbTx merkle root, credit pool, quorum block processor and later managers. The pre-V24 version failure is at Core's check layer with Core's own reason.
- Past that layer, `node-l1/src/dml_block.rs:155-192` treats Rust reader/store faults and out-of-domain exceptions as divergences; it compares payee, build/process stage, result class and reason, accepted canonical list bytes, decoded-and-canonicalized `dmn_D4` diff, optional `dmn_S3` snapshot and platform-ban resets. The testnet 7,300 case reaches `ProcessBlock`'s `bad-dip3-enf-block` rejection. Planting a different Rust reason in `dash-dml/src/process.rs:20` made that test fail with `Divergence(reason)`. The 576th-height test compares snapshot rows. I found no mismatch on these compared paths.
- The immediate persistent DML rows and platform-ban resets are covered on accepted compared blocks. Canonical bytes include PoSe fields and the registration counter; payee is separately compared. Core's in-memory `mnUniquePropertyMap` is part of full list equality (`src/evo/deterministicmns.h:616-624`) but is absent from canonical and disk list serialization and from this ABI's effects. A map-only error could affect the next block's duplicate-key verdict while this one-block comparison passes. `MNListUpdates` is not separately exported; Rust's `change` aliases the same old/new/diff values used for the compared row (`dash-dml/src/process.rs:90-104`). A checked multi-block sequence or an explicit unique-property projection is needed to cover hot-list behavior. This is a residual limit, not a demonstrated mismatch.
- ABI 21 adds only `oracle_dml_block_effects` to ABI 17's surface; the old `oracle_dml_block` uses the shared body and its signature remains intact. The installed plain and fuzz archive SHA-256 values match `dash-oracle-sys/pins.txt`. ABI 18–20's train merge numbering is outside this review.

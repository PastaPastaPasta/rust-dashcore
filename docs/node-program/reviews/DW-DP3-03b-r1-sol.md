# DP3-03b code review (Sol r1)

**Verdict: CHANGES REQUIRED**

1. **High — Stored requests can reveal the username after the user turns the toggle off.** `apps/desktop/src/screens/settings/Privacy.tsx:36` immediately changes only the setting query; it does not clear or mask cached `receiveRequests`. `apps/desktop/src/screens/Receive.tsx:269` renders those cached rows, and `Receive.tsx:305` passes an unmodified row to the sheet, which displays and copies its `user=` URI. Reproduce by creating a named request, holding `set_username_in_requests`, unchecking the box, returning to Receive, and opening the stored request before the write answers. A fresh request read can also return named rows while that write is pending. The QR-only pending-save test misses this. Gate request display/copy and creation on the effective off state, including pending off and read errors; sanitize or withhold old rows until an off-safe read completes, and test the held-write path.

2. **High — An engine request read can finish with `user=` after opt-out commits.** `rust/crates/dw-engine/src/receive.rs:435` checks the setting before the separate blocking `main_username` read. If `set_username_in_requests(false)` commits during that read, `username_of` still returns the name; `create_receive_request` and `receive_requests` then format a named URI. The existing engine test runs these calls sequentially, so it does not cover the interleaving. Serialize setting writes with username resolution/URI production, or otherwise verify the setting again at the point the URI is returned; add a synchronized race test.

3. **Medium — A pending old-wallet save can change a removed and re-imported wallet.** `rust/crates/dw-engine/src/receive.rs:468` checks wallet existence, then awaits an appdb job without holding `wallet_lifecycle`. Removal and re-import can complete while that job is queued; the old `false` write can then land after `readmit_wallet`, so the re-import starts off despite D17's default-on promise. Hold the wallet lifecycle across the existence check and setting write, and test a paused write spanning removal and re-import.

4. **Medium — The Receive QR accepts a name before the setting is known.** `apps/desktop/src/screens/Receive.tsx:55` leaves `included` undefined while the setting query is pending, but line 60 only suppresses the name for literal `false`. A username reply or cached name can therefore build a `user=` link before the setting has answered, contrary to D8's fail-closed rule. Require `included === true` before using any current or held name; add a test that holds the setting read while the username is available.

**Other checks:** The setting is stored in the wallet scope of the network's `app.sqlite`; removal clears that scope, the m1 §2.6 text matches the two new calls, and `dw-ffi` is untouched. With no username, the real engine and UI use dw-uri's `format_bitcoin_uri` path. The eight-decimal amount mismatch is confined to the TypeScript fixture; real request output uses eight decimals. The Rust URI test proves the plain URI and stored-request toggle sequentially. The restart test proves persistence, wallet isolation, and removal/re-import of the boolean, without a DashPay identity or URI claim. The Playwright tests cover QR and settled stored requests but miss findings 1–4. Four available mutant logs (D7, D8, D18, L1) each show the intended test failing; I found no fifth mutant artifact to assess.

The only changed baseline files are light and dark `settings-general`. The two D19 failures are plausible load flakes in untouched timing tests (one has a 200 ms worker bound); the design note reports each passing 3/3 alone, but I did not find those standalone rerun logs.

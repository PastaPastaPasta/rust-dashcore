## Findings

### F1 — major: BanList dump ordering can lose a completed mutation on disk

`dash-p2p/src/netcore.rs:639` (`dump_bans`), `dash-p2p/src/ban.rs:139` (`take_dirty`) and `:146` (`serialize`). The serialized snapshot and dirty-bit clear are separate critical sections, and saves have no dump mutex. A mutation between `serialize` and `take_dirty` can be cleared without being represented by the saved image. Independently, an earlier save may finish after a later save and replace the newer banlist with an older snapshot. Successful `ban`/`unban`/`clear_banned` operations can therefore disappear or reappear after restart with no dirty bit to cause repair. Core's `BanMan::DumpBanlist` (`banman.cpp:47`) serializes dumps with `dump_mutex` and takes its snapshot plus clears dirty together under `m_banned_mutex`.

Suggested fix: provide one atomic swept snapshot-and-dirty operation on BanList and serialize all dump/save attempts, retaining dirty on write failure. Add a deterministic barrier-controlled store test that finishes two saves in the opposite order, plus a mutation-between-snapshot-and-clear test. A scratch probe of the former schedule leaves two live bans but only one persisted ban after both calls complete; a subsequent `dump()` still persists only one because the dirty bit was cleared.

### F2 — major: the decoder/model gate misses Core-accepted boolean alternates

`node-fuzz/src/models/p2p_decode_model.rs:45` (`LENIENT`) and `:230` (error path); `dash-p2p/src/policy.rs:511` (`sendcmpct` row) and `:828` (`read`) expose the pinned base-sdk decoder. The pinned `pkgs/p2p_core/src/msg/compact.rs:38` rejects any high-bandwidth boolean other than 0/1 with `NonCanonicalBool`. Core reads a C++ bool (`net_processing.cpp:4274`, `serialize.h:239`), accepting every nonzero byte as true; P2a §3.2.3 explicitly requires `CoreBool` here. `sendcmpct` is absent from LENIENT; more critically, the model's rejection path treats this disagreement as an acceptable Throw, so a passing run supplies no evidence of Core-exact acceptance. This is a dependency/decode-boundary gap, not a claim that the not-yet-implemented P2a-core handler was exercised.

Suggested fix: implement required Core leniency at the approved node/shared decode boundary, enumerate the accepted alternates by field, and make the model compare the accepted/rejected verdict with an independent Core-derived oracle or a pinned acceptance matrix. Merely adding `sendcmpct` to LENIENT does not fix a decoder that rejects it. A scratch probe using high-bandwidth flags 0, 1, 2 and 255 with compact-block version 1 confirms the first two decode, the last two fail, and the decode model passes all four. A second probe confirms the same acceptance gap directly through SB6's `policy::read<SendCmpct>`.

The audit also confirms `getqrinfo`'s `extra_share` uses `decode_flag` (`pkgs/p2p_core/src/msg/rotation.rs:94`), whereas tagged Core's `CGetQuorumRotationInfo` reads a bool (`llmq/snapshot.h:111`). An empty base-hash vector, 32-byte request hash and flag 2/255 is accepted by Core's read but rejected by `policy::read<GetQrInfo>`; the decode model still passes. SB6's row maps that decode error to `+100 malformed getqrinfo`, so an eventual processor using this boundary would punish a Core-accepted alternate. `qrinfo` and `mnlistdiff` contain other strict flags; their Core full-node rows read nothing, and their SPV implications need separate dependency review.

### F3 — major: D18's stable eviction sort selects different peers for ordinary ties

`dash-p2p/src/inbound.rs:62` (`erase_last_k`), and `docs/node-program/designs/SB6-dash-p2p-notes.md:24` (D18). Core's `EraseLastKElements` uses `std::sort` (`node/eviction.cpp:82`); the port uses a stable sort. Equal minimum pings are normal, including `i64::MAX` before any successful pong. The difference changes which peers survive protection and ultimately which peer is disconnected. D18 explicitly defers this, but it is an observable parity gap under the current SB6 goal; porting Core's invariant tests does not establish equivalent decisions.

A scratch comparison compiled the tagged Core eviction functions with libstdc++ and equivalent candidate structs. With candidates in id order, connected time `1700000000 + id`, minimum ping `INT64_MAX`, no block/tx times, relay enabled, relevant services disabled, IPv4 and keyed group `id % 8`, Core evicts ids 30/38/62 for 32/40/64 candidates; Rust evicts 28/36/61. Both choose 99 for 100 candidates. The other flags are false and all candidates are inbound.

Suggested fix: make tie handling match the selected Core reference implementation, or obtain an explicit program-level parity exception. Add a differential eviction target with equal ping/group/time cases; changing to Rust's unstable sort alone does not establish libstdc++ tie-order equality.

### F4 — major: shutdown can return before a sweep-owned peer is finalized

`dash-p2p/src/netcore.rs:499` (untracked sweep task), `:974` (`shutdown`) and `:1083` (sweep removes peers before terminal cleanup). Taking peers out of the table prevents double finalization, but an empty table does not mean removal is complete. If the sweep removes a peer and is preempted during `remove_peer`, `shutdown` sees an empty table and returns while socket/grant/count/finalizer work may remain. The host has no sweep handle or completion barrier to join. Core joins its networking threads before `StopNodes`; D31's host-owned dial-loop join cannot join SB6's internally spawned sweep.

A barrier-controlled scratch probe pauses the sweep inside `NetEvents::finalize`, observes an empty peer table, and confirms `shutdown().await` returns before that finalizer completes. The barrier makes the schedule deterministic; scheduler preemption can create the same interval with a short callback. A host may now tear down the processor state that terminal finalization is supposed to clean. The current sim asserts exactly-once finalization after shutdown but does not force this interleaving. P2a §2.2.1's shutdown order requires terminal cleanup before stopping V/the dispatcher.

Suggested fix: retain task completion handles or a shutdown barrier, stop and join the sweep and peer I/O tasks, and wait for all removal/finalizer work before returning. Keep finalizers outside the table lock and add a deterministic shutdown/removal interleaving test.

## New findings

1. **Major — `.github/workflows/tauri-selftest.yml:134`, `rust/crates/dw-app/src/api/app.rs:88-93` — passphrase file permissions are not handled.** The workflow creates `$RUNNER_TEMP/passphrase` with a plain shell redirection and never sets a restrictive umask, mode or ACL. On a host with umask 022 and a traversable temp directory, the file is mode 0644; I reproduced that mode with the same `printf > file` pattern in scratch. `selftest_unlock` reads any supplied file without checking its permissions. A second local user can read the vault passphrase during the run. Create it with owner-only access (`umask 077` before creation and `chmod 600` on POSIX; equivalent restricted ACL on Windows), reject an unsafe file where the platform exposes permissions, and test that refusal. The bytes do stay in Rust `Zeroizing` values and only `selftestUnlock: bool` reaches the renderer; no passphrase logging path was found.

2. **Major — `apps/desktop/vite.config.ts:18-34`, `apps/desktop/scripts/check-bundle.mjs:15-18` — an unmarked relocated fixture module passes the production guard.** A later refactor can move a fixture module into a shared directory and drop the first comment. The plugin recognizes only the original path, the marker comment, and Tauri mocks; the post-build scanner recognizes only the index sentinel and mock IPC string. The scratch negative control above copied the real wallet fixture without its marker, dynamically imported it, and got a successful production build with real fixture rows in a separate JS chunk. Re-exports and dynamic imports of the *original* module were rejected, so this is specifically the unmarked-copy gap. Establish a production module allowlist or a mechanically enforced fixture-only boundary that covers relocated modules, add a negative control for an unmarked copy, and narrow the “no fixture code” claim until that control works.

3. **Major — `.github/workflows/tauri-selftest.yml:109,157`, `rust/crates/dw-app/src/launch.rs:126-135`, `rust/crates/dw-app/capabilities/app.json:15-19` — the shipped release build can enable selftest IPC.** The workflow builds the release binary (`pnpm tauri build --no-bundle`) and turns on `--selftest` at launch. The same release binary and main-window capability include `selftest_unlock` and `ipc_bench_rows`; `selftest_path()` correctly refuses them in an ordinary launch, but passing `--selftest <path>` enables both, and adding `--selftest-passphrase-file <path>` enables the Rust-side unlock. Thus the requested “production build cannot enable any of it” invariant is false. If that invariant is required, gate these commands and flags behind a CI-only build feature/configuration that is excluded from packaged releases; run the release selftest against that dedicated build and test that the shipping binary rejects the flags. This is a build-surface issue, not evidence that the normal renderer receives the passphrase.

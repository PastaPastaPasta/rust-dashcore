## Finding

### R2-M1 — major: the required Phase F differential evidence is still absent, and D14 understates the remaining comparison work

**Location:** `docs/node-program/designs/P2a-net-notes.md:20`; acceptance at PLAN `:605` and P2a §7.3 F; comparison machinery in `node-l1/src/p2p_node.rs:138-165,267-293,376-384,642-667,895-930`; relay script in `node-l1/src/p2p.rs:290-293,320-382`; registration in `node-l1/src/lib.rs:370-400` and `node-fuzz/targets.toml:330-375`. The `node-l1` files are inherited from P2a-core's merged leg, so this is an **acceptance gate and dependency finding**, not a request to edit that leg in this P2a-net branch.

**Scenario:** a bug that changes which peer receives an `addr` or `addrv2`, what addresses `getaddr` returns, or the relay's next send deadline can pass the present differential suite. None of `diff_p2p_addr`, `diff_p2p_addrv2`, or `diff_p2p_getaddr` exists in the target registry, target manifests, or fuzz target files. The registered `diff_p2p_multi_relay` does run Core and the node, but `left_out` drops **every** `addr`/`addrv2` output before comparing; its `PeerFields` projects neither `m_addrs_to_send` nor `m_addr_processed`, and omits `m_next_addr_send` and `m_next_local_addr_send`. Its `NodeRun` uses `Seams::default()` rather than `NodeAddressRelay`, and does not give `NetCore` the oracle draw stream. Consequently the current multi-relay target does **not** compare `RelayAddress` fanout, queued addresses, reply bytes, or the exponential deadlines it advertises. The script supplies at most 255 arbitrary payload bytes per command, rather than the designed address vectors, network IDs, oversize boundaries, relay states, and AddrMan states (P2a §6.2); even after lifting masks, it would reach substantive address handling sparsely. The oracle `PeerData` already exports the omitted fields (`dash-oracle-sys/src/peer_session.rs:114-125`), and SB6 now exposes `NetConfig::with_rand_source`, so these are actionable comparison gaps rather than a missing oracle ABI.

**Fix:** have the P2a-core session owner seed the node `NetCore` from O1c's draw-log stream, install `NodeAddressRelay`, and compare `addr`/`addrv2` outputs, `m_addrs_to_send`, `m_addr_processed`, both next-send deadlines, and consumed draws. Build and register the three single-command targets with structured valid and invalid address vectors and seeded AddrMan/relay state, then run their required campaigns and the corrected multi-relay gate to the current DEC-184/186 acceptance rule. D14 should name these target and projection changes in addition to its three session-leg steps. Until then, neither the three absent targets nor the current multi-relay target can certify Phase F.

The current registered tests can compare handshake and some intake side effects, not exact address relay or `getaddr` responses. The same session-leg and projection repairs should precede its certification.

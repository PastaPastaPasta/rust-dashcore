**Verdict: CHANGES REQUIRED.** Reviewed `docs/node-program/designs/O2b-diff-chain.md` at `e46de0ded` against the r1 review, the current PLAN and CH1/CH2 designs, and the pinned Dash Core v24.0.0-rc.3 commit `0364ed626ec2eaa518bf1ae4a0566ce638c7fe18`. This is a design and source review; no implementation or fuzz run exists to establish that the proposed witnesses pass.

## Findings

1. **BLOCKER — §§2.6, 5.1, 6.5, 11, 14: the M3 ChainLock census depends on an M4 spork implementation.** M3 requires `bad-prevblk-chainlock`, `bad-chainlock`, `CL_RECORD`/`CL_ENFORCE`, and an active spork-19 transition (§6.5). The Rust `Spork` op and state-driven helper are assigned to SP0 (§§2.6, 5.1), but PLAN schedules SP0 in M4, while O2b-1…4 gate M3 (§11 and PLAN M3 exit 4). Core's default spork 19 is off (`spork.h:69`); `Chainlocks::HasChainLock` and `HasConflictingChainLock` return false while off (`chainlock/chainlock.cpp:49-54,73-79`), and `EnforceBestChainLock` returns immediately (`handler.cpp:273-277`). Thus the required M3 CL reject and enforcement paths cannot be reached with the specified dependencies. **Fix:** either move the needed production SP0 state slice into M3 and add it as an O2b-3 dependency, or explicitly wire M3's CH1 `StaticSporks` through `NodeSut`, define its restart semantics, and state that the M3 CL gate checks production validation under a test spork provider while SP0 persistence parity gates M4. Update the M3 census and PLAN dependencies to match the chosen route.

2. **MAJOR — §§2.3 D34, 4.6, 14 SP0: filtering only post-`KILL` spork state cannot preserve step parity.** SP0 option (ii) persists a received spork while Core's killed restart reverts to its last `sporks.dat`. After `SPORK(19,0) → KILL`, a later `CL_RECORD → CL_ENFORCE` sees Rust with CL enabled and Core with CL disabled. That changes helper A records, replies, index/tip state and events, not merely a spork field. The §4.5 `POST` schema does not actually include a spork-state field to filter. Core's gate is explicit in `chainlock.cpp:33,49-54,73-79` and `handler.cpp:209-220,273-277`. **Fix:** choose SP0's persist-at-clean-shutdown option for inputs whose post-kill suffix is compared. If SP0 must persist on receipt, stop/discard the input at a divergent `KILL` or define a complete alternate comparison regime; do not award its later CL/restart census rows or imply that one named post-state filter is sufficient.

3. **MINOR — §§2.3 D31, 4.4–4.5: `CLEAN` restart loses the flush-count observation.** The design says flush counters are per open and reset on every restart (§2.3), while leg B removes `ChainStateFlushed` from the ordered event plane and compares per-op counts through the post-state `flushes` field (§§4.4–4.5). A `RESTART CLEAN` flush occurs on the old instance; a post-reopen counter is zero, so that op's shutdown flush and its cause are not observed by the stated count rule. Persisted-image equality still checks durability. **Fix:** include an op-local `(full,index-only) by cause` delta captured across teardown/reopen in the step report, separate from the counters since the new open; compare that delta on `CLEAN` and restore steps.

4. **MINOR — §2.3 D31, §12 D31: make the mid-op mirror order explicit.** Rule 2 says *every* Rust flush is mirrored; rule 3 calls a mid-op flush “unmirrored” and adds one `reconcile` flush on each side. The intended construction can work only if each mid-op Rust flush is still mirrored on Core at op end, under its original cause, **then** both sides receive `reconcile`; otherwise the per-cause counts in §4.5 differ on every mid-op case. **Fix:** state that order and assert, in the O2b-1/O2b-3 test, the mid-op Rust count equals Core's labeled mirrors plus one `reconcile` on each side. Keep the separate `reconcile` because Core's late mirror may persist changes Rust's earlier flush did not.

5. **MINOR — §14 CH2-KP: define the kill-parity oracle by the durable phase, not just the last completed flush.** “Recovery lands on the state of the last completed flush” is false for a kill after a split flush has written `head_blocks=[new,old]`: CH2's recovery replays that in-flight transition to `new` (`CH2-coins-flush.md` §3.5 and §4.3), even though its final batch did not complete. An index-only write can also persist new block-index entries without advancing the coins/evodb best-block markers (Core `validation.cpp:3048-3075` versus `:3077-3100`). **Fix:** make CH2-KP derive its expected recovered image from the durable B1/marker, coin sub-batches, final batch and index-only write at each crash point; record the per-cause schedule and compare both the coins/evodb root and index image after recovery.

## Focused checks

**Leg B.** S0p's small cache and fan-out give a plausible route to real Rust `THRESHOLD` and native cache causes; the ≥5% touched-op and named-cause census (§6.5) makes failure to reach them visible. Mirroring *all* Rust causes, suppressing Core's independent size causes, and reconciling both sides after a mid-op flush can make durable images comparable at op boundaries. It does not prove kill-anywhere parity; CH2-KP owns that. Findings 3–5 concern the precise observability and gate wording, not the manager's D31 choice.

**W-P3b.** The revised plant is logically discriminating. In Core v24's `InvalidateBlock`, `to_mark_failed` is the previous, higher disconnected tip when `invalid_walk_tip->pprev == to_mark_failed` is tested (`validation.cpp:3983-3988`), so that conversion cannot run during a downward walk. With the first flush emptying both dirty sets, the planted omission leaves exactly the walked descendants stale on disk. `LoadBlockIndexDB` may add `FAILED_CHILD` (`blockstorage.cpp:321-323`), and `VerifyLoadedChainstate` may reset failures after VerifyDB (`node/chainstate.cpp:436-465`), which is why the pre-load persisted image is essential. O2b-1 and O2b-4 must execute the directed witness both ways as specified.

**W-P3a.** The BIP68 failure is placed inside `ConnectBlock`: `ContextualCheckBlock`'s `IsFinalTx` can pass with `nLockTime=0` (`validation.cpp:4558-4560`), while `SequenceLocks` returns `bad-txns-nonfinal` inside the transaction loop (`:2723-2734`). With `-par=4`, tx 1's failing script can be queued at `:2749-2760`; the normal `control.Wait()` at `:2778` is not reached after tx 2's early return. Build tx 2 from a spendable, mature coin with a relative lock longer than its age so no earlier input check displaces the intended failure. The witness's explicit unplanted reply assertion is appropriate.

**Tie trigger and PLAN splits.** Core's pointer order follows only equal work and equal sequence ID (`blockstorage.cpp:32-48`). The narrowed §2.3 trigger covers the consequential call sites; discarding the triggering op means a real bug that manifests only on a top tie is outside this target's coverage, but the design now declares that exclusion and gives the input no credit. LK1b-s is correctly placed before O2b-5 with CH7a/b, LQ3 and SB8 dependencies; CH1-node-LR is correctly a production startup step after VerifyDB and before `ActivateBestChain`; M4 exit item 2 remains unchanged. SP0's milestone and persistence routes need findings 1–2 resolved before those deltas are implementable as written.

**Verdict summary:** CHANGES REQUIRED. The revised P3a/P3b witnesses, tie handling, exact per-op UTXO check, production load reset, template hook, symbolic ABI plan, and M4 IS split address the substantive r1 objections. The M3 ChainLock gate still lacks an available spork provider, and SP0's persist-on-receipt option would invalidate comparisons after a killed restart. Specify those routes and tighten the flush-count and CH2-KP rules before treating this design as an executable gate.

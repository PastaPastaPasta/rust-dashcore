# DW DP5-01 security review — Sol round 2

Reviewed detached `e5791ceea433a5c6130803c73000d55d84e72595`, the Sol round-1 report, D26–D31 and the changes since `a08c2ce3`. No branch files were changed. Only planted test secrets were used.

## Verdict

**ACCEPT WITH NITS.** No merge-blocking finding in the round-1 fixes. The remaining exposure after an interrupted or failed seal is real but is now explicit in the API and retried; the renderer has not yet displayed that state.

## Findings and residual failure scenarios

1. **Low — unsealed-link status has no user-visible consumer (F9).** `rust/crates/dw-vault/src/vault.rs:811-838` commits the vault before resealing the old plaintext links; a write failure returns successful creation with `unsealed_links=true`. `rust/crates/dw-app/src/dto/mod.rs:391-418` forwards it as optional `unsealedLinks`, but only the generated type uses that name (`apps/desktop/src/api/generated/LockStatus.ts:29`); the link offer checks only `stashedLinks()` (`apps/desktop/src/app/savedLinksOffer.ts:22-32`). Concrete case: a pre-vault invitation exists and the stash directory becomes read-only during creation, as `a_failed_seal_keeps_the_entry_and_is_reported_until_sealed` tests. The invitation remains in a 0600 plaintext file while the user sees successful onboarding and no warning. The next key-bearing call retries, and the flag remains queryable; showing it in the UI is a follow-up, not a merge blocker under D26's best-effort seal contract.

2. **Low — expiration is still trigger-driven for a continuously open idle process.** `rust/crates/dw-vault/src/vault.rs:550-553` sweeps at open, `:920-921` at unlock, and `rust/crates/dw-vault/src/vault/links.rs:619-665` on a stash read/write. Concrete case: a link is saved before a vault exists and the app stays open without another stash call for 31 days; no timer removes its plaintext file at day 30. The next open, unlock or stash call removes it. D29 should say that idle-open retention remains possible, or a periodic sweep should be added if physical deletion at TTL is required. This does not change D8's read-time expiry semantics.

3. **Documentation nit — an oversized file can contain former stash plaintext after local tampering.** `rust/crates/dw-vault/src/vault/links.rs:508-510,651-655` rejects and unlinks a file over 16 KiB; `:413-415` deliberately skips zeroing. Concrete case: a local writer pads a genuine pre-vault 0600 entry past 16 KiB, then a sweep unlinks it without overwriting its original secret bytes. This writer is outside D19's stated model, and D18 already calls zeroing best effort. D27's claim that every oversized file “holds none of the stash's plaintext” is too absolute; describe it as a file the stash could not have produced at that size.

## Round-1 closure

- **H1(a), status and retry: closed within D26.** `create` and `unlock` return the post-reseal flag (`vault.rs:838,921`), `status()` reads it (`:684-717`), and recovery updates it before returning (`:2631-2634`). `links.rs:758-816` scans the files after reseal/open, and `:938-942,1063-1068` refreshes it on stash operations. A crash after the vault commit and before reseal leaves plaintext until the next open or unlock; with no valid `stash.pub`, open reports it and unlock seals it. A crash after rename but before the old inode is zeroed can leave recoverable historical blocks, as D18 admits. Finding 1 covers the UI gap.
- **H1(b), fail closed: closed.** `links.rs:1013-1020` requires the data key or a valid `stash.pub` before cap eviction (`:1021-1033`); `:1045-1049` writes `plain` only with no vault. A locked vault with no public key returns `Locked`, leaving existing entries untouched.
- **H1(c), stale temporary names: closed for the one-process, one-session app path.** `links.rs:479-495` scrubs and removes a stale `.tmp` before `create_new`; `:634-640` does it on sweeps. `remove_any` uses `symlink_metadata` and does not follow a symlink (`:431-445`). A concurrent *different* `Vault` instance or local writer could replace a temporary name between steps; the desktop engine serializes one session per network (`rust/crates/dw-engine/src/engine.rs:123-136`), and `create_new` refuses a name taken after cleanup instead of following it.
- **M2, oversized allocation: closed.** `links.rs:413-421` copies at most 16 KiB of zeros through a fixed buffer; `:508-515` rejects a larger entry before reading it. Sweep, replacement, stale-temporary cleanup and destroy all use the bounded scrub. The local-writer size-check/read race is covered by the optional read hardening below.
- **M3, multiline stderr leak: closed.** `rust/crates/dw-app/src/launch.rs:138-149,211-213` omits unknown-option values and nonplain names; `rust/crates/dw-app/src/lib.rs:208-215` redacts the data-directory error. `rust/crates/dw-uri/src/redact.rs:158-174` cuts the entire event after its first recognized link. The round-1 planted `--bad=dashpay://invite?pk=cFirst\ncSuffix` cannot print the suffix through the launch error now.
- **Expiry sweep: partially improved, with finding 2's idle-open limit.** `Vault::open` and every successful unlock sweep expired entries and temporary names; a process that never calls either again still waits for the next stash call.

## New attack surface and follow-up rulings

- **`stash.pub`: accepted scope boundary.** The only vault binding of a *stored* public key is the vault id comparison in `links.rs:581-592`; the file is not authenticated. An actor able to write the private stash directory can replace the public key while leaving the vault id, so a locked intake seals a later link to the actor's key. Unlock rewrites the public key from the DEK and drops wrong-key entries (`:700-744`), but cannot recover that leaked link. The same actor can forge or replay entries, including plaintext ones, as D19 says. This is an active local disk writer, excluded by D19; the 0700 directory excludes other Unix users. A replayed payment only opens a prefilled pay form (`apps/desktop/src/app/shellBridge.ts:119-122`), and a saved item requires an Open action (`apps/desktop/src/screens/SavedLinks.tsx:39-45`); no payment or invitation claim happens automatically. D19's reference to “E0-08 §threats” could not be located in this repository, so its own explicit scope statement should be treated as the source of this exclusion.
- **Oversized unlink: accepted with finding 3's wording correction.** No stash-produced entry is that large; rejecting before `std::fs::read` prevents the round-1 memory-exhaustion path. Overwriting an attacker-sized sparse file would trade the memory bug for unbounded I/O. A local writer can pad a real plaintext file; that does not create an in-model confidentiality guarantee because overwrites are best effort even for small files.
- **Temporary-file clearing race: no blocker.** The stash mutex serializes normal calls on one `Vault` (`links.rs:526-530`), and the desktop engine has one network session per engine. A different handle sharing the same directory can race a sweep against an active temporary write, causing the write to fail. A local writer can also replace `.tmp` after the writer closes it but before rename, causing rename to install the writer's file or symlink under `.dwl`; rename does not follow the symlink, and this actor can already modify `.dwl` directly. Both races are outside the desktop's single-session, private-directory path.
- **F8 parser temporaries: follow-up.** `rust/crates/dw-uri/src/deeplink.rs:108-120,493-500` and `rust/crates/dw-uri/src/ext.rs:140-155` leave decoded/copied values in freed heap memory. A crafted `dash:?invite=cPlanted` leaves a copy even when not stashed, visible to a crash dump or process-memory reader. This is defense in depth for an attacker who can already inspect process memory, with no observed log/IPC path; it should not block DP5-01.
- **Skip zeroing multiply linked files: follow-up.** `links.rs:425-428,458-464` can zero an unrelated small file if a local writer hard-links it under an entry name. That writer can already modify the private directory and own linked file; hard-link count checking is useful damage containment, not a merge gate.
- **`O_NOFOLLOW` plus a read-size cap: follow-up.** `links.rs:508-513` and `:584-588` check `symlink_metadata` and then open by path. A local writer could swap a symlink or grow a file between check and read, causing an unintended read or allocation. The 0700 directory and desktop singleton keep this outside the stated threat model; descriptor-based reads would still be a sound hardening.

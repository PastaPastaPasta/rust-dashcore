# CH7 implementation notes

Decisions taken while implementing CH7 (`CH7-evo-llmq-chainstate.md`, APPROVED rev3.2, DEC-531).
The rows continue the design's numbering, which ends at D22. Each settles a point the design leaves
open or a shape the landed code forced. Core lines are at **375c64d2317**, with the design's keys
(`v:N` = `src/validation.cpp`, `bp:N` = `src/llmq/blockprocessor.cpp`, `snap:N` =
`src/llmq/snapshot.cpp`) plus `edbh:N` = `src/evo/evodb.h`, `dbw:N` = `src/dbwrapper.h` and
`timer:N` = `src/logging/timer.h`.

## CH7a-1: the store and the layer

| ID | Decision | Reason |
|---|---|---|
| D23 | **The mined rows' layout extends A1 §2.9 by the mining block.** `llmq_mined`: key `u8 type ‖ quorumHash`, value the commitment (base-sdk's `BaseCodec`, Core's serialization) ‖ the mining block's hash ‖ its height as `u32` LE; Core's value is the commitment and the hash (`bp:473`). `llmq_mined_h`: key `u8 type ‖ u8 family ‖ BE16 qIdx ‖ BE32(!minedHeight)`, value the base height as `u32` LE ‖ the mining block's hash; Core's value is the base height alone (`bp:479-483`), and A1's text had "base hash". The family byte (0 non-rotated with qIdx 0, 1 rotated) stands in for Core's two prefixes `q_mcih` and `q_mcihi` (`bp:308-320`), so a rotated quorum 0 and the non-rotated index of one type never share a key. The quorum index is a BE16 here; Core's key widens it to `int` (`int{qc.quorumIndex}`, `bp:316`, `:480`), a 4-byte LE `int32`, which CH6b translates. Reads go by one index's prefix, so the width changes no answer. In memory the layer keeps both column families in one ordered map, its key a tag byte (0 `llmq_mined`, 1 `llmq_mined_h`) then the column family's key; the tag never reaches the DB. A height-index key read back in any other length is a store fault (D5), not a panic. | `MinedCommitmentReader` resolves a row through the ancestry of the block it names (dash-evo's contract, which `MemEvoView` meets the same way). Core's reader needs no check, as it holds only the active chain's rows under `cs_main`; the node's view is pinned while V moves on, so a row must name its mining block. |
| D24 | **The by-hash rows.** `mn_diff`, `mn_snapshot` are dash-dml's record envelopes (`dash_dml::codec`); `mnhf` is Core's `std::map<uint8_t, int>` serialization: a compact size, then each bit and its height as `i32` LE, bits strictly increasing and below `VERSIONBITS_NUM_BITS` (A1's text had `u32`). Credit data (D10) sits in `credit_pool` under `hash ‖ 'd'`, two `i64` LE (the CbTx balance, the unlocked amount). The pool row is BL-259's codec: a tag, then `0` and Core's `CCreditPool` serialization for a pool, or one of the constructor's errors (EV3 D8): `1` previous locked, `2` previous indexes, `3` duplicated index, `4` negative limit with its `i64` LE, `5` unlock data with its reason (`0` payload, `1` txout out of range, `2` overflow). `llmq_snapshot` keeps A1's key `u8 type ‖ cycleBaseHash`, where Core keys by `SerializeHash(pair(type, hash))` (`snap:322`); the value is Core's `CQuorumSnapshot` serialization with the bit set's padding bits zero. Every decoder is strict: one encoding per value, nothing after it, and a refusal is a store fault (D5). | The store is the node's, not Core's evodb (D10; CH6b translates). Storing every pool error lets a child block read the exception Core would rethrow. |
| D25 | **Range reads seek** (D22's O(k + log n)). `dash_kv::KvRead` gains a provided `iter_prefix_from(cf, prefix, start)`: the prefix's keys from `start` on, in order. The default skips keys below `start`; `MemoryEngine`, its snapshot, `RocksEngine` and its snapshot override it with a seek (`IteratorMode::From`), and the wrappers forward it: `GuardedEngine`/`GuardedSnapshot`, `ProbeEngine` and its snapshot, dash-kv's `LatchedEngine` and its snapshot, and dashd-node's test engines `SharedMemory` and `WalFault`. dash-kv's `FaultyEngine` (the CRASH model's) keeps the default skip-while: each scan is one fingerprinted trace op, which a seek would split, and its results are the same. The contract suite gains `prefix_seek`, so every engine (memory, RocksDB, SQLite's default) is checked against it. `EvoReadView`'s `llmq_mined_h` read merges three ordered sources from the same start: the active index, the frozen one and the DB snapshot, the upper level winning a key and its tombstone hiding the rows below. | Core seeks its iterator to the first inverted height (`dbw:172`; `bp:736`, `:780`). Without a seek, a read at a low height walks every newer row. |
| D26 | **`EvoWindow::release`.** CH2's window trait gains `release(&mut self)`, which the controller calls when W reports the full flush in flight released (`report.coins` present), in both its tip and no-tip service paths; `NoEvo` and CRASH's stub do nothing. `EvoLayer::take` freezes the active index (an O(1) clone) and starts an empty one, and the frozen index stays readable until `release` drops it. A take with a frozen index still held is a bug (debug assertion): CH2 freezes one window at a time. | D22 keeps the frozen index readable until B1 is durable; only W knows when, and an explicit call keeps that fact out of reference counts. |
| D27 | **A window's evo tip.** The tip CH2's freeze check (`flush/control.rs`, `check_pair`) compares is the layer's last committed evo tip, kept across takes and releases (D37); a layer with neither a commit nor a durable tip to resume from has `None`, which the check accepts as it does `NoEvo`'s. A window with no commit since the last take has no `evo_tip` of its own; B1 still writes `meta.evo_tip = new` (`flush/machine.rs`), which the freeze check made equal to the last committed tip. The node's delta names its evo tip (D40). | The durable `meta.evo_tip` is the read of last resort (D7). |
| D28 | **The write checks are Core's `WriteDerived`.** A commit encodes the delta's rows, checks every by-hash row and every `llmq_mined` row against the active index, the frozen one and the DB in that order (the first level that holds the key answers; a tombstone answers "absent"), and only then merges. An equal row is not rewritten; a differing one fails the whole commit with `StoreError::Inconsistent` and leaves the layer unchanged. `llmq_mined_h` is a plain write. A disconnect's `MinedErase` tombstones both of its rows; a delta whose erase names another block's height, or that both mines and erases, is refused as `Inconsistent` before anything merges. | `WriteDerived` reads through its transaction to the DB and refuses a differing payload (`edbh:159-205`); the caller aborts the node (`bp:470-476`). The index row is Core's plain `Write` (`bp:479-483`). |
| D29 | **`EFFECT_CFS` is `["llmq_snapshot"]`** (Q1, DEC-517). The mined rows are written in B1 with `meta.evo_tip`, so a chainstate with no tip but mined rows is corruption, which the recovery test now asserts for both column families. CRASH's model kept its independent effect in `llmq_mined`; it moves to `llmq_snapshot` under keys `i:<height>`, the model's `LostEffect` fault deleting those keys only. The no-tip load now reads both mined column families, so its chainstate reads are 0–17 and the planted coin-read fault of FA7 and X16 (`crash_planted.rs`, the X16a/X16b repros) moves from read 16 to 18. | DEC-202's exception covers the effect rows alone. |
| D30 | **The D20 pair follows the window's type.** `StateDelta` gains `const EVO: bool = false`; `EvoWindowDelta` sets it. When it is set, B1's durable write (`engine.write(b, Commit::Durable)` or `write_final`) runs inside "FlushStateToDisk: write evodb cache to disk started" / "… completed (%.2fs)", logged in category ALL (`v:3164-3169`; `timer:38-47`). The node keeps `NoEvo` (`()`) until `NodeEvo` is wired, so it prints no pair before then. | A `()` window writes no evo state, and the pair would time nothing; Core always has an evodb. |
| D31 | **`EvoReadView` holds the ancestry, not yet `at`.** The view pins the two index clones and a DB snapshot and resolves blocks through a `ChainAncestry`; the `at` field and `ChainQuery::evo_view` (D17) come with the slice that adds the query route, as CH7a-1 changes no CH3 interface. So does D22's pending-delta level (an attempt's own delta, read before the active index), which §4.1.2's `QcBinding` needs: CH7a-2 adds it with the attempt. `mined_index` caps its height at the lower of its argument and the chain end, returns nothing for a cap or limit of 0, stops at height 0, and keeps only rows whose mining block is an ancestor of the chain end. | §8: CH7a-1 adds store and view code only. |
| D32 | **dash-dml's delta and its erratum.** `EvoDelta` gains `erased_mined: Vec<MinedErase>` and `evo_tip: Option<BlockHash>` (§4.1.4, D1). `MinedErase` holds the semantic fields only (type, quorum hash, mined height, rotation index); the codec derives both keys, where §4.1.4's sketch stored them. The store docs now say that list, pool and MNHF rows are never erased and that mined rows are erased on undo; `MemEvoStore` keeps them and its ancestry reads hide them. | One source for the key layout (D23). |
| D33 | **The differential compares the active chain's mined reads.** The `MemEvoStore` differential (memory and RocksDB engines; seeded connects, reconnects of stale children, disconnects, two-step flushes and snapshot effects) compares every `DmlReader`, `MinedCommitmentReader` and `EvoStore` read at blocks on the active chain. `MemEvoStore` keeps a disconnected block's mined rows, which no read on the active chain reaches; the node erases them (Q1). | The two stores differ only in rows Core's reader cannot reach either. |
| D34 | **`evo-index-depth`** (§7.1) is `dashd-chainstate/benches/evo_index_depth.rs`, run by `contrib/node/evo-index-depth.sh`: blocks through `RocksEvoStore::commit` until the active index holds 1,000 or 100,000 mined entries, every eighth block undone (tombstones), then rounds of an `llmq_mined` point read, a credit-data point read and an `llmq_mined_h` range read of up to 8 entries. `instructions:u` per round is (a run with R rounds − a run with 0) / R, each the median of 3 fresh processes. Result at 9aec7fc1a (20,000 rounds, load about 120): 3,091 instructions per round at 1,000 entries (125 blocks, 195,265 index bytes), 3,976 at 100,000 (12,500 blocks, 19,432,012 bytes), ratio 1.29: PASS. About 9 of a round's at most 10 rows are found at both sizes. The commitments are null-bodied version-1 commitments with zero key and signature bytes, which the base-sdk pin f27bc4f5 decodes. It is no `workloads.toml` row. It times `EvoIndex`'s own reads (§7.1's letter), not the view's three-way merge over the frozen index and the DB. | A growth guard, not a Core-parity row (D22). |
| D35 | **An evo-critical freeze waits for its release.** After a freeze, the controller waits for W's release when the evo window still reports at least `EVO_CRITICAL_BYTES`, beside CH2c D32's wait for a coins cache still critical (`flush/control.rs`). D18 counts the frozen index until its release, so without the wait the next block's IF_NEEDED check would see the same bytes, stall V on the flight (`WaitThenFreeze`) and then freeze a second, nearly empty window. The controller tests now run with a counting evo window that checks each take is released once, after B1 and never for an index-only write, on the tip and the no-tip paths. | Core's evo-critical flush is synchronous (`v:3095`, `:3164-3169`): its evodb usage is zero after it. Found by the CH7a-1 review pass; it could not show under `NoEvo`, whose bytes are 0. |
| D36 | **`cfg(fuzzing)` is off in rdashd's production build** (DEC-546). dashd-chainstate's evo store brings dash-dml into rdashd's production closure, and dash-dml gates code on `not(fuzzing)` (BL-370, `unique.rs`). The log-line ratchet (`dashd-node/tests/asserted_log_lines.rs`) resolves every `cfg` of that closure, so `fuzzing` joins its `OFF` names, and `cfg_predicates` now checks `not(fuzzing)` holds instead of expecting `fuzzing` to be unknown. | cargo-fuzz sets `fuzzing` for its own builds only; a release build never does. |
| D37 | **The freeze check keeps the last committed evo tip** (r1 Opus m1). `EvoLayer` holds the last committed delta's `evo_tip` apart from its indexes, and a take or a release does not clear it; `EvoWindow::best_block` reports it. `EvoLayer::resume(meta.evo_tip)` starts a layer from the durable tip, which CH7a-2's open uses, so the first freeze after an open is checked too. A window whose block skipped its commit now fails the check even when every earlier row is durable; an empty window still passes, its remembered tip being `new`. A tip at genesis stays as committed here: the check compares it with a flush at genesis, and only reads normalise it (D38). CH7a-2 resumes the layer from the raw, unnormalised `meta.evo_tip` (`Meta::read(..).evo_tip`, `store/meta.rs`), not from `EvoReadView::best_block`, which reads a genesis tip as absent (D38) and would leave the first freeze unchecked; it does so as read after recovery and any wipe: a layer resumed before a wipe would refuse the flush at genesis that follows it, and one built with `new()` over a non-empty store would skip its first check. | Core checks the evo best block per block (`v:2579`, `v:2311`); the node checks it per freeze, which an empty layer would otherwise skip. |
| D38 | **An evo tip at genesis reads as absent at every level** (r1 Sol M1; design D7, §3.1 rows 3–4). `EvoReadView::best_block` returns `None` for a tip naming genesis, whether the active index, the frozen one or `meta.evo_tip` holds it; `RocksEvoStore` takes the network's genesis hash. B1 still writes the marker for a flush at genesis. Core's `b_b4` can name genesis after block 1's disconnect (`v:2389`), a replay back to genesis (`v:5450`) or inside VerifyDB's transaction, each only after block 1 has connected, and this rule reads it as absent. Core checks a genesis marker only where DIP3 is active at block 1: `ConnectBlock` (`v:2577-2583`), which TestBlockValidity (`v:5117`) and VerifyDB's reconnect (`v:5310`) reach, and ReplayBlocks with genesis as the old tip (`v:5409`, DIP3 at height 0). Core never connects such a block 1, since its first connect fails that check, so the two agree wherever a check reads the marker. dash-dml's `MemEvoStore` does not normalise: after block 1's disconnect it reports genesis, a state the differential (D33) never compares, as it disconnects only at height 2 and above. | Genesis never writes `b_b4` (`v:2588-2592`), so `VerifyBestBlock` (`edb:120-126`) is false at a DIP3-active block 1. |
| D39 | **An index row based above its mining block is a store fault** (r1 Sol m2). `mined_index` refuses an `llmq_mined_h` row whose base height exceeds the height its key names, before the ancestry filter, in both families. A base at the mining height reads. This is stricter than Core, which asserts only that the base is an ancestor of the chain end (`bp:761-767`, `:804-809`): Core reads a row mined at 4 and based at 5 from a chain end at 9. The two refuse alike when the chain end is the mining block. | No commit is based above its mining block (`EvoCodec::rows` refuses one, as `MemEvoStore` does), so such a row is corruption. D5: a refusal is a store fault. |
| D40 | **The node's delta names its evo tip** (r1 Opus n6). `EvoCodec::rows` refuses a delta with `evo_tip == None` as `Inconsistent`; `MemEvoStore` keeps its default of the delta's own block. A disconnect's tip is its parent. | Core writes `pprev` on a disconnect (`v:2389`) and the block on a connect (`v:2967`); a default would record the disconnected block for a disconnect that forgot to stage it. |
| D41 | **`mn_diff` is read unchecked** (r1 Opus n2). The read names a block by hash only, and the record carries a height, so `decode_diff` checks the record kind and not the block; `decode_snapshot` checks the list's block. | Core reads `DB_LIST_DIFF` unchecked too (`evo/deterministicmns.cpp:796`, `:867`). |
| D42 | **The evodb pair closes on a failed B1** (r1 Opus n1). B1's "write evodb cache to disk completed" line is logged whether the write succeeds or not, then the failure halts as before. Core's evodb commit never returns false: `CDBWrapper::WriteBatch` throws from `HandleError` on a failed write (`dbwrapper.cpp:217-224`, `:271-278`), so `v:3166-3167`'s "Failed to commit EvoDB" is unreachable. Core logs started, the LevelDB error lines, completed (from `~Timer` as the exception unwinds) and then "System error while flushing: …" (`v:3202-3203`); the node logs started, completed, then CH2's halt with the same prefix. A failed coin write in Core comes before the pair starts (`v:3160-3161`) and prints none; a non-split B1 carries both, so the node prints the pair for either (D20). | `timer:38-47`, `v:3164-3169`. |
| D43 | **The D7 B1-only image is tested with real evo rows** (r1 Opus m3), and so is a tombstone over each lower level (Opus m2). A split flush stopped at B1's Durable mark holds the window's credit data, its tombstones' deletes, `head_blocks = (new, old)`, no tip and `meta.evo_tip = new` (`flush/machine/tests.rs`); recovery from that image replays the coins to `new` and leaves every evo row as B1 wrote it (`recovery/tests.rs`). A tombstone in the active index over the frozen one or the DB, or in the frozen index over the DB, hides the row from both mined reads at a block whose ancestry still holds it (`evo/tests.rs`). | §7.2's L0 row for D7, which CH2's `()` tests and the CRASH model's `StubEvo` do not reach. |

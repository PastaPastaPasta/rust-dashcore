# O17 PIN-DELTA — packet `wallet` (WAL)

Pins: v23.1.8 = `728f505583`, v24.0.0-rc.3 = `0364ed626e`. Every row was checked tag-to-tag (`git diff v23.1.8 v24.0.0-rc.3`, `git show <tag>:<file>`). PR diffs were used only for attribution. All 35 packet PRs are covered below, and so are the wallet-file hunks of 30 other-packet PRs (section 3).

Conventions used here:
- **RPC rows are keyed `profile`.** The per-pin `dash-rpc-spec` (A1 `rpc: &'static RpcSurface`) already has to carry them. The `rpc.*` field names the semantic overlay that the spec does not capture by itself.
- **On-disk wallet-format rows are `Both?=yes`**, as the brief asks. Two rules apply: the WL3 importer must read both pins' forms on every network, and the IM2/rdashd writer must emit the form of the active profile.
- A proposed new profile group, `wallet.*`, is described in §4.

**Surprises and format hazards (for WL3 and IM2):**
1. **Descriptor-ID drift on downgrade (WAL-21).** v24 stores `h`-marker descriptor strings: in every new descriptor wallet, in every `migratewallet` output (its `combo(...44h/...)`), and in any import that used `h`. Their DB ids are SHA256 of the `h` form. v23.1.8's `WalletDescriptor::DeserializeDescriptor` recomputes `id = DescriptorID()` from its own `ToString()`, which always prints `'` (v23 src/wallet/walletutil.h:81-90; src/script/descriptor.cpp:1176-1182). Its spkm is registered under the DB id, but later `WriteDescriptor(GetID(), …)` and cache writes from `TopUp` use the recomputed id. A v24-created wallet opened by v23.1.8 therefore appears to gain duplicate descriptor records. On the next v23 load, `next_index` for the active spkm may revert, so addresses may be reused. Bitcoin avoided this by making `DescriptorID` use a compat `'` format; Dash v24 did not. Please confirm with an O11 downgrade test. Implications:
   - WL3 must key descriptor, key and cache records by the **stored** id and never recompute.
   - IM2 must write `'` under the v23 profile if the output is to be loadable by v23.1.8.
2. **migratewallet output is v24-shaped**: SQLite, `h` markers, inactive combo descriptors with `creation_time` 0 (so a full rescan follows), and `<name>_watchonly`/`<name>_solvables` wallets added to the settings. WL3 sees these only from v24 users. On the v23 profile, rdashd must not offer the RPC (WAL-03).
3. **Legacy HD quirks WL3 must accept from v23-written files:**
   - an `hdchain` with an empty account map (WAL-22);
   - a plaintext `hdchain` inside an encrypted wallet after `sethdseed`, which is corrupt on both pins (WAL-23);
   - `ps_salt` alongside `cj_salt` in old legacy wallets. This is fine for legacy wallets, but v24 treats `ps_salt` as a LEGACY_TYPE and refuses any *descriptor* wallet containing it (WAL-25a). No Dash release wrote `ps_salt` into descriptor wallets, since descriptor wallets postdate the PrivateSend→CoinJoin rename.
4. **The default wallet kind flips (WAL-01/02).** Under DEC-02 (descriptor by default), the v23 profile still needs legacy-by-default for `createwallet` and `dash-wallet create`, and the v23 `load_on_startup` guard. This conflicts directly with DEC-02 on mainnet; PLAN should decide whether DEC-02 overrides parity here.
5. **The unlock semantics changed in two directions.** PSBT signing now needs a full unlock (WAL-08), and `rescanblockchain` now needs an unlocked wallet (WAL-16). Dashmate and Platform tooling that rescans on locked wallets will see -13 on testnet (v24) but not on mainnet (v23).

**Cross-packet hand-offs and de-duplication:**
- **p2p-init:** P2P-13 (#26551; A1#12) and P2P-15 (#26569) already cover the wallet-packet PRs #7715 and #7648. I agree with both deltas; for P2P-15, `profile` vs `v24-all` is their call. WAL-44/45 (`-loadblock`, `-fastprune`) could move to init-node or ST owners if they prefer.
- **mempool-index:** MPIX-04 (#26933) and MPIX-07 (#27622) cover #7237 and #7711. WAL-41 (getrawmempool order) and WAL-42 (submitpackage) are duplicated here because #7711 and #7085 are wallet PRs. The **rpc** auditor should own or merge them.
- **rpc:** WAL-29 (logging `scan`), WAL-40 (global arg type check), WAL-43 (utxoupdatepsbt), WAL-46 (descriptor parse), WAL-47 (scantxoutset). Also the non-wallet half of WAL-21 (`decodepsbt` bip32 `path` and other inferred `desc` strings now use `h`). Also #7600/#7751 protx wallet ops: partial-signing errors, the "specify feeSourceAddress" error, BasicBLS registrar updates (#7751 lives in src/evo/providertx_service.cpp, evo packet). WL5 must take its rows from the rpc and evo packets.
- **evo:** #7294 consensus side (AL v2 validity gated by V24; `decoderawtransaction` `creditOutputs[].address`); `validateaddress.isplatform` (#7294/#7578) is rpc.
- **mn-overlay:** #7480 `cj_pending_obs` semantics and `getcoinjoininfo.pending_inputs`; #7052/#7794 rebalance client logic (WAL-38 covers only the wallet rounds rule).

**ReleaseProfile shape suggestion.** Add a `wallet: WalletRules` group:

```rust
pub struct WalletRules {
    pub default_kind: WalletKind,                 // WAL-01 (Legacy | Descriptor)
    pub tool_create_default: WalletKind,          // WAL-02
    pub hardened_marker: HardenedMarker,          // WAL-21 ('\'' | 'h'), generation and normalised output
    pub empty_hd_chain_counts_as_one: bool,       // WAL-22
    pub extra_db_records: bool,                   // WAL-24 (writer only; reader always accepts both)
    pub init_rescan_option: bool,                 // WAL-26
    pub init_dust_protection_option: bool,        // WAL-27
}
```

Everything else here is either RPC surface (`rpc` / dash-rpc-spec: method set, args, result fields, error strings and codes, as in WAL-03…20, 29, 33, 39–43, 46, 47) or `v24-all`. The `rpc` spec generator (AR2) should take a small hand-written semantic overlay for behaviours that the help text does not reveal:
- the `warnings` shape (WAL-09)
- label sanitisation (WAL-14)
- rescan unlock (WAL-16)
- importwallet on pruned nodes (WAL-18)
- `getreceivedbylabel` errors (WAL-12)
- the `createwallet` guard (WAL-01)
- `getrawmempool` order (WAL-41)

**Low-value `profile` rows** that PLAN could downgrade to `v24-all` with explicit sign-off: WAL-17 (a success string), WAL-22 (an account count before the first derivation), WAL-29, WAL-41 (unspecified order), WAL-47. **Debatable `v24-all` rows:** WAL-31 (resubmission order) and WAL-36 (CoinJoin balance excludes phantom outputs) are client-observable. I kept them `v24-all` because the v23 behaviour is a bug that no honest client can rely on.

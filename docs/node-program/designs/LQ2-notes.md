# LQ2: final commitments, in-block rules, mined index, `merkleRootQuorums`: implementation notes and D-rows

LQ2 implements PLAN row LQ2 on top of SB8's `verify_commitment` (Core's one `CFinalCommitment::Verify`, DEC-109 (4)) and LQ1's members and scans. The parity reference is Dash Core v24.0.0-rc.3 (DEC-82: v24 only). This file records the implementer's decisions where the PLAN row, the EV addendum (§1.5, §5) and EV1's design leave a choice, per the IMPLEMENTER contract. Code comments cite rows as "LQ2 D*n*".

What LQ2 adds:
- `dash-evo::llmq::commitment`: `verify_null` and `verify_sizes` (Core's `VerifyNull`, `VerifySizes`) beside SB8's `verify_commitment`, with quirk tests 19, 20 and 36. The commitment type stays base-sdk's eager-BLS `Commitment` (D1).
- `dash-dml::blockprocessor`: Core's `CQuorumBlockProcessor` without its store and its pool. It covers:
  - `commitments_from_block`, `is_mining_phase`, `quorum_block_hash`, `has_mined_commitment` and `num_commitments_required`;
  - `process_block` (with `process_commitment`), which returns the `MinedCommitmentRecord`s of `EvoDelta` and emits the mineable-pool effects;
  - `undo_block`;
  - `qc_hashes`, Core's `GetMinedAndActiveCommitmentsUntilBlock` plus `GetQcHashes`, and `quorum_root`, which wires SB7's `merkle_root_quorums` to it.
- `dash-dml::blockprocessor::pool`: the mineable pool (`AddMineableCommitment`, its lookups, the miner's `GetMineableCommitments`) and the `qfcommit` verdict past the solicitation gate (`ProcessMessage`).
- `dash-dml::specialtx::qc`: `check_llmq_commitment` (type 6, `CheckLLMQCommitment`) and the `CommitmentVerifier` seam that EV1 D5 names.
- Tests and evidence: oracle differentials in `node-l1`, the testnet `quorum listextended` replay, the quorum-root history check, and the bench row (below).

## Block-level order

`ProcessSpecialTxsInBlock` (`evo/specialtxman.cpp:797-998`) runs `CheckLLMQCommitment` on every type-6 transaction inside the special-tx loop (`:258`, `:871`), then the quorum `ProcessBlock` (`:895`) with `fBLSChecks = fCheckCbTxMerkleRoots`, then the MN list, then `CalcCbTxMerkleRootQuorums(block, pindex->pprev)` when the CbTx version is at least 2 (`:945`). CH7a/CH7b own that sequence. LQ2 gives each step its function, and keeps each step's internal order exactly as Core's:
1. DIP3 gate;
2. `PreComputeQuorumMembers`;
3. `GetCommitmentsFromBlock`;
4. the count checks, per enabled type at `pprev`;
5. the v24 duplicate pre-pass;
6. the queued signature checks (`fBLSChecks`);
7. `ProcessCommitment` per commitment, in multimap order.

| D | Decision | Why |
|---|---|---|
| D1 | `LlmqCommitment` stays the alias to base-sdk's `dash_primitives::Commitment`. Its BLS fields are already eager (`BlsEagerPk`/`BlsEagerSig`, decoded under `qc_source(nVersion)`: legacy iff version 1 or 2, `commitment.h:110-113`), so A1 §1.4.1's eager decode needs no new type. `PartialEq` on `MinedCommitmentRecord` and `Effect` stays field equality: base-sdk's eager fields compare by their wire bytes and decode outcome, which for decoded commitments is Core's `SerializedEqual`. | BS8 landed the eager wrappers, so the alias the EV0 comment anticipated moving already points at the eager commitment. A second type would duplicate the codec. |
| D2 | `IsNull` is base-sdk's `Commitment::is_null`. Quirk 36's test pins `is_null ⇔ (no signer bit ∧ no valid bit ∧ !pk.is_valid ∧ vvecHash = 0 ∧ !membersSig.is_valid ∧ !quorumSig.is_valid)` on Core-produced commitments, and on each field flipped alone. "Valid" is the eager decode's outcome: an encoding that does not decode is the invalid object, the same as Core's `IsValid()`. | The PLAN row's `IsNull ⇔ !IsValid` reads field-wise: a null commitment is one whose BLS fields are all invalid objects (`commitment.h:118-131`). |
| D3 | LQ2 lands the whole `CheckLLMQCommitment`, steps 1–7, as `specialtx::qc::check_llmq_commitment`, plus the `CommitmentVerifier` seam EV1 D5 names (`verify_null`, and `verify(base, checkSigs = false)`). | D4 | `HasMinedCommitment`'s `mapMinedCommitmentBlockCache` is not modelled, and `GetQcHashes`' LRU and set caches were not until DEC-325 (now D22, for cost). Core's crash-replay branch (`Tip() == nullptr`: skip the count checks, take `qc.quorumHash`, `:235-238`, `:347-349`) is reachable only during `ReplayBlocks`. It is a `tip: Option<BlockId>` argument, so CH7b's replay can pass `None`. Before the assert, Core's replay still gives every reason that does not read the tip: `GetCommitmentsFromBlock`'s `bad-qc-payload`, `bad-qc-commitment-type`, non-rotated `bad-qc-dup` and `bad-qc-premature` (`:578-600`); the pre-pass `bad-qc-dup` (`:260-265`); and in `ProcessCommitment`, `bad-qc-block` (`:358`, `:366`), `bad-qc-invalid-null` (`:376`) and `bad-qc-dup` from a stored `q_mc` row for the quorum that is not `SerializedEqual` to `(qc, blockHash)` (`:381-392`). Ours gives the same, except that last one: replay reads through `prev` (`read_at = tip.unwrap_or(prev)`), which holds no such row. Core also replays with `fBLSChecks = false`: `RollforwardBlock` passes `fCheckCbTxMerkleRoots = false` (`validation.cpp:5196-5200`), which `ProcessBlock` takes as `fBLSChecks` (`evo/specialtxman.cpp:895`), so the queue's `bad-qc-invalid` is never a replay verdict. The verdicts past the assert (`ProcessCommitment`'s `bad-qc-height`, `:397`, and `Verify`'s `bad-qc-invalid`, `:414`) and the queue's `bad-qc-invalid` are LQ2's own, and CH7b must not treat them as parity (D23). The twin and the bench run `tip: None` with `bls_checks: true`, a harness mode ("replay counts skipped, BLS on") that Core never runs. | One shape for connect, template checks and VerifyDB. CH7b decides which tip each caller passes (VerifyDB level 4 reconnects on the tip it disconnected). |

| D11 | `fBLSChecks` signature checks go through one queue per block (DEC-325). `process_block` calls `dash_evo::llmq::queue_mined_signatures` (Core's `VerifySignatureAsync`, `commitment.cpp:35-110`) for each non-null commitment in order. It appends that commitment's `BlsCheck`s (members aggregate, then quorum; a single-member quorum's member signature checked at once) to one `Vec`, then hands the whole block's checks to `QcCtx::bls_checks: &dyn BlsCheckRunner`. One verdict comes back at the existing post-loop point (`:267-284`): any failure is one `bad-qc-invalid`, else a check without a BLS verdict is `BlsUnsupported`. As in Core, queuing does not stop at a failure: every commitment's members are read, and an unknown base later in the block is still the reasonless `false` (`:271-274`). Ours returns before any check runs; Core's control still drains the checks already queued and ignores the result, which nothing observes. The node's runner is `dashd_chainstate::checkqueue::bls::BlsCheckQueue`, Core's `m_bls_queue` on the CheckQueue port: batch size 4 (`blockprocessor.h:60`), threads from `bls_check_threads(-parbls, cores)`. That is Core's `-parbls` arithmetic (`init.cpp:2071-2081`): 0 means `GetNumCores()`, a negative value leaves that many cores free, and the result is clamped to `[1, MAX_BLSCHECK_THREADS + 1] - 1` with MAX 33 (`llmq/options.h:38-42`), started at `blockprocessor.cpp:81-90`. The pure crates keep `SerialBlsChecks` (no threads). Core adds checks while its workers run; we collect the block's checks and then add them all, so the instructions are the same and only latency differs. `verify_mined_signatures` stays as one commitment's queue run serially, so the twin and `verify_commitment(…, Mined)` keep their contract. BS11b's random-scalar batch (basic scheme only, A1 §2.4) plugs in as a `BlsCheckRunner` over the whole block's checks. Its contract is the runner's: `Invalid` iff some check's `verdict()` is `Invalid`, so a failed batch falls back to per-check verdicts, since an unsure check's failure is `Unsupported`. It must pass the same twin, `bls_checks_one_queue_for_the_block` and `the_queue_gives_the_serial_verdict` unchanged, and the legacy scheme stays individual; `a_single_member_check_without_a_verdict`, once on that list, was deleted at BS11a-4 4c (D2). `BlsCheck`'s accessors give it the values. Evidence, `qc_block_mainnet_instructions` (ignored, node-l1) under `perf stat -e instructions:u`, one block = (11 iterations − 1)/10, release, two repetitions: the qc-block-mainnet block (2,089,770, 32 commitments) costs Core 14.21 G instructions (`oracle_llmq_verify_mined` per commitment: `Verify(checkSigs = false)` plus the queued checks; >85% relic and GMP field arithmetic). Ours costs 3.62 G serially and 3.61 G on the pool (all threads counted), with the duplicate pre-pass, `ProcessCommitment` and the rows on top. That is an instruction ratio of 3.9× (blst against relic/GMP), not a time; the sides are close but not identical (Core's carries the oracle's decode and domain checks). The pool adds no measurable instructions; its latency gain is not measured here (wall-clock is noise on this box). The twin's 149 signer swaps are judged by Core's sync `Verify(checkSigs = true)` (`VerifySecureAggregated`, `commitment.cpp:90`), not by the mined `BlsCheck` (`utils.cpp:561-579`). The two agree for two or more signers, since both then call `VerifySecureAggregated`, and every multi-member type has `minSize ≥ 2`. | DEC-325 Major 1: Core's queue spans the whole block, so the seam does too, which is also the shape BS11b's cross-commitment batch needs. `SigPath::Mined` already encodes `BlsCheck`'s per-check semantics (SB8 D18). |

# O11: functional-test compat runner per pin, FT-MAP, implementation notes and D-rows

O11 runs Dash Core's functional tests against rdashd (A1 §4.8, PLAN M2 exit 4). It has three parts:
- a local Core branch for the one pin, v24.0, with the func-compat patch set (D9);
- a runner in rust-dashcore (`contrib/node/func-compat/`) that builds each pin's test tree, runs the phased passlist and writes the pin's matrix;
- FT-MAP, with the asserted-log extraction (v24.0 and v23.1.8) beside it.

## Pieces

- **Core** (`~/workspace/dash`, never pushed):
  - `node/func-compat-v24.0` off v24.0.0-rc.3;
  - `node/func-compat-v23.1` off v23.1.8 is kept frozen as a local ref and is never run (D9). Its worktree is deleted.
  - The patch set:
    - `test/functional/test_framework/rust_nodes.py` (masks, adaptations, unit tests registered in `test_runner.py`);
    - the hooks in `test_framework.py` and `test_node.py`;
    - `test/functional/rust_passlist.txt` and `test/functional/rust_expected_failures.txt`.
- **Runner:** `contrib/node/func-compat/func-compat.py`:
  - `build`, `run`, `ratchet [--update]`, `adaptations`, `selftest`;
  - `phases.toml`, which is A1 Appendix D;
  - `test_func_compat.py`.
- **FT-MAP:** `contrib/node/func-compat/ft-map.py` and `ft-map-rules.toml`, which write `node-program/compat/FT-MAP.md`.

## D-rows

| D | Decision | Why |
|---|---|---|
| D1 | **Node selection is by index mask.** `RDASHD_NODES` (or a test's `--rust-nodes`) is `all` or a list like `0,2-3`. `RDASHD` and `RDASH_CLI` give the binaries. `add_nodes` and `add_dynamically_node` apply the mask only to nodes whose binary the framework picks. A test's own `binary=` or `versions=` wins. DTF's `start_masternodes`, `create_simple_node` and `dynamically_add_masternode` all go through those two methods, so they follow the mask with no patch of their own. Role masks (A1's mixed modes: MNs vs non-MNs) are not here. `phases.toml` marks `mixed-a` and `M7` as not runnable; the role masks are O12a's. | A1 §4.8 m-5: DTF never passes per-node binaries, so the helpers had to be covered. Patching the two constructors covers every helper with the smallest diff. |
| D2 | **The tree is exported, and nothing in Core is built.** `build` runs `git archive <branch> test share/rpcauth` into `--work/<pin>-<wallet\|nowallet>`. It writes `test/config.ini` from `config.ini.in` with `BUILDDIR/src/{dashd,dash-cli,...}` linked to the pin's release binaries, taken from `contrib/setup-dashd.py`'s cache (24.0.0-rc.3, 23.1.8). The stamp `tree.json` holds the branch commit, and a new commit re-exports. `dash_hash==1.5.1` goes into `--work/pylib` when it is missing. | Release binaries are the pinned references, so a Core build would only add hours. Exporting from the branch means a run never reads uncommitted Core edits, and the matrix names the exact commit it ran. |
| D3 | **Mixed cache: the cache is always built by the reference dashd.** `_initialize_chain` keeps `self.options.bitcoind` (DASHD) whatever the mask says. Today rdashd *refuses* a copied Core datadir: DEC-201 Q6, "use -importcoredatadir" (`dashd-node/src/datadir.rs`), and `-importcoredatadir` itself is `Unsupported(CH5)`. That is not A1 §2.9's regtest auto-import. So every test on the cached chain (`setup_clean_chain = False`) is an expected failure owned by CH5. `dynamically_initialize_datadir` (DTF copies node 0's datadir) is left as Core has it: its first call on node 0 is `gettxoutsetinfo`, which rdashd does not serve. Patching the copy before that is reachable would be untested code. | One cache per run serves every test. A cache built by rdashd would need its mining RPCs (RP1a) and would poison the dashd-only tests. CH5's row already owns "regtest Core-datadir auto-import (incl. `indexes/`, m-5)". |
| D4 | **Adaptations: rdashd nodes only, each with an owner, and each with a tripwire.** `rust_nodes.ADAPTATIONS` drops options the framework sets on every node that rdashd refuses: `port` and `bind` (P2b), `tinyblk` (ST2), and `keypool`, `fallbackfee` and `createwalletbackups` (WL2a). They are dropped from `dash.conf` and from argv. Each option entry carries the value the framework sets: rdashd can accept one value as inert (`support.rs` `Inert`) before it implements the option, so the tripwire tests that value. `RPC_ADAPTATIONS` covers methods rdashd does not serve. A missing `getmempoolinfo` counts as loaded in the startup wait (MP1a). A one-node `sync_blocks`/`sync_mempools` returns at once instead of calling `getbestblockhash`, `getrawmempool` and `syncwithvalidationinterfacequeue` (RP1a, MP1a). Each workaround applies only while its methods are still listed, so dropping an entry also drops its workaround. Before every run, `func-compat.py adaptations` starts rdashd with each dropped option and calls each method. If rdashd accepts or serves one, the run fails: "drop it from ADAPTATIONS". If rdashd exits during the RPC probe, the tripwire stops with that error rather than reporting a served method. | Without them no test starts. Every node gets `port=`, `bind=`, `tinyblk=` and `-createwalletbackups=0`, and rdashd refuses them. The tripwire keeps them from outliving their reason. A one-node sync compares a node with itself, so skipping it changes no verdict. |
| D5 | **`getblockcount` is served early. Approved (DEC-359)**, as DEC-279 did for `getblockhash`. It returns the active chain's height through the `NodeChain` seam (`dashd-rpc::blockchain`, Core `rpc/blockchain.cpp:210-229`). `rdashd/tests/rpc_diff.rs` diffs its bytes against dashd v24.0.0-rc.3 on the same regtest chain: at height 0 (bare, empty and named params, an extra argument, `null`, a batch, its help), then after each block `submitblock` connects (heights 1 and 4), after a side chain's block, and after a rejected block (neither moves the tip). The diff (DEC-364) is byte-exact. It masks only the value of the HTTP `Date` header, reads each reply through `Content-Length` or until the connection closes, and fails on an incomplete reply. It cannot be skipped: with `SKIP_DASHD_TESTS` set it fails (`common::require_dashd`). An off-by-one `getblockcount` mutant differs in 8 of its 126 cases, including height 0. Two RP0 tests that used `getblockcount` as their missing-method probe now use `getbestblockhash`. RP1a keeps the rest of the blockchain RPCs. | The framework's first call on every node is `getblockcount`. Without it no functional test can pass at M2, and RP1a is M3. |
| D6 | **The ratchet (`judge`).** It refuses: (a) a passlisted test that did not pass, or that was not run in a complete run; (b) an expected failure that passed (`--update` moves it to the passlist); (c) a failure of a test in the run's phases with no expected-failures entry; (d) an entry whose owner field names anything that is not a BACKLOG row or a PLAN task (IDs from the first column of their tables; comma- or space-separated, every ID must exist); (e) a test on both lists, or a listed test the pin lacks; (f) a test any commit of the branch since the pin's tag added to the passlist that the passlist no longer has (a hand removal is a regression too). A skip is the test's own verdict on the host, as with dashd (for example `rpc_bind --ipv6` here), so it counts against the passlist only. `--update` only grows the passlist. It writes only when (1) the run used the phase's own mask, (2) the only refusals are expected failures that passed, (3) the worktree is at the pin's branch, and (4) the lists in the worktree are clean. Two rules guard the runner's selection. test_runner.py runs every script that starts with a name it is given, so a name another selected name prefixes is dropped from the selection. A summary that reports one test twice with different results is an error. | A1 §4.8 / NFR-CEQ-05: the expected-failures list only shrinks and names its owner. A partial run (`run … <tests>`) checks only what it ran. Without (f), a commit could drop a passlist line and the next run would pass. **(g), BL-356 (DEC-364):** a passlisted test that passed without starting rdashd is refused. On every rdashd start the patched `TestNode.start` appends the test's runner name to the file named by `RDASHD_STARTS`; the name is the script plus the test's own arguments, which come before test_runner.py's `--cachedir=`. The matrix records the count per test. Requiring a count above zero covers an empty or narrow `--rust-nodes` mask, a test's own `binary=`, and partial runs. The requested mask is not used to infer it. An expected failure that passes without rdashd is neither refused nor moved by `--update`. |
| D7 | **The lists live on the Core branch, one pair per pin,** as `test/functional/rust_passlist.txt` and `test/functional/rust_expected_failures.txt` (`test \| reason \| owner`). The runner reads them from the branch with `git show`. `--update` writes them into a given worktree for a commit. | The brief puts them on the Core branches. They are per pin because a pin's tests differ; v24.0 is the only pin (D9). A1's `node-program/compat/functional-passlist.txt` is replaced by these. |
| D8 | **Phases come from A1 Appendix D** (`phases.toml`, in order). `run --phase P` runs P's targets and every earlier phase's, plus both lists. Globs (`mempool_*`) and script stems match every runner variant (`rpc_bind` covers `--ipv4`, `--ipv6` and `--nonloopback`). Each phase carries its mask and whether the tree enables the wallet (M2–M5 `nowallet`, M6+ `wallet`). | Appendix D is the agreed adoption order. Running the earlier phases again keeps their passlists proven. |
| D9 | **v24.0 is the only pin. Ruled by DEC-359 under DEC-82.** rdashd has no v23.1 profile, so the runner's pin set is v24.0 alone. The local branch `node/func-compat-v23.1` (`c1cd6c46fed`, with the SPORK_3 guard) stays as a frozen ref and is never run, and its worktree is deleted. O17's v23.1 → v24.0 asserted-log deltas need no branch: `ft-map.py` reads the `v23.1.8` tag directly with `git show` (D11). **A1 §4.8's two-branch text (v24.0 and v23.1 trees) is superseded by DEC-82.** | rdashd is v24-only, so a v23.1 matrix would only measure v23-only behaviour rdashd will never have. |
| D10 | **FT-MAP is generated** from the v24.0 branch's `test_runner.py` scripts (266 at v24.0.0-rc.3; R4's 264 was counted at develop) and PRD §2's 168 story rows. Sources: `a` (the acceptance names the test or a glob), `r` (`ft-map-rules.toml`, reviewed family rules; a rule with an unknown story or no matching test fails generation), `t` (the story's Dash Core column names an RPC (one of the pin's `RPCHelpMan` names) or an option the test uses, minus tokens that more than 8% of tests or more than 2 stories share). Every test maps to US-DEV-07. `ft-map.py check` fails when the file is stale. | A skeleton the reviewers can correct by editing the rules, not the output. `t` is noisy by nature and is marked as the place to review first. |
| D11 | **Asserted-log extraction (R4 V6)** reuses `asserted-logs.py`'s resolver (`templates`, `fragments`, `core_files`) at two refs (`ft-map.py` `REFS`): the v24.0 branch and the `v23.1.8` tag. FT-MAP gives each test's fragment count at v24.0 / v23.1 and lists every fragment added or removed v23.1 → v24.0 (O17: `[error]`, WAL-28, P2P-25). The functional tests' sources are the same on the branch and at the tag, so reading the tag changes no content. The v24 ledger (`dashd-node/tests/asserted_log_lines.txt`) and its ratchet stay ND1's. | One resolver, so there is no second parser to drift from the reviewed one. |
| D12 | **Identity in asserted messages: a message adaptation, ruled by DEC-359.** rdashd says `rdashd` where Core's messages carry `PACKAGE_NAME` "Dash Core" (DEC-83: honest identity is deliberate). `rust_nodes.MESSAGE_ADAPTATIONS` maps a probe to (owner, framework text, rdashd text): `datadir-lock` → (ND1, "Dash Core is probably already running.", "rdashd is probably already running."). On rdashd nodes only, `assert_start_raises_init_error` swaps the framework text for rdashd's. The tripwire starts a second rdashd on its running node's datadir and fails if rdashd's error no longer contains the adapted text, or if an entry has no probe. `feature_filelock` now passes, and `ratchet --update` moved it to the passlist. The adaptation is recorded in node-program `compat/functional-adaptations.md`. | It uses the same mechanism as D4, with no exact-text option in rdashd and no permanent deviation. |

# EV2b: implementation D-rows

EV2b implements EV2-dml.md (rev4, DEC-58) §3.2–§3.8 in `dash-dml`: `build_new_list_from_block`,
PoSe, payee selection with its literal twin, confirmations, collateral spends, the ProTx effects
and the NetInfo migration, with members read through the addendum's `&DmlMemberSource`
(EV-addendum-SB0 rev6, DEC-122). This file records the implementer's decisions. Core references
are `v24.0.0-rc.3`; `sp` is `src/evo/specialtxman.cpp`, `dmn` is `src/evo/deterministicmns.cpp`.

| D | Decision | Disposition |
|---|---|---|
| D1 | The build follows v24's `RebuildListFromBlock` order verbatim (`sp:309-795`): payee of the previous list, confirmations, `DecreaseScores`, the special-tx loop, the collateral-spend loop, payee bookkeeping, streak resets. In ProUpServ, `IsValidMnType` runs before the NetInfo duplicate check, as v24 has it (DEC-82). | Proposed. |
| D2 | A payload that decodes to an unknown ProTx version (`UnknownProTxVersion`) is `DmlException::OutOfDomain`: Core's checked validation rejects it earlier (`bad-protx-version`), so a block that reaches the build never holds one. | Proposed. |
| D3 | The input is a `dash_consensus` `Block`, and each special transaction's payload is its cached decode. An incomplete or mismatched decode is `bad-protx-payload` (`bad-qc-payload` for a QcTx), Core's `GetTxPayload` failure. | Proposed. |
| D4 | Arithmetic that is undefined behaviour in Core wraps: the QcTx quorum height, `CalcPenalty` and the confirmation subtraction. No validated chain reaches the overflow. | Proposed. |
| D5 | The literal twin (`reference`) is behind an `xcheck` feature, used by tests, node-l1 and node-fuzz. The literal payee scans (`scan.rs`) are compiled in every build: the indexed path falls back to them whenever P1 or P2 does not hold. The twin landed (D24) and walks Core's order itself, so `literal_phase_order` was removed; `test-utils` implies `xcheck`, which only adds code (the BL-105 allow-list entry still holds). | Proposed. |
| D6 | Every run of copies in a projection (`voting_weight - nConsecutivePayments`, the weights, the paid copies), and the sort's offset, are capped at the projection's length. Core's reader accepts any `nConsecutivePayments`, and a streak far below zero would make Core allocate gigabytes or overflow `int`. The cap is exact: Core's first `count` entries do not change (the argument is at `scan.rs`'s `projected_scan`). Blocks only produce streaks of 0 to 4. This replaces the earlier 2^24 clamp (Opus review r0, finding 4). The shim refuses negative streaks (`ORACLE_E_ARG`), so that case is compared only in dash-dml's tests. | Proposed. |
| D7 | A payload's NetInfo enters the state as Core reads it (`netinfo::as_core_reads`): an invalid legacy address is the empty service, and an extended entry whose read is invalid is the invalid entry. | Proposed. |
| D8 | A previous list that is neither the default list nor the list of the block's parent (its hash, as Core's assert at `sp:317` checks; the height is not compared; "default" is Core's `operator==` with `CDeterministicMNList()`, so the registration counter must be 0 too, `dmn.h:618-624`) is `DmlBuildError::Store(StoreError::Inconsistent("dml-prev-list-mismatch"))`, a node fault, never a panic (the crate's no-panic rule) or a block verdict. This deviates from EV2 §3.2's `Invalid("dml-prev-list-mismatch")` (Opus review r0): the addendum's rule (§2.3, DEC-122) is that local faults are node errors, and a block verdict would let a wiring bug mark a valid block and its descendants invalid and penalise the peer. | ACCEPTED (manager, 10-16): Core's `operator==`, registration counter included, is the authority; this deviates from EV2 §3.2's wording. |
| D9 | `DmlRules` carries the `NetInfoRules` (the V24 and extended-address deployments) beside V19, MN_RR and V24, so the build reads every deployment from one value. | Proposed. |
| D10 | `process_block` sets the list's block hash (`ProcessSpecialTxsInBlock`, `sp:907-911`), so the build's list and the stored list are the same value. | Proposed. |
| D11 | EV2a D11's V24 gate on `has_operator_key` stays at its call sites; no token type is added. | Proposed (EV2a D11 deferred to EV2b). |
| D12 | A state Core's checked path never produces (a pre-V24 ProUpServ whose NetInfo kind differs from the state's, an operator key that does not decode in `SetStateVersion`) is `DmlException::OutOfDomain`, never a reject string; L1 counts it as out of domain. Core accepts such a ProUpServ in `RebuildListFromBlock` and stores an incoherent state, but `CheckProUpServTx` (`bad-protx-version`) rejects it first. node-l1's generator therefore draws only the versions a checked block can hold. A coin read error is `DmlBuildError::Store`. | Proposed. |
| D13 | L1 (`diff_dml_apply`) generates ProUpServ, ProUpRev, ProUpReg (rebuilt from raw v1/v2 bytes, since the crafted fixture has none), ProReg (listed, own and fresh collateral; from ExtAddr, shared registrations: D22), QcTx, spends of collateral (plain and ProUpRev-typed, including the collateral of a ProReg earlier in the block), ProUpShareTx and ProUpSharedRegTx (raw v1 bytes, preferring a shared masternode registered earlier in the block) and raw bytes. O2a-EV's crafted fixture has no shared masternode, so the share success paths are reached only through a shared ProReg in the same block (D22). | Proposed; the manager's answer (10-16): yes, as a node-l1 case derived from an earlier block, O2a-EV's fixture unchanged (D23). |
| D14 | L0 is O2a-EV's crafted regtest fixture (`dml-crafted-v24.0.json`), each block whole and with each special transaction alone beside the coinbase: 78 comparisons, 68 accepted and 10 rejected by both; with D23's derived case, 69 and 10. L1's generator starts every input from one of those cases (byte 0), so its public seeds are per case and per operation kind (D22; 348 files, `node-l1/examples/dml_seeds.rs`: 171 accepted and 177 rejected by both, none out of domain; 24 of them start from D23's derived case). | Proposed. |
| D15 | `diff_dml_apply`'s `min_certify_execs` is 300,000. Every input crosses the FFI with a whole evodb list and its quorum members, about 25 executions a second per core at load 90, so 300,000 is about 3.3 CPU-hours of certify window. | Proposed. |
| D16 | node-l1's `Headers` (the context's headers as `ChainAncestry`) gives the window's first header no parent, as the oracle's chain context does, so `prev` is `None` above genesis. The build reads only `ancestor`; any later reader of `prev` there must get a full header chain. | Proposed. |
| D17 | `mnlist_payee_queue` (node-l1 `dml_payee`, kind l1) is the PLAN's payee target and EV2 §6.2's direct Core check of `scan.rs`. It builds a list by additions, hot-field updates and removals (so the payee queue, streak index and P1/P2 flag are the incrementally maintained ones), then compares `payee` and `projected_payees` with `oracle_mnlist_payee`/`oracle_mnlist_projected`, on the built list and on the same list read back through our canonical reader. Six eras: mainnet before V19 and its activation block; regtest (V19 at 1, MN_RR at 432) at heights 0–2, from 100, at the MN_RR activation block and after it. The EV2 §6.2 payee fixtures (two-Evo, height-0, future revival, future registration, all-banned) are its first seeds. The default certify floor (10⁶ executions, about 12 operations each) is above EV2b-1's 10⁷ operations. The `pay_height` edge cases and a payee banned, removed or revived in the same block are the build's, and `diff_dml_apply` covers them. | Proposed. |
| D18 | Canonical bytes carry no collision-bucket history, so Core iterates its read list in its reader's bucket order. Core's evonode continuation takes the **last** match in that order (`dmn:166-181`). `mnlist_payee_queue` therefore compares the built list only when its `core_order()` equals the read list's (about two thirds of random inputs); the read list is always compared. The shim refuses (`ORACLE_E_ARG`) a projection over a valid evonode paid at the list height with a negative streak before MN_RR (D6's case; the harness tests exactly that condition, Opus r2 R1): then only the payee is compared, and the input counts as out of domain. Any other projection refusal, or this one on a list without such an evonode, is a divergence. | Proposed. |
| D19 | `DmlEvent::core_message` reproduces Core's `RebuildListFromBlock` log lines without the `": " + proTx.ToString()` suffix that Core appends to the added, updated, revoked, share and shared-registrar lines (`sp:451,519,584,616,646,699`). Each payload type has its own long `ToString` format; porting all of them for a log line is not worth it until a consumer compares the trace with Core's debug.log (EV2 §3.9). | Proposed. |
| D20 | `diff_dml_apply`'s soundness rules (Opus review r0, finding 2): one of our readers (block, list, header, member) refusing an input Core processes is a divergence; a store fault is a divergence (the harness's coins never fail); D12's ProUpServ must be one Core accepts; only the other out-of-domain exceptions (inputs Core's own checks refuse first, or on which Core's behaviour is undefined) and a missing list are uncompared. A QcTx is left without supplied members in one input byte in 64 (it was 1 in 8), and the generator draws ProUpShareTx and ProUpSharedRegTx too (operation kinds 8 and 9, and types 11 and 12 in the raw operation). | Proposed. |
| D21 | NetInfo values the build makes keep EV1-1's NetInfoV2 invariant (purpose groups sorted by purpose byte and unique; EV1-1 Opus N3): `migrate` starts from an empty `NetInfoV2` and adds every entry with `add_entry`, `as_core_reads` maps groups in place, and the evodb reader collects groups through a sorted map keeping the first (Core's `std::map` read). A stored PLATFORM_HTTPS domain of only hex/IP characters passes `Validate()` but fails the `AddEntry` round trip (EV1-1 N2); the migration rejects it as Core's `AddNetInfoEntries` does, unchanged. | Proposed. |
| D22 | V24 coverage (Opus review r1, findings 1–3): the only V24 crafted case has an empty list, so L1 never reached `SetStateVersion`'s migrations, the scheme-migration probes or ProUpRev's version restore with V24 active. Bit 1 of the input's flags byte (byte 1) now forces V24 on any pre-V24 case: Core runs `-vbparams=v24:-1:999999999999` with the context's V24 deployment Active, ours reads V24 from the same context, and the case's v1/v2 states meet V24 payloads. An ExtAddr ProReg is a shared registration one time in two (1–3 shares drawn from the key pools, zero join signatures, which `RebuildListFromBlock` does not check), and later transactions can update or spend it. The public seeds hold every case × operation kind with and without V24, and one input per shared-masternode path (`SHARE_PATHS`: a shared ProReg, ProUpShare and ProUpSharedReg accepted; `bad-proupshare-payee-reuse`, `bad-proupsharedreg-payee-reuse`, `bad-shared-collateral-spend`, and `bad-protx-dup-key` from a share owner key (`specialtxman.cpp` v24:417-419) and from the ungated ProUpSharedReg probe (v24:688-690)), found by `dml_seeds`'s bounded search (only inputs whose transactions hold a shared ProReg and then the path's update or spend are built) and checked against Core. Core returns `bad-protx-dup-key` from seven checks, so `share_paths` names the failing transaction, the last one of the shortest prefix our build rejects (Opus r2 C1: the first dup-key seed failed at the shared ProReg, not at the ProUpSharedReg), and a shared registration's share owner key counts as held only by a masternode other than the one it replaces by collateral, which Core removes first (v24:389-401; Opus r3). Every prefix of a dup-key seed must agree with Core, so both sides fail the same transaction; `l1_dml_apply` asserts the seeds reach every path and that accepted V24 blocks with provider updates occur in the generated run. A spend operation with no collateral to spend is skipped instead of ending the input. | Proposed. |
| D23 | `diff_dml_apply` has one derived case whose list already holds a shared masternode (manager, 10-16, on D13). `examples/dml_shared_case.rs` takes the first splitmix64 input on a pre-V24 crafted case with V24 forced on (D22) whose first transaction is a shared ProReg with its own collateral, keeps the coinbase and that transaction, and records the block and the list Core builds from it (`oracle_dml_apply`'s evodb encoding) in `node-l1/src/dml_apply/shared-case.json`; O2a-EV's fixture is unchanged. `input.rs` derives the case: the base's context with V24 forced on, the block's header as the new tip, Core's list as the supplied list, and as its own block the coinbase under a header whose `hashPrevBlock` is that block (the shim checks only that). The generator's share pool starts with the list's shared masternodes. `l1_dml_apply` checks that Core still builds exactly that list from the block, that it holds a shared masternode, that the case's own block builds on both sides, and that public seeds from the case reach an accepted ProUpShare and ProUpSharedReg and `bad-shared-collateral-spend` on the held masternode (blocks with no shared registration). An empty fixture (`"base": ""`) skips the case, which is how the example regenerates it. | Proposed. |
| D24 | The reference twin (`dash-dml/src/reference.rs`, behind `xcheck`, which `test-utils` turns on) keeps Core's layout: `mnMap`, `mnInternalIdMap`, `mnUniquePropertyMap` with reference counts and immer's collision buckets, and nothing else (no index, no cached order, counts or unique keys). `AddMN`/`UpdateMN`/`RemoveMN` recompute a state's unique keys and restore the map on a throw; `GetCounts` (written out, not through the fast list's incremental `Counts` step) and `CalcMaxPoSePenalty` walk the map; the payee and projections are `scan.rs`'s literal scans (made generic over a `ScanList` trait); confirmations, decay and the streak reset iterate a Core-order snapshot and `set` each eligible masternode. **Sharing scope, wider than EV2 §3.4's contract** (payload decoder, canonical encoder, `scan.rs`): the masternode types and their state methods, the unique-key pre-images (`UniqueKey`, `StateKeys`), `order.rs`'s CHAMP walk, and the special-transaction handlers, the collateral-spend loop and the payee bookkeeping, which `build/mod.rs` runs over either list through a crate-private `BuildList` trait. The handlers are already line-by-line ports; a second copy would copy their bugs, and `diff_dml_apply` checks them against Core directly. What the twin cannot catch is a shared handler's choice between `update`, `update_hot` and `try_add`; Core's results catch that. The twin's independent surface is the data structure the fast path adds: the four indexes, the payee queue and its P1/P2 gate, `phase_order`, the O(1) counts and the unique map. `reference::xcheck(fast, twin, rules)` runs `check_invariants()` and compares position, counter, every masternode's evodb bytes, the internal ids, the unique map (owner and count per key), the buckets, `core_order()`, the counts, the payee and the full projection. `check_invariants()` gains I-P: the lazily computed P1∧P2 flag must equal a literal count and scan, and P1 is asserted only on `FromGenesis` lists above height 0 (EV2 rev4). A list changed through the public `try_add`/`update`/`update_hot` becomes `Decoded`; the build, the readers and PoSe use crate-private bodies that keep the provenance. The twin reads a list itself (`RefMnList::decode_s3`: Core's `Unserialize`, each entry through the twin's own `AddMN` in file order), so its buckets are not the fast reader's. node-l1's `diff_dml_apply` and the quirk replay read the context's list into the twin, `xcheck` the predecessor, build the block with the twin too and `xcheck` the result (the same error, or equal lists); a disagreement is a divergence. The mainnet window does the same at every block, against our own list chain. `reference/tests.rs` runs 40 × 300 random operations on both lists (collisions, unconfirmed masternodes registered across the confirmation heights and shared masternodes with overlapping share owners included, each shown to occur) with `xcheck` after each. | Proposed. |

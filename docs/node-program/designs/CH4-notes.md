# CH4: IBD/reindex pipeline (D-rows)

CH4 is PLAN row CH4: S1 inside the awaited accept, S2's epoch-fenced prefetch (A1 §3.4), W and E. Its plan was approved
as DEC-694 (slices CH4-0…7). CH4-1 is the S2 producer library; the base is integration `56e2e93ea`, the design is CH2
§2.4.3 (the prefetch fence), and CH4-1's bench change is DEC-696. Core has no coins prefetch: a miss reads the
database on `cs_main` (`coins.cpp:44-59` FetchCoin, `txdb.cpp:90-92` CCoinsViewDB::GetCoin), so D1–D9 cite no Core
counterpart. D10 and D11 are CH4-4's, the connect read-ahead (DEC-835, PLAN-CH4 §CH4-4), whose Core counterpart is
`ConnectTip`'s read (`validation.cpp:3414-3422`). D12 and D13 are CH4-6's, E's order and backpressure under it
(PLAN-CH4 §CH4-6), against `LimitValidationInterfaceQueue` (`validation.cpp:3722-3728`, `:3766`). Where this file
and the design disagree, the D-row says why.

## D-rows

| D | Decision | Why |
|---|---|---|
| D1 | V stamps a `PrefetchRequest` with `released_gen` as it dispatches it; `read_batch` takes the snapshot afterwards and the batch carries the request's generation. No shared generation atomic. | CH2 §2.4.3 item 1 allows either order (generation read before the snapshot, or stamped at dispatch). Stamping on V needs nothing shared: the stamp follows the release that began its generation, which follows W's write of F, and every snapshot that reads the request follows the stamp. |
| D2 | No plant for "absence cached": `PrefetchBatch::entries` holds coins only, so a positive-only batch is a property of the type. The clear at a committed disconnect stays (CH2 §2.4.3 item 4) and is pinned by `only_a_committed_tip_disconnect_clears_the_prefetch` and a hand mutant of it, not by a plant. | A disconnect changes neither the database nor F, so a map entry still equals the database (or F shadows it) until the release clears the map; the model cannot kill a missing disconnect clear. Agreed in DEC-696. |
| D3 | X36 (admission past the B/16 headroom) is killed by `admission_stops_at_the_prefetch_headroom` alone. The model checks `usage().prefetch <= prefetch_cap` after each admission that admitted entries, as an invariant. | The model's maps (three keys a request, 256 keys) never come near B/16 at its budgets. DEC-696's text named the model's check; the deviation was accepted after DEC-705. |
| D4 | X34 (the generation read at admission) is killed by `admit_prefetch`'s epoch check, in the cache test and the model's plant matrix. The tests have no arm for builds without debug assertions. | `planted-bugs` refuses optimized builds (`lib.rs`), so every planted build keeps the check; an arm for the other case never ran, and the model's own stale-batch check would have fired first there. |
| D5 | `PrefetchProducer`: V dispatches with `try_send` and takes results with `try_recv`, with at most `depth` requests in flight; the results channel holds `depth`, so a worker's send never blocks. Workers carry LO-9's no-wait marker. A worker stops after handing back a read error (the latch has tripped at the read). Once every worker has stopped, `drain` joins them, raises a worker's panic, returns the credit and the producer refuses requests. The drop cancels the queued requests, closes the channel, joins every worker and only then raises the first panic; a marked dropper trips a debug assert. | LO-9: neither V nor a worker waits on the other. A snapshot must not outlive the producer (the D42/BL-366 class: a RocksDB snapshot past the engine's close), so no path detaches a worker; and a dead worker must not leave prefetch silently off with its credit leaked (Opus review). |
| D6 | `CoinsTable::decode` is `#[inline]`, with its failure (the corruption message) in a `#[cold] #[inline(never)]` helper. | `prefetch/batch_64` gave `decode::<MemoryEngine>` a second caller in `coins_micro` (`multi_get`), and LLVM then kept the whole body out of `get`: coins-fetch-db-1k read +1.582% instructions (34 per fetch, callgrind) with the head's own benches while its routine text was unchanged. DEC-696 condition 1 requires that row SAME; the train PF0 checks it. |
| D7 | The model's op 13 stamps a request and reads it at once half the time, leaves it in flight a quarter, and reads the oldest in flight a quarter; block op 6 reads the oldest in flight (or one stamped then). The coverage floors are unchanged. | A read must be able to follow a release its stamp preceded. Deferring every read halved the admissions below the floor (2,000); at this mix the counts are admitted 2,060 and stale 5,726, identical over four runs at load 190–210 (single-threaded, seeded, `Salt::fixed`). |
| D8 | coins-prefetch-batch-64 keeps `page_faults` ungated, as coins-fetch-db-1k's (DEC-696). | 10 processes × 2 builds: allocs 81,000 and alloc bytes 42,547,000 exact in all 20 and equal across the builds; faults 50,071 exact in one build and 50,071–50,075 in the other. |
| D9 | Deferred to CH4-2/CH4-3 (the wiring): a cache-side constructor that keeps `fetch_gen` private; `request` returning the refused request; tying a producer to the cache it drains into; the comment at `connect/connector.rs:458`, as batches in flight are admitted after a disconnect (safe by D2). | No production caller exists until CH4-3; these shape its API. |
| D10 | The reconnect's parity runs on the connector harness (`chain/tests/connector/read_ahead.rs`), not as a `ChainSut` scenario. A restarted V reconnects the build's stores from coins wiped back to genesis with the read-ahead off, settled and free-running, each with xcheck on and off, and every run must log the same StateDigest and send the same signals in order, the same reports and the same `AbortNode`, with faults in the read-ahead's reads, in V's or in both. `ChainSut` and the conformance replay seams keep the read-ahead off; dashd-node and rdashd run it threaded. | `ChainSut`'s V is the CRASH model's own activation (`crash/chain.rs` `VState::activate`): it reads each block itself and never runs `chain::abc`, where the read-ahead lives, so a scenario there would run none of it. The reader writes to no store. (Opus review r1.) |
| D11 | No PF0 rows `connect-chain-serial-32` and `connect-chain-readahead-32` in this slice. The `connect_chain` bench measures the reconnect from outside with exact `perf stat -e instructions:u` on V's thread, on the reader and on the whole process (DEC-835's gate). | PF0 is not a merge gate (DEC-783); the rows can follow as a backlog row once the slice merges. (Opus review r1.) |
| D12 | CH4-6's event order and backpressure run on the connector harness (`chain/tests/connector/event_order.rs`), not on `ChainSut`. A listener records each `ValidationInterface` notification as two lists, V's inline calls and E's queued ones, each in its order; it leaves the `release_point` and `before_accept` waits at their defaults. The parity covers IBD-shaped windows of 16 blocks, a heavier reorg, and a reorg into an invalid block and back, with a W that releases each flush at once (`ModelW::releasing`), so E runs `ChainStateFlushed` too. It runs with the read-ahead off, settled and free-running, each with xcheck on and off, and the settled run's reader counts are exact: V takes every block it connects from the reader, after an epoch for each disconnect and for the invalid block. Every run stays in IBD and none has a ChainLock, so `NotifyChainLock` and the paths outside IBD are not covered. CH4-4's reconnect parity now records the same full set. The backpressure test holds E at a marker of the test's, with one callback pending, before block 1 arrives. V then waits at the limit after block 5 with 11 pending plus its barrier, in every mode, and the settled reader has read `DEPTH` blocks past block 4. It finds V there when two queries in a row see the same tip: V serves queries where each ABC cycle starts and in the limit's wait, and with E held each cycle connects one block. A failure inside the hold lets E go before the rig's stop waits for it, and each wait has a timeout. | D10's reason: `ChainSut` never runs `chain::abc`. One list across both threads would order the calls by scheduling, not by V. Holding E on block 1's own callback left the pending count to a race, under which a threshold of 11 stopped V at the same block; the marker makes it exact. In a reflink copy, `limit_queue` never waiting, and waiting only above 11, each fail the test. |
| D13 | BL-471 (Q9): `limit_queue_services_queries_while_it_waits` waits for the post's own reply before it reads the log, instead of for a later query of its own. Once V's wait ends, its select takes the post (marked lane) and the test's query (unmarked) in either order. Even after the query, the test could read the log before V ran the post. | A readiness signal, no timeout. Reproduced in a reflink copy by forcing a choice V's select may make: the wait ends at the barrier with the post queued, and V takes the query first and pauses 100 ms before its next command. The old order failed 40/40 and the fix 0/40. Unforced, the old order failed 1/40 and then 0/40 at load 20–30, and the fix 0/40 both times. |

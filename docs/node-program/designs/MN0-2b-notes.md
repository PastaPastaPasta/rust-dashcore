# MN0-2b: implementation notes

Slice decision rows that are not design changes (the plan is PLAN-MN0 §10, in node-program-docs). Core citations are at `v24.0.0-rc.5`.

## MN0-2b-2: the template and proposal read-fault sweep (§10.9-10.11)

| Row | Decision | Why |
|---|---|---|
| 2b-D1 | **The seam.** `dashd-chainstate/src/chain/tests/read_faults.rs`, test-only: `ReadFaults` is a `MemoryEngine` whose reads of one column family and key prefix fail with the engine's own I/O error, answer undecodable bytes, or hide the row, on `get` and on scans alike. Writes pass through. It counts the matching reads and records their keys. The recorded rig (setup-dashd's masternode network, `tests/data/mn0-qc`) runs its coins and evo store over it. Cold = evo and coins flushed, V restarted on the stores, the next block's inputs uncached; warm = no flush. An armed I/O error gets the guarded engine's handling of a real RocksDB read error (`fidelity` tests). No production type is widened | OD-CP-95 |
| 2b-D2 | **Template reads (B-2).** The list, the credit pool and the mined rows are three pins of one committed state: reads in one V turn agree (`EvoReads`, `chain/seams.rs`), which is §10.6's "same pinned view" (OD-CP-115 R1-3). The mineable pool is copied first (`EvoView::mineable`), its leaf lock held only for the copy, as Core takes `minableCommitmentsCs` per quorum for the lookup (`llmq/blockprocessor.cpp:882-936`); no read runs under it, which V's thread checks in tests at the EHF rows read (`mn0_dmn_tip`, OD-CP-115 R1-1). An engine read error is reported once, where the engine read it, and trips the latch. The read answers its error, and `dashd-mining` throws it as `CreateNewBlock` does (`Failed("CreateNewBlock: ..")`). `NotBuilt` is the readiness refusal. An undecodable `mn_diff` row (P4) is the evo store's read error: unreported, no latch, and the node runs on. An undecodable `llmq_mined` row (P3, through `GetQcHashes`) stops the node as in 2b-D5 | OD-CP-20, OD-CP-99 |
| 2b-D3 | **An evo read fault is reported once (F1).** Every evo store-read fault maps to `evo::node::store_fault`, which is `Fatal::new`: V reports it unless the latch shows a report came first, the rule a coins mutation error follows. Before this, `Fatal::abort_node` reported it a second time after the guarded engine, on the tip path, the proposal path and the undo walk alike. The quorum `UndoBlock` maps its `Fault` the same way and keeps `abort_node` for its other errors | OD-CP-96 F1, OD-CP-96a, OD-CP-101 |
| 2b-D4 | **I/O faults stop the node (P3, P4, P5, P7).** V's class is D5's: a store fault on the evo path is `Fatal` and the node stops (DEC-517/518, DEC-77 Q1), with one report. Core's catch-all rejects the block and runs on (`evo/specialtxman.cpp:1053-1055`, `failed-procspectxsinblock`), and its height-index scans never check the iterator's status (`dbwrapper.h:186-215`). This is the declared difference; no new declaration | OD-CP-96 F2 |
| 2b-D5 | **P3 decode is a declared fail-stop.** An `llmq_mined` or `llmq_mined_h` row that does not decode, or an index row based above its mining block (D39), is the guarded engine's corrupt row (`GuardedEngine::corrupt_row`, as a corrupt coin is, DEC-78): the latch trips with kind Corruption and the row is reported once, named by column family and key. Core reads such a row as missing (`dbwrapper.h:322-326`) and rejects later (`llmq/blockprocessor.cpp:680-682`, `:718`). P5 has no read of its own; it reads through P3 | DEC-1185 (1) |
| 2b-D6 | **P4, the parent list.** I/O: 2b-D4. Decode: fail-stop with one report from V; the latch stays open, the stop being V's shutdown request and ended thread, so the next block is never answered (OD-CP-51, DEC-1073; Core reads it as missing). Absent, single chainstate: Core's initial snapshot, an empty list (`evo/deterministicmns.cpp:863-889`, DEC-1064), so the proposal answers `bad-cbtx-mnmerkleroot` (`evo/specialtxman.cpp:995`) with no report and no list cached (OD-CP-46) | OD-CP-49 #2, OD-CP-51, OD-CP-96 |
| 2b-D7 | **P4 absent's residue is Core parity.** The proposal's walk marks the tip as an initial snapshot, as Core's sets `m_initial_snapshot_index` on the same `TestBlockValidity` walk (`evo/deterministicmns.cpp:882-888`). Core also caches the empty list; V caches no fallback list (OD-CP-46). With the row back, the next connect writes the extra snapshot the mark asks for (DEC-1064, `evo/node.rs` `extra_snapshot`), holding the real list at that block. OD-CP-49 #5's "no write" is amended for this row only | OD-CP-100 |
| 2b-D8 | **P2, coins.** I/O: one report and the latch, as Core's `CCoinsViewErrorCatcher` aborts (`coins.cpp:356-369`). Decode: DEC-78's declared fail-stop | OD-CP-96a |
| 2b-D9 | **P6, the parent block for the ChainLock check.** An unreadable parent block reads as no previous ChainLock (`evo/cbtx.cpp:192-195`): no fault, no report, the node runs | OD-CP-49 #3 |
| 2b-D10 | **P7, MNHF signals: decode is a declared fail-stop.** Core rebuilds the signals from blocks on a missing or undecodable row (`evo/mnhftx.cpp:297-319`), so the difference costs availability only; rebuild parity is not required. DEC-1028 (2)'s stop stands; its mechanism moves from today's panic (`EhfSignalSource::signals_for_block`) to a typed `Fatal` under BL-683. Until BL-683 lands, P7's fault rows are probes, not tests | DEC-1185 (2), OD-CP-96 F4 |
| 2b-D11 | **P8, the credit pool, warm and rebuilt.** The recording ends at 406, before the first multiple of 576, the only heights Core and V read the `credit_pool` row (`evo/creditpool.cpp:137`); elsewhere both rebuild. Warm: no row read, and the pool equals a cold rebuild. The cold row waits for a recording past 576 (status/MN0.md follow-up) | OD-CP-96 F6 |
| 2b-D12 | **P1 is a doc row.** The dummy overlay adds no fallible read: `ChainReader`'s `lookup` and `entry` answer `Option`, `with_dummy` is in memory, and the engine holds no block index row on this path. Core keeps its block index in memory too | §10.10 |
| 2b-D13 | **P9, deployments.** A question about the dummy's child ends the attempt in `Fatal::assert` (`connect/proposal.rs`, C-2). On the masternode network past V20 and MN_RR, cold and warm, a proposal asks none | §10.10 |
| 2b-D14 | **Warm controls.** The rows V holds whole (the height index, the lists, MNHF, the credit pool) are not read. The mined rows and the coins still look up absent keys, as Core's positive-only `mapMinedCommitmentBlockCache` and coins cache do, but never a resident key | OD-CP-49 #4, OD-CP-95 c3 |
| 2b-D15 | **The disconnect path reads no mined row.** The quorum processor's `UndoBlock` erases the block's mined rows by the keys the block names: a cold invalidate of 300 reads no `llmq_mined` or `llmq_mined_h` row from the engine (pinned at zero reads by `an_evo_read_error_undoing_a_block_is_reported_once`), so a P3 fault cannot reach it. Its `QcBlockError::Fault` arm, mapped to `store_fault`, is **unreached on this chain**. The undo walk's reads (`mn_diff`, `mn_snapshot`) are reported once | OD-CP-101 (1), OD-CP-103 |
| 2b-D17 | **Past 432 on default regtest (MN0-2b-3): window placement, null-only.** `mn0_template_dashd`'s `templates_equal_dashds_blocks_through_three_dkg_cycles` mines 1 to 504 on dashd and the node: every template is dashd's block byte for byte, through the DKG cycles at 432, 456 and 480. Each cycle's commitments are mined at +10 to +20 (3 at +10 and +11, 5 at +12 to +18, 2 at +19 and +20; `llmq_test` and `llmq_test_dip0024`'s windows with their boundaries, 441/442/450/451 and 443/444/452/453 in the first). Default regtest registers no masternode, so every commitment is null; non-null content is 2b-D16's. **E-a:** `templates_equal_dashds_blocks_from_dip3_at_48` mines 1 to 200 on both nodes under `-dip3params=48:48 -testactivationheight=dip0024@1000`, every template dashd's block: the CbTx before V20 (E1) from its first block at 48. Waived: the E1→E2 and E2→E3 transitions and a `-dip3params=2:2` byte comparison (`mn0_dmn_tip` covers 2:2's height and parent); V connects dashd's 48:48 chain (`ch7a4b_dashd`) and the eras' reads are V's own deployments. V24 (CbTx version 4) is BL-712 | PLAN-MN0 §10.7, OD-CP-60 c2, OD-CP-106, OD-CP-115 R1-2 |
| 2b-D16 | **`with_qc`'s null-commitment caveat: what covers what.** Window placement (which heights carry commitments, and their bytes) is covered against dashd by 2b-D17, on null commitments only. Non-null root content is covered by the recorded masternode network, whose `with_qc` quorum roots equal dashd's from the first signed commitment to 406, every checked block over a non-empty active set (asserted: as many non-empty as checked), and by the mineable rig test's non-null mined row. No test covers a non-null commitment inside a dashd-compared template window; that leg is BL-707 | OD-CP-60, OD-CP-106, OD-CP-115 R1-7 |
| 2b-D18 | **The template's list and the DMN tip's.** The source reads `tip_list` (`GetListForBlock(pindexPrev)`, `masternode/payments.cpp:152`), not `dmn_list` (`GetListAtChainTip()`). Between V's commands after init the two are equal: every tip signal whose tip is not its fork moves the DMN tip, `InvalidateBlock`'s included, with or without a mempool (`chain/view.rs` `dmn_tip`, `chain/signals.rs` `sync_updated_block_tip`); `mn0_dmn_tip` pins it on the masternode network with V on no mempool, as rdashd runs. They can differ inside one ABC command, at a release point between a fork block's failed connect and the reconnect, and before init's `InitializeCurrentBlockTip`. No payee is observable in MN0-2b (a registered list is refused, "DIP0003"), so mutant b2 survives; the payee test with a differing-lists control and the release-point window test are BL-711. `node-l1`'s `diff_chain` keeps `no_mempool` false: its suites read V's disconnect pools through `NodeSide::pools()` (DEC-500), and the two lists are equal at command ends; a `GetListAtChainTip` read at a release point stays BL-711 | OD-CP-108, OD-CP-110, OD-CP-113 |

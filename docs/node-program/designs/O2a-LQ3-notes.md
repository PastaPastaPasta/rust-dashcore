# O2a-LQ3: oracle lock and recovered-signature verdicts, implementation notes

O2a-LQ3 adds four Core entries on the LLMQ context: `oracle_llmq_verify_chainlock`, `oracle_llmq_verify_islock`, `oracle_llmq_verify_qsigrec` and `oracle_llmq_verify_mined`. They are ABI 25, on Core branch `node/o2a-lq3-oracle-v24.0`. This note also covers their `dash-oracle-sys` bindings and the node-l1 differentials. Those differentials compare the bindings with LQ3a's `verify_chainlock`, `verify_islock` and `verify_qsigrec` and their inventory hashes, and with SB8's mined path (`SigPath::Mined`, SB8 D18). Program decisions live in DECISIONS.md. Core references are to v24.0.0-rc.3.

Individual verification; possible security note: see manager.

| D7 | `oracle_llmq_verify_chainlock` is `VerifyChainLock` for any height. | D10 | The mined entry runs, for one non-null commitment: stage 1: `CheckLLMQCommitment`'s `Verify(checkSigs=false)` (`llmq/commitment.cpp` v24:301, called from `evo/specialtxman.cpp` v24:258, repeated by `ProcessCommitment`); stage 2: `ProcessBlock`'s signature checks. ## Asks

- **A1 (V19 crossings in the oracle).** Core could give an oracle verdict on a crossing if an entry took separate read and check schemes. That is a small change to the four signatures while ABI 25 is still a build identifier. It is not done: LQ3a D20/D21 already show both directions with real signatures, and the crossing is a race. Say if the oracle should cover it as well.

# BS11a-4: pairing and verify on Exotic operands, implementation notes

Decision rows for BS11a-4 (BS11a design §9's slice 4; DEC-449 orders it after BS11b). The slice makes `dash_pkc::bls::core`'s three verifies give Core's answer on every operand: today they answer `BlsVerdict::Unsupported` when the legacy verify flag meets an operand off the curve or outside the prime-order subgroup. It adds:
- a transliteration of relic's optimal-ate Miller loop (`pp_map_sim_oatep_k12`'s B12 branch);
- the engine branch behind BS12's serial verify (design D22);
- `BlsValue::resolve`;
- the D64 legacy-flag verify rows against dashd;
- `diff_bls_verify`;
- quirk 45 to `tested`;
- BL-398 (provenance for ten older corpus files) and BL-399 (`verify_secure_aggregated`'s legacy re-decode).

Citations are at Core `v24.0.0-rc.3` (`0364ed626e`), whose `src/dashbls` and `src/bls` are unchanged at rc.4 (SW-V24-rc4-pin-delta.md §2), and the oracle shim `77dbec824` (ABI 28). Design D-numbers are BS11a-legacy-bls.md's, cited "design D*n*"; BS11b's are cited "BS11b D*n*". relic paths are under `src/dashbls/depends/relic/src/`.

## relic's pairing as configured

`PP_METHD "LAZYR;OATEP"` (`relic_conf.h:533`), so `pp_map_sim_oatep_k12` (`pp/relic_pp_map_k12.c:523-599`) runs on Core's verifies:
- **Input.** Pairs with an infinity side (z = 0) are dropped. The rest are normalized (`ep_norm`, `ep2_norm`; `inv(0) = 0`, R3). `r` starts at 1 (`fp12_set_dig`). With no pair left, `r` stays 1.
- **Loop** (`pp_mil_k12`, `:51-133`):
  - It runs over `bn_rec_naf(|x|, 2)`, with `t[j] = Q_j`.
  - Doublings evaluate at (3x_P, −y_P), and additions at P with `Q_j` or `−Q_j`.
  - The **first doubling line is written into `r` itself**. `pp_dbl_k12_projc_lazyr` (`pp/relic_pp_dbl_k12.c:237-`) writes slot `[0][0]` and two more, so the initial 1 is overwritten.
  - Every later line goes through one buffer `l`, zeroed once, and is multiplied in with `fp12_mul_dxs`. That product reads only the line's sparse slots. Doubling (`l[1][1]`) and addition (`l[one][one]`, `pp/relic_pp_add_k12.c:173-`) write their slots by the twist type, so a stale slot left by the other is never read.
- **x < 0.** `fp12_inv_cyc(r, r)` is a conjugation, not an inversion off the cyclotomic subgroup. FE commutes with it, so FE(conj f) = FE(f)⁻¹ in μ_r and the "= 1" verdict is unchanged (design Lemma E).
- **Final exponentiation.** `pp_exp_k12` (`pp/relic_pp_exp_k12.c:220-`) is not ported (design D7). The verdict is "every f_c ≠ 0 ∧ FE(Π f_c) = 1", with FE on blst's `blst_final_exp`.

## Decisions

| D | Decision | Source |
|---|---|---|
| D1 | **Chunk routing.** A `NativeVerify` chunk whose pairs are all Group (in the subgroup, on blst) stays on BS12's blst Miller loop. A chunk with any Exotic operand, or any engine result outside the subgroup, runs **whole** on the engine: Group operands are rebuilt per Lemma T′. The engine and blst Miller values are therefore never mixed within a chunk, only multiplied across chunks before the one final exponentiation. **Landed (4b):** `bls/native.rs`. A wrapper's element is a Group operand exactly when it passes `IsValid` (the point blst holds, whatever coordinates Core keeps, since relic normalizes before pairing), otherwise relic's coordinates. The 250-pair chunk is kept as Core's structure (`schemes.cpp:337-341`); it is structural, not observable, since no partition of the pairs changes the product. relic's `pp_exp_k12` and blst's final exponentiation are the same power map on every element, zero included (D5), so one final exponentiation over the product of the chunks' Miller values gives Core's product of per-chunk pairings exactly; relic's pairing sets no error code on any class, so `NativeVerify`'s code check never decides | design Lemma E, Lemma U, D22 |
| D2 | **`BlsVerdict::Unsupported` stays in the API and is no longer produced** by the three verifies or `BlsBatchVerifier`. Removing it changes dash-evo, dash-dml and dash-coinjoin, which other rows own. **Ruled (DEC-465):** kept, never produced; its removal is BL-400, with the EV and CJ0 owners. **Landed (4b):** the three verifies never answer it; `BlsBatchVerifier` drops its tracking and `unsupported()` always returns `false`, kept with the variant until BL-400. dash-evo's `a_single_member_check_without_a_verdict` asserts an `Unsupported` that no verify now gives; it is deleted, with its one-member roster, at the pin bump to the fork head (made with 4c, whose bench rows need `resolve`), with the note "premise removed by 4b (BL-400)". The dead `Unsupported` arms downstream go with BL-400 (DEC-485) | inventory above, DEC-485 |
| D3 | **Fp12 arithmetic.** relic's tower is blst's: Fp2 = Fp[u]/(u²+1), Fp6 = Fp2[v]/(v³−(1+u)), Fp12 = Fp6[w]/(w²−v). Field products are exact, so `fp12_sqr`, `fp12_mul` and `fp12_mul_dxs` are computed by blst's serial `blst_fp12_sqr`/`blst_fp12_mul` on the element relic holds. `mul_dxs` multiplies by the line with only its sparse slots set, which is the product relic forms. The slot placement is checked by the Lemma E probe (D5) and by D6's model. **Landed (4a):** relic's `fp12_mul_dxs_lazyr` reads exactly the three slots both line functions write, and is safe for the aliased `r = r·l`, so every Fp12 step is an exact product; the replay (D5) confirms it. | design §3.2, D6 |
| D4 | **Line and Miller port.** `pp_dbl_k12_projc_lazyr`, `pp_add_k12_projc_lazyr`, `pp_mil_k12` and the B12 branch of `pp_map_sim_oatep_k12` are transliterated line by line. That includes the first-line-into-`r` write, the shared `l` buffer, (3x_P, −y_P) for doublings, `bn_rec_naf(|x|, 2)` and the `fp12_inv_cyc` step. Each function's doc cites its relic span. **Landed (4a):** `relic/pp.rs`. Two departures, both proved: the general-b branch of the doubling is the one ported (b = 4 is `RLC_TINY`, `relic_ep_curve.c:44-66`); `pp_mil_k12`'s addition after the first doubling runs only when the NAF's second digit is non-zero, and for |x| = 0xd201000000010000 it is zero (top digits 1, 0, −1), so it is not ported and a test pins the digits. | design D5, D7 |
| D5 | **Lemma E probe** (design's proof obligation): a C probe links the pinned `librelic.a` and blst 0.3.17, compares `pp_exp_k12` with `blst_final_exp` on 10^6 random Fp12 elements (unitary, non-unitary and 0), records "is 1" agreement and k, and compares relic's Miller value with the engine's on random Usable and Exotic pairs (up to Fp6* factors, and zero-ness exactly). The probe source goes in the fork's `contrib/vectors/bls_oracle/`, beside `probe.c`; the results go in these notes. **Landed (4a):** the probe is `contrib/vectors/bls_pairing/` (its own directory, since it links relic and blst rather than the oracle). The probe clears relic's `seeded` flag before `rand_seed` (`core_init` has already seeded the HASHD generator from urandom, and a second `rand_seed` mixes into that state, `relic_rand_hashd.c:176-215`), so a seed reproduces a run byte for byte. Linked against the pinned `librelic.a` (sha256 `be445a04…`): `probe fe 1000000 bs11a4-lemma-e` found `pp_exp_k12` **equal** to `blst_final_exp` on all 10^6 elements (k = 1; general, unitary, 0 and 1), so "is one" agrees everywhere. `probe pairs`: the engine's Miller value through blst's final exponentiation equals relic's `pp_map_sim_oatep_k12` exactly on 10^5 calls (`probe pairs 100000 bs11a4-replay`, 1–4 pairs each, every point class, zero Miller values included: P4, P5).

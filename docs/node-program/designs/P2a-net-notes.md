# P2a-net: `dashd-net` implementation notes and D-rows

P2a-net implements `designs/P2a-outbound.md` rev3 (DEC-56) §7.3 phases D and F, reshaped by SB0 rev6.1 §3 and §12.1: SB6 owns AddrMan, the dial steps, seeds, anchors and the addr intake; P2a-net owns the threads that drive the steps, the binds, the files, the RPC back ends and the relay. This file records the implementer's decisions where those sources leave a choice, per the IMPLEMENTER contract ("decide, record a D-row, continue"). Core line numbers are Dash Core v24.0.0-rc.3 (DEC-82), from `/work/scratch/p2a-fable/v24.0.0-rc.3/src`.

| D | Decision | Why |
|---|---|---|
| D1 | P2a-net is a new crate, `dashd-net`, depending on SB6's `dash-p2p` and P2a-core's `dashd-p2p`. It edits neither. The base is integration 9da1e93bf with SB6 **0818fa776** (cf8924712) and P2a-core **0a0ff5e1c** (a086985fc) merged; P2a-core already contained that SB6 head. | The brief: build on SB6, code against its API and edit neither crate. P2a-core's `AddressRelay` seam, `PeerMap`, `PeerSlot` and `PeerState::net` are public, so the relay fits outside `dashd-p2p`. Folding the crate into `dashd-p2p` later (P2a §2.3's `net/` layout) is a move, not a rewrite. |
| D2 | The relay's hook point is P2a-core's `AddressRelay` seam (P2a-core D14): `relay` after SB6's intake, `send_section` at `SendMessages` section 5, `on_getaddr` for inbound `getaddr`. `NodeAddressRelay` implements it; the host installs it as `Seams::addr_relay`. | P2a-core defined the seam at Core's three positions, so no new hook is needed. P2a-core phase E (77a5341a3) closes the `addr`, `addrv2` and `getaddr` registry rows on the host installing `NodeAddressRelay` as `Seams::addr_relay`. |
| D3 | Superseded. `MaybeSendAddr` advertises the peer's `m_our_services`, which P2a-core phase E (374e8db72) passes to `send_section`; the recompute from config and permissions is gone. | Core reads the stored `m_our_services` (`net_processing.cpp:6205`); P2a-core now hands over that value. |
| D4 | `InitBinds` has v24's rules only: any failed `-bind`, `-whitebind` or onion bind, or a failed `0.0.0.0` default bind, fails startup with `"Failed to listen on any port. | D5 | Superseded by SB6 68cd1ef4b (ask A1). `addconnection` takes `NetCore::try_grant(DialLoop::OpenCon)` after the type limits, returns `false` without a slot, and passes the grant in `OpenRequest::grant`, as Core's `CSemaphoreGrant(*semOutbound, true)` does. | Loopback `add_connection_needs_a_slot`. |
| D6 | Every random draw in the relay comes from the core's `FastRandom`: the cache lifetime's `GetRandMillis(6 h)`, `PushAddress`'s overwrite index, the `m_addr_known` reset tweak and both `GetExponentialRand` timers. | Core draws from a fresh `FastRandomContext` or the global RNG. SB6 maps those to the core's stream (SB6 D26), so deterministic mode reproduces a run, and the differential targets can seed it. |
| D7 | `FileStore` writes all three images as Core's `SerializeFileDB` does: `<prefix>.<4 hex>` in the data directory, `fdatasync`, then rename. Then it syncs the directory (P2a §4.1; Sol r1 R1-m4), which Core skips; a failed directory sync is a warning, since the image is already in place; Windows has no directory handle to sync. Core writes `banlist.json` in place (`WriteSettings`, `addrdb.cpp:143`). | The bytes are Core's either way, and an atomic replace cannot leave a torn ban list. The directory sync makes the rename durable and is invisible on the wire and in the file. |
| D8 | The thread drivers and the dial `sim` share one step function (`driver::step`) and differ only in the `DialExec`: `RuntimeExec` blocks the loop's OS thread on the host's runtime, while `SimExec` moves the virtual clock, attaches in-memory sockets after Core's `OpenNetworkConnection` checks (for an address: `IsLocal` at the listen port and bans; for a name: an existing connection by name; for both: an existing connection to the service) and `addrman.Attempt`, and stops the run when the loop waits for a slot no connection will free. Closing a `sim` connection waits for its `FinalizeNode`, which SB6 calls after the grant is released. | The `sim` then tests the drivers' code path, not a copy. `SimExec` repeats Core's checks because `NetCore::open` dials TCP directly. Waiting only for the table removal would leave a window in which the grant is still held, and the loop would wrongly report itself blocked. |
| D9 | `DumpAddresses` runs on a runtime task that sleeps the full interval (15 minutes) and then awaits `NetCore::dump` through `spawn_blocking`, so each interval counts from the end of the previous dump (Core's `CScheduler::Repeat`, `scheduler.cpp:102-111`; Sol r1 R1-m3). The dump is never cancelled: `stop_threads` waits for it (D19). | Core runs it on its scheduler thread. The store blocks on file I/O, so it must not run on a runtime worker. Runtime test `dumps_wait_a_full_interval_after_each_dump` (300 ms saves, 200 ms interval) fails on the earlier tick-based schedule. |
| D10 | The bind errors keep Core's text, including `PACKAGE_NAME` ("Dash Core") in `"Unable to bind to %s on this computer. %s is probably already running."`. | Log and error texts are ported verbatim. DEC-83 concerns the wire identity, and functional tests match this text. |
| D11 | `MaybeSendAddr`'s `IsInitialBlockDownload()` comes from P2a-core's `ChainAccess::is_initial_block_download`, given to `NodeAddressRelay::new`. Like Core, it is evaluated only when `fListen` holds. | It is the latch Core reads, and the snapshot is the processor's own chain view. |
| D12 | `SystemResolver` is Core's `LookupHost` over a `DnsLookupFn` (Core's `g_dns_lookup`): NUL and empty names fail, `[…]` is stripped, internal results are dropped, and at most `max` are kept. The default lookup is `wrapped_getaddrinfo`: a numeric host decodes as glibc's `getaddrinfo(AI_NUMERICHOST)` does (D17); with lookups allowed anything else goes to the standard library's `getaddrinfo`, which passes no `AI_ADDRCONFIG`. `allow_lookup` comes from the caller per call (`NetConfig::name_lookup`, `-dns`, for named connection targets; `true` for DNS seeds; D16). `.onion` and `.i2p` names resolve to nothing. SB6's `NetAddr` keeps no IPv6 scope id, so a link-local answer loses Core's `sin6_scope_id`. | Core's `SetSpecial` makes those names addresses, which only a proxy can reach. SB6 has none, so failing early is the same outcome, and the name never leaks to DNS. Without `AI_ADDRCONFIG` a host with no IPv6 route may get AAAA answers. Core would not, but those connects fail like any unreachable address. The crate stays `forbid(unsafe_code)`, so the `AI_ADDRCONFIG` call is not made directly. |
| D13 | Superseded by SB6 a55e0e807 (ask A2). `ConnMan::start` calls `NetCore::start_addresses()` after the binds succeed (or at once when not listening); a failed `InitBinds` returns before it, so `anchors.dat` is left alone and shutdown dumps nothing, as in Core. The sim calls it right after `NetCore::new`. | Loopback `bind_failure_is_fatal` checks that `anchors.dat` keeps its bytes and `peers.dat` (written at load by `LoadAddrman`) is not replaced. |
| D14 | `diff_p2p_addr`, `diff_p2p_addrv2` and `diff_p2p_getaddr` are session targets in `node_l1::p2p_addr` (D25), registered with owner `dashd-net` and run on P2a-core's session leg (`node_l1::p2p_node`). On today's leg (`Seams::default()`, so `NoAddressRelay`) any script that delivers address messages may differ on peer state, whether or not Core sends one, so agreement or difference proves nothing yet. **Acceptance:** after the leg lands and FZ1 merges (train 10), one `fuzzctl certify` run per target (DEC-184, DEC-186) and a multi-relay smoke (`diff_p2p_multi_relay`) on the corrected leg, where `addr` is no longer masked and the relay is installed. (Superseded text: the three targets were first deferred on three blockers. Comparing the four projections catches queue and timer differences even when no message goes out in the script. | D15 | The accept loop sleeps 50 ms after an accept error other than `ECONNABORTED`. | Core's loop spins on `EMFILE`/`ENFILE` because the listener stays readable (`net.cpp:1853-1858`). Under tokio the same error would spin a runtime worker. 50 ms is Core's `SELECT_TIMEOUT_MILLISECONDS`, so an accept retry comes no later than Core's next socket pass would. Per-connection errors that Linux reports through `accept` (`EPROTO`, `ENETDOWN`, …) also wait, which only delays the next accept. |

| D17 | The numeric decode is a port of glibc's `getaddrinfo(AI_NUMERICHOST)` path: `inet_aton_exact` (one to four parts, decimal/octal/hex, the same port as `dash-coreimport`'s `netstate::subnet`), else an IPv6 address with an optional numeric `%scope` (dropped). (Sol r1 R1-m1.) | `127.1` and `0x7f000001` now resolve with `-dns=0`, as in Core. A port instead of the FFI call keeps the crate free of `unsafe`. | D18 | `ConnManOptions::open_filter` (`driver::OpenFilter`) is a boundary on what the node may dial: the dial threads' `RuntimeExec` and the `addconnection`/`onetry` back ends check it before any socket exists, and a refused open is dropped with its grant. | D19 | `ConnMan::interrupt` sets a `watch` flag instead of aborting tasks. | D25 | The generators build every relay state from script prefixes, since O1c's session seeds no AddrMan, relay state or permission: two to four peers at 70242, 70223 (`ADDRV2_PROTO_VERSION`) or 70222; handshakes with `sendaddrv2` before `version`, before `verack`, after it or never; AddrMan seeding through a live outbound full-relay or manual peer's `addr` (10, 100 or 1000 fresh routable addresses, each in its own /16: its bucket holds 1001 tokens after the node's `getaddr`), else a live inbound peer's (one token); `diff_p2p_getaddr`'s seeder is manual); entry classes (routable and unroutable IPv4/IPv6, OnionCat, internal, IPv4-mapped, TorV3/I2P/CJDNS, TorV2's id 3 and other ids v24 skips (unknown ids also at 511, 512 and 513 bytes: Core skips the first two and throws on the third, `MAX_ADDRV2_SIZE`), wrong and oversize lengths, times stale, future and at the 100000000 cut, non-canonical services); entry counts around 1000 (`MAX_ADDR_TO_SEND`); truncated payloads; one address message in four is built for Core to relay (one to ten routable addresses stamped now, from an inbound peer, after another peer's relay is on); `getaddr` mostly from an inbound peer that has not asked (Core answers one per connection); clock jumps around the token refill and the reply cache (21 h, 24 h, 27 h); a 5-min flush at the end. To keep Core's peers: at most one preferred-download peer (outbound full-relay, manual or block-relay; later picks are inbound); outbound peers serve blocks, except feelers; inbound peers serve blocks only without a preferred peer; outbound full-relay and block-relay peers `inv` the genesis block (the tip); every message gets its own pass; and a clock move past 19 min since the last `ping` first has every connected peer answer it, in a pass at the moved time. Messages go only to peers Core keeps. The generator tracks the four ways it ends one on purpose: a feeler at its `version` (no handshake message follows it); a `sendaddrv2` after `verack` at 70223 or later (D28); an ADDR_FETCH peer at an address message of more than one entry and at most `MAX_ADDR_TO_SEND` that Core reads (a read that throws, on a truncated payload, non-canonical services, an address above 512 bytes or a known id at the wrong length, acts on nothing, relay included; more than `MAX_ADDR_TO_SEND` turns relay on and returns before the disconnect, `net_processing.cpp:4410-4420`), and at the first pass more than 300 s (`10 * AVG_ADDRESS_BROADCAST_INTERVAL`, `net_processing.cpp:6334`) after its `m_connected`, which is the session's start, once it is connected, so it gets no `pong` across a jump and nothing after; one whose handshake comes past that mark ends in its own `verack` pass, and its script stops there. AddrMan's seeder is chosen after its handshake: a session has at most one outbound full-relay or manual peer, so one that a late `sendaddrv2` ends gives way to an inbound one (`diff_p2p_getaddr` re-picks at each re-seed). `tests/p2p_addr.rs::scripts_reach_core_address_paths` checks this on Core's leg: every delivery of 64 scripts per target must reach a peer Core has not ended, and every peer Core ends must be one of the four, for that reason, and after every pass the peers Core has ended must be exactly those the script has (D28) (Sol r3 R3-M1: r2's test exempted ADDR_FETCH and late-v2 peers and ignored failed deliveries, which hid 177 deliveries to removed peers). | Core disconnects otherwise, and a script whose peers are gone compares nothing: an outbound peer without `NODE_NETWORK` during IBD goes after `version`; the 15-min header-sync timeout drops the sync peer (an inbound one serving blocks, if it came first) when another preferred peer exists, and a feeler serving blocks is one; `ConsiderEviction` drops an outbound full-relay or block-relay peer that has not shown the tip's work 22 min on; the 20-min ping timeout drops peers across clock jumps, and a pass at the old time would send a fresh `ping` just before the jump; a pass processes one message per peer, so a second delivery would wait past the next clock move.

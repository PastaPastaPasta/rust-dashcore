## 0. Summary

1. **What exists.** SB7 landed Core's `CSimplifiedMNListEntry` (`SmlEntry`, its hash without
   `nVersion`), the full `merkle_root_mn_list` and `SmlList` with a cached merkle tree. EV2a landed
   `MnList` over `imbl` with a structural diff that skips shared subtrees (`MnList::diff_to`),
   `core_order()` (quirk 41) and Core's evodb decoders (`codec::core_disk::{decode_list_s3,
   decode_diff_d4}`), which IM1b already uses for `governance.dat`.
2. **What EV4-serve adds.** In `dash-dml`: `Dmn::to_sml_entry`/`MnList::project_sml` (D1), the
   entry's network form per band (D2), `SmlRootCache` with the full reference (D3, D4), and the
   mnlistdiff builder with its message encoder (D5–D8). In `dash-coreimport`: `evodb`, which
   rebuilds Core's list at any block from evodb records the way `GetListForBlock` does (D11).
3. **Evidence** comes only from Core: five functional-test regtest chains that rc.3 produced
   (BS2's `/work/conformance/regtest-v24`), their evodb records, and rc.3's `mnlistdiff` replies
   to `getmnlistd` in all seven serialization bands, plus the ABI 8 shim on every imported entry
   (D9, D10). No live oracle is read (D9).

## 2. What CH7a needs

- `SmlRootCache` for `CheckCbTxMerkleRoots`' MN root (`cbtx` `CalcCbTxMerkleRootMNList`), one per
  chainstate, fed each connected block's list (and the reorg target's on a disconnect; D3 makes
  that exact).
- An `MnListDiffSource` over the evo store, LQ2's block processor and the block store, for P6b's
  `getmnlistd` server and the `protx diff` RPC (RP2a adds `extended`). Its contract:
  - `active_quorums` is LQ2's `GetMinedAndActiveCommitmentsUntilBlock`. The vector test takes the
    sets from each reply (D14), so it is not yet checked against Core: re-run
    `dash-coreimport/tests/evodb_serve.rs::mnlistdiff_matches_core_in_every_band` with LQ2's sets
    in place of `ReplySource`'s.
  - `quorum` gives the height of the block `quorumHash` names and the commitment's `quorumIndex`
    (0 for commitment versions 1 and 3); `None` exactly where Core's `GetQuorum` returns null.
  - `coinbase_chainlock(target, height)` resolves the work block as the target's ancestor at
    `height` (`GetAncestor`, `sd:87-98`), never as the active chain's block at that height. It
    returns `Ok(None)`, never `Err`, for a negative height, a block before V20 and any failure to
    read the work block's data, pruned or not (`cbtx:192-195`): Core answers those requests with
    the null signature. `Err` is for failures outside that read (the block index, quorum storage).
  - `v20_active_after` is `DeploymentActiveAfter(target, V20)`.
  - `target_block` is `ReadBlockFromDisk(target)` and cannot fail with a storage error: every
    failure of the read (open, I/O, decode, hash mismatch) is `None`, `BlockRead`, scored, as
    Core's read catches them all and returns false (`node/blockstorage.cpp:805-848`, `sd:229-233`). The builder asks for it last, so the
    server must not read the target block before calling the builder; it checks `check_request`,
    reads both lists (a `ListUnavailable` or corruption is reported before any block read), then
    calls `build_mnlistdiff` (D17's order).
  - The target's list is Core's default list (null block hash) below DIP3, never
    `MnList::new(target, height, 0)`: Core's reply then names the null hash (`dmn:828-832`,
    `sd:125`; vectors in D9). Above DIP3 it names the target; the builder debug-asserts one or
    the other (`MnList::is_default`).
  - **One immutable chain view per request.** The server holds one read guard or snapshot of the
    chain state from request validation (`check_request`'s statuses) through the list and quorum
    reads, the work blocks' ancestry, the target block's data and the encoding, as Core holds
    `cs_main` (`np:5615-5622`, `sd:159`). No input may come from a later view: a reorg between two
    reads would otherwise mix branches (D18; the reorg race test is CH7a's).
  - The server maps each refusal to Core's P2P outcome with `MnListDiffError::peer_outcome`: no
    reply, and `Misbehaving(1)` except for the unavailable-data sentinel errors and its own
    failures, which are only logged (`np:5611-5633`, `sd:154-252`; D17, whose mapping test is
    CH7a's).
- P6b: Core answers `getmnlistd` from any peer that finished the handshake: no IBD guard, no
  permission check, no rate limit (`np:5611-5636`). A short payload throws in `vRecv >> cmd` and
  is only logged (`np:5612-5613`, `:5940-5943`); trailing bytes are ignored. A Bitcoin-style IBD
  guard would diverge silently.
- CH6b: a LevelDB reader feeding `EvoDbImage::from_records`.

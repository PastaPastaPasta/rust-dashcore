# O1c: oracle AddrMan and peer sessions, implementation notes

Decision rows taken while implementing O1c (`dash-oracle-sys` AddrMan and peer-session
bindings, Core branch `node/o1c-oracle-v24.0`). Program decisions live in DECISIONS.md.

| Row | Decision | Evidence |
|---|---|---|
| D1 | **`SessionConfig::check_block_index`** passes `-checkblockindex=0/1` to the session (P2a-core ask, 2026-10-11). With the check off, a passing session's output is unchanged; only its cost moves. Crash detection is not the same: with the check on, a run that breaks a block-tree invariant asserts (and the check's own allocations can fail), where with it off the run continues. **Ruling (manager, after Sol r2):** fuzz legs run with the check off. Certification replays (`-runs=0`, before and after the window) run with it on, so every corpus input keeps block-tree assertion coverage. Everywhere else in this tree it stays at Core's test default (on). Every `ChainstateManager::Options::check_block_index` read is the early return in `CheckBlockIndex` (validation.cpp:5609). The body only reads the block tree and asserts. It makes no draws and sends no messages. Its header-hash check is commented out, so it makes no X11 calls either. The session's options take `-checkblockindex` through `ApplyArgsManOptions` (setup_common.cpp under `DASH_ORACLE_HOOKS`), so no Core change and no re-pin is needed. Cost: the check walks the whole tree after each change. For a session that handshakes and takes one `headers` message of N new headers, it costs 324/338 ms CPU per 5 inputs on/off at N = 100, 1,455/601 at N = 1,000, and 4,947/863 at N = 2,000 (5.7×). These figures come from a temporary probe on a debug test build against the pinned plain archive (task-clock). | `tests/peer_session.rs` `check_block_index_changes_no_transcript`: 5 seeds over the handshake script and both reorg scripts give byte-identical outcomes (draws and calls included) on and off. Witness: with the check on, a `headers` delivery allocates under `ChainstateManager::CheckBlockIndex`; off, nothing does. |
| D2 | **A session's logger starts from a fresh process's filters** (Sol r2 F1). Core's init only adds to the logger: `SetLoggingCategories` enables categories (`-debug=0` enables none and disables nothing), `SetLoggingLevel` sets only the levels it names, and `DisconnectTestLogger` keeps both. So an earlier session's `-debug` categories and `-loglevel` overrides carried over. They decide what Core computes and records: NET lines hash headers (X11 calls) and report Misbehaving. Before `TestingSetup`, `oracle_peer_session_new` saves the caller's category mask, global level and per-category levels. It then sets all three from a default-constructed `BCLog::Logger`, which is the state a fresh dashd's init applies its options to, so no values are hard-coded. The logger's other settings are assigned from the options on every start, so between sessions they need no reset. `oracle_peer_session_free` restores, on every path including failed starts, the saved filters and the caller's line format: timestamps, microseconds, thread names, source locations, `m_always_print_category_level` and `fLogIPs`. The oracle's other calls (`LogCapture`) set that format once per process. It restores the level map first, so if copying it fails nothing changes. The real diagnostic X11 calls stay in the call log. Only Core's private `m_started_new_line` carries over, and only after a line with no newline, which Core never writes. | `tests/peer_session.rs` `a_sessions_logging_starts_fresh`: a fresh child process per scenario runs quiet/debug/quiet and default/`net:info`/default, ten unconnecting headers each. The first and third sessions' complete raw transcripts are equal, and the second's differs. Both scenarios fail against the r2 pin. The handshake's raw outcomes are included. `tests/contextual.rs` `sessions_leave_the_logger_as_they_found_it`: a debug-level LLMQ reason reads the same before any session as after a session, a refused start and a start that throws, each with `-loglevel=llmq:info`. It fails on the filters-only fix. |
| D3 | **A session may start after a contextual call.** Contexts install a process-lifetime EHF stand-in (`NoSignalsEHFManager`) as `AbstractEHFManager::globalInstance` and never remove it. A later session's `CMNHFManager` asserts that it is the only instance, so the process aborted. `oracle.h` lets other calls run before and after a session, and this predates O1c (O2a). A session start clears the stand-in, and only the stand-in; the next context build installs it again. | Found by D2's caller test (it aborted on `evo/mnhftx.cpp:51`). That test now covers it. |
| D4 | **A session leaves the process as a fresh one would** (Sol r3: the stats client was left null, so a later `check_block` crashed at validation.cpp:4429; D2 and D3 were the same class). The audit took every process-global that `TestingSetup`, the session's start or its teardown writes, plus the static memory a session changes. That memory was found by diffing the test binary's writable segments around a session and symbolizing the diff. The table below gives each entry's outcome. **Saved at start, restored at free:** these are the caller's values, put back when free has torn the node down: after a session, a refused start or a start that threw. If the teardown itself throws, the node is not destroyed and nothing is restored. The session then leaks and stays the process's session, and the Rust binding refuses every later call of the pin (D5). **Reset at free:** these return to the state a fresh process has, through Core's own reset, a fresh value, or a `DASH_ORACLE_HOOKS` reset. **Already fresh:** these needed no change. **Left:** these were checked and cannot change any oracle result. | `tests/process_state.rs` `sessions_leave_the_process_as_a_fresh_one`. A fresh child process runs every non-session entry point with fixed inputs, on mainnet and regtest. It then runs, in order: a plain session; a session with non-default options, 16 blocks and a peer script; a refused start; and three starts that throw (one in argument parsing, one at `BasicTestingSetup`'s stats client, one in `ChainTestingSetup`). After each, it runs the whole set again. Each result must equal the fresh result byte for byte (`Debug` of the full result). At the end the plain and the busy session run again, and their complete raw transcripts must equal the first ones. Not reached by this test: a session that stores script verdicts the sweep then reads (blocks connect without caching, and the fixture spends no coins), and the quorum and CbTx caches (16 regtest blocks reach neither). Against the r3 pin the child dies with SIGSEGV after the first session. |
| D5 | **No other call while a session lives, a start whose options dashd refuses fails, and a failed teardown poisons the pin** (manager, after r4). (1) The pin's lock is an `RwLock`. Chain calls and peer sessions hold it exclusively, as before. Every other call that returns a `Result` now holds it shared, so calls that select no chain still run alongside each other. `oracle_addrman_op`, the one such call that sets Core's mock time, holds the shim's process-state mutex for it. Before, `check_input_scripts`, the decoders, `merkle_root` and the rest took no lock, so safe Rust could run them during a session, which oracle.h forbids. Another thread's call now waits until the session is freed. A call on the session's own thread is refused with `ErrorKind::SessionLive`, where it would otherwise wait for itself. A per-thread marker lets a call nested in another call run under the outer one's hold. Three getters that read constants (`abi_version`, `core_version`, `script_error_string`) and `AddrMan`'s drop (a plain `delete` of its own objects) take no lock. Cost: the node-l1 and dash-oracle-sys differential binaries ran 7.999e11 instructions:u and 117 s of task-clock before, and 8.035e11 and 116 s after. The four largest suites moved by −0.11% to +0.04%. The small multi-threaded suites scatter by 10–25% between repeated runs of the same build, which covers their differences. (2) In a session's setup (`DASH_ORACLE_HOOKS` with the oracle's RNG hook installed, as for the other session-only changes there), setup_common checks `AppInitParameterInteraction`. On failure the start throws InitError's message, captured from the UI signal's error-icon messages since noui is not connected yet. It is cleaned up like the other throwing starts. Other setups, upstream's included, still ignore the result. (3) Free empties the thread's last error and, if the teardown throws, sets it to `teardown failed: <reason>`. A start whose teardown fails returns `ORACLE_E_EXCEPTION` with that error. The session's Rust guard then marks the pin poisoned, and every later call of the pin fails with `ErrorKind::Poisoned`. With an allocation fault, nothing in the teardown throws before the node is destroyed except Core's noexcept destructors, which terminate. So the test sets `DASH_ORACLE_FAULT_TEARDOWN`, an environment knob that makes the teardown throw before it touches the node. A process with a leaked session also aborts at exit: Core's static `CCheckQueue` asserts its workers are gone. No ABI change. | `tests/peer_session.rs` `other_calls_wait_for_a_live_session`: with a session live, a decoder on another thread has not returned after 500 ms and returns once the session is freed. On the session's thread a decoder, a chain call and a second start are each refused with `SessionLive`. `a_failed_teardown_poisons_the_pin`: child processes with the knob set, once for free and once for a refused start's teardown. Afterwards a decoder, a chain call and a new start all fail with `Poisoned`. `tests/process_state.rs` adds a `-prune=-1` start to the throwing starts. Each throwing start must now fail with its own Core message ("Prune cannot be configured with a negative value" here), not merely as an exception. |

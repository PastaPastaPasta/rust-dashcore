# BS11b: dash-pkc API completion on `BlsElem`, implementation notes

Decision rows for BS11b (PLAN row BS11b, M1; DEC-449 orders it before BS11a-4). The slice adds Core's remaining BLS wrapper operations to `dash_pkc::bls::core`, built on BS11a-3's `BlsValue`/`BlsElem` (BS11a-3 notes, "How BS11b's API attaches"):
- aggregates and `SubInsecure`, insecure and secure;
- threshold share derivation and signature recovery;
- `DHKeyExchange` and multi-recipient BLS-IES;
- `GetHash` and the verification-vector hash;
- scheme conversion;
- Core's batch verifier and the `CBLSWorker` compositions LQ3/LQ4a call.

Citations are at Core `v24.0.0-rc.3` (`da567d7db`) and the oracle shim `77dbec824` (ABI 28). The scope inventory with every Core citation is `/work/scratch/bs11b/inventory.md` (untracked); the rows below carry the citations they rely on. Design D-numbers are BS11a-legacy-bls.md's, cited "design D*n*"; BS11a-3's are cited "BS11a-3 D*n*".

| D2 | **Everything Core-shaped lives in `bls::core`, never on the typed API.** New private submodules `core/{aggregate,threshold,ies,batch,worker}.rs`, re-exported from `bls::core`. They take and return `BlsValue`/`BlsElem` and `Fr`, never `BlsSecretKey`/`BlsPublicKey`/`BlsSignature<S>`. The typed API keeps its stricter rules (it refuses zero sums, infinity results, id ≡ 0, unreduced weights and empty IES plaintexts) as a policy API; every Core-parity caller (LQ3, LQ4a) uses `bls::core` | Core produces valid zero keys and valid infinities from aggregates, shares, `Recover`, `SubInsecure` and DH (`bls.cpp:36-60,83-110,179-220,289-294,360-391`), which the typed API cannot hold |
| D3 | **Receivers.** A Core function that writes into `*this` and returns `bool` (`SecretKeyShare`, `PublicKeyShare`, `Recover`, `DHKeyExchange`) takes `out: &mut BlsValue<…>`: it invalidates `out` first, returns `false` with `out`'s element kept, and on success assigns the result (design D69, BS11a-3 D9). A Core function returning an object returns `BlsValue`, with Core's `{}` as `BlsValue::invalid()` | `bls.cpp:83-110,179-206,208-220,360-391` clear `fValid` first and assign `impl` only on success |
| D4 | **Secret-key arithmetic is `Fr`, constant time.** A secret key's element is its stored 32 bytes (BS11a-3 D6); arithmetic reads them big-endian reduced mod r through a new crate-visible `Fr::from_bendian_mod` that accepts zero and never branches on the value. Results are stored as `Fr::to_bendian`. So a basic-decoded sk = r enters as 0, as `bn_mod_basic` makes it (`privatekey.cpp:237-255`). No result is checked for zero | `PrivateKey::Aggregate` reduces each term; DEC-354; inventory §6.7 |
| D5 | **Insecure aggregates.**<br>- `aggregate_secret_keys_insecure(&[&BlsSkValue])`: empty gives invalid; otherwise the `Fr` sum of every element, **valid or not** (F11), and a valid result even when zero (`bls.cpp:43-60`).<br>- `aggregate_public_keys_insecure` / `aggregate_signatures_insecure` (span): `BlsElem::aggregate_insecure` into a valid value; empty gives invalid (`bls.cpp:155-177,233-255`).<br>- Pair forms (`bls.cpp:36-41,144-153,222-231`) are the span over `[a, b]` with Core's assertion as the caller's precondition: an invalid operand returns the invalid value, not a panic. The oracle refuses those (`E_ARG`), so the harness skips them | Core asserts; this crate does not abort a node on a peer's object |
| D6 | **`sub_signatures_insecure(a, b)`** is `from_impl(a).add(from_impl(b).neg())` with `a` as `p`, valid even when infinite. Same precondition as D5's pairs. It has no production caller at the pin; it is ported for the oracle's `SUB_SIG` and completeness | `bls.cpp:289-294`; D63 operand order |
| D7 | **`aggregate_signatures_secure(sigs, pks, flag)`** (`bls.cpp:257-287`, `schemes.cpp:194-223`): empty or unequal spans give invalid; no validity test. Keys are sorted by `from_impl(pk).to_bytes(flag)` (an invalid key holding the default element sorts as `c0 00…`); weights are BS11a's `secure_weights` over the sorted bytes; each sig in sorted order is `from_impl(sig).mul(t_i mod r)`. The weight is reduced before `mul`: the engine's `mul` matches relic only for a scalar already below r, since a raw value below 2^64 takes relic's `mul_dig` path, which differs on Exotic operands (BS11a-3 D26). Shares (D11) and recovery (D12) pass their ids and Lagrange coefficients reduced for the same reason; the products fold left from the default element. The message argument is dropped: Core never reads it | the typed `secure_aggregate` multiplies unreduced weights and cannot hold invalid operands |
| D8 | **Sort order.** D7's sort is stable. libstdc++'s `std::sort` is insertion sort up to 16 elements, so it is stable there; above 16, equal keys get introsort's order. Two equal keys with different signatures above 16 signers is the only divergence; DKG `cvec` members have distinct operator keys (EV2a quirk 23), so it is recorded as an exclusion, not ported. The harness skips that class | `schemes.cpp:203`; inventory §6.3 |
| D9 | **Ids.** Threshold functions take ids as `&[u8; 32]`, the `CBLSId(uint256)` memory bytes, read big-endian mod r (`bls.cpp:29-34`, `threshold.cpp:98`). Every id is valid and zero is allowed, as for every Core caller (ids come from proTxHashes). The existing `BlsShareId` converts by `as_bytes` | the typed API refuses id ≡ 0 where Core returns `c[0]` |
| D10 | **`secret_key_share(out, msk, id) -> bool`** (`bls.cpp:83-110`, `threshold.cpp:169-188`): `false` on any invalid coefficient or fewer than two coefficients; otherwise Horner in Core's order, `y = c[n−1]`, then `y = y·x + c[i]` for i = n−2 down to 0, all in `Fr` (D4). x is public; the coefficients and y are secret and never branched on | `Poly::Evaluate`; inventory §6.7 |
| D11 | **`public_key_share(out, mpk, id) -> bool`** (`bls.cpp:179-206`): the same gates; Horner on `BlsElem` with `y = y.mul(x).add(c[i])` (y is `p` in both, D63). x = 0 makes `mul` the default infinity and `add` copies `c[0]`, so id ≡ 0 gives `mpk[0]`. A legacy-flag vvec may hold Exotic entries; the engine runs them (BS11a-3) | `threshold.cpp:169-188`; S9 |
| D12 | **`recover_signature(out, sigs, ids) -> bool`** (`bls.cpp:360-391`, `threshold.cpp:190-248`): `false` for empty or unequal spans, an invalid share, fewer than two shares, a zero product of ids, or a zero factor in any `b_i` (duplicates mod r). The coefficients are Core's `δ_i = a · b_i⁻¹` with `a = ∏ S_j` over all j and `b_i = S_i · ∏_{j≠i}(S_j − S_i)`, in `Fr`; the result folds `r = r.add(share_i.mul(δ_i))` from the default element in input order. Ids and δ are public. Public-key and secret-key recovery are not added: Core's wrapper has neither | Core's Lagrange; inventory §1.2 |
| D13 | **Share order is the caller's.** `CSigSharesManager` takes the first `threshold` shares in `std::unordered_map<uint16_t>` order (`signing_shares.cpp:704-708`). On Group inputs every subset gives one value; with Exotic legacy shares the value depends on hash-table history, which is not portable. Excluded as design D63 excludes the parallel aggregators; LQ3 documents its own order | `signing_shares.h:172,331` |
| D14 | **`dh_key_exchange(out, sk, pk) -> bool`** (`bls.cpp:208-220`): `false` with `out` kept when either side is invalid; otherwise `out = BlsPkElem::from_impl(pk).mul_secret_value(sk's stored bytes)`, valid even when infinite (sk = r). It is flag-independent. `mul_secret_value` loses its `dead_code` expectation. On a Group key it is blst's constant-time ladder; on an Exotic key the engine, variable-time, reachable only under the legacy flag (DEC-354) | BS11a-3 D15, D26 |
| D15 | **Multi-recipient IES** (`bls_ies.{h,cpp}`), new `core` types holding `BlsValue`s:<br>- `BlsIesMultiBlobs { ephemeral: BlsPkValue, iv_seed: [u8; 32], blobs: Vec<Vec<u8>> }` and `BlsIesBlobValue { ephemeral, iv_seed, data }`, each with `to_bytes(flag)` / `from_bytes(bytes, flag)` for Core's wire format: the key eager under the flag with the opposite-scheme fallback (`BlsEager::decode`, `bls.h:183-204`), the seed, `CompactSize` lengths, and no recipient cap.<br>- `encrypt_with(eph_sk, iv_seed, recipients, plaintexts) -> (BlsIesMultiBlobs, bool)`: Core's `InitEncrypt` then `Encrypt` per recipient, stopping at the first failure. A DH failure leaves that blob empty; a length not a multiple of 16 leaves it zero-filled (`out.resize` precedes the cipher); later blobs stay empty. An empty plaintext succeeds with an empty blob (`crypto/aes.cpp:51-55`). `encrypt` draws the ephemeral key with `make_new_key` (Core's `MakeNewKey`: 32 random bytes, retried until they read as a non-zero canonical key) and then the seed, both from a caller's `CryptoRng`.<br>- `decrypt(idx, sk) -> Option<Vec<u8>>` and the single-blob `BlsIesBlobValue::decrypt(sk, idx)`: no `IsValid` check, IV = `SHA256d^idx(seed)` cut to 16 bytes, key from `ies_key`; empty decrypts to empty.<br>- `decrypt_secret_key(…, flag) -> Option<BlsSkValue>`: `CBLSIESEncryptedObject<CBLSSecretKey>::Decrypt`, which reads the first 32 plaintext bytes with `BlsEager::decode` under the flag and ignores the rest. It can succeed with an invalid key (zeros; r under legacy), as Core does. Shorter plaintext fails | `bls_ies.cpp:31-109`, `bls_ies.h:47-118`; inventory §1.3, §6.6, §6.12 |

| D17 | **Hashes.** `BlsValue::serialize_hash(flag)` is `SHA256d(to_bytes(flag))`, zeros hashed for an invalid value (`bls.h:141-147`). | D19 | **Batch verifier.** `BlsBatchVerifier<S: Ord, M: Ord>` ports `CBLSBatchVerifier` (`bls_batchverifier.h`) with its constructor flags (`secure`, `per_message_fallback`, `sub_batch_size`), `push_message` (first entry wins for a repeated message id; an invalid sig or key is the caller's precondition, refused as D5), `verify(flag)`, `bad_sources()` and `bad_messages()`, with Core's `std::map` orders as `BTreeMap`.

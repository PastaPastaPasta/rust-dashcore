# O2a-MNHF: oracle MNHF signal step, implementation notes

Decision rows taken while implementing O2a-MNHF: the Core entry `oracle_mnhf_step` (ABI 23, DEC-238; Core branch
`node/o2a-mnhf-oracle-v24.0`), its `dash-oracle-sys` binding (`Oracle::mnhf_step`, module `mnhf`), the crafted tests
(`tests/mnhf.rs`), the Core-mined chain test (`tests/mnhf_regtest.rs`), and dash-dml's L0 vectors and harness
(`dash-dml/tests/data/mnhf/`, `dash-dml/tests/mnhf_step_vectors.rs`). The byte formats are in `oracle.h`, "MNHF
signals (ABI 23; v24 only)". Program decisions live in DECISIONS.md. `evo/mnhftx.cpp` and `chainparams.cpp:109-130`
are v24.0.0-rc.3's byte for byte at the pin; `evo/specialtxman.cpp` lines are the pin's (its oracle hooks shift
them).

| Row | Decision | Evidence |
|---|---|---|
| D1 | **One stateless entry, v24 only, additive.** The call seeds the context's evodb with the signal rows, installs Core's own `CMNHFManager` (the `ContextEHFManager` that `oracle_versionbits_state` already uses), and runs `ProcessBlock(block, pindex, fJustCheck, state)` as `ProcessSpecialTxsInBlock()` does (`evo/specialtxman.cpp:997-1001`). A non-v24 build returns `ORACLE_E_UNSUPPORTED` (DEC-82). ABI 23 adds one symbol over 22. The row seeding moved out of `oracle_versionbits_state` into `SeedSignalRows()` unchanged, so both entries read the same rows. | `oracle.h`; `tests/smoke.rs` ABI 23; the versionbits L1 targets and SB4 `--check` pass unchanged. |
| D2 | **The rows are the caller's, as for versionbits.** The MNHF context is `oracle_versionbits_state`'s signal changes: the row `GetForBlock()` reads at every header where V20 is active. The step does not rebuild rows from blocks, because Core reads them from evodb (`DB_SIGNALS_v2`), not from the blocks. A chained run feeds each step's `signals` back as the next change from `V20Height` on, where Core stores rows (D7; `tests/mnhf_regtest.rs` `Walk`). | `active_chain_stages_are_getdeploymentinfo_ehf_heights`. |
| D3 | **Undo checks only, and changes nothing.** `UndoBlock()` only asserts that `GetForBlock(block)` holds the block's bits (`evo/mnhftx.cpp:264-283`). Rows are keyed by block hash, so the parent's row is untouched. The record has `undo_ok` and the tip's stage read again after the undo (`stage_undone`). A false `undo_ok` would be `extractSignals()` failing, which an accepted block cannot do, and the assert cannot fire after an accepting `ProcessBlock()`. Since nothing changes, `stage_undone == stage_before` always holds: the tests assert it as the record's invariant, not as evidence about undo (Opus r1 L3). | Every connected step in both test files. |
| D4 | **`fJustCheck` returns the stage without the block's bits.** `ProcessBlock()` returns `signals` before inserting the new bits (`:242-245`), so a proposal's result is `stage_before`, and nothing is written. The step does not connect a just-checked block (`has_after` 0). | `process_block_verdicts_and_signals` ("just check"); `proposals_get_core_verdicts`. |
| D5 | **Bits at or above `VERSIONBITS_NUM_BITS` are refused (`ORACLE_E_ARG`) wherever they are in the block.** `IsValidMNActivation()` asserts on one it reaches (`chainparams.cpp:111`). Core would still give a verdict for some such blocks: a bit twice, a held bit, or a refused bit before it (Opus r1 M1). No node runs `ProcessBlock()` on such a block, because `CheckMNHFTx()`'s `MNHFTxPayload::IsTriviallyValid()` rejects it first (`bad-mnhf-nbit-out-of-bounds`, `evo/specialtxman.cpp:895`). The refusal covers a state no chain reaches, not a verdict a node gives. | `refusals_and_missing_context` (bit 29). |
| D6 | **Median-time-past reads below the headers are `ORACLE_E_CONTEXT`.** Placeholders have `nTime` 0, so Core would compute silently: a held signal would look expired, and a window check would see time 0. Two reads exist. (a) `GetSignalsStage(tip)` reads each held signal's block MTP (`:72-76`): its block and the ten below it, when V20 is active after the tip. The record holds that stage, so the shim requires it even when `extractSignals()` rejects first. (b) `ProcessBlock()` reads the block's own MTP only once it reaches `IsValidMNActivation()` (`:228-241`): no bit twice and the first bit not held. That needs the tip and the nine below it. Holding a bit already implies (a)'s headers, which cover (b)'s, so only the "bit twice" exemption shows. | `refusals_and_missing_context`: first header 31 → context, 30 → verdict; a held signal at 30: 21 → context, 20 → stage; `[V24, V24]` on a one-header context → `bad-mnhf-duplicates-in-block`. |
| D7 | **Before V20 the step still validates bits.** `GetSignalsStage()` returns `{}` before V20 (`:63`), but `ProcessBlock()` still runs the per-bit checks and returns the signals. Core stores no row there (`AddToCache()` writes evodb only where V20 is active, `:368`; `GetFromCache()` returns `{}` without evodb below V20, `:343`), so the walk records rows only from `V20Height`. The block at `V20Height - 1` is the exception: see D13. | `before_v20_the_stage_is_empty`; `signals_below_v20_are_not_stored`; crafted vector "before V20". |
| D8 | **`CheckMNHFTx()` is not run.** `ProcessSpecialTxsInBlock()` runs `CheckSpecialTxInner()` per transaction (`evo/specialtxman.cpp:877-899`) before `ProcessBlock()`, so a bad payload, quorum or signature is rejected there first (`bad-mnhf-*`). `oracle_check_special_tx_block` owns that check. The step reads only the version bits of transactions whose payload decodes, as `extractEHFSignal()` does (`:176-188`). An undecodable payload is skipped there, not rejected, as Core's code does. The crafted tests' null-signature signals are therefore enough. Core's proposals with a zero-signature second bit-28 signal (`bad-mnhf-invalid` from `CheckMNHFTx()`) get `bad-mnhf-duplicates-in-block` from the step, and the test maps that explicitly. | `signal_payloads_are_ones_core_decodes`; `proposals_get_core_verdicts`. |
| D9 | **Expiry is checked on Core-mined blocks.** The fixture's node0 restarted with a later testdummy start (`feature_mnehf.py`), so under the final arguments the bit-28 signal mined at 187 is expired from 188 on. The re-signal at 247 is then accepted, not `bad-mnhf-duplicate`. The unknown bit 27 never expires (no deployment uses it). The walk's `stage_after` equals `getdeploymentinfo`'s `ehf_height` for every deployment at all 257 heights (`rpc/blockchain.cpp:1492-1494`, with the stage of `:1733`). The crafted chains cover a window start just before, at and just after the re-signal's block, and an EHF bit after its timeout (an unknown bit then: valid). | `expired_signals_leave_the_stage_and_free_their_bit`; `active_chain_stages_are_getdeploymentinfo_ehf_heights`; crafted vectors. |
| D10 | **The side branch is stepped here, not re-validated in dashd.** The fixture's dashd judged bases below the side branch on a second node started from a fresh copy of the datadir (PROVENANCE.md). The step connects every side-branch block on rows computed under the fixture's final arguments. | `the_invalidated_branch_connects`. |
| D11 | **L0 vectors plus a reference model for EV3; no L1 target yet.** The crafted vectors also cover a later bit failing after a valid one, so a port that checks only the first bit fails (Opus r1 M2), and pin the order of the checks within a bit: "a held non-EHF bit" (the stage before `IsValidMNActivation()`, `:232` before `:237`) and "a held bit twice" (duplicates in the block before the stage) kill a reference model that checks the deployment first (Opus-h r1 L1). A model that reads only the first deployment on a bit cannot be pinned: every chain has one deployment per bit and `-vbparams` cannot move a bit (Opus-h r1 I1, for EV3). `dash-dml/src/mnhf.rs` is only the record type, so there is no Rust `ProcessBlock()` to diff. Each vector line carries everything `ProcessBlock()` and the next stage read: the deployments, the V20 flag, the height, the MTP, the stage, the bits in block order and `fJustCheck`. The answer is Core's. The harness's `reference` module is the model EV3 replaces with `dash_dml::mnhf`. Only new signals can expire in `after`, because held ones already passed the same check. The GetSignalsStage recurrence itself is already L1-diffed through `dash-consensus` `ehf_signals_stage` (node-l1 versionbits). `DASH_ORACLE_REGENERATE=1` rewrites the vectors; otherwise the oracle tests fail if Core's answers change. | `dash-dml/tests/data/mnhf/README.md`; `crafted_cases_are_dash_dml_vectors`; `regtest_steps_are_dash_dml_vectors`; `mnhf_step_vectors`. |
| D12 | **The Core fixture is Core's own functional test.** It was mined with release dashd v24.0.0-rc.3 running `feature_mnehf.py` under a read-only capture wrapper. No live oracle was used: the reference nodes' pure-read list has no MNHF or deployment-history call (historic `getdeploymentinfo` is not on it), so their stages could not be compared. | `tests/data/PROVENANCE.md` "MNHF signals regtest chain". |
| D13 | **At `V20Height - 1` the next stage is the connecting node's.** `AddToCache()` keeps that block's signals in the manager's in-memory cache only (`:368-382`), and `GetSignalsStage(block)` passes its V20 check and reads the cache before the V20 test in `GetFromCache()` (`:337` before `:343`). So the step's `stage_after` holds the block's signals. The step of the next block, built on stored rows, reads none at that block, because the oracle does not seed the cache unless asked (format 1, or format 2 with `seed_tip_cache` 0) (Opus r1 H1; Opus-h r1 M1 ruling: "does not", since `CMNHFManager::AddSignal()` is public and `AddToCache()` is reachable). Unseeded, a non-empty signal change at a header where V20 is not active is refused (D14), so the drop is explicit. Format 2's `seed_tip_cache` seeds that entry (D16, BL-211), so the next block's step reads them as the connecting node does. The vector "V20 from the next block" carries the connecting node's answer and is marked in the vectors' README. | `signals_below_v20_are_not_stored`; crafted vector "V20 from the next block". |
| D14 | **A signal change where V20 is not active is refused (`ORACLE_E_ARG`), except a seeded one at the tip.** Core writes no row there (`AddToCache()`, `evo/mnhftx.cpp:368`), so a change at such a header sets no row there; the block's signals live in the manager's cache alone. The step used to drop the row at that header silently (Opus-h r1 M1 ruling); an empty change there is still taken. The refusal is broader than that drop (Opus-h r2 R2-N1): a non-empty change at `V20Height - 1` also used to set the rows of the V20-active headers after it, so a caller whose signals hold from V20 on puts the change at the first header where V20 is active, with the same answer. A change at the tip with format 2's `seed_tip_cache` is taken into the tip's cache entry instead (D16). `oracle_versionbits_state` keeps its rules (a change there still sets the rows of the V20-active headers after it); the refusal is the step's. | `signals_below_v20_are_not_stored`; `a_seeded_tip_cache_is_the_connecting_nodes`. |
| D15 | **Blocks `CheckBlock()` rejects are refused (`ORACLE_E_ARG`).** A block with no transactions, or whose first is not a coinbase, never reaches `ProcessBlock()` (`ConnectBlock()` checks the block first), as `oracle_credit_pool_step` refuses them (Opus-h r1 N2). The tip's subsidy height is not checked here: the step reads no subsidy. | `refusals_and_missing_context`. |
| D16 | **Format 2 seeds the tip's cache entry (BL-211, ABI 28: the T19 bundle number under DEC-238, above the installed 26 and 27, the rider build number reserved for BL-211).** MNHF context format 2 appends `uint8_t seed_tip_cache`. With 1, a non-empty change at the tip where V20 is not active goes into the tip's entry of the manager's cache through Core's private `CMNHFManager::AddToCache()` (`PrivateAccess`), as the node's `ProcessBlock()` of the tip left it (`:221`, `:250`); V20 is not active there, so no row is written (`:364-382`). `GetForBlock(tip)` reads the cache first (`GetFromCache()`, `:337`), so at `V20Height - 1` the next block's stage is the connecting node's. A seeded signal's median time past is read as a row's is (D6). The seed is the tip's alone: below V20 only the tip's entry can reach a stage (`GetSignalsStage()` is empty unless V20 is active after its block, `:63`), so a non-empty change at a lower header is still refused. Where V20 is active at the tip the flag has no effect: the cache would hold the tip's row, and calling `AddToCache()` there would only re-check that row. The seeded signals must each be at the tip's height: there the stage of the tip's parent is empty (`:63`), so `ProcessBlock()` leaves the tip's own bits at `mined_height` (`:227`, `:247`), and no other entry is reachable (`AddSignal()`, `:385`, has no caller in Core); a seed at another height is refused (Opus r1 F1). Whether `IsValidMNActivation()` accepted the bits at the tip is the caller's, as for rows. Unseeded, the step reads what a manager without that entry reads: the empty entry `GetFromCache()` inserts below V20 (`:343-346`). The binding writes format 1 unless it seeds; `Oracle::mnhf_step_raw` sends other bytes, and the tests check that format 2 with 0 equals format 1 and that a flag above 1, a missing flag, trailing bytes and other formats are refused (`ORACLE_E_ARG`). Evidence: the step on that tip, seeded with the connecting step's `stage_after`, has it as `stage_before` (a held bit is `bad-mnhf-duplicate`; another bit is accepted, connects and undoes to it); two dash-dml vectors carry those answers. Both answers come from Core's own manager in separate calls; a Core-mined chain with a signal at `V20Height - 1` would need a new capture (the crafted signals carry null signatures, which `CheckMNHFTx()` in a chain session refuses), so none is used. Simplifier: `ReadMnhfContext()` keeps its own format check rather than generalizing `ReadFormat1()`, whose other callers belong to other riders' code. | `a_seeded_tip_cache_is_the_connecting_nodes`; crafted vectors "on V20 from the tip's cache"; `mnhf_context_bytes`; `contexts_serialize_as_formats_1_and_2`. |

## 0. The design on one page

**What it is.** One fuzz process holds two chainstates side by side: a **Core chain session** (`oracle_chain_*`, a new oracle ABI numbered at merge, §10), which is Core's own `ChainstateManager` + evo/LLMQ objects built in-process over in-memory LevelDB environments, and the Rust **`NodeSut`** (CH3 §7.8), which is production V + `CoreConnector` over `dash_kv::memory::MemoryEngine` and in-memory flat files. Each fuzz input is a short program of **ops** (submit a block, submit a header, propose a block, invalidate, reconsider, precious, record/enforce a ChainLock, set a spork, flush, restart clean or killed, set mocktime; at M4 also build a template, write an IS lock, and the evo ops of §9). The harness applies every op to both sides and compares, after every op:

1. the **reply** (RPC-shaped result or reject string, and the `BlockChecked` verdicts the op caused);
2. the **O8 records** (C/R/D with `org`, compared by O9a in stream mode) and **A records** (helper decisions, strict sequence);
3. the **events** (validation-interface notifications, in order);
4. the **post-state**: tip, best header, `getchaintips` rows, an exact UTXO digest, a block-index status digest, best ChainLock, IBD latch, flush counts by cause, deployment states; at every restart also the **persisted image** read from storage before any load logic (D37); at M4 the IS lock set (D29), snapshot rows, mineable commitments, MN metadata, credit pool.

**How the Core side is wired (§2).** The session reuses O1c's session machinery (process-state save/restore, inline validation queue, one session per process under the exclusive pin lock) and assembles the objects that `LoadChainstate` (`node/chainstate.cpp:298`) needs, the way `BasicTestingSetup` and `ChainTestingSetup` (`test/util/setup_common.cpp:138-249`, `:250ff`) do. All LevelDB instances run on **memenvs that outlive their `CDBWrapper`** (a test hook, D3), so a **restart** is Core's real path: destroy every object, then `LoadChainstate` + `VerifyLoadedChainstate` + `ActivateBestChain` over the same in-memory data. Block/undo files are real files in a per-session 0700 directory with `-fastprune` and a no-op `FileCommit`. No mempool, no net, no governance manager, no LLMQ signer (the only key is the spork test key, §2.6): the regime CH3 D49 declares (not-synced, `gov_valid = false`). Time is mocktime; Core's periodic flush runs on `SteadyClock` and never fires inside an input, so flushes happen only at explicit ops (D6). ChainLock state is real Core state reached through the handler's own steps (signature check stubbed at M3, real at M4). After a reload Core breaks equal-work ties by heap address (`node/blockstorage.cpp:42-45`); an input in which that tie-break **decided** something (the best candidate, the best header, or an admission against the tip) is discarded before any later op is scored (D30).

**How the Rust side is driven (§5).** Through `NodeSut` with a list of deltas to CH3 §7.8 (state-driven helper answers instead of `Answer(HelperScript)`; `ClRecord`, `ClEnforce`, `Spork`, `Activate`, `Restart(kind)` ops; a test-only Core-flush-causes regime for leg A; events, A records, the persisted image and the extra post-state in `StepReport`; image save/restore). PLAN delta: CH3a a10 lands them (§14). Core's load-time failure reset is **production** startup code in a new M3 row, CH1-node-LR, not a harness option (D32).

**Generator (§3).** A world model (block tree, UTXOs per branch, keys, locks, time) turns fuzz bytes into *intents* that resolve to well-formed ops, then applies CH3 §7.3's non-evo mutation operators. Every byte string decodes. Every input starts from a **prefix image** (≥ 110 mature blocks) restored by the restart path. Heights are compressed by **schedules** (S0–S2 at M3, S3–S5 at M4) that both sides take from the same args, parity-checked by `oracle_chainparams_json`.

**Fuzz and farm (§6).** Targets `diff_chain` (S0, `-par=1`), `diff_chain_par` (S1, `-par=4`), `diff_chain_av` (S2, assumevalid) and `diff_chain_prodflush` (S0p: S0 at `-dbcache=4` with Rust's production flush policy and Core mirrored, D31), private route, `kind = "l1"`. Gate per DEC-184/186: plateau with 0 divergences and 0 crashes, then `fuzzctl certify` at the gated head with floors set from measured throughput, census floor first; CPU-h are reported, not a goal.

**Acceptance evidence (§7, §8).** Planted bugs behind `planted` features: at M3 a check-order bug (P3a) and a persistence omission caught in the persisted image (P3b), each with a directed witness that fails planted and passes unplanted; at M4 the PLAN's DML ordering bug (P4a) and effect omission (P4b). The **disposable-datadir proposal experiments** replay sampled corpus programs against a stock statedigest-patched regtest `dashd` over RPC and compare it with the shim session (the A1 adapter cross-check rule), and the results are committed.

**Slices (§11).** O2b-1 Core session (ABI: next free at merge) → O2b-2 `ChainSession` binding + Core self-determinism → O2b-3 generator/comparator over `NodeSut` → O2b-4 targets, census, planted pair, M3 X-check, farm → O2b-5 evo + IS (ABI: next free at its merge; needs CH7a/b and LK1b-s). M3 exit item 4 needs O2b-1…4.

### 1.3 Non-goals

- **Crash images inside a flush.** Core's side cannot be killed mid-`FlushStateToDisk` deterministically; torn-write and power-loss coverage is CRASH/ST3a's (Rust only, `MemoryEngine::simulate_power_loss`). O2b's `KILL` restart is a kill at a quiescent point (D5).
- **Cache-pressure flushes.** `CoinsCacheSizeState` depends on `DynamicMemoryUsage` (allocator accounting; CH3 D25 declares the difference), so leg A runs both sides with a cache large enough that `IF_NEEDED`/`PERIODIC` never flush by size (D6). Leg B (D31) lets Rust's own size causes fire and mirrors them onto Core, with Core's size causes switched off; whether Core *would* have flushed there is not compared. CH2's own tests own the size arithmetic.
- **Mempool, P2P, wallet, governance objects, CoinJoin.** The session has no mempool (`ChainstateLoadOptions::mempool = nullptr`, `node/chainstate.h:35`); `DisconnectTip`'s mempool re-add is not exercised. That is the mempool rows' differential (P3, O10), not this one.
- **IS at M3** (D29). The Rust side has no IS store at M3: `NodeHelper::is_conflict` answers `None` and `NoEvo` refuses every effect (CH3a notes D61; CH3 §3.2). Spork 2 therefore stays off at M3 on both sides, so Core's `GetConflictingLock` returns `nullptr` (`instantsend/instantsend.cpp:425-429`) and the IS loop (`v:2801-2819`) finds no conflict on either side. IS is **in** the M4 gate: a production LK1b store slice (LK1b-s) lands before O2b-5, and `ISLOCK`, `conflict-tx-lock` and the `is_rm` effect are M4 acceptance items (§9, D29).
- **IS relay, verification windows, mempool hooks.** LK1b's remaining node role (M5) stays out of `diff_chain`; the M4 IS surface is the store `ConnectBlock` reads and the effects it applies.
- **Log-line parity.** Not compared (CH3's `-debug=bench` and MNPAYMENTS lines are declared elsewhere).
- **mainnet/testnet chains.** Regtest only; L2 replay (CH3a a7, O9a) covers real chains.

### 2.2 Storage (D3, D4)

- **LevelDB.** `CDBWrapper` with `fMemory` creates a `leveldb::NewMemEnv` and deletes it in its destructor (`dbwrapper.cpp:131-196`), so a restart would lose the data. A `DASH_ORACLE_HOOKS` hook keeps a **memenv registry** keyed by the wrapper's path: a wrapper opened with `fMemory` takes the registry's env for its path (creating it on first use) and does not delete it. `oracle_chain_free` drops the registry. `CDBWrapper` ignores `fWipe` for memory DBs (`dbwrapper.cpp:139-149`), so the registry implements wipe itself: `oracle_chain_new` and `oracle_chain_restore` start from empty (or image) envs, and a restart reuses them. `RecoverSnapshotCleanup` is skipped because `dash_dbs_in_memory` is set (`node/chainstate.cpp:324`). LevelDB's background compaction runs on `Env::Default()`'s thread; images are taken only after every DB is closed (§2.3), so a dump never races a compaction.
- **Block and undo files.** Real files under a per-session directory `<TMPDIR>/oracle-chain-<pid>-<n>/` created 0700 (never `/tmp` or `/dev/shm`: the runner sets `TMPDIR`). `-fastprune` keeps preallocation small (`node/blockstorage.cpp:634`, `:671`). A hook makes `FileCommit` (`util/fs_helpers.cpp:122`) a no-op inside the session: durability is not observable in-process and fsync on `/work` would dominate exec/s. `oracle_chain_free` removes the directory; `fuzzctl` removes stale `oracle-chain-*` directories of dead PIDs at leg start.
- **Disk-space checks** (`CheckDiskSpace`, `util/fs_helpers.cpp:107`; called at `v:3050`, `v:3088`, `node/blockstorage.cpp:715`, `:739`) read the host's free space, which the Rust in-memory files do not have. A hook makes them pass inside the session (D33); the budget (§6.3) keeps a session under 64 MiB on disk.

The Rust side uses `MemoryEngine` and CH3's in-memory flat files (`MemFlatFs`). File positions are not compared (D16): layout parity is CH2/ST3a's, and the comparison sees reads through post-state and reorgs.

### 2.3 Restart and images (D5, D9)

`RESTART` has two kinds:

| Kind | Core | Rust (`NodeSut`) |
|---|---|---|
| `CLEAN` | `ForceFlushStateToDisk` (`v:3122`) on the active chainstate, then destroy objects in `Shutdown`'s order, then reload | V's shutdown flush, drop V, reopen through CH2b recovery |
| `KILL` | destroy objects without flushing, at a quiescent point between ops, then reload. Equivalent to a SIGKILL of `dashd` at that point: LevelDB hands every write to the OS at once, and the coins DB and block index are written only inside a flush | drop V without its shutdown flush; `MemoryEngine` keeps committed batches only |

**Restore on the node until a10 (O2b-3b).** `NodeSut` has no image, so the node's image restore is a replay: it rebuilds V over the image's chain rather than loading stores. V flushes through ND1's `NodeFlush`, but `NodeSut`'s shutdown flushes are not wired (BL-271), so a clean restart does not give the load either. Core's restore is a load, and its `Open()` resets the process statics (`ResetNodeProcessState`, `oracle_chain.cpp:761`, through `OracleResetValidationStatics`, `validation.cpp:3237-3241`), which clears the last notified header tip (`validation.cpp:3799-3824`) as a `dashd` start would. The replay leaves V's latch at the image's tip, so the first header after a restore that is not a new best one is notified by Core only. This is a declared gap (an ignored `l1_chain_diff` case) until `NodeSut` loads the image.

**Two flush regimes (D31).** `KILL` makes flush timing observable, and CH2's production policy has flush causes Core lacks (`THRESHOLD`, `DMAX`, `LEFT_IBD`; `CH2-coins-flush.md:1683-1686`). So the target runs two legs:

- **Leg A** (`diff_chain`, `_par`, `_av`): Rust under `flush_regime = CoreCausesOnly` (test-only, §5.1), both sides with a large `-dbcache`. Both sides flush only at explicit ops, and everything — including the persisted image after `KILL`, the per-cause flush counters and the `ChainStateFlushed` events — is compared exactly. This leg's claim is narrow: *given the same flush points, Rust persists and recovers exactly as Core.*
- **Leg B** (`diff_chain_prodflush`, schedule S0p): Rust under its **production** policy. With a large cache almost no Rust cause would fire (`THRESHOLD` needs active ≥ f·B(t), `CH2-coins-flush.md:1010`; `DMAX` needs a subscriber; the index-only write needs an hour of steady time), so S0p runs **both sides at `-dbcache=4`** (Core's floor, `txdb.h:37`, a setting a user can choose) and the generator's `EXTEND` uses a **fan-out** shape (up to 64 outputs per transaction) so that a few blocks fill Rust's coins share. Core's own size causes (`fCacheLarge`, `fCacheCritical`, `fEvoDbCacheCritical`, `v:3036-3040`) are switched off by a hook in this leg, so Core flushes only at explicit ops and when mirrored. The rules:
  1. After every op the harness reads Rust's flushes by cause, each with an "at op end" flag (no connect, disconnect or index-status change after it within the op).
  2. **Every** Rust flush Core did not make at the same op — `THRESHOLD`, `DMAX`, `LEFT_IBD` and Rust's native `CACHE_LARGE`/`CACHE_CRITICAL`/`EVO_CRITICAL` alike, at op end **or in the middle of the op** — is mirrored onto Core **at op end**, in Rust's order, each under its own Rust cause, before the op's post-state is compared. A full flush is mirrored by a `FLUSH ALWAYS`; an index-only write by the forced index-only write hook (§2.9), which runs `v:3048-3075`'s write branch without the coins flush. The mirror hook takes the Rust cause as a label, and Core's counter books the mirrored flush under that cause.
  3. If any of those Rust flushes was **not** at op end (e.g. `THRESHOLD` between two blocks of one reorg), the mirrors of rule 2 run first and then **one** `FLUSH ALWAYS` runs on **each** side (cause `reconcile`). The reconcile is needed because Core's late mirror persisted the op-end state while Rust's earlier flush persisted a mid-op state; Rust's reconcile brings its storage to the op-end state too. So for such an op, per cause, Core's mirror count equals Rust's flush count, and each side has exactly one `reconcile`; the O2b-1 selftest (Core: mirrors then reconcile) and an O2b-3 `l1_chain` case (a reorg that fires `THRESHOLD` between its blocks) assert both. The reconcile also covers Core's non-dirtying marks: `MarkConflictingBlock`'s marks are not dirty (`CH1-node.md:864`) and reach disk only with a later dirtying write, so a mid-op Rust write followed by a non-dirty mark in a later op would otherwise leave different images. Within one op no non-dirty mark follows a flush: `EnforceBlock` marks (`v:4048-4077`) before `EnforceBestChainLock` activates the chain. Reconcile flushes are counted and reported.
  4. `ChainStateFlushed` events are removed from leg B's ordered event plane (a Rust flush's event sits where its freeze happened, a mirror's at the op's end); the number of flushes per op and cause is compared through `flushes` instead.

  Durable points then coincide at every op boundary, so the exact comparison, persisted image included, applies. Leg B's claim: *under the production policy, at every op boundary, Rust's durable state is identical to Core flushing at the same points.* The index-only mirror is reachable only through a forced write in the O2b-1/O2b-3 tests (the one-hour steady timer never expires in an input); it is not a census row.
- **Not claimed by O2b:** durability after a kill in the middle of an op under the production policy. That is named as a CH2-owned gate, **CH2-KP** (kill parity): CRASH/ST3a's kill-anywhere legs run over the production policy, record the per-cause flush schedule, and at each crash point derive the expected recovered image from **the durable phase** reached — B1 with or without the `head_blocks` marker, each coin sub-batch, the final batch, an index-only write — not merely from the last completed flush: a kill after a split flush wrote `head_blocks = [new, old]` recovers to `new` by replay (`CH2-coins-flush.md` §3.5, §4.3), and an index-only write persists index entries without moving the coins/evodb markers (`v:3048-3075` vs `:3077-3100`). After recovery both the coins/evodb root and the index image are compared with that expectation (a PLAN delta on CH2).

Flush timers and counters are **per open**: Core's `m_last_write`/`m_last_flush` (`validation.h:810-811`) belong to the rebuilt chainstate and restart at the first `FlushStateToDisk` call (`v:3029-3034`); Rust's timers restart with the reopened V (CH2's "set to now on the first call"). The `flushes` field (§4.5) counts since the last restart or restore. Because a reset counter would lose a `RESTART CLEAN`'s shutdown flush (it runs on the old instance), each step also reports **`flush_delta`**: the op's own flushes, `(full, index-only)` by cause, counted from the op's start across teardown and reopen to its end — for `CLEAN`, the shutdown flush of the old instance plus any flush of the reload; for `KILL`, the reload's only. **Restore** tears the old instance down **without** a shutdown flush on both sides (its state is discarded: Core's objects are destroyed as on `KILL`, Rust's V is dropped without its shutdown flush, and the spork stores are suppressed too), so its delta holds the reload's flushes only. `flush_delta` is compared on every step and is the flush plane on `CLEAN` and restore steps.

Reload is `LoadChainstate` → `VerifyLoadedChainstate` (`node/chainstate.cpp:412`) → `ActivateBestChain`, as `LoadVerifyActivateChainstate` does (`setup_common.cpp:317`). Consequences both sides must reproduce, and which the comparison sees directly:

- After `KILL`, the coins DB, the block index and evodb's committed root are those of the **last flush** (block-index writes happen only inside `FlushStateToDisk`'s write branch, `v:3048ff`; evodb's root commits at `v:3096-3097`). Blocks received after it lose their index entries; their file bytes remain but are unreachable until resubmitted. A `KILL` with a pending head-blocks marker cannot happen at a quiescent point, so `ReplayBlocks` (`v:5222`) runs and replays nothing (no records); `org = replay` records stay in the comparison for when CRASH-style images are added later.
- `VerifyLoadedChainstate` refuses a tip more than `MAX_FUTURE_BLOCK_TIME` ahead of mocktime (`node/chainstate.cpp:424-428`). A program that moves mocktime back and restarts gets Core's `FAILURE` with that message; the session is then **down**: every op except `SETTIME` and `RESTART` returns `ORACLE_REJECT` with reason `session-down`. The Rust side must refuse the same load (CH1-node's load path) — a real parity surface, not a harness artefact.
- `VerifyDB` runs at `-checkblocks`/`-checklevel` (defaults 6/3). `nCheckDepth <= 0` means **all** blocks (`v:5050`); a schedule never uses 0 to "disable" it.
- **At `check_level >= 3`, a load with a non-empty coins view calls `ResetBlockFailureFlags(nullptr)` after `VerifyDB`** (`node/chainstate.cpp:415-417` for the emptiness test, `:436-441` VerifyDB, `:463-465` the reset), which reconsiders `m_best_invalid` when it descends from the tip (`v:4152-4163`; `m_best_invalid` is set while loading, `v:5356`). So `INVALIDATE` of the tip followed by `RESTART` brings the block back and reconnects it. This is production startup behaviour, so it is production code (D32): a new **M3 row CH1-node-LR** adds, to rdashd's startup after CH2b's `open_chainstate` returns, the hook point where Core's `VerifyLoadedChainstate` tail runs — the future VerifyDB call (CH5's; a no-op until CH5 lands), then, when the coins view is non-empty and `check_level >= 3`, CH1-node's `reset_failure_flags_null()` (`CH1-node.md:532`) — with its own directed test. `open_chainstate` itself is CH2's and CH1-node only owns its step 4 (`CH2-coins-flush.md:1259-1263`, `CH1-node.md:868`), and CH1-node is an M2 row, hence the new row. `NodeSut` gets the reset only by running that production startup path. CH1-node-LR is a hard dependency of O2b-3 (§11). The case is a census row (§6.5).
- The IBD latch (`m_cached_finished_ibd`, `v:1970-1993`) resets because the chainstate is rebuilt; Rust's latch must reset too.
- Core forgets the best ChainLock (`Chainlocks` is memory-only) and the ChainLock seen-set; a program records ChainLocks again if it wants them.
- **Sporks persist at clean shutdown only, on both sides** (D34, the manager's ruling on Sol r2 finding 2). `CSporkManager::~CSporkManager()` stores a valid map to `sporks.dat` unconditionally (`spork.cpp:46-50`), and init loads it (`init.cpp:1967-1972`); no other `sporks.dat` write was found in `init.cpp`, and the spork experiment (§8) confirms it on a running `dashd`. The session keeps a real `sporks.dat` in its directory: `CLEAN` destroys the manager normally (store); `KILL` and restore's teardown set a hook flag that **suppresses that one store** before destruction; every reload calls `LoadCache` on the file as it is. **rdashd does the same**: SP0-s's store is written only by ND1's shutdown sequence — train 14 already calls `SporkManager::store` (`dashd-masternode/src/sporks/file.rs:217`, `:235`) there (`dashd-node/src/node.rs:450-454`, citing Core's `init.cpp:415`), and the SP0 delta in §14 carries that one call into SP0-s, adding no second call — in rdashd's own spork file (Policy F; Core's `sporks.dat` stays import-only, PLAN SP0, O17 MNO-04, `O17-pin-delta.md:145`, `:360`), and loaded at startup. `NodeSut`'s `Restart(Clean)` runs that same shutdown step, `Restart(Kill)` and restore skip it. Persist-on-receipt is not an option. A `KILL` therefore reverts **both** sides to the last clean store (or none), and every step after it — CL replies, A records, tips, events — stays comparable. Spork state is a post-state field (`sporks`, §4.5). Generator spork intents are admitted only after the X-check's spork experiment (§8: isolated `KILL` and `CLEAN` trials from a spork-19-on baseline, on a stock `dashd`, the session and `NodeSut`) has confirmed the model on all three and been recorded.
- **Process-wide state reset on every restart and restore** (D35), not only at `oracle_chain_free`: `static pindexHeaderOld` (`v:3696-3705`; a dangling pointer whose address a new index entry can reuse silently skips `NotifyHeaderTip`, as O1c D4 saw), the script-execution and signature caches (re-initialised, so an input never depends on the inputs before it), `bls::bls_legacy_scheme` (set by `VerifyLoadedChainstate` when V19 is active, `node/chainstate.cpp:458-461`); at M4 also the CbTx best-CL cache (`evo/specialtxman.cpp:148`) and the quorum-member caches. The list lives in one function in `oracle_chain.cpp`, and O2b-1's selftest checks "program B alone" equals "B after A".
- **The persisted image** (D37). Between teardown and reload, both sides read their storage directly, before any load logic runs. Core: a `CDBIterator` over a **copy** of each registry memenv (the same deep copy images use; opening LevelDB replays its log and may rewrite tables, so the env the reload uses stays byte-for-byte as teardown left it) — the block-tree DB's `DB_BLOCK_INDEX` (`'b'`) records, the coins DB's `DB_BEST_BLOCK` (`'B'`) and `DB_HEAD_BLOCKS` (`'H'`) markers (`txdb.cpp:31-34`) and evodb's `EVODB_BEST_BLOCK` (`evo/evodb.cpp:115`). Rust: a `test-support` read of its stores — SB4's `BlockIndexRecord`s (whose `Status` has Core's `nStatus` layout bit for bit, `SB4-dash-chain.md:74`) and CH2's `meta.tip`, `meta.head_blocks` and `meta.evo_tip` (`CH2-coins-flush.md:1139-1150`) as the counterparts of `'B'`, `'H'` and `EVODB_BEST_BLOCK`. The digest covers, per index record, header-only entries included, (hash, height, header fields, `nTx`, `nStatus` bits `BLOCK_VALID_MASK \| BLOCK_HAVE_DATA \| BLOCK_HAVE_UNDO \| BLOCK_FAILED_VALID \| BLOCK_FAILED_CHILD \| BLOCK_CONFLICT_CHAINLOCK`), sorted by hash, plus the three markers (an absent marker and Core's null `uint256` both digest as "none"); file positions excluded. This is the plane that sees persistence: Core's load logic rewrites status before anything else can observe it (`LoadBlockIndexDB` adds `BLOCK_FAILED_CHILD` under a failed parent, `node/blockstorage.cpp:321-323`; `ResetBlockFailureFlags(nullptr)` then clears the best-invalid chain, `node/chainstate.cpp:463-465`), so a write-path omission need not reach any post-load field.
- **Equal-work ties after a reload** (D30). Blocks loaded from disk all get `nSequenceId = 0` (`node/blockstorage.cpp:100`), so `CBlockIndexWorkComparator` falls through to the heap-address tie-break (`node/blockstorage.cpp:42-45`; fixed upstream after v24 by Bitcoin #29640), which no Rust port reproduces (CH3's arena id stands in for the pointer but is not the same order). The comparator reaches that branch constantly without deciding anything: `LoadBlockIndex` adds every loaded candidate while the tip is still null (`v:5351-5355`, `TryAddBlockIndexCandidate` `v:4245`), the `m_best_header` scan compares every entry (`v:5359`), and set operations compare an element with itself. So the taint fires only at the points where an address order can **decide** an outcome, each with two distinct entries of equal `(nChainWork, nSequenceId)`:
  - (a) **the best candidate**: when `FindMostWorkChain` takes `setBlockIndexCandidates.rbegin()` (`v:3527-3530`), another candidate has the same work and sequence id;
  - (b) **the best header**: at the end of the load loop (`v:5359`), another `BLOCK_VALID_TREE` entry has the same work and sequence id as `m_best_header`;
  - (c) **an admission or pruning against the tip**: a comparison with `m_chain.Tip()` (or, inside `InvalidateBlock`, with the new tip `pindex->pprev`) that reaches the address branch with `pa != pb` — `PruneBlockIndexCandidates` (`v:3588`), `ActivateBestChain`'s loop condition (`v:3811`), `InvalidateBlock`'s admissions (`v:3926`, `v:3993`, `v:4029`), `MarkConflictingBlock`'s re-admission (`v:4133`) and `TryAddBlockIndexCandidate` once a tip exists (`v:4245`).

  The hook evaluates (a) and (b) as predicates at those two points (an equal-key neighbour exists in the set or the index) and counts (c) in the comparator calls at those call sites. **The first time the taint fires, the op that fired it is not scored, the input stops, and the fuzz target returns `Corpus::Reject`** so the input is not kept. Ops before that point were compared normally (a difference there is a finding). A discarded input gets no census credit and no planted-bug credit; the discard rate is recorded per run. The generator keeps the rate low by deferring `RESTART` while two loaded candidates could tie (§3.2), and makes forks strictly lighter or heavier than the active chain around restarts. O2b-1's selftest includes a fork followed by a restart with no top tie, which must **not** fire the taint, and a forced top tie, which must.

**Prefix images.** Building 110+ blocks per input would cost seconds. Each process builds, once per schedule, a **prefix image**: Core's image is a deep copy of every registry memenv (all files, by path) plus a copy of the blocks directory and of `sporks.dat`, independent of the registry; Rust's is a `MemoryEngine` snapshot plus the flat-file snapshot plus a copy of SP0-s's spork file plus the harness's world model. Every M3 image is built with **spork 19 on**: a `SPORK(19, 0)` on both sides before the image's `CLEAN` save, so both spork files carry it and the ChainLock ops and census rows are reachable from step 0 of every input (spork 19 off makes `HasChainLock`, `HasConflictingChainLock` and `EnforceBestChainLock` no-ops, `chainlock/chainlock.cpp:49-54`, `:73-79`, `chainlock/handler.cpp:273-277`). `oracle_chain_save` = `CLEAN` flush, destroy every object (all DBs closed, so no compaction is running), copy, reload. Every input starts with `oracle_chain_restore` on the live session: destroy objects, replace the memenvs and the blocks directory with the image's, run the per-restart reset list, then the reload path above. Restore therefore *is* a restart, one code path per side; worker threads and process globals stay up across inputs, and the restore step's records and post-state are compared as step 0 (D9).

### 2.4 Time (D7)

- `SETTIME t` calls `SetMockTime(t)` on Core and `MockClock::set_mocktime(t)` on Rust. The session has no peers, so `GetAdjustedTime()` = mocktime (time offset 0).
- Mocktime drives: header time checks (`MAX_FUTURE_BLOCK_TIME`), the IBD tip-age test (`v:1987`, `DEFAULT_MAX_TIP_AGE` = 6 h, `kernel/chainstatemanager_opts.h:18`), spork activation (`activation_time < now`, `spork.cpp:163-169`) and the load-time future check (§2.3).
- `FlushStateToDisk` reads `SteadyClock` (`v:3027`), not mocktime; `PERIODIC` writes need an hour of steady time (`v:3042`, `DATABASE_WRITE_INTERVAL` `v:104`) and never fire inside an input. **Rust's periodic flush must likewise not follow mocktime** (D6); in leg A the per-step flush counter catches a mocktime-driven Rust flush, and in leg B it would show up as a flush cause Core never has.
- The generator advances mocktime monotonically by default and moves it backwards only through an explicit `TIME_WARP` intent (§3.3).

### 2.8 The report (§10 has the ABI)

`oracle_chain_step` returns one byte buffer with four sections, each length-prefixed, using O8's canonical JSON rules (sorted keys, integers as JSON numbers, hashes as lowercase hex):

1. `REPLY` — the handler's JSON result or `{"error":{"code":…,"message":…}}`, plus the list of `BlockChecked(hash, state)` pairs the op caused;
2. `RECORDS` — O8 JSONL records the op emitted (C, R, D, A records; the in-memory O8 sink replaces the file sink);
3. `EVENTS` — validation-interface events in order (§4.4);
4. `POST` — the post-state object (§4.5).

### 3.2 Input encoding (D10, D18)

An input is a byte string decoded by a cursor into at most **48 intents**; the decoder never fails (an exhausted cursor yields zeros; a tag is taken modulo the tag count). Intents, not raw ops, are the fuzzed unit, so most inputs reach deep state:

| Intent | Resolves to |
|---|---|
| `EXTEND(branch, n, tx_shape)` | `n` (≤ 8) well-formed blocks on a branch tip, each with up to 16 transactions spending the branch's mature UTXOs, X11-ground to regtest bits; submitted as `BLOCK`s (or as `HEADER`s first, then `BLOCK`s, by a flag). `tx_shape` includes a fan-out shape (up to 64 outputs per transaction), weighted up in leg B (S0p) so that Rust's coins share fills (D31) |
| `FORK(depth, n)` | a new branch from the active chain at `depth`, then `EXTEND` |
| `MUTATE(op, target)` | one non-evo mutation operator (§3.4) on the next block built |
| `PROPOSE(on_tip, mutate?)` | a `PROPOSAL` of a block built on the tip (or elsewhere) |
| `INVALIDATE/RECONSIDER/PRECIOUS(ref)` | the op on a world-model block (often one on the active chain) |
| `CL(ref)`, `CL_ENFORCE`, `SPORK(19, on/off)` (after D34's experiment); at M4 `IS(tx_ref, conflicting?)`, `SPORK(2, …)` (D29) | state ops; `IS` builds a lock on a world-model transaction, optionally on one a later block will conflict with. In an input that has an `IS` intent, `TIME` keeps the tip within 6 h of mocktime and `TIME_WARP` is not drawn, so the IS loop (`v:2801`) runs |
| `FLUSH(mode)`, `RESTART(kind)` | as named; `RESTART` is deferred (one `EXTEND(active, 1)` first) while two candidates the reload would load with equal work exist (D30). Leg B's mirror and reconcile flushes (D31) are harness steps after an op, not intents |
| `TIME(+Δ)`, `TIME_WARP(−Δ)` | `SETTIME` forward (default) or backward |
| `RAW_BLOCK(bytes)` | a raw `BLOCK` with fuzz bytes (decode failures, garbage) — capped at 1 per input |

The world model (blocks, per-branch UTXO sets with keys, per-tx lock state, best CL, mocktime) lives in `node-l1::chain::world` and is updated from **the Rust side's reply** after each step (a divergence stops the input, so either side's view works). Block construction uses `dash` for serialization, `dash-consensus` for bits and subsidy, and P2PK/OP_TRUE outputs as CRASH's `synth.rs` core mode does (maturity 100), so building a block needs no signing for the happy path. Signed P2PKH/P2SH spends exist for the script-failure operators.

### 3.3 Reorgs, restarts and failures

Reorgs arise from `FORK` + `EXTEND` with more work, `INVALIDATE` of an active block, `PRECIOUS` among equal-work tips, `CL_ENFORCE` against a conflicting branch (`EnforceBlock`, `v:4048`, `MarkConflictingBlock`, `v:4080`), and `RECONSIDER` after an invalidation. Restarts are `RESTART` intents at any point. Failures are mutated blocks (§3.4), blocks on unknown parents (`prev-blk-not-found`, reached through `BLOCK`: `submitheader` errors first with `Must submit previous header`, `rpc/mining.cpp:1091-1093`), headers and blocks on invalid parents (`bad-prevblk`), headers and blocks under a conflicting CL (`bad-prevblk-chainlock`, `bad-chainlock`; `AcceptBlockHeader`, `v:4598`), raw garbage, duplicate submissions, and the `session-down` state after a refused load. Failure injection at the storage layer is out of scope (§1.3).

### 3.4 Mutation operators (non-evo, CH3 §7.3's set)

The generator applies, to the next block it builds, one of CH3 §7.3's operators: coinbase value ±1, locktime/sequence at MTP and height boundaries, sigops at limit and limit+1, size limits ±1, the duplicate-tx merkle mutation (`MUTATED`, never cached invalid), nBits ±1 and time edges, tx version/type incl. `bad-tx-type-dip3-inactive` and `bad-cbtx-payload` (CH3 D32, D54), missing/spent/duplicate inputs, premature coinbase spend, in < out, value ranges, BIP30, bad signature (P2PKH and inside P2SH), NULLDUMMY/DERSIG/CLTV/CSV at their boundaries, and **multi-failure blocks** in CH3 §2.4's matrix (meaningful under S1). At M4 (D29) the IS loop operators join: a block spending an IS-locked input's conflict, with and without a ChainLock on that block (CH3 D35's `conflict-tx-lock` vs the `RemoveConflictingIsLock` effect).

### 3.5 Seed programs

`node-l1/tests/chain_seeds/*.prog` are text programs (`extend main 3`, `fork 2 4`, `invalidate main@-1`, `restart kill`, …) compiled to input bytes by `node-l1::chain::seed`. The set covers every op kind and every row of §6.5's census at least once. Programs, not bytes, are committed, so the encoder can change without re-minting the corpus.

## 4. Per-step comparison

### 4.1 Planes

| Plane | Core source | Rust source | Rule |
|---|---|---|---|
| Reply | `REPLY` section | `StepReport.reply` shaped (§5.4) | byte-equal canonical JSON, except `getchaintips`-derived arrays, which are sorted by (height desc, hash) first (Core orders equal heights by pointer, `rpc/blockchain.cpp:1745-1756`) |
| `BlockChecked` | session's recorder | CH1-node's `block_checked` stream | same `(hash, state class, reject reason)` list in order; the debug message is never compared (O8 §4.3's `dbg` rule); CH3 D14's reordering is about commit vs signal, not the list |
| O8 records C/R/D | `RECORDS` | `StepReport.records` | O9a `Comparator` in **stream** mode with `org`; patch keys required; golden keys excluded (§4.2) |
| A records | `RECORDS` (`q` decisions) | NodeSut's recording helper wrapper (§5.1) | strict sequence, by a new O9a sequence comparator (§4.3) |
| Events | `EVENTS` | NodeSut's event capture | §4.4 |
| Post-state | `POST` | `StepReport` post fields | §4.5, field-by-field |

The first difference stops the input and is reported with the op index, the plane, the field name and both values (as `node-l1`'s `Divergence`, which prints field names only on the public route; this target is private, §6.2).

### 4.2 O8 records (D15, D17)

- Records C (connect attempt), R (reject), D (disconnect) with `org ∈ {tip, proposal, verifydb, replay}` (O8 §8.2), compared by O9a in stream mode. `org = proposal` records come from `PROPOSAL`; `org = verifydb` from restarts and image restores.
- `H` records (one per producer start, O8 §4.1) describe the producer and are not compared; each restart's records begin after its `H`.
- C-record **patch fields** (`prev, ver, mrkl, time, bits, nonce, work, ntx, undo, mnl, qc, cp, ehf, bls, bur, dep`) are required on both sides; at M3 the evo fields are the empty values O8 defines below DIP3.
- **Golden fields** (`muhash, txouts, amount, unspendable, bi, stats`) are **excluded per record**: Core's patch does not emit them (O8 emits them only from the extractor), Rust's digest tap does. The per-op exact UTXO digest (§4.5) covers the coin set (`muhash`, `txouts`, `amount`). The per-block and cumulative accounting fields `unspendable`, `bi` and `stats` (O8 §5.3) are **not covered** by `diff_chain`; CH3a a7's L2 replay compares them against goldens. Adding session counters for them is a possible later extension, not claimed here. O9a today has no per-record key exclusion (an uncovered key is exit 3, "incomplete", O9a D2); O2b-3 adds an explicit exclusion list to `Options` (an O9a delta, §14), and any key outside the list that is uncovered still fails the step.
- **`org = verifydb` at M3:** compared only once CH5 (VerifyDB) lands on the Rust side; until then the harness filters them on both sides and counts them (a census row shows they occur). Non-evo VerifyDB has no lasting effects, so nothing else is lost. At M4 they are compared (EV-addendum effects in VerifyDB's transaction roll back; the records still show the attempts).

### 4.3 A records

O8's `q` decisions (`cl_conflict, cl_best, ibd, cl_has, is_conflict, sb_required, gov_valid, sb_triggered, sb_payments`) are the chain helper's answers. Core's patch records them at their `validation.cpp` call sites; Rust's `NodeSut` wraps its `ChainHelper` in a recording wrapper that emits the same records (CH3's `RecordedHelper` is the replay direction; this is the record direction). O8 §4.5 calls A records "replay inputs, not comparison targets", and O9a's `RecordedDecisions` is a lookup, not a sequence comparator; so this plane needs an O8 note (A records become a comparison target for `diff_chain`) and a small O9a addition (a strict sequence compare over `(t, q, key, value)`), both listed in §14. The comparison is strict in sequence and value. A difference in a decision **sequence** is a finding even when verdicts agree (it is the earliest symptom of an ordering bug).

### 4.4 Events (D15)

Recorded on both sides, in order: `UpdatedBlockTip(new, fork, ibd)`, `BlockConnected(hash)`, `BlockDisconnected(hash)`, `BlockChecked(hash, state)`, `NewPoWValidBlock(hash)`, `AcceptedBlockHeader(hash)`, `NotifyHeaderTip(hash, ibd)`, `ChainStateFlushed(locator tip)`. Core's synchronous signals run at their call sites. Its queued ones (`UpdatedBlockTip`, `BlockConnected`, `BlockDisconnected`, `ChainStateFlushed`, `NotifyChainLock`; `validationinterface.cpp:215-227`, `:254-278`, `:309-316`) do not: under O1c's inline queue they run on the caller's thread at the queue's drain points, which are the op's end (the shim's `FinishReport` syncs the queue, `oracle_chain.cpp:1044-1049`) and, inside `ActivateBestChain`, the start of an iteration with more than ten callbacks pending (`LimitValidationInterfaceQueue`, `validation.cpp:3826-3831`, called at `:3870` and `:4050`). An op's list is therefore its synchronous events in emission order, then its queued ones in queue order, unless the queue drained inside the op. Rust's CH1-node notifications are recorded at emission, split the same way, and V's signal queue is synced before the post is read. Until a drain inside an op can be placed on the node's side, an op that queued more than ten signals on both sides alike is refused as out of domain (O2b-3b) once the steps are otherwise the same, Core's events taken in the order a drain at the op's end gives (a drain inside the op only interleaves the two subsequences); any other difference is reported. `NotifyMasternodeListChanged` is synchronous (it iterates the listeners directly, `validationinterface.cpp:349-352`); the node has no counterpart today, and below DIP3 Core does not emit it. Only the order of events within one op is compared, not their position relative to state changes. In leg B, `ChainStateFlushed` is taken out of the ordered list (a Rust flush's event sits at its freeze, a mirror's at the op's end) and the flush counts per cause are compared through `flushes` instead (D31). Core-only events (`NotifyChainLock`, `NotifyMasternodeListChanged`, `SynchronousUpdatedBlockTip`) are recorded and counted but not compared at M3 (declared uncovered); `NotifyChainLock` joins at M4 with CH7b/LK1a's notification.

### 4.5 Post-state (D16)

| Field | Core | Rust |
|---|---|---|
| `tip` (hash, height), `best_header` | `ActiveTip()`, `m_best_header` | `ChainView` |
| `tips` | `getchaintips` rows | `StepReport.tips` |
| `utxo` = (set hash, txouts, amount), **after every op** | full scan: coins DB cursor ∪ `CoinsTip()` cache entries (hook; dirty/fresh entries override, spent entries delete); never a flush | `StepReport.utxo` |
| `index` = SHA256 over (hash, height, `nStatus & (BLOCK_VALID_MASK \| BLOCK_HAVE_DATA \| BLOCK_HAVE_UNDO \| BLOCK_FAILED_MASK \| BLOCK_CONFLICT_CHAINLOCK)`, `nChainTx != 0`) for every index entry, sorted by hash | hook walk of `BlockIndex()` | V's index walk |
| `is_locks` (M4) = sorted `is_i` keys of the IS DB plus the mined-height and archive keys | IS DB cursor (hook) | LK1b-s's store |
| `best_cl` (height, hash) | `Chainlocks::GetBestChainlockWithPindex` | V's best CL |
| `ibd` | `IsInitialBlockDownload()` (this read may latch, on both sides alike) | V's IBD |
| `flushes` = (full flushes, index-only writes) by cause, **since the last restart or restore** (timers and counters are per open, §2.3) | hook counters at the full-flush completion (`v:3078-3102`) and the index-only write branch (`v:3048-3075`); leg B: mirrored flushes booked under the Rust cause they mirror, plus `reconcile` | CH2's flush counters by cause; leg A: the non-Core causes are off and asserted never to fire; leg B: every flush by its cause, plus `reconcile` (D31) |
| `flush_delta` = the op's own flushes, (full, index-only) by cause, across teardown and reopen (§2.3) | the same hook counters, kept by the session across the rebuild | NodeSut's counters, kept across the reopen |
| `persisted` (restart and restore steps only) | the persisted-image reader (§2.3, D37) | the `test-support` store read |
| `sporks` = for every spork id in Core's table (`spork.h`), (value, active at mocktime) | `GetSporkValue`, `IsSporkActive` | SP0-s's `SporkManager::value`, `is_active` |
| `deployments` | `getdeploymentinfo` | V's deployments (CH3a a8) |
| `down` | session-down flag | NodeSut's load-failed state |

Index equality needs undo writes: `BLOCK_HAVE_UNDO` is in the mask, and Core sets it in `ConnectBlock`'s undo write (`validation.cpp:2935-2938`) before raising the entry to `BLOCK_VALID_SCRIPTS` (`:2946-2949`). V connects through ND1's `CoreConnector`, which writes the undo data and sets the bit, so the node's `index` digest is compared with Core's as it is (O2b-3b). V also disconnects through that connector (CH3a a5), so a reorg is compared plane by plane as any other op. Until a7 and a10 a difference in a plane V lacks (records, the flush counters) masks none after it; `utxo` is V's coins read as the shim reads Core's (CH3b b2a D192): the divergence is named by the first other plane that differs, if one does. The post is read in the shim's order: the node first waits for V's deferred work (the fence), then syncs its signal queue, then reads the post.

**The set hash.** A full scan hashes the coin set **sorted by outpoint** with SHA-256 over `(outpoint, TxOutSer)` entries — exact and cheaper than MuHash3072. The incremental form needs an order-free hash and uses MuHash3072 over the same entries; whichever form a schedule uses, both sides use the same one (CH3's `UtxoDigest` gains the sorted-SHA-256 form). Regtest sets stay below ~3,000 coins (leg B's fan-out a few tens of thousands), so a full scan per op should be cheap; O2b-2 measures it. If it is not, each side maintains the **incremental** MuHash/count/amount updated at every coin add and spend (Core: hooks wherever `CoinsTip()` changes — `AddCoin`, `SpendCoin` and the per-block child view's `BatchWrite` into it, `coins.h:286`, `:302`; Rust: the same points on its coins view), recomputed by one full scan after every restart and cross-checked against a full scan at the input's last op. The check stays exact after every op; no sparser schedule is allowed (D16). File positions (`nFile`, `nDataPos`, `nUndoPos`) are **not** compared (§2.2).

**Transient states inside one op** (between the blocks of a multi-block reorg) are not digested: the post-state is per op. Each connected or disconnected block is still compared through its own C/D record (patch fields incl. `undo`, `fx`) and its `BlockConnected`/`BlockDisconnected` event, so a wrong intermediate coin set that the same op repairs exactly, without changing any record, is declared uncovered (§4.6, D16).

### 4.6 What is declared, not compared

CH3's declared differences (the `compat/ALLOWED-DIFFS.md` CH3 §11 creates; not on the base yet: D14 BlockChecked after commit, D25 pool accounting, D33 undo before effects, D45 undo-read exception class) do not reach these planes: none changes a reply, a record, an event order within an op, or the post-state. If one ever does, the comparator gains a named filter with the ALLOWED-DIFFS row cited, never a blanket skip. Declared here: the tie discard (D30), which removes inputs rather than filtering differences; intra-op transient coin sets (§4.5); in leg B, the position of `ChainStateFlushed` within an op (§4.4). Spork state is compared after both restart kinds (D34); nothing about it is declared.

The bins share one seed set (programs compile per schedule). The registry rows: `kind = "l1"`, `pins = ["v24.0"]`, `route = "private"`, `owner = "node-l1"`, `smoke = 60`, `nightly = 1`. New deps on `node-fuzz` follow the nested-workspace lock rule (update `node-fuzz/Cargo.lock` in the same commit).

### 6.2 Private route (D19)

Findings may be consensus differences, so the targets are private: crashes, divergences and minimized inputs go to the private tree per the program's private-route rules; public logs print op indexes and field names only.

### 6.3 Budget per input

≤ 48 intents, ≤ 64 blocks built, ≤ 16 transactions per block, ≤ 64 KiB input, ≤ 64 MiB of block files per session. Expected throughput (to be measured in O2b-3 and recorded): restore dominates (`LoadChainstate` + `VerifyDB` at 6/3 + ABC on each side), so an estimated **5–30 execs per CPU-second** on S0/S1 and less on S2 (DEC-186 counts the whole process's CPU, so S1's script-check workers count against it). The estimate decides nothing: certification floors come from measurement at the gated head (§6.4).

### 6.4 Gates (D20)

- **Per PR (any slice touching the chain path):** `cargo test -p node-l1 --features oracle --test l1_chain` (seed programs on S0/S1, planted witnesses with the `planted` feature in a separate invocation) and the fuzz smoke (`smoke = 60` s per target).
- **Plateau run (DEC-184):** each target runs until coverage plateaus, with 0 divergences and 0 crashes; a low plateau triggers a coverage review (missing census rows, generator rework) before more CPU is spent.
- **Coverage stability (O2b-3 gate, D36):** replay the seed corpus twice in one process and require equal `cov`/`ft`. Background threads add timing-dependent edges: LevelDB compaction, script-check workers (S1), the idle `cl-schdlr` and `bls-work` threads, Rust's V and W loops. The Core fuzz build compiles `leveldb/`, `crc32c/`, `checkqueue.h` users' queue internals, `scheduler.cpp` and `bls/bls_worker.cpp` without coverage (`-fsanitize-coverage-ignorelist`); if Rust's thread loops still make the replay unstable, that is escalated as a DEC-186 question (a stability-filtered `NEW` rule), not worked around in the target.
- **Certification (DEC-186):** `fuzzctl certify <target>@v24.0` for every target at the **gated head**: single process, 3600 CPU-s window, replay before/after. A million execs is out of reach for a two-chainstate target, so each target gets a per-target `min_certify_execs` override **set from throughput measured at the gated head** (O2b-3 measures on its head; O2b-4 re-measures on the head it certifies): `floor = ⌊0.5 × r × 3600⌋`, where `r` is the median execs per CPU-second of three 600-CPU-s runs of the minimized corpus, recorded with the commit SHA in the registry row's comment. No number is fixed in this design. If `r × 3600 < 10,000` the target is too slow to certify meaningfully: that is a **target-design problem** (lighter image, cheaper restore, smaller input budget), fixed before certification, never compensated by more farm hours.
- **Feature check:** the gate runs `cargo tree -p rdashd -e features` (and for every product crate in `layers.toml`) and fails if `test-support` or any `planted-*` feature appears, so `NodeSut`, `flush_regime` and the plants stay unreachable from product builds.
- **CPU-h are reported only** (DEC-184(2)): the farm reports clean CPU-h per target and milestone. They are not a goal and not a closing condition.

### 6.5 Census floor (before certification)

The harness counts, per run, `(op kind × reply class)` and every reject string reached. Certification starts only when the corpus covers: every op kind with ≥ 1 success and ≥ 1 failure where one exists; every non-evo reject string of CH3 §7.3's census reachable from `submitblock`/`proposal`; `bad-prevblk-chainlock`, `bad-chainlock` (reachable from step 0 because M3 images carry spork 19 on, §2.3) (and at M4 `conflict-tx-lock` and an `is_rm` effect, D29, both reached with the tip out of IBD); at least one each of: a reorg of depth ≥ 3, a `KILL` restart that loses unflushed index entries, an `INVALIDATE` of the tip that a `RESTART` undoes (D32), a ChainLock whose header arrives after `CL_RECORD` (§2.1), a refused load, a `RECONSIDER(ignore_cl=true)` across a conflicting CL, a `PRECIOUS` that switches tips, an IBD latch flip by `SETTIME`, a testdummy transition to ACTIVE, and a CH3 §2.4 multi-failure row under S1. The census counts only inputs that were not discarded. It also reports the deferred restarts and the tie-discard rate (D30); a discard rate above 1% of inputs is a generator bug to fix before certification. Leg B adds: at least one mirrored `THRESHOLD` flush, one mirrored native `CACHE_*` flush, one `reconcile` after a **delayed** mirror of a mid-op flush (mirrored at op end, then reconciled), and one `KILL` and one `CLEAN` restart after a mirrored flush; the census reports the share of leg-B ops with an op-end or a delayed mirror (a share under 5% is a generator problem to fix before certification). There is no index-only row (§2.3). Spork rows — a spork-19 off→on edge followed by `CL_RECORD` (the `ResetChainlock` path, `chainlock/handler.cpp:209-221`), `SPORK` then `KILL` (both sides revert), `SPORK` then `CLEAN` (both keep) — enter the census when D34's experiment admits generator spork intents; they are M3 rows. `fuzzctl` reads the census from the target's stats file.

## 8. The disposable-datadir proposal experiments (D22)

The PLAN asks that these be recorded. They answer one question: **does the shim session behave like a real `dashd`?** (A1's adapter cross-check rule: every in-process adapter is checked against the stock binary.)

- **Harness:** `node-l1::chain::xcheck` replays a corpus program against (a) the shim session and (b) a stock regtest `dashd` built from the same Core commit plus the O8 patch (no `DASH_ORACLE_HOOKS`), started on a **disposable** datadir under `/work/scratch/o2b-xcheck/<run>/` with the schedule's args plus `-statedigestlog=<file>` and `-recordstatedecisions=<file>` (O8 §2), `-mocktime=<program time>` on **every** start (the load-time future check reads `GetTime()` before any RPC, `node/chainstate.cpp:424`; `-mocktime` is applied at `init.cpp:1368`), `-connect=0 -listen=0 -dnsseed=0` (no peers, so `mnsync` never advances, `node/sync_manager.cpp:215-228`; each start asserts `mnsync status` reports not synced, as CH3 D49 does), and the harness waits until the startup import and activation are done (`getblockchaininfo` stable, RPC warm) before the first op. It is driven over RPC: `submitblock`, `submitheader`, `getblocktemplate` proposals, `invalidateblock`, `reconsiderblock`, `preciousblock`, `setmocktime`, `gettxoutsetinfo` (as `FLUSH ALWAYS`, since it forces a flush), `stop` + start (`CLEAN`), SIGKILL + start (`KILL`). Concurrency 1; the datadir is deleted after each program.
- **Compared:** replies, digest records, `getchaintips`, tip, `gettxoutsetinfo muhash` at the end (a flush is acceptable on the last step), IS/CL state where reachable.
- **M3 scope:** programs without `CL_RECORD` and `ISLOCK` (they need real signatures on `dashd`); `SPORK(id, value)` maps to `dashd`'s `sporkupdate <name> <value>` (`rpc/node.cpp:207-245`, which calls `UpdateSpork`; `spork` itself only takes `show`/`active`, `:156-202`) once the spork experiment has passed, and spork state is observed with `spork show`; and the X-check `dashd` runs with the session's `-sporkaddr`/`-sporkkey` and sets spork 19 on while it builds the prefix, as the images do (§2.3); programs also exclude `ACTIVATE` and `FLUSH IF_NEEDED/PERIODIC` (no RPC; the X-check sampler drops them, and `FLUSH ALWAYS` maps to `gettxoutsetinfo`). A refused load is an `InitError` exit in `dashd`; the harness compares the exit and the message in `debug.log` with the session's `session-down` reply and ends the program there, ≥ 200 sampled programs per schedule plus all seed programs, **with proposals in every program** (the "proposal experiments"): proposals on the tip, off the tip, after `INVALIDATE`, after `KILL`, duplicates of accepted/invalid/inconclusive blocks.
- **Spork experiment (gate for spork ops, D34):** two **isolated** trials, `KILL` and `CLEAN`, each started from the **same clean-saved baseline** in which spork 19 is **on** (value `0`): for `dashd`, a fresh copy of a baseline datadir made by `sporkupdate SPORK_19_CHAINLOCKS_ENABLED 0` and `stop` (started with the session's `-sporkaddr`/`-sporkkey`); for the session and `NodeSut`, a restore of an image saved the same way (restore suppresses the old instance's store, §2.3). In each trial: `sporkupdate SPORK_19_CHAINLOCKS_ENABLED 4070908800` (off; the default, `spork.h:69`; activation is `value < adjusted time`, `spork.cpp:163-169`) and **assert off** with `spork show` (the session's and `NodeSut`'s `sporks` field); then SIGKILL + start (`RESTART KILL`) in one trial, `stop` + start (`RESTART CLEAN`) in the other; then assert **on** after `KILL` (the last clean store holds `0`) and **off** after `CLEAN` (the shutdown store wrote the update) — on `dashd`, the session and `NodeSut` alike. Because each trial starts from its own copy of the baseline, an earlier trial's clean store cannot mask a killed result. Recorded in the M3 evidence file; generator spork intents are admitted only after all twelve assertions pass (a pre-restart and a post-restart check for each of 2 trials × 3 systems).
- **M4 scope:** everything, with real signatures, the tip kept within 6 h of mocktime in programs with IS locks (so `dashd`'s IS loop runs, `v:2801`), (`submitchainlock`, IS locks from a regtest masternode set, `-llmqtestparams`) and cycle-base proposals at DIP24 boundaries (A1 §2.10.1's "proposal at cycle base" row).
- **`TEMPLATE` mapping (M4, D38).** The session builds templates with `BlockAssembler` directly; `dashd` only offers `getblocktemplate`, whose wrapper is not under comparison. The X-check maps GBT's JSON to the fields both expose — `previousblockhash`, `height`, `bits`, `coinbasevalue`, `coinbase_payload`, `masternode` and `superblock` payment lists, and the non-coinbase `transactions` (quorum commitments) — and compares those only. It issues a `TEMPLATE` only when `dashd`'s tip **hash** differs from the tip hash at `dashd`'s previous template call, and nothing else that feeds the template (a `CL_RECORD`, a `QFCOMMIT`) happened since that call (otherwise `dashd` may answer from its static template cache, `rpc/mining.cpp:809-813`, which is wrapper behaviour; an invalidate/reconsider back to the same tip counts as no change) and only when `getmempoolinfo` reports an empty mempool (a stock node re-adds disconnected transactions to its mempool on a reorg; the session has none). Skipped template ops are counted in the evidence file.
- **Record:** `docs/node-program/evidence/O2b-xcheck-M3.md` (and `-M4.md`): commit SHAs, schedules, program counts, the agreement table, and every disagreement with its disposition (shim bug fixed, or a declared session difference added to §4.6 with Sol's sign-off). A disagreement is never filtered silently.

`KILL` on `dashd` is a real SIGKILL sent between ops (no flush in flight); LevelDB hands each write to the OS at once, so nothing written is lost and the full post-restart state is compared. Spork persistence (D34) is exercised by the spork experiment above before any spork op is generated. Address ties (D30) are as possible in `dashd` as in the session; the X-check uses the same deferral and discards a program whose session run fired the tie taint (§2.3).

## 10. Oracle ABI planning (D23)

ABI numbers are **symbolic** in this design: each O2b slice that changes `oracle.h` takes the **next free number at its merge**. Current allocation (manager, 10-16): 17 = the train-14 bundle (current pin), 18 = O2a-GV, 19 = BS11a-2, 20 = CJ0. O2b reserves a number only when its slice is merge-ready, and only then updates the ABI ledger, `pins.txt`, the `/work/cache/oracle/<sha>/{plain,fuzz}` installs (install before cleanup) and SB4's vector regeneration.

| ABI | Row | Content |
|---|---|---|
| next free at O2b-1's merge (`ABI_O2B_M3`) | **O2b-1** | `oracle_chain_new`, `_step`, `_report_bound`, `_save`, `_restore`, `_image_free`, `_free` |
| next free at O2b-5's merge (`ABI_O2B_M4`) | **O2b-5 (M4)** | `TEMPLATE` (via `BlockAssembler`), `QFCOMMIT`, coinbase-CL, `ISLOCK` with real signatures and the IS listener, real-signature switch, evo `POST` fields, VerifyDB level-4 |

```c
typedef struct oracle_chain oracle_chain;          /* one per process */
typedef struct oracle_chain_image oracle_chain_image;

/* args: schedule args as argv strings (no "-regtest"; implied). mocktime: initial.
 * image: NULL builds an empty chain at genesis. Refused (ORACLE_E_ARG) while another
 * chain or peer session is live. A load failure is ORACLE_REJECT with the message
 * in *out_err (ORACLE_E_BUFFER rules). */
int oracle_chain_new(const char* const* args, size_t n_args, int64_t mocktime,
                     const oracle_chain_image* image, oracle_chain** out,
                     char* out_err, size_t* out_err_len);

/* op: one tagged frame (u8 tag, then the payload in Core serialization).
 * out: the four-section report (§2.8). A stateful call: ORACLE_E_BUFFER is returned
 * before the op runs (the caller sizes the buffer by oracle_chain_report_bound()). */
int oracle_chain_step(oracle_chain* s, const uint8_t* op, size_t op_len,
                      uint8_t* out, size_t* out_len);
size_t oracle_chain_report_bound(const oracle_chain* s);

/* CLEAN flush, destroy every object (all DBs closed), deep-copy the memenvs and the
 * blocks directory, reload. The image owns its copies and outlives the session. */
int oracle_chain_save(oracle_chain* s, oracle_chain_image** out);
/* Destroy objects, replace memenvs and blocks with copies of img, run the per-restart
 * reset list, reload; the reply section is RESTART's. Threads and globals stay up. */
int oracle_chain_restore(oracle_chain* s, const oracle_chain_image* img,
                         uint8_t* out, size_t* out_len);
void oracle_chain_image_free(oracle_chain_image* img);
int oracle_chain_free(oracle_chain* s);   /* non-OK: the Rust binding poisons the pin (O1c D5) */
```

The "stateful call runs once" rule is kept by sizing: `oracle_chain_report_bound` returns an upper bound (it grows with the number of index entries and coins); `oracle_chain_step` checks capacity against it **before** running the op and returns `ORACLE_E_BUFFER` without side effects. Until a slice merges, its branch, docs and tests say `ABI_O2B_M3`/`ABI_O2B_M4`; the concrete number is written into `oracle.h`, `dash-oracle-sys`'s version check and the ledger in the merge commit only.

## 15. Open questions (with recommendations)

1. **Should `diff_chain_av` (S2) gate M3?** It needs an 8,100-header image and is slower. *Recommendation:* yes — the assumevalid boundary is NFR-CEQ-08 — with its floor from D20's measured rule; if it falls under the 10,000-exec design threshold, lighten the image first.
2. **`KILL` on the Rust side: drop V or simulate power loss?** *Recommendation:* drop V without shutdown flush (Core-equivalent); power-loss images stay in CRASH.
3. **Who owns the RPC shaping before RP1a?** *Recommendation:* O2b-3 (`node-l1::chain::shape`), replaced at RP1a; RP1a's reviewers get the port as a test oracle.
4. **Per-op UTXO cost at M4** (larger sets with MN collateral). *Recommendation:* full scan per op; switch to the incremental digest (D16) if O2b-5 measures > 20% of step time. A sparser schedule is not an option.
5. **Leg B's mirrored vs reconciled shares.** *Recommendation:* measure in O2b-3/O2b-4; if most leg-B flushes are reconciled (mid-op), shift leg B's generator to single-block `EXTEND`s and larger fan-out rather than drop the leg.

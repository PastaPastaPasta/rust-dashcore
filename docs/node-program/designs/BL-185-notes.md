# BL-185: a selftest shard started the shared sccache server (D27 escape)

BL-155's post-merge proof (`bl155-st`, `selftest.sh 9703ec480` on slot s, 10-16 20:40Z to 10-17 05:49Z) passed all 323 cases over 3 shards, then failed on the reaper's line `FAIL  a shard started the shared sccache server (session 4136683), left running (D27)`. BL-155 D27 says no shard starts a server. This task found the path, closed it, and kept the reaper's flag.

## D-rows

| D1 | **Root cause: D27's wrapper looked, then connected; the shared server can vanish in between, and the client then starts one.** The shards' rustc wrapper checked that something accepted on 127.0.0.1:4226, then `exec sccache`. If the server goes in between, sccache 0.18's client gets `ConnectionRefused` and starts a server where it connects (`connect_or_start_server`, src/commands.rs:315-352 at v0.18.0: refused or timed out starts one). That server carries the run's nonce and double-forks into its own session, which is exactly what the reaper flags. The gap is not microseconds, as D27 assumed: on a gate, `sccache` is gate-fast's shim (bash, `mktemp`, a `tee` pipeline) running `~/.local/bin/sccache` (bash, a `readlink -f` per PATH entry, `mkdir`, `chmod`) before the client connects, a dozen forks at load 150-200 with hypervisor steal. **And the shared server goes often.** A server lives in the cgroup of the unit whose client started it, and systemd kills that cgroup when the unit stops. Measured: a private-port server a client started inside a throwaway `systemd-run --user` unit listened while the unit ran, and was gone once it ended. So the box's server dies whenever the unit that happens to host it ends (today pid 3783187 lives in `bs11a-2-smoke-t15.service`), and every client on the box then races to restart it. Over a 9 h run with 3 shards compiling at `-j12`, a shard sat in the gap during one of those restarts. **Two D27 premises were also wrong** (sccache 0.18, src/commands.rs:726-735): `--show-stats` with no server prints empty stats and exits 0, and starts nothing. So the driver's pre-start never started a server, and the supervisor's keep-alive never restarted a dead one. | **Evidence.** (1) Reproduced on node/integration dd6e06247 with `contrib/node/test-selftest-sccache.sh node/integration`, scenario race (D4): shard 1's compile through D27's wrapper started pid 390021 (pgrp = sid 390020, leader gone) with `SCCACHE_START_SERVER=1`, `SELFTEST_RUN_NONCE=<the run's>`, `SELFTEST_RESULTS=…/1/results`, in the test unit's cgroup. | D2 | **The shards' sccache clients never use the shared server's address. The supervisor relays a port of its own to it.** Given an sccache, the supervisor listens on 127.0.0.1:<ephemeral> for the whole run and passes each connection on to the shared server. That address is `SCCACHE_SERVER_UDS`, else 127.0.0.1:`SCCACHE_SERVER_PORT` (4226 unless a number up to 65535 is given), as the driver read it. If the shared server doesn't answer, it closes the connection. The shards get `SCCACHE_SERVER_PORT=<relay port>` and no `SCCACHE_SERVER_UDS`, so every sccache client a shard runs, through the wrapper or not, connects to the relay. A client only starts a server when its connect is refused or times out. A timed-out connect to the relay would start one whose bind fails (the relay holds the port), after which the client reconnects. The relay holds its port until the supervisor exits, and on every orderly way out the supervisor kills the shards first. So while the supervisor runs, a shard's client can't start a server at all, whatever the shared server's state. **Residual case (review M1):** if the supervisor dies abruptly (SIGKILL, OOM, a crash), a shard keeps going until the reaper's sweep. A client already past the wrapper's checks could then start a server on the relay's port, never on the shared address. It would use the shared cache directory, and the reaper takes it for the shared server: it spares it and fails the run. The wrapper narrows this by also checking that the supervisor is alive (`kill -0 $SELFTEST_SUPERVISOR`), and compiles uncached once it isn't. **The wrapper** checks that, and that the shared server answers, and compiles with `rustc` itself, uncached, when either fails. That's the quiet path while the server is down. Otherwise it runs sccache, streaming stderr (cargo reads rustc's notices there as they arrive) while keeping a copy. If sccache exits non-zero and printed a `sccache: error: ` line, it reruns the compile without the cache. **Every uncached compile appends its reason to `$run/uncached`** (review M2): the supervisor gone, the server not answering, or sccache's first error line. After the run, the driver prints `sccache: N compile(s) in the shards ran uncached, by reason:` and the top five reasons. A selftest slowed by a dead shared server says why, and a persistent sccache fault, which no longer fails compiles, still shows up. A dropped relay connection ends that way (measured: `failed to execute compile … Connection reset by peer (os error 104)`, exit 2). rustc's own errors never start with that prefix. **The relay** runs one thread per connection and a pump each way. End of input passes on as a half-close; any error shuts both sides. Its TCP connect to the shared server gives up after 10 s (a stalled server with a full accept queue would otherwise hold it for the kernel's ~127 s of SYN retries). A connect to a socket (`SCCACHE_SERVER_UDS`) whose backlog is full fails at once, and the connection is dropped. It sets `TCP_NODELAY` on both TCP sides, so the extra hop adds no Nagle delay to a short reply. A connection it can't get a thread for is dropped, as if the server didn't answer. The client and the shared server see a byte stream, so compiles, hits and stats are unchanged. The keep-alive is unchanged: `--show-stats` every 120 s against the shared address, without the nonce, which resets the server's idle timer (src/server.rs:860) and never starts one. | Closes the race by construction instead of narrowing it. The probe and the connect can't be made atomic from outside sccache, but the address can: what answers on the relay's port is always the relay. Rejected: (a) `SCCACHE_NO_DAEMON=1` in shards would keep a shard-started server in the shard's session, but that server would still bind 4226, become the box's server, and be killed with the shard mid-way through other threads' compiles. (b) Making the server start fail through sccache internals (an unwritable `TMPDIR` for its notify socket, a broken `SCCACHE_DIR`) depends on undocumented startup order, and `~/.local/bin/sccache` rewrites `TMPDIR`. (c) A private server per run was rejected in D27: a second server on the shared cache directory. (d) `RUSTC_WRAPPER=` for shards means K cold builds (D17). (e) Having the driver start a server when none answers, which was D27's intent: that server would live in the gate unit's cgroup and die when the gate ends, under other threads' compiles. A shard compiling uncached while the shared server is down is slower, not wrong (D17). **Limits.** (1) Review N2: in a gate, `sccache` is gate-fast's shim, which itself compiles uncached on a transport error and passes sccache's error lines on. If that uncached compile then fails for real (some cases plant compile errors), the wrapper sees the error line and runs rustc once more. The diagnostics appear twice, and the verdict is unchanged. (2) Review N3: the driver reads the address more strictly than sccache's `get_addr` does. A port of `+4227` or `0004227`, an empty `SCCACHE_SERVER_UDS`, or an abstract socket name gives uncached compiles, or a relay to 4226. None of them can start a server. |
| D3 | **The driver no longer probes the server before the shards start.** D27's loop (`timeout 60 <sccache> --show-stats`, three tries, then `FAIL  no sccache server answered in 3 tries …`) is gone. In sccache 0.18 it started nothing (D1), so it only waited out stalls, and could fail a run on a stalled server. With the relay, a missing or stalled server costs uncached compiles and nothing more. A stall can cost time, though: the wrapper's look has no timeout, so a server whose accept queue is full can hold a compile for up to the kernel's ~127 s of SYN retries. D27's loop and client waited just as long. The driver now only decides whether the wrapper names an sccache that can be found (same rule and limit as D27). This supersedes D25 (2)'s "the driver now starts the server itself, before any shard" and D27's pre-start, keep-alive-restart and residual-race paragraphs. D27's reaper rule (spare an sccache server in a session of its own, fail the run) and D28 are unchanged. | The reaper still fails a run in which any process of the run started a server: a check that sets its own `SCCACHE_SERVER_PORT` or `SCCACHE_SERVER_UDS` still can, and D4's leak scenario proves the flag. |

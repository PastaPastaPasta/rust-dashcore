# O2a-CJ1: the CoinJoin rules in the oracle, implementation notes

Decision rows taken while implementing O2a-CJ1: Core's session-free CoinJoin rules as oracle entries
(`oracle_cj_*`, built as ABI 27 on Core branch `node/o2a-cj1-oracle-v24.0` and installed as ABI 26 in the train-17 bundle, D1), their `dash-oracle-sys` bindings
(`Oracle::cj_*`, module `coinjoin`, test `tests/coinjoin.rs`) and the L1 differential `diff_coinjoin`
(node-l1 `src/coinjoin.rs`, test `l1_coinjoin`, node-fuzz target and public seeds). This is CJ0's follow-up
F2, group 1 (CJ0 notes D5, D18). Groups 2 and 3, the rounds and the session replay, are O2a-CJ2. The byte
formats are the comments in `oracle.h` ("CoinJoin rules (ABI 26)") and node-l1 `src/coinjoin.rs`'s module docs.
Line numbers cite Core v24.0.0-rc.3. `src/coinjoin/` is unchanged at the oracle pin.

| D2 | **Calls with no chain run shared; view and context calls select the chain.** `cj_rule`, `cj_entry`, `cj_message_hash`, `cj_check_signature` and `cj_queue_time_out_of_bounds` read no network parameter and no global, so they run under the shared lock. `CheckSignature` decodes the signature as basic (`CBLSSignature(Span, false)`, `coinjoin.cpp:51`, `:84`) and the key in the scheme the caller names. `cj_in_outs` and `cj_collateral` build a `ChainstateManager` for `Params()`, and `cj_dstx_structure` reads the pool sizes and V24, so these three run `on_chain`. | `dash-oracle-sys/src/coinjoin.rs`. |
| D3 | **`IsLocked()` is a `--wrap` seam over the caller's lock set.** Core's `CInstantSendManager` answers from its database of InstantSend locks, and building one would need signed ISLOCKs. The shim wraps `llmq::CInstantSendManager::IsLocked(const uint256&) const`. While a CoinJoin call runs on the thread, the wrapper answers whether the txid is in the call's set; at other times it is Core's function. A `static_assert` pins the member's type. The asm labels use the same calling convention as a free function taking `this` first (the Itanium ABI). | `oracle_coinjoin.cpp` seams; `tests/coinjoin.rs` `in_outs_seams`: an unlocked mempool coin gets `ERR_MISSING_TX` and the locked one is accepted. |
| D4 | **`ProcessTransaction()` gets the caller's answer.** `IsCollateralValid` asks ATMP for a test accept through `ATMPIfSaneFee` (`coinjoin.cpp:439-455`). The shim does not run a mempool, and the Rust side has none, so the call wraps `ChainstateManager::ProcessTransaction`. It returns `Success(vsize, base_fees)` or `Invalid(TX_CONSENSUS)` as the caller says, and counts the calls by `test_accept`. `ATMPIfSaneFee` reads only the result type and `m_base_fees`. The tests are of CoinJoin's checks around ATMP. ATMP itself is CS-layer code with its own diffs. | `oracle.h` `oracle_cj_collateral`; `tests/coinjoin.rs` `collateral`: one test-accept call, no submission, and a fee above 0.1 DASH refused. |
| D5 | **The harness answers as Core's mempool would.** `diff_coinjoin` gives both sides the same `MempoolAccept` answer. The answer is a refusal whenever ATMP would refuse on amounts: an output, a running output sum, an input coin or a running input sum outside `MoneyRange` (`CheckTransaction`, `CheckTxInputs`). Otherwise it accepts or refuses as the case's flag says, and an acceptance carries the transaction's fee, inputs minus outputs. With any other answer the diff would compare the harness, not the node: dash-coinjoin applies the range checks itself (CJ0 D12), and Core's verdict would be the injected one. | node-l1 `src/coinjoin.rs` `compare_collateral`, `amounts_in_range`. |
| D6 | **Sums that overflow in Core are refused.** `IsCollateralValid` adds output values, then input coin values, in `CAmount` before anything checks a range. It then subtracts them (`coinjoin.cpp:461-490`). On adversarial values that is signed overflow, which is undefined behaviour. The shim repeats the sums in Core's order with `__builtin_add_overflow`/`__builtin_sub_overflow` and returns `ORACLE_E_ARG` where one would overflow. The order is: outputs up to and including the first whose script fails, inputs up to the first without a usable coin, and the difference only when every input was found. A difference of `INT64_MIN` is refused too: the log line's `nValueOut - nValueIn` (`:491`) would negate it. That line is evaluated only when the COINJOIN category is enabled, which the oracle never does, so this refusal is conservative. `IsValidInOuts`' `nFees` cannot overflow at a real session denomination: it adds a value only after `checkTxOut` has held it to a denomination, so reaching 2^63 would take about 9×10^8 inputs. At session denomination 0 that premise fails (Opus-h r1 F0). `AmountToDenomination` is 0 for every non-denominated amount, so `checkTxOut` passes any value and `nFees -= txout.nValue` (`:371`) / `+= coin.out.nValue` (`:402`) overflow on adversarial ones. No session has denomination 0: the server refuses such a dsa (`server.cpp:925`) before it sets `nSessionDenom` (`:1015`), and the client never selects at it. So `oracle_cj_in_outs` refuses a `session_denom` of 0 with `ORACLE_E_ARG`, as Core's session start would. dash-coinjoin's `is_valid_in_outs` used to panic there (`inouts.rs`, overflow checks on); its fee sums now wrap, as Core's `CAmount` arithmetic does in practice, so it answers on any input. | `tests/coinjoin.rs` `collateral`: an overflowing output sum, input sum and difference, and a difference of `INT64_MIN`, are refused; a huge first output with a non-P2PKH script is not (Core returns before the next add), nor an input sum after a missing input or an unlocked mempool coin (it is after a locked one). `l1_coinjoin` `collateral_overflow_rows`. |
| D7 | **Test-accept calls are compared only when every amount is in range.** Out of range, dash-coinjoin returns before asking the mempool, while Core asks it and gets the refusal (D5). The verdicts agree and the call counts differ by design. Out of range the node must still ask nothing: its own `MoneyRange` checks (CJ0 D12) are what keep its verdict Core's, and the harness's refusing answer would otherwise hide them (Opus-h r1 F2). So a test-accept call there diverges ("asked the mempool out of range"). In range, both ask exactly when the fee passes. Neither side ever submits (`submit_calls` is always 0). | `compare_collateral`. |
| D8 | **The view is a real `CTxMemPool` restricted to what a mempool holds.** Mempool transactions go through `addUnchecked`, so `CCoinsViewMemPool::GetCoin` is Core's own (`txmempool.cpp:1866-1887`). Core refuses, with `ORACLE_E_ARG`: a coinbase, a special transaction (`addUnchecked` indexes payloads by type), a repeated txid, and two transactions spending one outpoint. The coins are the chain contexts' coin records. Refused there: value −1, unspendable scripts, repeated outpoints and a height of `MEMPOOL_HEIGHT` (`INT32_MAX`), which `CCoinsViewMemPool`'s readers would take for a mempool coin. The harness drops all of these before calling, so the two sides read one view. Its mempool transactions spend chain outpoints only. | `tests/coinjoin.rs` `view_refusals` (each refusal); node-l1 `Reader::view`. |
| D9 | **Rule arguments must be in range.** Every int argument must fit in `int`. `ShouldPromoteDenoms`/`ShouldDemoteDenoms` counts and goals must be in `0 ..= INT32_MAX / 2`, because the deficit sums in `common.h:232-260` overflow `int` beyond that, and no wallet has those counts. A `ValidateFinalTxComposition` size must be non-negative. Each is `ORACLE_E_ARG`, and the diff treats it as out of the domain (D16). | `tests/coinjoin.rs` `rules_and_their_domain`. |
| D10 | **The multiplied composition counts are capped at `u64::MAX / 10` in the diff.** Core multiplies the larger-denomination `size_t` counts by `PROMOTION_RATIO`, which wraps modulo 2^64. dash-coinjoin's `validate_final_tx_composition` saturates. They differ only at a count of at least 2^64/10, and no transaction comes near that (pool sizes are at most 200 inputs). The oracle accepts any non-negative size, and `tests/coinjoin.rs` shows Core's wrap. The diff compares every larger count up to `u64::MAX / 10`, where no product wraps, and skips larger ones rather than port the wrap. The totals are never multiplied and are compared up to `i64::MAX`. | `rules_and_their_domain`; `l1_coinjoin` `rule_rows`. |
| D11 | **V24 for the structure check comes from a chain context.** `IsValidStructure` reads `DeploymentActiveAt(*tip, chainman, V24)` (`coinjoin.cpp:131`). The shim passes the context's tip and its `ChainstateManager`, whose version-bits cache the context seeds for the block after the tip. The tip reads the same seeded period unless it is a period's last block, so the harness moves such a tip down one. dash-coinjoin's `v24_active` is computed the way `GetStateFor` short-circuits (`versionbits.cpp`): true for `ALWAYS_ACTIVE`, false for `NEVER_ACTIVE` (mainnet only at the pin; devnet's V24 has a start time), and otherwise the seeded state is `ACTIVE`. The pool sizes are the network's `PoolLimits::of`. | `tests/coinjoin.rs` `dstx_structure`; `l1_coinjoin` `structure_rows`: four networks, five states, twelve heights, with the last block of a period on every network (99, 119, 249 and 4031, and 199, 239, 499); `pool_size_rows`: balanced 180, 181, 200 and 201 (the pre- and post-V24 pool sizes, 20 participants of 9 and of 10 inputs) on every network and state at heights 1 and 4030, so mainnet's rows are pre-V24 only. 180 is valid everywhere and 201 nowhere; 181 and 200 are valid exactly after V24, and are possibly valid post-V24 before it. Sol r1's mutant 2 (`<=` to `<` in `is_balanced_within`) diverges there and on the seeds. |
| D12 | **Operator keys must be canonical in their scheme.** A masternode list holds operator keys through `CBLSLazyPublicKey`, which round-trips them. The node's keys are therefore always canonical. The shim decodes the caller's 48 bytes with `CBLSPublicKey::SetBytes(bytes, legacy)`, and invalid bytes give an invalid key that Core's check rejects. The diff compares only keys that `BlsPkValue::from_canonical` accepts. Basic-scheme signatures never answer `BlsVerdict::Unsupported` (CJ0 D9), so that answer diverges (Opus-h r1 F4): a base-sdk change that started giving it would otherwise silently move every signature row out of the domain. That excludes the legacy keys that only Core's Exotic decode accepts; their decoding is BS11a's class, not these rules. | `l1_coinjoin` `message_rows`: the signature is valid under the key in either scheme's encoding, and invalid under another key or a changed message. |
| D13 | **Messages are decoded whole on both sides.** The shim reads a dsq or dstx with `DecodeWhole`: a failed read is `ORACLE_E_DECODE` and leftover bytes are `ORACLE_E_TRAILING`. The diff decodes with base-sdk's `DsQueue`/`DsTx` codec and requires that it consumes everything. Both mean "no message". Core's P2P handler ignores trailing bytes, but that is BS9's decode question, not these rules. | `message_rows`: a long and a short message are both rejected. |
| D14 | **The input format is structured, not raw wire.** Entries, views and collaterals are built from compact selectors: denomination and collateral value tags, P2PKH tags, outpoints into eight chain txids or the view's mempool, and lock masks. Both sides get the same Rust-built objects, and Core gets their wire encoding. Random bytes then reach accepted entries, mempool-locked coins and repeated scripts. Raw values (tag 2) still reach the extremes. Message cases (hashes, signatures, time, structure) take raw wire bytes, and the seeds supply signed ones. | node-l1 `src/coinjoin.rs` module docs. |
| D15 | **Seeds and fuzzing.** `seed_inputs` (851 inputs, from the `coinjoin_seeds` example) covers every rule at every pick, valid and invalid entries, and sessions and collaterals on all four networks. It also has a signed queue and broadcasts, signed by a fixed base-sdk key (`SignBasic`), in each message case. They are inputs only, and the oracle judges them when they run. `l1_coinjoin` checks that the seeds are current and that none diverges. The fuzz target registers in `targets.toml` as owner dash-coinjoin, private route, smoke 30, nightly 2. node-fuzz's lock adds `dash-coinjoin`, whose dependencies were already locked. | `node-fuzz/public-seeds/PROVENANCE.md`; `fuzzctl check` ok. |
| D16 | **Only the refusals the harness predicts are out of the domain.** A rule's `ORACLE_E_ARG` (D9) is out of the domain. Entry and structure calls are built inside the oracle's domain, so any error there diverges, as does a message error other than a decode one (D13). A session call is out of the domain exactly at denomination 0 (D6): `ORACLE_E_ARG` there and nowhere else, and a mismatch either way diverges. The node's `is_valid_in_outs` is still run there, so it must not panic. For collaterals the harness repeats the shim's overflow scan in Core's order (`core_sums_overflow`, D6). On a refused collateral the node's answer must be invalid, without a mempool call (Opus-h r1 F3): overflow needs an amount outside `MoneyRange`, and dash-coinjoin checks every prefix Core sums. Core's `ORACLE_E_ARG` must come exactly when it predicts one: both give out of the domain, and a mismatch either way diverges ("ORACLE_E_ARG without an overflow", "overflow not refused"). Both sides read the harness's mempool answer (D5), so the node's own `MempoolAccept` (ATMP) is not tested here. That is the CS layer's diff. | node-l1 `compare_in_outs`, `compare_collateral`; `l1_coinjoin` `denomination_zero_rows`, `collateral_overflow_rows`. |
| D17 | **The node's mempool admission stays open until MP1a.** Sol r1 raised the D16 point independently: `diff_coinjoin` injects one `MempoolAccept` answer into both sides, so a CoinJoin server built on dash-coinjoin is only as right as the `MempoolAccept` it is given. dash-coinjoin's collateral and entry checks are covered, but the trait's implementation is not. MP1a's mempool differential (ATMP against Core) must cover the implementation that CJ1's server runtime plugs in, before that runtime uses the trait for collateral or final-transaction admission. Until then the server row depends on MP1a. | D5, D16; Sol r1 (`reviews/O2a-CJ1-r1-sol.md`). |

# SP0: spork manager implementation notes and D-rows

SP0 (PLAN rev1 split, M-10.1) implements Core's `CSporkManager` for v24 only (DEC-82): one spork
key, the five `sporkDefs`, mainnet's hard-coded values (O17: every spork 0, SPORK_21 = 1),
`getsporks` with v24's repeat dedup, and the chain's `SporkView`. This file records the
implementer's decisions where the sources leave a choice, per the IMPLEMENTER contract ("decide,
record a D-row, continue"). Core line numbers are v24.0.0-rc.3's; `spork.{h,cpp}` are identical at
the oracle pin.

## Where it lives

- `dash-evo::spork` (layer P): the pure core shared with SPV (SB4 D29). Core's hashes
  (`GetHash`, `GetSignatureHash`, the message form), compact-signature recovery with Core's
  header masking, signing (RFC 6979, byte-equal to Core's), `IsValidSpork`, the store with
  `ProcessSpork`'s newest-wins rule, `GetSporkValue`/`IsSporkActive`, `CheckAndRemove`, and
  `mapSporksActive`'s libstdc++ iteration order.
- `dashd-masternode::sporks` (layer N, new crate per A1 §2.6): `SporkManager` (the key, signer,
  lock and logging), `file` (`sporks.dat`), `handler` (`spork`, `getsporks`, `MSG_SPORK` for
  P2a-core's registry).
- `dashd-node::sporks`: init (`-sporkkey`, step 7a), shutdown store, and the chain's `SporkView`.

## D-rows

| D | Decision | Why |
|---|---|---|
| D1 | The pure core is `dash-evo::spork`; the runtime is the new N crate `dashd-masternode::sporks`. dash-evo now depends on `dash-p2p-core` (the `Spork` wire type) and `secp256k1` with `recovery`. | SB4 D29 puts spork verification where SPV can share it; A1 §2.6 names `dashd-masternode` for the MN-network services. dash-evo's clippy bans `BaseCodec::encode`, so `core_bytes` writes Core's serialization itself (20 bytes plus a compact-size signature). |
| D2 | `secp256k1`'s `recovery` feature is enabled on the pinned 0.33.1. | Compact signatures need public-key recovery; the feature adds the module only, and the `dash` crate already enables it in workspace builds. |
| D3 | `sporks.dat` is rdashd's own format (`"rdashd-sporks"` ‖ message start ‖ `"SporkStore-1"` ‖ by-hash list ‖ active list ‖ SHA256d) with Core's `CFlatDB` outcomes: a file that cannot be opened (missing or not), or a header or body cut short or badly formatted → start empty; shorter than its hash, a read error after opening, corrupt, wrong magic, another network → refuse with Core's `"Failed to load sporks cache from %s"`; `Store` re-reads first and leaves a file it would refuse untouched; another version string loads empty and succeeds (`SporkStore::Unserialize`); of two saved active entries with one ID the first stays (`UnserializeMap` inserts). | PLAN: `sporks.dat` is import-only (MNO-04, IM1b); rdashd refuses Core datadirs (DEC-201 Q6), so the formats never meet. A distinct magic keeps either node from reading the other's file. |
| D4 | Core's object-request bookkeeping (`ReceivedResponse`, `ForgetTxHash`) and `RelayInv` of a new spork go through the `SporkObjects` seam, a no-op (`NoSporkObjects`) until P5a. The registry's `spork` row stays a deviation, now closed by P5a; `getsporks` is exact. | P5a owns the object tracker and overlay relay (PLAN). | D5 | SP0 sends no `getsporks` of its own. | D6 | P2a-core's `clsig`/`isdlock` stubs (P2a-core D6) are exact only while ChainLocks and InstantSend are off. | D7 | `ActiveSporks` reproduces libstdc++'s `std::unordered_map<SporkId, …>` order: insert before the bucket's first node (or at the front), rehash at libstdc++'s prime growth (measured with g++ 15, table capped where unreachable), `(size_t)(int)id % n` buckets, `clear()` keeping buckets, reload reinserting in saved order. | `getsporks` replies in that order, and P2P indistinguishability needs the same message order. Tested against g++-computed orders and the dashd transcripts. |
| D8 | The adjusted time is the `dash_clock::AdjustedTime` seam. The node binds it to its clock with no peer offset (`dashd-node::sporks::NodeAdjustedTime`) until P2a-node runs the network core, whose `adjusted_time()` replaces it. | No peer offsets exist before the node runs P2P. |
| D9 | No oracle entry point checks sporks, and O1c's `TestingSetup` sporkman has no address (every spork is invalid there). Signature and hash parity are proven against real dashd v24.0.0-rc.3 instead: the transcripts (signatures byte-equal), `verifymessage.txt` (2576 Core verdicts) and the live vectors. **Follow-up for O2:** `oracle_spork_{hash,sighash,check}` and a session spork address. | The brief allows a D-row and follow-up where no oracle entry exists. |
| D10 | P2a-core's transcript replay moved from `dashd-p2p/tests/dashd_transcripts.rs` into `dashd_p2p::sim::transcript` (`sim` feature) with a `Hooks` trait (extra input records, later tasks' sends), so `dashd-masternode` replays its fixtures with the same engine. The engine now also removes a peer the node disconnected (`Sim::remove_disconnected`) and settles again before it compares the segment. | One engine, not two copies. dashd deletes a disconnected peer (freeing its sync slot) and runs `SendMessages` again long before the capture tool's next input, so what the removal frees belongs to the same segment; without it `sporks-receive`'s second peer would not get the `getheaders` dashd sends it. Removal runs only when a peer was disconnected in the segment. P2a's 11 fixtures still pass unchanged. |
| D11 | `-sporkkey` is decoded with `dash_pkc::ecdsa::EcdsaSkBytes::from_wif` and the network's `SECRET_KEY` version byte; an invalid scalar is a parse failure. Core's test signing after the key check is left out. Init fails with Core's `"Unable to sign spork message, wrong key?"`; the support table marks `-sporkkey` implemented. | `DecodeSecret`'s rules; RFC 6979 signing with a valid key cannot fail. |

| D23 | Train 14's PF0 attribution put node-startup-genesis peak RSS +372 KiB and faults +7 on SP0's step (dba58a79a). At `exit_group` (ASLR off, binary warm in the page cache, per-mapping smaps and pagemap) rdashd's whole `r-xp` mapping is resident except a few untouched 64 KiB fault-around windows (base 6, SP0 3), so the row's peak RSS tracks `.text` size plus where those windows fall. On 657a28c28 the same 157 KB lands with no window lost: VmHWM 19,452–19,464 base vs 19,460–19,464 head. dashd v24.0.0-rc.3 with the same arguments reaches VmHWM ≈ 117,500 KiB (12.5 MB of its 18.7 MB `.text` resident). | Measured on the real release `rdashd` (perfgate's `cargo build --release -p rdashd`); scripts in `/work/scratch/sp0/ab`.

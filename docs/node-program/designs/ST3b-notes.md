# ST3b implementation notes

Decisions taken while implementing ST3b, the device- and VM-level power-loss harness (plan at
`/work/scratch/st3b/PLAN-ST3b.md`, approved as DEC-698). The rows are numbered `ST3b-Dn`, not in
the program's shared D series, which parallel rows extend at the same time. Core cites are
v24.0.0-rc.4.

| ID | Decision | Reason |
|---|---|---|
| ST3b-D1 | **A product behaviour change, approved as DEC-698/Q1: rdashd's `-dbcache` and `-dbbatchsize` move from refused to implemented** (`dashd-node/src/init/support.rs`, `init/caches.rs`, `node.rs`); without them rdashd behaves as before (`sub_batch(DEFAULT_DB_BATCH_SIZE, …)`), and with them it differs from Core as (a)–(c) below say. The PR text names this change (r1 n-7). **`-dbbatchsize` is read as Core reads it, a `size_t`** (`txdb.cpp:117`): a negative value wraps to the maximum, 0 closes a sub-batch after every entry. The flush's sub-batch is `tuning::sub_batch(dbbatchsize, sizes)`, which also caps it by the coins share (CH2 §2.5), so a huge value still splits a flush at `coins/8`. `-dbcache` keeps CH2a's `CacheSizes` split; the S0 tests compare the help blocks, the cache log lines and stderr with dashd's for 12 cases, and `dbbatchsize_splits_the_node_s_coins_flush` drives the value through the node's RocksDB chainstate. **Where the behaviour is not Core's** (S0 r1 n-1, n-3, n-4): (a) the `coins/8` cap moves the split both ways: at `-dbcache=4` (coins share 1,605,632 B, so `coins/8` = 200,704 B) the default splits at about 196 KiB where Core never splits below 16 MiB, and `-dbbatchsize=-1` (Core's `SIZE_MAX`, never split) still splits at `coins/8`; so no ST3b check compares rdashd's partial-batch count with dashd's. (b) The split test counts B1's records (index, file infos, evo state), not only Core's marker and the coins (`txdb.cpp:138-139`): at `-dbbatchsize=1000`, a flush of ten headers' records (about 1.2 KB) and 500 B of coins is one batch in Core, and B1 then Bk here, with a marker-only state between them that recovery replays from; the partial-batch count is 0 on both sides. (c) A `-dbbatchsize` in settings.json that is neither a string nor a number (`[1]`) fails rdashd's init; Core reads it at its first flush and aborts there ("System error while flushing"). Command-line and config-file values match Core in every case. | Q1 (DEC-698): ST3b wires the two options the crash runs need. |
| ST3b-D2 | **The coins-setup log test compares whether rdashd refuses, not the exit status.** Stopping at genesis (`-stopatheight=-1`) exits 0 or 1 by timing, in dashd as well as rdashd (seen both ways in 2 of 3 local reruns, and on tier 1 at f5a05edbf). What the case needs is that rdashd does not refuse `-dbcache`/`-dbbatchsize`: its "is not supported by rdashd" line. | A flaky assertion of a race both binaries have. |
| ST3b-D3 | **The log-writes reader is ours** (`dash-testkit::crash::logwrites`), in the kernel's format (`drivers/md/dm-log-writes.c`), with no `replay-log` from xfstests. Replay points: before each flush entry (`prefix = i`), after each FUA write (`i + 1`), seeded random boundaries, and torn points (a flush prefix plus a seeded subset of the writes before the next flush, every FUA write kept). A torn point's acknowledgements count up to that next flush: an fsync is durable once its flush and FUA writes complete, and both are in the state. | The harness must run unattended in a nightly with no extra host packages; torn points are Q11's WAL non-prefix layout. |
| ST3b-D4 | **`st3b-priv` checks a table as plain words, by position per target.** The kernel unescapes `\`, splits on any whitespace and resolves relative paths against dmsetup's cwd (`dm_split_args`, `lookup_bdev`), so a check on whitespace-split tokens could be bypassed (`\/dev/sda`, `\v`, a second line, `dev/sda`). Only `^0 <len> (linear|flakey|log-writes)( [A-Za-z0-9/._-]+)+$` passes, and then each device argument must be one of ours. A sweep holds the run's lock and refuses a live run (exit 3); dm names match literally; marks only; mounts `nodev,nosuid,noexec`. | Opus review of S2 (critical C1, medium M1–M3). |
| ST3b-D5 | **Left open from that review: L5 and L9.** L5: a same-user swap of a path component between the wrapper's `realpath` check and its use; the harness is the only writer under its root. L9: `leak-tests.sh` checks the whole box for `st3b-*` devices, so it must run when no other ST3b run is up (its header says so). **`st3b-priv` is a guard against harness bugs, not a privilege boundary** (r1 m-1): it runs under the box's blanket NOPASSWD sudo, from a path its user can write (the worktree, or the nightly's checkout), so its checks bind only an honest caller, and L5 is harmless only for that reason. No scoped grant is planned. One naming only the wrapper would first need a root-owned copy (`/usr/local/sbin/st3b-priv`, root:root 0755), root-owned mount directories the wrapper creates, and `chown-mnt` checking the mount by device and inode with `chown -h`; without those, L5 becomes a root escalation (`chown-mnt` or `mount` through a swapped component). | Accepted at the S2 checkpoint; r1 m-1 (DEC-826) states the scope. |
| ST3b-D6 | **The fixture coins are P2SH(OP_TRUE), with no wallet.** The plan had a dashd wallet doing `sendmany`; profiled, signing and wallet bookkeeping cost about 0.4 s a transaction under the box's load, about 10 h for W-40k. The generator builds its transactions itself (version 2, a fixed `OP_TRUE` redeem-script push, 2–20 outputs, fewer when the pool passes 2,000 coins), and dashd still validates, relays and mines every one. F01's spend pushes another redeem script, which fails the scriptPubKey under any flags. | The crash checks test the coins database, not signatures; the run fits a background unit (about 0.15 s a block, `gettxoutsetinfo` dominating). |
| ST3b-D7 | **F01's reference verdict is what dashd answers, recorded per fixture** (`f01.json`): F submitted after its equal-work sibling is `inconclusive` (stored); C is `inconclusive` too, and connecting F fails as `ConnectBlock: CheckQueue failed` / `block-validation-failed`; C ends `invalid` in `getchaintips`, and the sibling stays the tip. The plan expected the text `mandatory-script-verify-flag-failed`; a script failure in the check queue reports the generic reason. The baseline holds rdashd's two replies and C's status to dashd's. | The reference is dashd's behaviour, not a string guessed in advance. |
| ST3b-D8 | **Fixture times are mocktime from a fixed start** (1,700,000,000 + 30 s × height), and every run gives both nodes `-mocktime` = the final block's time + 1 h (in `schedule.json`). A fixture made on one day then behaves the same on every later nightly. | Determinism over weeks of nightlies. |
| ST3b-D9 | **D-IBD-S splits its coins flushes at `-dbbatchsize=20000`, not Core's 200,000** (`feature_dbcrash.py`). W-small's UTXO set stays near 2,000 coins, so with `-dbcache=4` (sub-batch `min(200000, coins share/8 ≈ 196 KiB)`) no flush wrote a partial batch in the baseline; at 20,000 the same run writes 54 to 57 (flush timing varies), and C2 still holds at every acknowledgement. Every fixture run passes `-debug=coindb` and counts them: a campaign recording with none fails, and `st3b-crash baseline --min-partial N` asks the same of a plain run (S0 r1 m-2). **The coins memtable** (S0 r1 n-2): S also sizes the RocksDB `coins` write buffers (three of them), which RocksDB floors at 64 KiB (`column_family.cc:237`). At 20,000 the coins family runs three 64 KiB memtables, not 16 MiB or `coins/8`, so a D-IBD-S run flushes memtables to L0 every few sub-batches: many small SSTs, more compaction, possibly L0 at its stop trigger (36; DEC-164's retry). That is a regime the default never runs, and more interleavings for the power-loss checks, not a defect; a slow or stalled D-IBD-S run should be read with it in mind. | Split flushes are what D-IBD-S is for. |
| ST3b-D10 | **perfgate's `bench_inputs` rewrites `Cargo.lock`.** Running it from a worktree (`tools/bi-diff.py`) runs `cargo metadata` with the criterion shim, which appends `[[patch.unused]]` entries to the lockfile. The script saves and restores `Cargo.lock` around it. | Manager, 10-29: keep the trap in the notes. |
| ST3b-D11 | **A node started on a crash image gets `-connect=0`** (`RustNodeConfig::without_peers`, the harness's only way to pass it, since `-connect` is an option it reports). The image's `peers.dat` still holds the recording's peer, on a port that may by then belong to another process on the box. C1 (PLAN §3.4) must start from local data only; C5 starts the node again with `-connect=<its own peer>`. | A crash check that syncs from a stray peer, or from the next run's, proves nothing about recovery. |
| ST3b-D12 | **A point holds acknowledgement `a<k>` when `a<k>`'s mark index ≤ the point's window end** (`campaign::floor`). dm-log-writes logs a mark at once, ahead of plain writes that completed but are not yet flushed (they are logged before the next flush), so a mark alone proves nothing. The rule holds because every acknowledgement is a `gettxoutsetinfo`, whose synced flush puts its FLUSH entry, and the FUA writes before it, ahead of the mark: a state with every entry before index `m` holds mark `m`'s acknowledgement. `check` refuses a recording without a FLUSH between each `a<k>` and the mark before it (`start` for `a0`), or between the last `a<k>` and `stop`, whose `Stopped` floor rests on the clean stop's own sync (`campaign::acks_follow_flushes`, ST3b r1 n-2, r2 n-2). The window end is the point's prefix, or for a torn or split point the next flush (`logwrites::window_end`, ST3b-D3). The same rule makes the floor `Stopped` once the `stop` mark is held, and `Start` before `a0`. It is the selftest's rule (`acked = acks ≤ end`), shared, not restated. | One rule for the file workload and the node: the selftest's two controls already showed it neither too strict nor too loose on a log the kernel wrote. |
| ST3b-D13 | **C5 picks up where the recovered node is, not where the crash was:** `baseline::run` from the trajectory position C3 found. The P2P part ends once the node is at or past the peer's tip on the trajectory. The submits resume at the first stored block the node lacks (`getblockheader`); a stored block after that gap is a failure, since a flush writes every new index entry at once. F01: if the node kept the parent but lost C, the harness delivers C (and F, if lost too) before the rest, with dashd's verdict as the reference; at the end C's `getchaintips` status must be dashd's either way. | The continuation must not resubmit what survived (its replies would differ: `duplicate`), and must not skip what was lost. |
| ST3b-D14 | **D-IBD-S points inside rdashd's first chainstate creation fail C1, and stay FAILED until BL-509 merges** (DEC-718: no allowlist, no expected-fail). A power cut after RocksDB's `CURRENT` and `MANIFEST-*` but before its `OPTIONS-*` leaves a chainstate that `datadir::is_leveldb` takes for Core's LevelDB, so rdashd refuses the datadir on every start ("holds a Dash Core data directory"); nothing was ever flushed, so recovery should start empty. Seen at every pre-`a0` point from ext4 prefix 600 and xfs prefix 404 (seed 20261029; the window ends on ext4 between prefixes 683 and 733). BL-509 (ND1) writes an rdashd marker, fsynced with its directory, before a new store and trusts it before the heuristic. The failed points' images stay in `run/1793266802-2137011` (ext4, `pt27.img` is the reference repro) and `run/1793267066-2205696` (xfs) until a campaign passes them on BL-509. | The red nightly is the signal that the fix is still owed. |
| ST3b-D16 | **C6, the shard and a point range.** C6 (`campaign::double_crash`) takes a point's pristine image, records rdashd's recovery on it (C1, `-connect=0`) over a second log-writes stack to a clean stop, then replays every flush and FUA point of that recovery's log onto copies of the image. Each must pass C0–C4 with the first crash's floor and recover to the first recovery's tip (I4). It runs on every `mid` point, and on one in `--c6-every` of the points whose index holds block data above the tip. `--shard I/N` checks the points whose index is I mod N; a shard's `pre`/`one`/`post` phases are relative to its own previous checked point, `mid` is exact. The nightly's d-ibd-s runs shard (UTC day mod 24)/24 (DEC-718), so every index is checked once in 24 nights at about 140 points a night. `--points A-B` limits a campaign to one index range, for a rerun of one window: the same seed on a fresh recording draws its points from a new log, so an index names a point of the same kind near the same place, not the same state. | PLAN §3.4's C6; the full campaign is about 40 CPU-h, the nightly budget 2 (§9). |
| ST3b-D17 | **Known red at the `--shard` commit (DEC-735/736): points 40, 160 and 200 of shard 0/40, seed 20261029** (run 1793271984-4185261, ext4, stopped at the 200G floor after 21 points). 40 is BL-509 (ST3b-D14). 160 and 200 are BL-512: in their C6 the recovery's `settings.json` write was cut after its rename and before its extent conversion, so it reads as zeros and C1 refuses it; 240, 360, 400, 440, 480, 520, 560 and 680 failed the same way. No other cause: C6 passed every other second-crash point. On a binary with BL-512's fix, 4 C6 recoveries had no `settings.json` failure; one hit BL-518 instead (a preallocated MANIFEST tail, kept in run 1793276291-2542071). The nightly stays red until BL-509 and BL-512 merge; one fresh shard on the merged binary closes them. | The red runs are the signal, not noise (DEC-718). |
| ST3b-D18 | **W-small is one schedule for three scenarios:** D-IBD-S (1,500 blocks over P2P to height 1,000, then submitted), D-REORG-S (reorgs of depth 3 at 1,100 and 8 at 1,350) and D-F01 (the invalid-sibling pair after 1,210, ST3b-D7). A campaign's points fall in all three, so the nightly component `d-ibd-s` covers them together. | One recording per filesystem a night instead of three. |
| ST3b-D19 | **`campaign --split-chainstate` puts the chainstate on a filesystem of its own (BL-509 r1 M-1, DEC-726).** The recording's log-writes device is one disk of two `dm-linear` partitions: the first holds the datadir, the second is formatted and mounted on `rdashd/regtest/chainstate` before rdashd starts, so the store's directory is a filesystem root with `lost+found` in it. Every write of both goes through the one log, so each crash point is a state of one disk, consistent across both filesystems; replays and checks mount the two partitions the same way, and the recording syncs both filesystems' roots before `start` (each has its own journal: without the second, points before its first commit replayed a store root still owned by root, and C0 failed writing `RDASHD`). C6 is off in this layout. | The only way the harness can hand rdashd a store directory it did not create and that is not empty. |
| ST3b-D20 | **`dm-remove` retries for up to two minutes while the device is busy, and `leak-tests.sh` proves which namespaces pin it (ruling after DEC-718).** A mount namespace copied with private propagation while our filesystem is mounted (`unshare --mount`, as perfgate's `holder.py`) keeps the filesystem, and so our device, open after our own `umount`, until it exits: that is what failed the BL-509 window runs' teardowns ("dm-remove … busy"). The retry rides out a holder that exits within two minutes; a longer one is BL-510's to fix. The hold case (a 20 s `unshare --user --mount --propagation private` started with the recording stack mounted) passes with the retry, the run's device going as the holder exits, and fails without it with that same error. perfgate's bench sandboxes (`bwrap --ro-bind / /`) never pinned it: bwrap makes its copy a slave, and an umount propagates through the parent's tree (`/work` is shared), so our `umount` takes the sandbox's copy too. The pin case proves this with the sandbox still up, and `mount --make-unbindable`, approved for it, is left out: bwrap's `--make-rslave` clears the flag before it binds `/` (the sandbox's copy was there either way), and the pin case passes with and without it. | Teardowns failed while the PF0 lane ran, and that lane is busy most of the day, so gating campaigns on it is no option; a wrapper change for the wrong namespace would only have hidden that. |
| ST3b-D21 | **The harness waits up to 10 min for an RPC reply (`checks::RPC_PATIENCE`), where jsonrpc waits 15 s.** Regtest runs `CheckBlockIndex` after each header and block, as Core does (`ProcessNewBlockHeaders`, `validation.cpp:4737`), and rdashd refuses `-checkblockindex` (CH1-node), so a call queued behind a 2,000-header batch waits for every check in it: O(n) each, about 1.9 µs an entry on the release build. W-40k's baseline stopped at header 8,000 on both builds ("Couldn't connect to host: Resource temporarily unavailable", the transport's read timeout), with rdashd busy in `HeaderChain::check_index_with` (`perf`); with the patience it syncs through. One C6 sub-point on W-small under load also timed out on the debug build, and passed C0–C4 when rechecked. | A slow reply under regtest's checks is not a crash finding; a stuck node still fails at the patience. |
| ST3b-D22 | **A plant build (`--features planted-bugs` on rdashd, passed through dashd-node to dashd-chainstate) arms the bug `RDASHD_ST3B_PLANT` names, read once as the chainstate opens, in its guard and coins cache; an unknown name refuses the start. `campaign --plant BUG` arms it in the recorded run only and refuses a recording whose log lacks `ST3b: planted bug BUG armed`; every check node runs with the variable removed.** The plant is a dev-profile build, like every campaign binary: dashd-chainstate's `compile_error!` keeps the feature out of optimized builds, and `test_feature_scope` checks that the product rdashd carries none of it. **T1 (B1 before the files barrier) is caught on both filesystems at prefix points (S5, 10-29, w-small, seed 20261029, shard 0/20, `-dbcache=4 -dbbatchsize=20000`):** ext4 run `1793302771-1325599` point 220 (`fua at prefix 1088`, mid; 47 C0 I1 failures: short blocks and undo checksum mismatches the index names), xfs run `1793302771-1325804` point 200 (`fua at prefix 587`, mid; 23 C0 I1 undo checksum mismatches). Both repros replay: the kept log replayed to the prefix (`lw-replay.py`) is byte for byte the kept `pt<i>.img`, and C0–C4 on it with the clean binary fail with the same failures (`tmp/replay-<run>-<point>.txt`). The clean build, on the same configuration, was checked to point 780 on ext4 (DEC-816): run `1793312214-1379025` (recording of 1,366 points, 69 in the shard), 40 of 40 points ok through point 780, marker points with C6 included, when the disk floor stopped it. That is well past T1's failing points 200 and 220. Earlier shard runs gave another 13 clean points on ext4 and 14 on xfs, all ok. **Under r1's stricter I1** (ST3b-D24; DEC-826): both T1 repros are still caught, with the same failures (47 on ext4, 23 on xfs; `tmp/replay-<run>-<point>-r1.txt`). Run `1793312214-1379025` was deleted under DEC-816, so the clean control's C0 rerun is a new recording on the same configuration: run `1793326535-3718677` (1,715 points), `--c0-only` over shard 0/20 to point 780, 40 of 40 ok, and its whole log replayed equals the recorded device. The binaries were node/st3b d3ac6b522 with BL-509, BL-512 and BL-518 applied (not yet in node/integration), rdashd and `st3b-crash` built from one tree: a node/st3b-only rdashd fails C1 with BL-509's Core-dir refusal, and a node/st3b-only `st3b-crash` refuses BL-509's `RDASHD` marker in C0. | Arming only the recording keeps the test honest: the broken order is written, and an unchanged recovery has to cope with what it left. A binary built without the feature ignores the variable, and without the log-line check its campaign would pass as though the bug had been missed. |
| ST3b-D23 | **T18 (no pre-Bk barrier, Bk Buffered) is not observable through a torn state on ext4 (`data=ordered`) or xfs, and is not rerun (DEC-790); T1 (D22) is S5's caught broken-ordering plant.** Every torn point drawn by the four torn campaigns (T18 and clean, ext4 and xfs; runs `1793307891-2066846/-2066853/-2066860/-2066870`, seed 20261029, 128 torn points each, 509 in all) was redrawn from its kept log by a port of `logwrites::points` (it matches every point the campaigns logged). Each torn state was then mounted beside its window's start and end, and the chainstate's WAL files compared byte for byte. 72 torn states fall in windows that change a WAL file, and in none does the torn state keep new WAL bytes past lost ones (`tools/t18/holes.py`, `tmp/t18-holes-*.jsonl`). In 18 of them the window's WAL-side writes are two bios, and the torn state kept one of the two in 7; the WAL each of those 7 shows is the window's whole WAL (`holes-detail.py`). Recovery therefore never met a hole: no point-in-time recovery ran past one, and no Bk survived without an earlier batch. RocksDB alone would not have masked it: under `PointInTime`, RocksDB 11.8.1 skips a zeroed record header to the next 32 KiB block and replays on (memory `rocksdb-wal-nonprefix-recovery`). The masking is the filesystems' (an inference the counts fit): appended WAL bytes become visible only through the size or extent update that the fsync commits after a cache flush, and a flush ends a torn window, so a torn state shows a prefix of the WAL. A torn point keeps or loses whole log entries (bios); it never splits one, so that evidence is at bio granularity. **Split points (r1 m-5, ST3b-D24) add tearing inside one write**: T18 again on ext4 and xfs at the same torn-only budget, 128 split points each (`--rand 0 --torn 0 --split 128 --torn-only`, seed 20261029; runs `1793326535-3718644` ext4, 1,688 points, and `1793326535-3718653` xfs, 1,157 points). The log's sector is 512 B, so a split keeps any 512 B subset of a 4 KiB or larger write. The same WAL comparison over all 256 split states (`tools/t18/holes-split.py`, `holes-split-detail.py`; `tmp/r1-hd-<run>.jsonl`, the Python draw checked against every point the campaigns logged): 23 (ext4) and 26 (xfs) fall in windows that change a WAL file; none has a hole, and every one shows the window's whole WAL. **17 of the 256 split points tore a WAL write** (r2 m-2): their split entry overlaps a WAL file's extents in the window-end state (4 on ext4, 13 on xfs; in 7 of them some torn sectors lie inside the file's size there; FIEMAP via `filefrag`, `tools/t18/split-files.py`, `tmp/r2-files-<run>.jsonl`). 11 of the 17 lie in windows that change a WAL file's visible bytes, and each of those shows the same WAL with or without the torn part; the other 6 lie in windows whose WAL change is not visible at the window's end. So no split state changed a WAL file's visible bytes, 17 of them by tearing a WAL write. Why is an inference the counts fit, not a measurement: the window that writes a WAL append's data does not commit the file's size, and the window that commits it (a FUA journal write) already has the data flushed. The campaigns' own checks of the split points (C0–C5, C6 at marker points; 512 B splits, before the 4 KiB unit of ST3b-D24) did not finish: an outside stop ended both units at 06:44Z on 10-30, about 4.5 h in, while /work was down to 176G (other threads' units stopped at the same moment). By then 58 of 128 were checked on ext4 (20 with C6) and 83 of 128 on xfs (24 with C6), all ok: no failure, and no C1 mount failure. The other 115 split points were not checked by the campaigns; the WAL comparison above covers all 256. T18 stays invisible with split points: no finding. Not covered: tearing inside one 512 B sector (a sector is written whole or not at all, the device model's atomicity), `data=writeback` or another filesystem, WAL recycling (RocksDB's default 0, which the store keeps), and WAL rotation across files at prefix points (r1 n-1): with 64 KiB coins memtables (D9) and `atomic_flush` RocksDB switches WAL files often, and on xfs a log force from another file's fsync could make a newer WAL's records durable while an older WAL's unsynced tail is lost. That state would show at a prefix point, and DEC-790 limited the T18 rerun to its torn windows. | The device harness cannot catch what the filesystem hides. T18 stays caught where the order is the model's (ST3a's CRASH suite). |
| ST3b-D24 | **The r1 fix round (DEC-826) tightens what a passing point means.** (1) **I1 checks the stored block, not its header** (M-1): with a fixture each HAVE_DATA record must begin with the fixture's block, and a block the fixture lacks fails; without one (`st3b-crash inspect`) the block must decode to its header's merkle root. A kept header over a lost body fails either way (`a_kept_header_over_a_zeroed_body_fails_i1`). (2) **A run's whole log replayed must equal the recorded device** (m-4): campaign, C6 and selftest compare the replay of every entry with `data.img` before removing it; a difference fails the run and keeps `data.img`. (3) **Split points** (m-5): a `split` point is a torn point that also keeps part of one more non-FUA write of its window, its first k units or a seeded subset of them (never none or all). **The unit is 4 KiB, aligned on the device** (`logwrites::SPLIT_UNIT`, r2): what a 4Kn or 512e device writes atomically. r1 split at the log's 512 B sector, and the r2 leak test's ext4 pin selftest then failed one split point (run `1793333688-1269831`, point 184 of 185): it kept sector 2 of a superblock write (log entry 575) over sector 3 of an older one (entry 144), and ext4 refused the image ("invalid superblock checksum"), a state such a device cannot leave and no fault of what it checks. The r1 split campaigns of D23 ran at 512 B, a superset of these states; split points are drawn after the rand and torn points and listed after them (indices `N + j`; the check walks every point in prefix order, `logwrites::replay_order`), so a seed's other points keep their states and their indices, and with them `pt<i>` names, shards, `--points` windows, the C5/C6 cadence and the per-point seed (r2 n-1; `--split N`, default 16; `--torn-only` checks them too). In r1's head (12a56478e–c4b98600f) split points sorted in among the rest and moved later indices: a point number from a run of that head is reproduced with that head. (4) **`--c0-only`** checks C0 alone at each point, for a pass of I1 over a recording. (5) A stale run that does not sweep is reported and new runs still start (m-2); an orphan, a run with devices or mounts but no run directory, is one of those: the wrapper's sweep refuses it with exit 4 and `sweep --stale` fails on it, and the nightly prune keeps a run directory that still has devices (r2 m-1, n-3); the nightly's leak check covers only the runs its components printed (m-3); the peer dashd dies with the harness (n-6). | The checks judged the header, trusted the reader's replay unverified, and tore only whole bios; each gap is now closed or measured. |

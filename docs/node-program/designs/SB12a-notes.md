# SB12a: implementation D-rows

**Status: READY for train 16** (PF0 dropped SB12a from train 14: fix round D22–D25; follow-merge of train 15 D26). ACCEPTED 10-16 (Opus r3 ACCEPT-WITH-NITS, Sol r2 APPROVED); only the fix delta is re-reviewed. D11 re-measure after merge.

SB12a has no design document: PLAN's row, SB0 §5.5 and DEC-112 O2 are its spec. This file records
the implementer's decisions, each with its disposition. Base: node/integration `0d0939b8a`.

| D | Decision | Disposition |
|---|---|---|
| D1 | **Two ways across.** Headers map field by field (`bridge::headers`): they are the hot path, and the mapping hashes nothing. Everything else crosses as Core's serialization: one side writes it and the other decodes all of it (no bytes left over), so a value either converts exactly or fails with a `BridgeError` naming the kind and the decoder's error. base-sdk refuses some bytes dashcore accepts (non-canonical BLS points, BS4b's decode domain), so the crossing into base-sdk is fallible by design. | Proposed. |
| D2 | **Targets.** The message kinds cross to `dash_p2p_core`'s message types (`Headers`, `Headers2`, `CFilter`, `CFHeaders`, `MnListDiff`, `QrInfo`, `ClSig`, `IsdLock`), not to `dash-p2p`'s `policy::decode` result: the bridge converts values, and a peer policy is SB16's. Headers and blocks cross to `dash_consensus::{Header, Block}` too. | Proposed. |
| D3 | **`mnlistdiff` and `qrinfo` format.** base-sdk decodes both with `MnListFormat::CURRENT` (protocol ≥ 70230: the ClSigs table and versioned entries), which is what dash-spv negotiates. Older formats do not cross. | Proposed. |
| D4 | **`headers2` without a second hash (to base-sdk).** `Headers2::decode` hashes every header with `dash_pow` to restore the next one's `prev_hash`. `messages::headers2_to_base` instead takes the hashes dash-spv's decompressor already computed (`CompressionState::process_headers_with_hashes`) and decodes through `Headers2::decode_with_hasher`, which looks each one up, then checks that the headers it restores equal dash-spv's (`Headers2Mismatch`). What that catches: a hash list that disagrees with the message where base-sdk asks for a hash. What it cannot catch without hashing: the last header's hash, a hash followed by a header carrying its own prev hash, and a hash dash-spv's decompressor got wrong and used consistently; those are trusted. The result is base-sdk's wire value, which carries no hash, so nothing trusted here reaches `dash-consensus` (DEC-224); into `dash-consensus`, `headers2` crosses by D17's `headers2_to_consensus`. Tests (`messages::tests`): with a stand-in hash for header 0 and header 1 naming it, the crossing succeeds and restores the stand-in (a re-hashing crossing would fail), and a stand-in alone fails with `Headers2Mismatch`. | Proposed; f1: unchanged, scope stated. |
| D5 | **Blocks.** `block_to_consensus` takes a dashcore block, builds the header with `Header::new` (its one X11) and decodes each transaction with `decode_tx_exact` from dashcore's bytes, then `Block::new`. `hashed_block_to_consensus` does the same for a `HashedBlock` and refuses it unless its hash is the header's (D17). No new `dash-consensus` block API is needed. `block_from_consensus` keeps the `dash-consensus` hash (`HashedBlock::with_trusted_hash`, crate-private). | Proposed; f1: revised for D17. |
| D6 | **The counting wrapper.** An internal, test-only `__x11-count` feature in `dashcore_hashes` (counts `hash_x11`'s backend call) and in `dash-consensus` (counts `hash::x11`), turned on by dash-spv's `__x11-count` feature. The counters compile only under `all(feature = "__x11-count", debug_assertions)` (Sol r1 F2): `cargo build --release --all-features` emits no counter symbol, and the hash-once tests run in debug builds only. `debug_assertions` is the release gate, not the profile name: a release profile that sets `debug-assertions = true` with the feature on compiles both counters into the X11 path (one thread-local increment per X11). The workspace sets no such profile, and the `__` prefix marks the feature internal (Opus r3 nit 4). dash-spv's `[package.metadata.gate] test-features` makes the gate's feature-tests step run `src/bridge/hash_once_tests.rs`. Limitation: X11 computed inside base-sdk (`dash_pow`, for example by `Headers2::decode`) is not counted, and the counters are per thread. `headers2_to_consensus` passes `decode_with_hasher` a hasher that is `Header::new`, so its hashing is counted; `headers2_to_base` is proven not to hash by D4's stand-in test. The round-trip test's `Headers2::decode` call is outside any counted span. | Proposed; f1: F2 applied. |
| D7 | **A thread-local counter in a pure crate.** `dash-consensus` is layer P (no globals). The counter is a `thread_local!` that exists only under `cfg(any(test, all(feature = "__x11-count", debug_assertions)))`, so no release build has it, whatever its features. It is in the linted library wherever all features are on: `check-pure.sh` and the workspace clippy. `pure-clippy.toml` does not ban it, and the layer checks pass, but a review of the pure crates' globals should know it is there. | Proposed; for the globals review. |
| D8 | **Platform's queries.** `bridge::platform` fills dashcore's `MasternodeList`, `QualifiedMasternodeListEntry` and `QualifiedQuorumEntry` from base-sdk's `SimplifiedMnListEntry` and `Commitment`, and maps back. `queries.rs` and `sml_engine` are not rewired (SB12/SB14's): a round trip through base-sdk on every query would re-hash every entry and lose the engine's `Arc` sharing for no change in value. The tests prove equality instead: a whole-list diff (mainnet 2,227,096 and testnet 1,296,600) filled through the bridge equals `MasternodeList::from_diff`, and every list and quorum the engine holds after the mainnet `qrinfo` at 2,518,986 crosses to base-sdk and back unchanged, including what `quorum_entry_for_hash_at_or_before_height` (behind `get_quorum_at_height`) returns. Limits of that proof: the lookup finds each quorum in the list it came from, `verified` and the ChainLock signature are the caller's (not on the wire), and the storage fallback in `client/queries.rs` is not exercised; what the test does compare is every commitment's and entry's bytes and hashes. Two things SB12/SB14 must keep when they route values through the bridge: dashcore's `masternode_merkle_root` is `from_diff`'s first merkle hash, so pass that value, not a recomputed root; and `masternode_list` makes one `Arc` per entry per list, so filling list after list loses the engine's sharing (fill once and share, or diff). SB15 switches the source when the engine moves to `dash-evo`. | Ruled (manager, 10-16): accepted; `queries.rs` stays, the equality tests are the proof. |

| D17 | **Hash provenance (Sol r1 F1, DEC-224 as amended), design (a): invert.** `Header::from_parts_hashed` is removed, so `Header::new`, which hashes, is `dash-consensus`'s only constructor: a hash in `dash-consensus` is always the X11 of the header's own bytes, and no type or caller can set it. The bridge hashes a received header there, once, and dash-spv takes its header and hash back from the result (`header_from_consensus`, `block_from_consensus`): `header_to_consensus` / `headers_to_consensus` (a dashcore header), `block_to_consensus` (a dashcore block), and `messages::headers2_to_consensus`, which decompresses with base-sdk's `decode_with_hasher` and hands it `Header::new` as the hasher, keeping each header it hashes, so a header the decompression needs a hash for is not hashed again. A pair that comes with a hash (`HashedBlockHeader`, `HashedBlock`: storage's public decoders, dash-spv's own hashing) crosses only through `hashed_header_to_consensus` / `hashed_block_to_consensus`, which hash again and refuse a mismatch (`BridgeError::WrongHash`), in every build. `decompressed_to_consensus` is removed. Why (a) over (b): a provenance type in dash-spv cannot be checked by `dash-consensus` (layer P cannot name dash-spv's types), so (b) needed a new minted type in a crate below both (`dash-x11`) threaded through dashcore's decompressor and `HashedBlockHeader`'s storage format; (a) needs neither, and `Header` itself is the provenance type. Hash-once (counter tests, debug): a 2,000-header reply (0 dashcore, 2,000 `dash-consensus`), two 8,000-header `headers2` replies (0, 8,000), a block (0, 1); a stored pair costs one more (0, n). Today's sync managers still hash with dashcore for their own use and do not cross into `dash-consensus`; when SB12/SB14 route headers there, they take dash-spv's pair from the bridge's result (or pay D17's re-hash for stored pairs) — CANDIDATE-SB12a. Negative tests, run with `--release`: `bridge::headers::tests` forge a header and a block paired with a hash that meets the target, through `HashedBlockHeader::consensus_decode` and `HashedBlock::consensus_decode`, and both are refused; the forged header's own hash misses its target while the paired one meets it. **Ask:** PLAN's SB12a row and SB0 (§2.2 `dash-consensus`, §5.5, the SB12a row) still name `Header::from_parts_hashed` and the acceptance "a mismatched hash fails the debug assertion"; f1 needs that delta: "`Header::new` is `dash-consensus`'s only constructor (DEC-224); a header that comes with a hash is hashed again and a mismatch refused (`WrongHash`) in every build". The manager owns those files. | Proposed (f1); **ask:** PLAN/SB0 delta. |

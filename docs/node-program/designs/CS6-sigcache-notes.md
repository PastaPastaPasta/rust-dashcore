# CS6: implementation D-rows

CS6 (PLAN: `dashd-chainstate::{sigcache, checkqueue}`, FR-CHS-10, F20) has no design document; these
rows record the implementer's decisions. Core references are `v24.0.0-rc.3`: `v` is
`src/validation.cpp`, `sc` is `src/script/sigcache.cpp`, `cq` is `src/checkqueue.h`, `cc` is
`src/cuckoocache.h`.

| D | Decision | Why |
|---|---|---|
| D1 | CS1 phase B's script sources (`dash-consensus/src/script/*`, as `d4fe4ba9a`) are carried as one prerequisite commit (`b0d547b9a`), with one fix in `tx.rs` (`i64::from(LOCKTIME_THRESHOLD)`, Core's `int64_t` promotion) that the carried sources need. Its node-fuzz and node-l1 parts are not carried. | CS6 needs `InputCheck`, `check_input_scripts`, `TxSigData` and `SigVerifier`, which only phase B has. Drop the commit when CS1b merges. |
| D2 | The check queue is a Core-shaped stack (`Shared`: one lock, LIFO, batches of `max(1, min(128, n / (total + idle + 1)))` where `total` is the workers plus the master once it waits (Core's `nTotal`), an early-abort flag) run on a rayon pool through `in_place_scope`. The pool has `-par`'s additional threads; the caller drains at the end as Core's master does in `Wait`. | The same thread count and scheduling as `CCheckQueue` (`cq:69-121`), batches taken in order off the top as `vChecks.assign` takes them, and the scope lets checks borrow the block's data instead of copying each spent `CTxOut` (`v:2106`). The caller keeps the spent scripts alive for the scope. |
| D3 | A control without threads (`-par=1`) runs each check as it is added and skips the rest after a failure. | Core never adds to a serial control: `CheckInputScripts` runs the inputs itself (`v:2182-2226`). Our serial `check_input_scripts` does too, so the inline path only serves callers that queue explicitly; its verdict is the same AND. |
| D4 | Both caches keep Core's full 32-byte salted SHA-256 entries, in 8-way buckets over at most 64 mutex shards, with CuckooCache's soft erase: a lookup with `erase` marks the way reusable but the entry stays visible until it is overwritten (`cc:264-276`, `allow_erase`; `contains` `cc:476`), and inserting a present entry clears the mark (`please_keep`). Capacity at the default budget is ~0.99× Core's elements (259-byte buckets of 8). Eviction differs from cuckoo hashing (free way, then erasable, then round robin). | A cache only ever forgets, so eviction order changes hit rates, never verdicts (model test `verdicts_never_depend_on_the_cache`, the vectors in every cache state, the oracle diff). r1 truncated entries to 128 bits for ~1.8× capacity; the review pointed out that a known salt would then admit a 2⁶⁴ offline collision search where Core's entries need 2¹²⁸, so the entries are now Core's and `with_nonce` (tests, benches) carries no extra risk. |
| D5 | `-maxsigcachesize` follows `ApplyArgsManOptions`: `clamp(n, 0, i64::MAX >> 20) << 20`, half to each cache. A size whose element count exceeds `u32::MAX` is refused (`CacheError::TooLarge`), as `setup_bytes` refuses it; a failed allocation is `CacheError::Alloc`, where Core throws `bad_alloc`. | Core's limits, as errors the caller reports. |
| D6 | The cache's init log line keeps Core's wording ("Using {} MiB out of {} MiB requested for signature cache, able to store {} elements") with our table's size and capacity. | The numbers describe this cache, not Core's. |
| D7 | `script_check_threads(par, num_cores)` reads `-par` into an `int` (Core's `GetIntArg` cast, so 2³² + 2 is 2), adds the core count when ≤ 0, and returns `min(max(n − 1, 0), 15)`. The caller passes the core count. | `init.cpp:1554-1565`; Core asks `GetNumCores()` itself, the node passes it in. |
| D8 | The differential test against Core is `node-l1/tests/l1_sigcache.rs` (oracle feature). | The gate's oracle-diff step runs only dash-oracle-sys and node-l1 with `--features oracle`. |
| D9 | `sighash.json` is not rerun with the caches. | `signature_hash` reads no cache; CS1's L0 covers it. The caches sit in `script_tests.json` and the transaction vectors, which run in every state. |
| D10 | Per-worker scratch reuse (a stack and buffers per worker) waits for CS1 phase C's interpreter scratch. | Phase B allocates per evaluation; CS6 adds nothing per check beyond the queue's batch vector. |
| D11 | L3 is a recorded fixture: `contrib/node/cs6-checkqueue-vectors.py` drives two release dashd nodes (`-par=1`, `-par=2`), builds and solves ten blocks itself, and records `TestBlockValidity` (`generateblock … false`), `submitblock` and the state `ConnectTip` logs. `tests/l3_checkqueue.rs` replays them through `ConnectBlock`'s transaction loop as far as inputs and scripts go: CS5b's `check_tx_inputs`, CS6's `check_input_scripts` with the queue, `UpdateCoins`, then the queue's verdict. | No oracle entry point runs `ConnectBlock`; the full loop belongs to the block connector. The cases have no special transactions, BIP68 locks or sigop excess, so the replayed part decides every recorded result. Two runs wrote identical bytes. |
| D12 | The PF0 queue rows (`script-queue-*`) report their instructions, allocations, syscalls and faults instead of gating them; I/O and peak RSS stay gated. The serial and cache rows gate everything. | PF0 pins each bench process to one CPU, where the number of helpers that start (`Shared::add`) and which thread takes which batch follow the scheduler. |
| D13 | The bench salts its caches with fixed nonces. | A random salt moves entries between bucket ways, and the probe length with them. |
| D14 | Script-execution entries are never inserted from a parallel control, and never for a coinbase. | Core inserts only after a serial pass (`v:2227-2230`: `cacheFullScriptStore && !pvChecks`), and returns before the lookup for a coinbase (`v:2159`). |
| D15 | Performance (perf stat `instructions:u`, Δ between run lengths, one P2PKH input): cold 461.0 K, warm (signature-cache hit) 38.6 K, with D4's 256-bit entries (r1's 128-bit entries: 461.3 K and 38.5 K). dashd v24 (PF1 §4): 438 K per one-input transaction, of which the ECDSA verify is 379 K (`bench_dash`). Our verify (`verify_lax`, secp256k1-sys 0.14) is 421.6 K per call. Our overhead beyond the verify is 39.4 K against Core's 59 K (1.50× fewer); the cold total is 5% above dashd's because of the library's verify. The queue adds 0.1–0.15% instructions at 3 and 7 threads (680 inputs). Wall-clock scaling on agentbox (load 45–60, shared CPUs) measured 0.46–0.62 × cores × serial, with run-to-run swings of 75%: not a measurement of the BG. | The BG ("never slower than dashd"; "≥ 0.7 × cores × serial") is not met or not shown here: see follow-ups F1 and F2. |
| D16 | `OP_CHECKDATASIG` signatures carry a hash-type byte in the bench, because Core checks their encoding with `CheckSignatureEncoding` (`interpreter.cpp:1059`), which reads the last byte as one, and the lax DER parse ignores it. | Found while building the bench: CS1's interpreter already rejects a bare DER data signature with `SIG_DER`, as Core does. No code change. |
| D17 | The gate launcher (`/work/scratch/cs6/gate-launch.sh`) admits on DEC-219's conditions (fewer than 7 rdc gates, CPU PSI some avg300 < 25 %, 1-min load < 64, /work ≥ 150 GB) and also waits for the manager's dispatcher (`mgr-gate-dispatch`) to finish, resolving the branch only at admission. | The brief's ≤5 rule predates DEC-217/219; the dispatcher's queue has an order the manager chose, which a new waiter should not jump. |
| D18 | `CheckQueue::control` takes a per-queue mutex for the pool path (Core's `m_control_mutex`, `cq:130`, held by `CCheckQueueControl`, `cq:221-246`); a serial control takes none, as Core passes no queue then. | Two concurrent controls would otherwise share the pool's threads, each starting helpers for its own stack: a latency difference, not a verdict one. |
| D19 | The core count stays the caller's (`script_check_threads(par, num_cores)`); it must be Core's `GetNumCores()`, `std::thread::hardware_concurrency()`, which libstdc++ answers with `get_nprocs()` (online CPUs). | D24 | **A transaction and its signature-hash data are one value** (manager decision, after Sol r1's Major). `check_input_scripts(slot: &TxSlot, …)` replaces `(tx, txdata: &OnceLock<TxSigData>)`. `TxSlot` holds the `&Tx` and a private `OnceLock<TxSigData>` that only `TxSlot` fills, from its own transaction, at Core's `txdata.Init` (`v:2179`). So the scripts that run, the sighashes, and the script-execution entry read and stored all come from one transaction, as Core's `CScriptCheck` builds its checker from its own `ptxTo` (`v:2107-2109`). The per-block arena the block connector will hold is a `Vec<TxSlot>` built from the block's transactions (Core's `txsdata`, `v:2648`); the mempool builds one slot. `ScriptExecCache::cache` is `pub(crate)`, so outside the crate no caller can read or store a script-execution verdict except through `check_input_scripts`. Evidence: paired doctests: a compile-fail one (filling a slot from another transaction does not compile; with the fields made public it compiles, so it guards exactly the privacy boundary) and a passing twin with the same imports (stable rustdoc does not check the `E0451` code, so the twin shows the compile-fail one fails for privacy and not for a broken import); and `a_transaction_is_checked_and_stored_as_itself` (B spends A's output with a wrong signature, checked after A passed and was stored: B is rejected serially with Core's reason, the parallel verdict is false, and B is never stored), run in debug and in release. | r1's `debug_assert!` (D20) disappears in release, so a mis-bound slot would check A and store B's (txid, flags) as passed. The slot lives in CS6's crate because the cache key needs `Tx::txid()`, which CS1's `TxSigData` (a `&Transaction`) cannot give without rehashing; CS1 phase C keeps its precomputed midstates inside `TxSigData` behind the same slot. |
| D25 | No full re-gate for f1. The train-13 gate covers the merged tree, and Sol r2 reviews the delta. The f1 evidence is the CS6 test set (dashd-chainstate in debug, the queue and cache tests in release and with the crash and planted-bugs features, the node-l1 oracle diff, loom), clippy `-D warnings`, the locked node-fuzz build, and the D15 instruction counts rerun (per P2PKH input: cold 461.0 K, warm 38.6 K, verify 421.6 K instructions:u, the same as r1, so the slot costs nothing on the hot path). | Manager decision for f1. |

## Follow-ups

- **F1 (secp256k1 backend).** CS1's `verify_lax` costs 421.6 K instructions against Core's 379 K. Core builds libsecp256k1 with its x86-64 assembly field arithmetic, and secp256k1-sys does not. That makes our cold block connection 5% slower than dashd's in instructions, and it is the largest part of every script check. Owner: CS1 (verifier backend), or a workspace build-flag change for secp256k1-sys.
- **F2 (BG wall-clock).** The `≥ 0.7 × cores × serial` throughput needs a reserved-window run (PF0 README: wall-clock comparisons are for milestone windows), e.g. `serial/680_cold` against the queue at `-par=8` on idle CPUs. The instruction overhead (D15) puts no ceiling below it.
- **F3.** Callers: the node's init passes Core's core count to `script_check_threads` (D19); the mempool (MP1) passes `cache_sig_store = true` with the standard flags, then both stores with the tip's block flags (`v:1186`, `:1217`); the block connector passes `fJustCheck` for both. `ScriptOptions` carries them; neither caller exists yet.
- **F4.** Drop `b0d547b9a` when CS1b merges (D1).
- **F5.** `dashd-store-bakeoff/Cargo.lock` fails `cargo metadata --locked` on node/integration too (it predates CS6). The gate does not build that workspace, so nothing catches it.

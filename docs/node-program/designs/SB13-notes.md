# SB13: implementation D-rows

SB13 (PLAN: dash-spv's SQLite store and migrator v3, M4, SB0 §9.5 and §7, DEC-112 O4/O5) has no
design document beyond SB0 §9.5, its errata (§17) and SB5 §3.7/§7. These rows record the
implementer's decisions.

| D | Decision | Why |
|---|---|---|
| D1 | The store is written on dash-kv's `KvEngine` column families, generic over the engine, not on raw SQL. `dash-kv-sqlite` stores each family as a `WITHOUT ROWID (k, v)` table. SB5's recursive CTE (the `active` walk) and expression index (`children`) become point reads and an `hdr_prev` family keyed `prev ‖ id`; range scans go through `scan.rs`'s prefix cover, since `KvRead` scans by prefix only. | One code path runs on SQLite in production, on `MemoryEngine` in the contract tests, and on ST3a's `FaultyEngine` in the crash sweep (the `Sut`), with no SQL dialect to keep in step. |
| D2 | `hdr` is keyed by id and `hdr_hash` maps hash → id. | SB5 §7 names the hash the primary key and the id `UNIQUE`: both are unique indexes either way, and the id-keyed table serves the height-ordered reads (`hdr_h`, `active`) with one point read per record. |
| D3 | The store lives at `<storage_path>/spv/kv.sqlite` (with dash-kv-sqlite's `LOCK`); the `<storage_path>.lock` file of `DiskStorageManager` stays. | One directory per database (dash-kv-sqlite's layout); the migrator builds `spv.migrating/` and renames it. |
| D4 | Until SB14 puts the header sync on dash-chain's step, the legacy height-indexed writes produce full records: the next id, `VALID_TREE`, the active parent's chain work plus `GetBlockProof(nBits)` (chain.cpp:132-145, via `dash_consensus::pow::block_proof`), the running `time_max`, the skip id at `GetSkipHeight(h)` (chain.cpp:86-95) when that height is stored, kind 0, and the leaf/branch rows. `active` is set by height with no `prev` walk (the unit tests' headers do not link). A stored hash at the same height reuses its record; at another height it is refused; a gap is refused. The first store sets `meta` with that header as the anchor, Established. A truncation removes `active` rows only; the records stay (every branch, SB0 §4.4). | The same tables SB14 will write through `HeaderStepSink`, so SB14 changes the writer, not the schema; and the migrated store is Established at its v2 anchor (§9.5). |
| D5 | The subscribers (`cfhdr`, `cfilter`, `blocks`) are height-keyed. Each `WriteSet` carries the subscriber's locator: the hash and height of the active header at the subscriber's top (removed when there is none). Recovery at open runs the engine barrier, then per subscriber: an unknown locator hash resets it (rows and locator, one Durable `WriteSet`); a known hash off the active chain rewinds it to where its branch leaves the active chain; a failed walk resets it. An absent locator is not checked. | SB0 §9.5's blind recovery, with the rewind SB0's "rewinds that subscriber" implies for a stale branch (the hash is known, so the fork is found without guessing from heights). |
| D6 | The legacy `MetadataStorage` values live in `meta` under `md:<key>`. The old masternode path's message log lives in an `mn_log` family keyed `height ‖ kind` until SB15 persists verified lists; `mn_lists`, `mn_quorums`, `mn_snapshots`, `peers` and `bans` are in the schema and empty. Peers stay in `network/`'s files until SB16. The migrator drops the masternode log. | One database, one `clear`, one durability barrier for everything the store owns; the log is transitional and SB0 says the migration drops it. |
| D7 | `locks` holds `best` (height ‖ hash) and `floor` (id ‖ height ‖ hash). There is no signature column. | `ClPersisted` carries no signature; the floor carries its record's height and hash so the row reads without a join. |
| D8 | The header step's batch holds all of its operations until one `KvEngine::write`, instead of E8's streamed open transaction. Peak memory is about the step's rows (~1 MB at B = 2000). The lease is the store's writer mutex, held by `HeaderStep` from `begin_step` to `commit` or drop. | `KvEngine` has no open-transaction API; one batch is one `BEGIN IMMEDIATE … COMMIT`, and a dropped or failed step writes nothing (MemHeaderStore's all-or-nothing). |
| D9 | No differential against `MemHeaderStore`: its constructor is behind dash-chain's `test-util` feature, and a dev-dependency enabling it would turn on dash-chain's test hooks in every `cargo test --workspace` build (GATE-FAST does not honour per-package test features). The store's own suite mirrors `MemHeaderStore`'s checks and messages, on MemoryEngine and SQLite. SB5 OQ3 (P2–P5 on SQLite) is SB14's, when the driver runs on this store. | Feature unification would change other crates' tests. |
| D10 | Migrator v3 streams each v2 folder one segment file at a time into a fresh store in `spv.migrating/`, in `WriteSet`s of ≤ 2000 rows (≤ 8 MiB for subscribers), through the legacy write path; the last commit is Durable, then the directory is renamed to `spv/` and `migration_loop` writes `version.json = 3`. A crash before the version write redoes the migration (the v2 folders are intact). Headers are read up to the first hole; filter headers likewise; filters and blocks within the header heights. V2 data that does not decode is moved intact to `v2-unmigrated/` and the client syncs afresh; an I/O error fails the open. Once the version is 3, leftover v2 folders are deleted at open. | SB0 §9.5's migrator: no O(chain) memory, a failed migration leaves v2 intact and falls back to a fresh sync. |
| D11 | The store uses `std::sync` locks (the writer lease, the view), with `clippy::disallowed_types` allowed on the `store` module only. | The store is synchronous and runs on blocking threads or with no runtime; tokio's `blocking_lock` panics inside a runtime. No store lock is held across an `.await`. |
| D12 | `DiskStorageManager` keeps dash-spv's height-indexed storage traits and puts them on one `SpvStore` (an `Arc<Store<SqliteEngine>>`) that every handle shares. Each engine call runs on tokio's blocking pool (`SpvStore::run`). The segment store (`segments.rs`, `header_hash_index.rs`, `io::atomic_write_items`) is removed. `PersistentStorage` stays for the peer files, until SB16 moves peers into `peers`/`bans`. | The sync managers stay unchanged until SB14 drives headers through `dash-chain`'s step (SB0 §9.5's transition). The store's engine is synchronous (D11), and no store call may block an async worker. |
| D13 | Every legacy write commits Buffered. The storage worker calls `sync_wal` (the store's Durable barrier) every 5 s, and `stop` calls it once more. The worker holds a `Weak` handle and first ticks one interval after it starts, so dropping the manager closes the engine and frees `spv/LOCK`; `Drop` aborts the worker. | This stands in for SB0 §9.5's checkpoint and sync-complete barriers until SB14's driver places them. A power loss loses at most the last interval's commits, the same window as the segment store's 5 s persist worker. Recovery then rewinds the subscribers (D5). |
| D14 | `clear` removes every row in one Durable `WriteSet` (`clear_all`), deletes every other entry of the storage path (peers, leftovers) and rewrites `version.json = 3`. The open engine and its lock stay. | A store directory cannot be deleted under its own open engine (dash-kv-sqlite's `LOCK`). Callers of `clear` keep using the same handles. |
| D15 | The bench `storage/disk/persist` (perfgate rows `spv-storage-*`, bench `dash-spv/storage`) now measures `stop`, one Durable `sync_wal`, after three Buffered chunks; it used to measure the segment flush. This is a bench-input change and is reported with READY. | `persist()` no longer exists. The barrier is what a shutdown pays. |
| D16 | The old masternode path's log is `mn_log`, keyed `height ‖ kind` (0 diff, 1 QRInfo). Its in-memory index is the set of heights per kind. A row of an unknown kind is logged and skipped, and a row that does not decode is dropped from the replay, as a corrupt file was. The `dashd_masternode` restart test counts the store's rows (headers, filter headers, the log) by reopening the store after shutdown, instead of counting files per folder. | D6. The test checks the same thing: a clean shutdown persisted each kind of data, and a restart did not shrink it. |
| D17 | Migration memory is gated by `tests/migrate_v3.rs`, using a counting global allocator over a v2 fixture built in the test (`test_utils::v2_fixture`: segment files of linked headers, filter headers and filters). `migration_memory_does_not_grow_with_the_chain` migrates 20 000 and 200 000 headers and requires the larger run's peak heap to stay under the smaller one's plus 8 MiB. The `#[ignore]`d `mainnet_sized_migration` migrates 2 400 000 headers. The peak heap is 3.8 MiB at every size; the times are D46's. | SB13's acceptance: v2→v3 on a mainnet-sized fixture with flat memory. The fixture is synthetic, because the migration only copies bytes and checks links, with no consensus rule. Provenance: the v2 layout is the segment store at node/integration 6993f2f2f (`dash-spv/src/storage/segments.rs`), removed by D12. |
| D18 | The crash acceptance is a `Sut` in `storage/store/crash.rs` (test-only) under ST3a's harness. The real `Store` runs on a `FaultyEngine` named `spv`. A second `FaultyEngine` named `wallet` holds the wallet's rows and Core's locator (`LocatorEntries`, chain.cpp:32-49), so each database crashes on its own. Recovery is `Store::new` + `recover`, the anchor step, and then the wallet's E3 rewind to its first locator entry on the active chain. The checks: S1 on the booted images, S2/S3 after recovery, S5 after the continuation. The tests cover every crash point of a fixed workload (32 images, 261 branches), nested crashes during recovery (2321 branches, R7a converged), six injected failures split between the wallet and the store (Applied and NotApplied), and a 500-case seeded sweep. Two planted wallet bugs are found and replay: W1 (the fork from heights) gives S2, and W2 (a boundary without the wallet's barrier) gives S3. Two store mutations are caught by the exhaustive test: recovery that keeps a stale locator (S2/S3), and a `sync_wal` that commits Buffered (S3). R6-M2's store half is `r6_m2_store_witness`: after the power loss the durable floor is A70 and the tip A100, no B record survives, and the wallet rewinds to A69. | SB13's acceptance: crash points between a header step and a subscriber commit, a crash in each database independently, a faulty wallet store, and R6-M2's witness. The wallet's rescan after the E3 rewind is SB14's (DEC-115). |
| D19 | dash-spv's CPU work runs in one `CpuPool` (`dash_spv::pool`, an `Arc<rayon::ThreadPool>` with threads named `dash-spv-cpu-i`). The host injects it through `ClientConfig::cpu_pool`; with `None`, `DashSpvClient::new` builds one of `min(2, cores)` threads. The client keeps it for its lifetime (a field, not read back from the config), and every set of sync managers shares it: `new`, each `start_sync` and the fork restart. `update_config` does not change it. `BlockHeaderValidator` and `FilterValidator` own the pool, so their `new` takes it, and they run their parallel iterators inside `install`. The filters manager calls `check_compact_filters_for_elements` inside `install`. | SB0 §7: the SPV client never builds rayon's global pool, and the host bounds the threads. When the validators own the pool, no caller can reach the global pool by forgetting `install`. A first draft built the pool in `build_managers`, which made three pools per run (new, start, the reorg's restart); a gdb trace of `pthread_create` in the thread-count test found it, and the test now requires the same CPU-pool threads throughout. The validators' `new()` and `Default` are gone (a breaking change in a 0.x crate). |
| D20 | With `parallel-filters`, `key-wallet-manager`'s `check_compact_filters_for_elements` matches in parallel only when it runs on a rayon pool's thread (`rayon::current_thread_index()`), and serially otherwise. | A W crate cannot see dash-spv's pool. The check keeps every caller off the global pool. perfgate's `kwm-filter-scan-2000` builds the bench without `parallel-filters` (`cargo bench -p key-wallet-manager`), so its loop was already serial and still is. Its source change shows up as a CHANGED crate, not as a bench-input change. |
| D21 | dash-spv-ffi's runtime runs `worker_threads` (0 means `MOBILE_WORKER_THREADS` = 2, no longer "auto") and `MOBILE_MAX_BLOCKING_THREADS` = 2 blocking threads. blst is built `no-threads` on Android and iOS, a target dependency of dash-spv-ffi. Elsewhere it is the opt-in feature `blst-no-threads`. Both entries use the dependency name `blst`, because Cargo refuses one crate under two names. | SB0 §7's mobile bound is the runtime's threads plus the CPU pool, with blst's pool compiled out. The Linux feature lets the thread-count test run the same configuration on agentbox. A host that wants more workers sets `worker_threads`. |
| D22 | Rule O5 in `check-layers.py mobile`: no N workspace member's own graph (`cargo tree -i blst@V -e normal,build,features --target all`) turns on blst's `no-threads`. `selftest-checks.sh` plants a direct `no-threads` dependency, and a dependency on dash-spv-ffi with `blst-no-threads`, in dashd-store, and expects O5 to fail on both. `check-spv.sh` lints the V crates with `spv-clippy.toml` (rayon's global-pool entry points) and the blst and dash-pkc entries of `pure-clippy.toml` (DEC-79's pooled calls). It runs on the host and for aarch64-linux-android, with all features and with none, and the lints are denied. It passes `--no-deps`, so the V crate's path dependencies keep their own layers' rules (dash-kv's std locks are S's to judge). The selftest plants `rayon::spawn` and `ThreadPoolBuilder::build_global` in dash-spv and expects check-spv to fail on both. check-mobile.sh runs it in nightly; `--no-size` skips it, because it needs the NDK. | DEC-112 O5: only dash-spv-ffi may compile blst's pool out, since a full node's BLS batch verification needs it. A per-member `cargo tree` sees what that member's build unifies, which is what ships. The workspace's `--all-features` clippy unifies `no-threads` everywhere, but that is a lint build, not a product. |
| D23 | The thread-count test is `dash-spv-ffi/tests/thread_count.rs`. It runs the old masternode path (QRInfo and MnListDiff verified by dashcore's verifier, which reaches blst's pooled calls), the filters with wallet matching, and a reorg, against the regtest masternode network through the FFI client. A 1 ms sampler of `/proc/self/task` must never see more than the baseline plus the workers, the blocking threads and the CPU pool. `required-features = ["blst-no-threads"]` keeps it out of tier-1 `cargo test --workspace`; SB13's evidence runs it with `--features blst-no-threads`. No CI or nightly job runs it yet (D34). DNS discovery is not exercised, because regtest has no seeds and the test restricts peers; its lookups run on the blocking pool that the bound counts. | SB13's acceptance, the SB0 §7 thread count. GATE-FAST's `cargo test --workspace` builds with no features, so a test that needs `no-threads` cannot run there. |
| D24 | `FilterStorage::store_filters(start, filters)` writes a run of consecutive heights in one `WriteSet`. The filters manager sorts a verified batch by height and writes each run of consecutive heights once (`chunk_by`), instead of making one `store_filter` call per filter in `HashMap` order. | Each store call is one SQLite transaction and one blocking-pool hop (D12). Per-filter writes made the initial filter sync about 6 s per 1000 filters at load ~150, so `test_runtime_add_during_initial_sync` (20 000 committed within 60 s) and `test_sync_restart_consistency` failed in every run. The segment store had buffered them in memory. |
| D25 | The BG row `spv-startup` (open-to-ready with 2.55 M stored headers, SB0 §8) has no perfgate cell until SB17, so SB13 records its storage part by hand (the storage open to the tips; the masternode-log replay that follows at a second start is D45's): `startup_with_mainnet_headers` (`tests/migrate_v3.rs`, `#[ignore]`d) reopens a migrated store of 2 550 000 headers and reads its header and filter tips. A scratch copy of the same test at node/integration 6993f2f2f measured the segment store on the same fixture (`test_utils::v2_fixture`). On agentbox at load ~150, debug builds, three reopens each: v2 was ready in 62.2 / 57.7 / 53.5 s with a 302 MiB peak heap; v3 in 0.172 / 0.132 / 0.200 s with 0.1 MiB. | The guard's intent is that startup must not regress. The v2 store read every header into memory at open, and v3 reads `meta` and the bounds. |
| D26 | `spv-clippy.toml` also bans rayon's parallel iterators and joins (`into_par_iter`, `par_iter`, `par_iter_mut`, `par_bridge`, `par_chunks*`, `par_windows`, `par_sort*`, `join`, `join_context`, `scope*`, `in_place_scope*`). The two validators, whose iterators run inside `self.pool.install`, allow the lint on `validate` and say why. The selftest plants a `par_iter` in dash-spv and expects check-spv to fail. | Review m5: a parallel iterator outside an install runs on rayon's global pool and starts it, which is what O5 forbids. Banning only `spawn` and `build_global` left the commonest entry point open. key-wallet-manager is W and not linted by check-spv; its runtime guard is D20. |
| D27 | A fence (`RwLock<()>`) is write-held across each commit, after the lease and until the view is published; `headers` and `sub_range` read-hold it across their engine reads. The view's own lock is taken only to copy it or to publish, so `view()` on an async thread never waits out a commit's fsync (lock order: lease, fence, view). The largest stored id moved from the writer's state into the view, and `HeaderStore::max_id` reads it without the writer lease. | Review m3: a reader could check bounds against the old view and then read rows a commit had just truncated (or see the engine ahead of the view). Moving `max_id` fixes a deadlock that SB14 would have hit: dash-chain's `write_header_step` calls `store.max_id()` while its sink, a `HeaderStep`, holds the lease. A store test reads `max_id` with a step open. |
| D28 | Migrator v3 takes version-2 filter headers from one below the first header height (the filter header the first filter chains from). Version-2 data that the store refuses (for example a header whose hash names the wrong height) counts as data that does not decode, so it is set aside in `v2-unmigrated/`. Other store errors still fail the open. | Review M1 and m1. `v2_data_the_store_refuses_is_kept_aside` covers the refusal. |
| D29 | The crash Sut has a second header path, `headers=legacy` (`put_headers`, with `truncate_headers` for a reorg, op `tN`), which is what dash-spv writes until SB14. `the_legacy_header_path_is_clean` explores it exhaustively and with nested crashes, and the sweep picks either path. A subscriber's locator names the highest active header at or below its top (D35); with none, `put_sub` keeps the previous locator. | Review M2: the crash evidence covered only the step path, which no dash-spv caller uses yet. A legacy reorg leaves the old branch's records, which recovery walks back to the fork (store test `recovery_after_a_legacy_truncation_rewinds_to_the_fork`). Review m2: a locator naming a height with no stored header could not be recovered. |
| D30 | A store written through the legacy path (by dash-spv until SB14, and by migrator v3) marks its first stored header the Established anchor without an anchor pack, and counts chain work from that header (absolute only when it is genesis; a checkpoint start leaves out the work below it). SB13 does not fake the missing parts. SB14, which moves dash-spv onto `write_header_step`, must re-anchor such a store at open (or migrate it v3 → v4) before dash-chain opens it in SB5 mode. `Store::reset` refuses an Established store, so the re-anchor goes through `clear_all` or the migrator. Every version-3 store before SB14 is legacy-written, so a v4 migration can tell them apart without a marker. | Review M3. The legacy path has no source for an anchor pack or for chain work below the stored range; inventing them would make SB5's open trust values nothing checked. Follow-up for SB14. |
| D31 | The storage worker stops through a cancellation token checked between syncs, and `stop` and `clear` await it, so a sync in flight finishes before they go on. Drop cancels without waiting. | Review m4: `abort` dropped the worker's future but not the blocking sync it was awaiting, which kept the store open after `stop` returned. |
| D32 | `atomic_write` syncs the parent directory after its rename (Unix), and the migrator syncs `v2-unmigrated/` and the storage path after setting data aside. `FilterStorage::store_filters` has a default implementation that stores one filter at a time. `fork_of` refuses a parent that is not exactly one height below its child, so a cycle in corrupt records cannot loop. `Store::engine` is gone. | Review m9, m7 and nits. Without the directory sync, a power loss could keep `version.json = 3` and lose the moves, and the next open would delete the version-2 folders as leftovers. |
| D33 | `tests/migrate_v3.rs` also measures the peak resident set on Linux (`clear_refs` 5, then `VmHWM`), which includes SQLite's own allocations that the counting allocator misses, and holds it to the heap's 8 MiB slack plus SQLite's page caches (3 connections × 4 MiB, which a larger store fills to their cap). At 200 000 and 20 000 headers it peaked at 15.0 and 7.4 MiB. | Review m8. |
| D34 | Follow-ups, not SB13's: (a) no CI or nightly job runs `thread_count` with `--features blst-no-threads` (D23); the gate owner should add one to the dashd `ffi` group. (b) headers2 decompression runs on the blocking pool (`network/manager.rs`, up to 4 at once); it should move onto the CPU pool. (c) The unified mobile SDK links blst through its own graph; whether that graph keeps `no-threads` is unchecked. (d) `v2-unmigrated/` is never deleted; a host may remove it after a successful sync. | Review m6, m10 and nits. |
| D35 | A subscriber's locator names the highest active header at or below its top (`active` is dense, so its top clamped), in `put_sub`, `truncate_sub` and `rewind_sub` alike. Recovery drops a subscriber's rows above its locator when the locator's header is active (`Rewound` to it): those rows were written above the header tip, and nothing checked them. | Review round 2, minor 3: `put_sub` kept an older locator for rows above the header tip, and recovery then reported `Kept` with those rows unchecked, while `truncate_sub` and `rewind_sub` deleted the locator in the same state. dash-spv's syncs write no subscriber row above the header tip, so this changes nothing for them; the store test covers it. |
| D36 | Round-2 fixes: `put_headers` refuses a hash repeated within one call (it reported `Corrupt`), and the migrator test repeats a hash within one write and across two. The migrator keeps what an interrupted earlier attempt set aside in `v2-unmigrated/`, moving only the folders still in place. `migrate_v3` migrates the large store first, so allocator reuse cannot flatter it. The worker's `select!` is `biased` towards cancellation; `atomic_write` syncs `.` for a bare file name. The clippy ban list adds rayon's remaining slice, string, extend and drain methods and its iterator constructors; the validators allow the lint on the `install` statement only. On the legacy path the crash Sut's reorg op requires its explicit truncation (`tA`). Not changed: Drop does not wait for a running sync (a reopen right after a drop can find the engine's lock taken; `stop` waits); a corrupt parent height in `fork_of` fails the open rather than resetting the subscriber. | Review round 2, minors 2, 4 and 5 and nits. |
| D37 | The filter pipeline reads each batch's headers in one store call when it sends the batch's `getcfilters` (`load_headers`, the last one's hash being the stop hash) and keeps their hash → height map, so an arriving `CFilter` finds its height there, not by a store lookup. An entry leaves when its filter arrives, `init` clears the rest, and a filter nothing awaits (a resend's duplicate) is still looked up in the store. | Each store call is a blocking-pool hop and three SQLite reads (D12): one per `CFilter` made a 1000-filter batch take ~0.85 s to receive in debug builds, where the segment store's in-memory index took microseconds. The gate's `dashd_sync` timed out at 900 s (sb13-t1). |
| D38 | `CpuPool::run` runs a closure on the pool and lets the async caller await it (a rayon `ThreadPool::spawn` and a oneshot; a panic resumes in the caller), without blocking the caller's thread. The filters manager's matching (`scan_batch` and the rescan for new scripts) uses it, on the batch's filters shared through an `Arc` (`FiltersBatch::shared_filters`; `filters_mut` copies only while a match still shares them). The validators still call `install`, which blocks the calling thread for a batch's checks. | `install` blocked the async task's thread for the whole match: on a current-thread runtime (`#[tokio::test]`, which the dashd suites use) that stopped the network and every other task, and with SB0 §7's 2-thread pool a 5000-filter match took ~1.3 s at load. `test_sync_with_multiple_restarts` restarts on every second progress event, and blocks never arrived between two matches, so it restarted 118+ times and took 1108 s alone; with `run` it took 102 s and 37 restarts at load ~200. Follow-up: the validators' `install` (header X11 batches, filter header checks) could move to `run` too. |
| D39 | The set-aside to `v2-unmigrated/` can be resumed, and it never deletes anything. `set_aside` creates the directory and syncs the storage path before its first move, so the directory records the intent. While it exists, `migrate` builds no store: it moves every version-2 folder still at the root into the aside, then syncs the aside and the root before the version write. This holds even when the root's version 2 is valid (say, a restored backup beside an old aside): it is set aside, not migrated, and nothing is lost. A folder whose name the aside already holds takes the next free `<folder>.<n>` instead of replacing the older copy. `remove_v2_leftovers` deletes leftover version-2 folders only when `spv/` exists, that is, when the store holds their data; otherwise it sets them aside and logs it. The fallback that clears unreadable storage (an unparsable `version.json`, a version newer than this client, or version-1 or version-2 data its own migrator calls corrupt; D55 corrects this list) keeps the aside, as it keeps `logs/`, and first finishes an interrupted set-aside (D42). `clear` still deletes it: the caller asked for empty storage. Directory syncs (`sync_dir`, as in `atomic_write`) run on Unix only: Windows does not open a directory as a file, and NTFS journals renames. Tests through `StorageMigrator::migrate`: every one of the 64 subsets of the six folders moved before the interruption (each followed by two opens), an I/O error midway (a folder its owner cannot write fails `rename(2)` with EACCES after three moves, the open fails, nothing is lost, and the next open finishes), leftovers without a store, and the corruption fallback (D42 crosses the subsets with an unreadable `version.json`). With the resume removed, the subset test fails at its first case (an empty aside, nothing moved). **Ownership (SB14, Sol r3 #2, Opus-h r2 m3):** a completed build lets `remove_v2_leftovers` delete `filter_headers/`, `filters/`, `blocks/` and `metadata/` only when each held nothing the build did not read: regular segment files under the names Open reads (or regular `<key>.dat` files in `metadata/`). The only exceptions are entries that never hold v2 data: v2's atomic-write leftovers (`.<name>.<pid>.<n>.tmp`) and OS artefacts (`.DS_Store`, `Thumbs.db`, `desktop.ini`). Any other entry makes the build `Corrupt`, so the v2 tree is set aside. `masternodes/` stays owned whole and discarded (SB13 D6). `<dir>.lock` lives as long as the store, held by its last handle, not by the manager (Opus-h r2 m1). | Sol r1 Blocker.

Notes for R5 and the rdc side of R6 on `node/ev-rc4`. The design is `SW-V24-rc4-pin-delta/ce.md` (CE4-01…05). The review is `reviews/SW-V24-R5-r1-opus.md`. Program decisions live in DECISIONS.md.

|---|---|---|
| N1 | **Intermediate commits pair ABI 29 with an ABI 28 archive** (r1 n1). `dash-oracle-sys/src/ffi.rs` declares ABI 29 from bb4ef7eba on. pins.txt reaches the ABI 29 shim (375c64d231) only in 15edfad82: it names 77dbec8242 (ABI 28) from bb4ef7eba through 21428ba61, and dd440ca847 (ABI 28) in the merge 141ee0528. So every oracle test is red on bb4ef7eba…141ee0528. The history is not rewritten | the branch merges `--no-ff`, and its tip is consistent. Bisect over the first-parent line or skip that range |
| N2 | **Interim workarounds for base-sdk's rc.3 purpose read** (r1 m2). DEC-472 lists three. A fourth uses the same check: the node-fuzz netinfo model (`models/netinfo.rs`) filtered with `ext_purposes_in_order` before `NetInfoV2::decode`. After R6's re-pin to 029b40bda, base-sdk refuses an unknown, repeated or out-of-order purpose itself. So R6 removes conformance `BASE_SDK_RC3_PURPOSES`, dash-dml `build::net_info_reads`, the public `netinfo::ext_purposes_in_order` and the node-fuzz filter (9b2dadf86). The tests that covered them assert base-sdk's refusal at the purpose byte (`DecodeError::InvalidValue`). `consumers::ev2b::net_info_purposes_read_as_rc4_reads_them` (r1 m1) runs `payload()` and `build_new_list_from_block` on v3 ProRegTx and ProUpServTx payloads with repeated, descending and unknown purposes, plus an ascending control, so plain `cargo test -p dash-dml` fails if base-sdk reads them again | each check would otherwise go dead silently once base-sdk turned strict |
| N3 | **`core_error` in `dash-oracle-sys/tests/mnlist.rs` stays** (r1 m2). It covers the rc.3 records of `test-vectors/core/0364ed626ec2/transcribed/evo_snapshot_tests.json` against the rc.4 oracle, not base-sdk. PROVENANCE says nothing there is hand-written, so it goes when that tree is re-transcribed at rc.4 (`contrib/node/regen-core-vectors.sh`). R6 does not re-transcribe it. Its assert trips on the first rc.4 record. The manager assigns the re-transcription row | R9 kept the tree at rc.3 ("recorded vectors: provenance of the Core that produced them") |
| N4 | **CE4-03's two-fault vector** (r1 m3). `check_layer_mutant_inputs_compare_exactly` adds row "CE4-03 raw": a crafted V24 ProRegTx made version 3, with an unknown-type entry in its network info and operator reward 10001.

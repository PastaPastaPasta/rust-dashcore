## Beyond the reviews (found by the rev1 verification, and now in the design)

1. **Core's own crash gaps.** All three are closed by A1 §3.5 and are visible only after a crash or a disk failure:
   - Lagging `rev` files are never fsynced by `FlushStateToDisk`, yet the synced index records `HAVE_UNDO` for them.
   - `UnlinkPrunedFiles` runs *before* the coins write.
   - After a failed block-file fsync, Core keeps writing the index, coins and EvoDB in the same flush.
2. **Core's EvoDB-after-coins window.** A crash between `:3090` and `:3095`, or in the replay-to-startup-commit window, ends in "you must reindex". The single atomic B1 makes it impossible.
3. **BLS legacy decode has no curve or subgroup check.** Off-curve legacy points are VALID objects, some bytes are canonical in both schemes, and secret key = r is VALID under basic. This drives the relic port and the `Exotic` handling (A1 §1.4.1).
4. **16 non-deployment-gated v23.1.8 ↔ v24 differences** beyond M-2's list (A1 §2.25 rows 3–4, 8–16, 19–20, 23–24, 26). The largest is the object-download machinery: v23.1.8 is pre-`TxRequestTracker`, so P5 must build both trackers.
5. **More non-transactional effects than F04 lists:** mineable-pool erasure (observable through GBT), platform-ban resets (persisted), VerifyDB level-3/4 effects, and v23.1.8's BLS-flag leak (A1 §2.10.1).
6. **ST1's store contract.** The engine sets no ordering by design, so the protocol owns it. `atomic_flush` is not yet set (a rev1 delta to ST1). The in-memory engine models no crash, hence ST3a.
7. **V24a needs the AU stable txid per release** (PLAN §8.1).

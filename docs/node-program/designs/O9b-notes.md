# O9b: segment snapshots, per-PR windows, `-consensusxcheck`: implementation notes and D-rows

O9b's plan is `PLAN-O9b.md` (scratch), approved with its phase split as DEC-697. Phase A (S1–S5) is what V can run today, below DIP3. Phase B (S6–S7: the evo section and the post-DIP3 snapshots) closes late, after CH7a-4 and CH7b-2, as CH3 D55's pattern. This file records the implementer's decisions where the sources leave a choice, per the IMPLEMENTER contract.

What S1 adds:
- `-consensusxcheck` in rdashd: registered with rdashd's own options, marked implemented in the support table, read at step 7's coins setup (`node::coins_configuration`), and handed to the connector and the coins cache.
- `NodeSut` soft-sets it, so its sessions keep CH3a D189's xcheck and a test can negate it.
- dashd-node's `planted-bugs` feature: `CoinsSetup::planted` and `NodeSut::planted` arm a `dashd_chainstate::Planted` bug on the connector, for xcheck's positive control in the node.

| D | Decision | Why |
|---|---|---|
| D1 | **`-consensusxcheck` is a debug-only option, off on every network** (DEC-697 Q9). It is registered as Core registers its consistency checks: `ALLOW_ANY \| DEBUG_ONLY` in `OptionsCategory::DebugTest` (`init.cpp:801` `-checkblockindex`, `:805` `-checkmempool`), so `-help` leaves it out and `-help-debug` lists it in "Debugging/Testing options:". The default is 0 on every network and in every build profile; nothing ties it to `debug_assertions`. It is read with `GetBoolArg` at step 7, so `-noconsensusxcheck` and `-consensusxcheck=0` are off. When it is on, step 7 logs `Consensus cross-check (-consensusxcheck) is on`. | Core has no such option, so there is no Core default to follow. A default that differed by network or build would make rdashd's behaviour depend on how it was built, which PF0 and the functional tests would then have to track. L2 and `NodeSut` pass it explicitly; the FT harness's pass-through is D15's. |
| D2 | **What the flag turns on**: the connector's memo xcheck (`ConnectorParts::xcheck`, CH3a D189) and the coins cache's prefetch-hit xcheck (`CoinsCache::set_xcheck`, CH2), which the node never called before S1. No prefetch producer exists in the node yet (CH4), so the cache's check has nothing to compare until CH4 lands; it is wired now so CH4 inherits it (DEC-694 Q12/Q13), and `sut::tests::consensusxcheck_reaches_the_coins_cache_prefetch_hits` admits a batch itself (a coin the database does not hold: the corruption under the flag, returned as found with `-noconsensusxcheck`). The help text names only what is wired ("the connect loop's coin reads"); CH7a widens it when it wires the DML twin. The DML reference twin (`dash-dml` feature `xcheck`, EV2 §6.7) is CH7a's to wire into `NodeEvo`, reading `CoinsSetup::xcheck`. A difference is `Fatal` with the text `consensusxcheck: …`, which stops V through the node's `AbortNode` (`*** <text>` in the log, Core's default user message). | A1 §3.10 and §3.4 item 5 name both reads. `CoinsSetup::xcheck` is the one place each later consumer reads, so the flag is parsed once. |
| D3 | **`NodeSut` soft-sets `-consensusxcheck=1`** on its arguments after the config files are read (as Core's `SoftSet*` calls in parameter interaction, so a `consensusxcheck=0` in `dash.conf` wins), replacing the forced `setup.xcheck = true`, so `diff_chain`'s node side and node-l1's chain suites read the flag through the node's own step 7 (`coins_configuration`), as before but with a negation available to tests. | Before S1, NodeSut's xcheck bypassed the node's parsing. Now NodeSut exercises the production read of the flag, and the positive control can show both states. |
| D4 | **The positive control in the node** (`sut::tests::consensusxcheck_stops_the_node_on_a_planted_memo`, feature `planted-bugs`), CH3a D189's connector-matrix case driven through rdashd's flag and setup instead: two mature OP_TRUE coinbases of 30 and 20 DASH, spent together to 55 in block 103. Unplanted, the block is invalid (`BlockChecked` reports `bad-txns-in-belowout`) and the tip stays at 102. With `Planted::L1` (the memo answers input 1 with input 0's coin) and `-noconsensusxcheck`, the invalid block connects. With L1 and the flag on, AbortNode runs with `*** consensusxcheck: the memo's coin for …` and the block does not connect; after V's own ALWAYS flush at 102, the abort, its teardown and an unplanted reopen, the store's `meta` tip and the reopened coins are at 102 and V's tip is not the block, the two coins it spends are unspent and its output is not a coin. S1 r1 m-1's commit-on-abort mutant A (the connector commits the block's overlay into the coins cache before it returns the Fatal) is not equivalent (S1 r2, DEC-716). Tier 1 kills it at its own layer: `chain/tests/connector.rs:1432` checks the coins' best block after V stops, and `:1430` checks for one report. At the node level the store checks cannot see it, because another layer masks it. In this base the shutdown flushes are BL-271's WAL-sync stub, so nothing of the cache reaches the store. With BL-271, the shutdown's ALWAYS flush finds a cache whose best block (103) is not V's tip (102), and CH1-node §7.1's freeze-pair check (`check_pair`, `flush/control.rs:653`, tested by `a_mislabelled_freeze_aborts_the_node`) refuses it with a second AbortNode, `*** a freeze at …`, so the store stays at 102. That guard is not Core's. Core's protection is structural: ConnectTip's scoped `CCoinsViewCache` is dropped without a `Flush()` when `ConnectBlock` fails (rc.4 `validation.cpp:3436-3453`), and Core's shutdown still runs `ForceFlushStateToDisk()` after an AbortNode (`init.cpp:383`, `:453`). The control therefore also asserts, after the reopen, exactly one `*** ` line in the log (the logger survives `open()`) and none containing `a freeze at`; once BL-271 is in the base that assertion kills A. The store checks stay: they test the stored state, not V's handle. The connector matrix (`chain/tests/connector.rs:1402`) checks nothing committed at the connector's level. Only connector bugs (L1, T12) are accepted on this path; any other `Planted` panics, since `CoinsCache::plant` is never called here. `node::tests::consensusxcheck_is_read_at_step_7` shows the real node reading the flag (unset, set, negated). `support::tests::consensusxcheck_is_a_debug_only_option` covers registration and help. | The connector matrix already proves the check inside dashd-chainstate. What S1 adds is the path from the command line, so its control has to start there. A `planted-bugs` feature on dashd-node forwards dashd-chainstate's and implies `test-support`, whose release-build canary (`lib.rs`) keeps it out of product builds. The gate's feature step builds dashd-node with `planted-bugs` (`[package.metadata.gate] test-features`), so tier 1 runs the control with the other `sut::` tests. |
| D5 | **Compatibility note for O14:** `-help-debug` from rdashd lists one option dashd does not have (`-consensusxcheck`). `compat/ALLOWED-DIFFS.md` does not exist yet; O14 seeds it, and this is the entry it needs. Plain `-help` is unchanged. | The difference is an rdashd-only debug option, the class O14's registry is for. |

What S2–S4 add (phase A):
- `dash-conformance segment bundle | validate` (`conformance/src/segment/bundle.rs`): a segment snapshot bundle, checked against the golden.
- `dash-conformance segment select` (`conformance/src/segment/select.rs`) over the registry `conformance/segments.json`: which windows a change runs.
- `conformance/scripts/segment-run.sh`: the selected windows, each `digest l2 --start-utxo` from its bundle, then `digest compare`.
- Tests: `conformance/tests/segment.rs` (bundles over a synthetic regtest chain) and `tests/segment_run.rs` (the script over a stub).

| D | Decision | Why |

| D6 | **Bases: 68,589, 328,007 and 614,819** (DEC-697 Q2), not R4 §2.3.4's 328,008 and 614,820. A base is the last block before the transition, so the window's first block is the first one under the new rule. The rules: mainnet `nBits` is tolerance-checked for `nHeight <= 68589` (`validation.cpp:4482`), so 68,590 is the first exact block and 68,589 is already a base; budget payments start at `nBudgetPaymentsStartBlock` 328,008 (`chainparams.cpp:168`; `masternode/payments.cpp:266`, `nBlockHeight < nBudgetPaymentsStartBlock` is the old rule); superblocks at `nSuperblockStartBlock` 614,820 (`chainparams.cpp:171`; `payments.cpp:271`, `nBlockHeight >= nSuperblockStartBlock`). The later heights in R4's table are already one below their activations (`chainparams.cpp:185-196`). | A base at the first block under a rule would leave that block out of every window. |
| D7 | **A bundle is checked by a fresh scan of its snapshot's bytes** (`bundle::scan_snapshot`): the file read whole through Core's loader rules (`digest::utxo::read`), its coins inserted into a new `MuHash3072`, and the finalized hash, `txouts` and `amount` compared with golden(B) and with the sidecar, as are the base's block, the coin count and the file's sha256. `make` checks before it creates anything, `validate` checks a stored bundle again. `digest l2 --start-utxo` checks the coins it loads against golden(B) once more (CH3a D166), and that scan seeds the window's MuHash (DEC-697 Q3). | `--save-utxo`'s own check scanned V's cache, not the file. The bundle's check reads only the file, so a bundle is never trusted on what wrote it. |
| D8 | **The bundle layout** is fixed: `utxo.dat`, `utxo.dat.json`, `MANIFEST.json` and `SHA256SUMS`, which lists exactly the other three, each once. `bundle::open` (`segment open`) refuses any other file or a missing one, a `utxo.dat` checksum that is not the sidecar's `sha256`, and a manifest whose chain, base or `utxo` section (file names, sha256, coin count, scan) is not the sidecar's. It does not scan and reads no golden; the manifest's `validated.golden_sha256` is a record, not checked, since a golden may be copied or recompressed. `make` copies the two files in first and checks the copies, so what it checked is what the bundle holds. It builds in `.<id>.partial` beside the bundle and renames it into place once whole: a run killed part way (S5's stopped 1,028,159 bundle left a partial `main-1028159/`) leaves nothing under the bundle's name, and a stale partial directory makes the next `make` refuse until it is removed. The manifest's `evo` is null: below DIP3 there is no evo state, and phase B adds Core's `EvoSnapshot` v3 bytes with `GetEvoSnapshotHash` (DEC-697 Q4). Until then `open` refuses a non-null `evo`. Bundles live in `/work/conformance/o9b/` (DEC-697 Q11), one directory per registry window id. | A fixed file set tied to the sidecar means a checksum match covers the whole bundle, and a rewritten checksum still has to agree with the sidecar. |
| D9 | **No mid-run save (`--save-at`); the snapshots are made by chained `digest l2` runs** (a plan change from S3): genesis → 68,589 with `--save-utxo`, then each later base from the previous bundle with `--start-utxo` and `--save-utxo`. Each run checks its start against golden(B) and its save against golden(N), so every link is checked at both ends. | A save inside one forward run needs a pause in `l2`'s feed loop, a change to the driver CH3a's suites cover (on the 2400 s SLOW list). The chain costs one fixed start-up per base (about 4 min at load, D169) and no change to `l2`. |
| D10 | **Validation against a live oracle is not in phase A.** Every phase A base is at or below 1,028,159, which the mainnet golden covers, so `segment validate` reads only the golden. The pure-read RPC allow-list (DEC-697 Q5) comes with phase B, whose post-DIP3 bases need it. | Nothing in phase A would exercise it; shipping it untested would be dead code. |
| D11 | **The registry** is JSON (`conformance/segments.json`; dash-conformance has `serde_json` and no TOML parser). Path rules are prefixes, a leading `./` allowed. Every workspace crate in `dash-conformance`'s normal and build dependency closure (by `cargo metadata`: crypto, dash, dash-chain, dash-clock, dash-consensus, dash-dml, dash-evo, dash-filters, dash-kv, dash-netaddr, dash-network, dash-sha256, dash-statedigest, dash-x11, dashd-chainstate, dashd-store, hashes, internals), `conformance/src/`, `conformance/Cargo.toml`, the registry, the runner and the root `Cargo.toml`/`Cargo.lock` hit every area (`*`): each is linked into the binary that runs a window. dash-governance (`payments`, `evo`) and dash-mnlist (`evo`) are not linked yet; their rules are for phase B. `select` is first-fit in registry order under `budget_s` (3,300 s, DEC-697 Q8): a window over what is left prints as `NIGHTLY`, and a later one that fits still runs; `--nightly` runs every active window. `segment select` refuses an empty path list (a failed diff upstream, more often than an empty change). A window's wall time is `default_wall_s` (900 s, from D169's 10 min 42 s for a 25k-block suffix at load 105–193) until measured. Deferred rows: the post-DIP3 windows ("phase B: CH7a-4" / "CH7b-2"), and MN_RR and WITHDRAWALS on mainnet ("data ends at 2,094,670; see manager"). The testnet V24 row waits for its activation height. | One small file, no new dependency. The closure is listed by hand: a crate added to it needs a rule (follow-up: check it in a test). |
| D12 | **`segment-run.sh`** takes a whole `segment select` output: it refuses input not ending in the `BUDGET` line (so a failed `select` upstream runs nothing and fails), and RUN lines on more than one chain (one run takes one chain's blocks, headers and golden). Before any window runs, it checks that no log exists and opens every bundle (`segment open`, D8), whose chain and base must be the RUN line's (exit 2). Then each window runs as the suffix check runs its one (D167): `digest l2 --assumevalid on --par 16 --start-utxo`, a reverse leg to the base, then `digest compare --mode linear` over base+1..=to with D167's `--require` and `--exclude`, passing only on exit 4 and only when the compare lists each evo key (`mnl`, `qc`, `cp`, `ehf`) at 0 pairs on the log's side, so the run fails once V writes one and it must leave the exclude list. Unlike the suffix check, it does not count the pairs holding `muhash`: `digest l2` itself checks the finalized MuHash at the window's end against the golden (`forward_golden`). Nor does it checksum the blocks, headers or golden; the caller installs them read-only with their own checksums. | With the reverse leg ending at the base, the log finalizes MuHash at the window's end only, which `digest l2` checks. |

| D28 | **The bundle's evo section, manifest v2 (S6a-2; amends D8).** `segment bundle --evo <file>` adds `evo.dat`, Core's `EvoSnapshot` v3 bytes (D17–D27 in O9b-S6a-notes). `make` copies it in and decodes the copy as Core's `Unserialize` does, which ends in `Validate(true)` (the history replays). It refuses bytes after the snapshot, a base hash that is not the bundle's block, and a base list at another height. The manifest's `format` becomes `O9b segment snapshot bundle v2`, and its `evo` records `{file, sha256, version, evo_hash, masternodes}`, where `evo_hash` is `GetEvoSnapshotHash` (`snapshot.cpp` rc.4:339) in display order, as Core prints a `uint256`. `SHA256SUMS` then lists `evo.dat` as well. `open` first refuses any name `SHA256SUMS` lists that is not one of the bundle's four, so an absolute path, a `../` or a device is never read, and a bundle file that is not a regular file (a symlink); then it hashes them and checks the file set, the section's file name and its sha256 against the manifest, without decoding; `validate` decodes it again and compares the whole record. A v1 manifest (S2–S5's four bundles) still opens, and never with an evo section. Masternode network info is checked under the bundle chain's v24 rules without `-cjdnsreachable` (Core's `netInfo->Validate()` under the running chain's `Params()`); a devnet bundle can't carry a section, since its parameters aren't recorded. Whether a base needs a section (DIP3 active) is the producer's call (S6b-1), not checked here; nor is the section checked against the golden's `mnl`/`qc`/`cp` yet, which is S6b-1's (DEC-746 (3)). The recorded `sha256` is of the bytes decoded (one read). Core's own bytes pin the scan: rc.4's `populated` vector gives the hash its test pins (`evo_snapshot_tests.cpp` rc.4:317-320) and 3 masternodes under mainnet's rules, and is refused under testnet's and regtest's (port 9999); its list moved to unroutable addresses on port 19999 is accepted under regtest's rules only.

## 1. What the crate is

`dash-mnlist` is SPV's masternode-list, quorum and lock engine (SB0 §5.3). It is **sans-io and
synchronous**: it never sends a message, never spawns, and never owns the header chain. Its host
(dash-spv from SB15, the node's mnxcheck task from SB19) feeds it `mnlistdiff`/`qrinfo` payloads,
asks it what to fetch, and applies what it verifies. Everything it trusts comes through SB0 §5.2's
trust chain:

| Step | Rule | Where |
|---|---|---|
| 1 | the diff's target is an accepted header | `MnChain::lookup` (§2) |
| 2 | the CbTx partial-merkle proof reproduces the target's merkle root, coinbase at index 0 | `dash_evo::cbtx::verify_cbtx_proof` (SB7) |
| 3 | base list + diff → `SmlList` whose root equals the CbTx `merkleRootMNList` | `SmlList::merkle_root`, `cbtx::check_mn_list_root` |
| 4 | the quorum set after the diff hashes to `merkleRootQuorums` | `sml::merkle_root_quorums_from_hashes`, `cbtx::check_quorums_root` |
| 5 | each new commitment of a **used** type passes Core's `CFinalCommitment::Verify` with signatures; other types `Skipped` | `llmq::verify_quorum(…, SigPath::Mined, …)` with `UncachedMembers<SmlList>` (SB8) |
| 6 | a lock selects over the authenticated set at its selection start, then requires that exact commitment `Verified` | `locks::verify_chainlock` / `verify_islock` over the engine's `QuorumScanView` (SB8) |
| 7 | a verified CL goes to `HeaderChain::apply_chainlock`; a CL whose selection start is not a known header waits | host, with the engine's `pending_cl` |

Core: `mnlistdiff` is `BuildSimplifiedMNListDiff` (`evo/smldiff.cpp` rc.3:154-235; quorum list
`BuildQuorumsDiff` :31-67 from `GetMinedAndActiveCommitmentsUntilBlock`,
`llmq/blockprocessor.cpp` rc.3:818-832); `qrinfo` is `BuildQuorumRotationInfo`
(`llmq/snapshot.cpp` rc.3:77-257, diffs to each cycle's work block `ConstructCycle` :35-65); the
CbTx roots are `evo/cbtx.cpp` rc.3:65-156.

## 4. Storage

SB10's `WriteSet` is a convention, not a type: one `KvEngine::write(batch, Commit)` of a
`KvBatch` (SB0 §9.5). The SPV store reserves `mn_lists`, `mn_quorums` and `mn_snapshots`
(`dash-spv/src/storage/store/schema.rs`, CFs 12–14, SB13) and per-subscriber locators. The engine
does not depend on dash-spv: `take_dirty()` returns `MnWrites` (puts and deletes per engine table
plus the MN locator) and `MnWrites::write_into(&mut impl KvBatch, MnCfs)` writes them into the
host's batch with the host's `Cf`s. Pruning is deletes inside that same batch; no table is ever
cleared (SB0 §4.3.1 step 3, §5.3). Codecs are the engine's own (`dash-kv::codec` helpers). Slice
3; slices 1–2 hold state in memory only.

Where they straddle V19, the authenticated set at V19 − 1 on that set's chain decides, and the engine asks for it (`getmnlistd`) when it is not held. That set lacks the commitment (else it would be the lowest), so the commitment was mined at or above V19. Where it is unauthenticated (V19 below A_q) the commitment is `Unavailable(MiningScheme)`, below the floor `BelowFloor`; never `Unverified`. Amended after review (Sol r2 major 1): that set was global to the commitment's hash, so a commitment held on two branches asked for the stale branch's block at V19 − 1, and a failed request left it `FetchFailed` for good. The set is now read on the active chain at each step 5 (`first_sight`); a commitment `Pending` or `FetchFailed` runs step 5 again on each applied payload, so a branch change retargets its request. A failure whose block is off the active chain at a step 5 is forgotten, so a reorg back asks again (if no step 5 ran while it was off, the failure stands until the host calls `tip_changed`), and a failure reported for a request no longer outstanding is ignored (validator r2). No request names a block off the active chain, which Core refuses with a misbehaviour point (`net_processing.cpp` rc.3:5611-5632 for `getmnlistd`, 5660-5683 for `getqrinfo`): a commitment needing one is `Unavailable(OffChain)` and runs step 5 again on each applied payload, and a listed request whose block a reorg leaves off the active chain, a lock check's too, is dropped at the next step 5 (a stale request still on the active chain stays: Core serves it). A `qrinfo` so dropped and asked again counts no row retry (D20): no peer answered it. A branch change with no payload is the host's to report: `tip_changed` runs step 5, and the host-integration slice calls it on each tip change. Amended after review (Sol r3 major 1): a final verdict outlived a change of its mining scheme, because a `Verified` or `Unverified` record never ran step 5 again. Each state now keeps the set that decided its scheme (its decider): the lowest set holding the commitment when that is below V19, or the set at V19 − 1 lacking it. No decider is kept where the base is at or above V19, since that scheme reads no branch. A lock check reads a state as none (`Unavailable`) while its decider is off the active chain, both by hash (`ScanView::quorum`) and in the scan's entries (`ScanView::entries`, which ChainLocks and rotated InstantSend locks select from; validator r4 major 1). So no lock uses a verdict reached on another branch, even before step 5 runs again. Step 5 runs again, at the next payload or `tip_changed`, for every final state whose decider is off the active chain. A final state whose new decider is its old one stands without a BLS run, since the scheme is the same over the same base-chain members. So a commitment held only on a branch the chain left costs one `first_sight` per payload, and a `RowsDisputed` spends no retry over a reorg. The per-payload cost is one ancestor read for each final state with a decider. Only commitments based below V19 have one, so on mainnet and testnet, where V19 is long past, none does.

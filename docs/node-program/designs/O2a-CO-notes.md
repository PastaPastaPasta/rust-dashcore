# O2a-CO: oracle coins-cache ops, implementation notes

Decision rows taken while implementing O2a-CO: the Core entry `oracle_coins_ops` (ABI 15, Core
branch `node/o2a-co-oracle-v24.0`), its `dash-oracle-sys` binding (`coins_ops`), and the node-l1
harness CH2c's `diff_coins_ops` drives (`node_l1::coins_ops`). Program decisions live in
DECISIONS.md.

| Row | Decision | Evidence |
|---|---|---|
| D1 | **One stateless entry, one script per call.** `oracle_coins_ops` builds the whole stack for the call: a `CCoinsViewDB` on an in-memory, obfuscated LevelDB (`fMemory`, `fObfuscate`, as the chainstate is), a tip `CCoinsViewCache` over it and the child views the script pushes (at most 16 views). It drops them all on return. There is no handle API, so nothing can leak between calls, and a fuzz input is a self-contained script. The only process-wide state it touches is gArgs (D5), under the shim's process-state mutex. | `tests/coins_ops.rs` `calls_are_deterministic_and_independent`: the same 40-coin script returns byte-identical output, DynamicMemoryUsage included, before and after a different script that flushes coins and a best block. A fresh script's database has no coins and a null best block. |
| D2 | **DynamicMemoryUsage is an explicit op (USAGE), not a field of every op's output.** DEC-94 Q3 asks for usage per op. A script gets that by following any op with USAGE, which returns Core's `DynamicMemoryUsage()` and `GetCacheSize()` for any view. Ops that don't need it stay small. Its consumer is DEC-99's Core-model meter (`CoreCacheMeter`, CH2 §2.4.5), which c3 checks against Core after every op. That meter does not exist in the tree yet, so the smoke harness compares no usage: CH2's native ledger is not Core's memusage (DEC-99, DEC-102). HaveCoinInCache is an op of its own too. The smoke harness compares every answer except the one-way case D13 (2) skips; the entry flags (ENTRY) wait for CH2c's aligned mode. | `tip_flush_writes_the_database` (a flushed tip has 0 coins); `calls_are_deterministic_and_independent` (40 coins, usage > 0, the same on every call). |
| D3 | **The allocator assumption: Core's memusage is computed, not measured.** `DynamicMemoryUsage` adds `memusage::DynamicUsage` of the map: the pool resource's chunks plus `MallocUsage(8 × bucket_count)`, where MallocUsage is the 64-bit glibc rounding `((n + 31) >> 4) << 4`. It also adds `cachedCoinsUsage`, which sums each coin's script through the same formula. No allocator is queried, so the number is the same on every run and every machine with the same libstdc++. Its bucket-count growth policy is the only build input. The oracle archives build against the depends libstdc++ pinned with them, so the number is stable per pin. It is not the bytes malloc actually returns. CH2's own measurement (the tagging allocator, CH2 §6.7) is a different quantity, which is why D2 does not compare them. | oracle.h, the coins section ("USAGE"); `memusage.h` at the pin. |
| D4 | **The caches are deterministic** (`CCoinsViewCache(base, /*deterministic=*/true)`, a fixed SaltedOutpointHasher salt), as Core's coins tests and fuzz targets build them. Production salts randomly, which changes only the map's iteration order. That order reaches two places. (1) The order in which BatchWrite visits the child's entries decides which FRESH-misapplied entry throws first. The message is the same, and the script ends either way (D7). (2) The order of a flush's writes into the database batch, which is invisible once the batch is written whole (D5). | oracle.h; `calls_are_deterministic_and_independent`. |
| D5 | **`-dbbatchsize` per call; `-dbcrashratio` forced to 0.** `CCoinsViewDB::BatchWrite` reads both from gArgs. The shim forces them in `forced_settings` for the call's duration and restores whatever was forced before. A crash ratio above 0 calls `_Exit(0)` at random partial batches, which would end the test process as if it had passed. A chain's arguments cannot set the ratio anyway: `oracle_set_network` parses them against the chain-parameter options only, so `-dbcrashratio=1` is refused (`ErrorKind::Network`). Partial batches are therefore unobservable: the head-blocks marker is written and erased within the call, and BatchWrite's replay assertion is unreachable. A crash-point differential (a partial batch left on disk) is out of scope here. It would need a hook on `CDBWrapper::WriteBatch` (for example `ld --wrap`) and belongs with CH2's CRASH model if wanted. | `tip_flush_writes_the_database`: the same database at batch sizes 16 MiB (the default), 0 (every coin ends a partial batch), 1 and 40 bytes, with no head blocks. `crash_ratio_is_unreachable`: the chain argument is refused, and a one-byte-batch flush runs to the end. |
| D6 | **Entry flags are DIRTY and FRESH only** (SEED, BATCH_WRITE). Those are Core's only flags (`CCoinsCacheEntry::Flags`). Any other bit is `ORACLE_E_ARG`, not passed to Core. | `malformed_scripts_are_refused` (flags 4). |
| D7 | **A `logic_error` or an assertion ends the script.** Core leaves a view partly updated after either: BatchWrite throws mid-map, and an assertion aborts. The node treats both as fatal, so a script never continues past one. The outcome (LOGIC_ERROR with Core's `what()`, or ASSERT) is the op's last record. | `logic_errors_end_the_script`: both of Core's texts, and the DB_STATE op after them is not run. `null_best_block_flush_is_an_assert_outcome`. |
| D8 | **Two assertions are checked by the shim, not run:** AddCoin's `assert(!coin.IsSpent())`, which no decoded coin can reach (decoding never yields the null output), and BatchWrite's `assert(!hashBlock.IsNull())`, a tip flush or sync before the tip's best block is set or read. Each returns the ASSERT outcome with the assertion's text and source location. Every other Core assertion on these paths is unreachable from a script: the replay assertion (D5), and Flush's "not all cached coins were erased", which is a `logic_error` and cannot fire: `BatchWrite(erase = true)` erases every entry it visits, before Flush's `ReallocateCache`. | `null_best_block_flush_is_an_assert_outcome`: tip FLUSH and SYNC report the assertion. A child's flush into the tip does not (`CCoinsViewCache::BatchWrite` copies the child's null hash). |
| D9 | **ENTRY and SEED are test-only ops**, Core's `coins_tests` `GetCoinsMapEntry` and `InsertCoinsMapEntry`. They make Core's own state tables transcribable. SEED adds the coin to `cachedCoinsUsage` as `InsertCoinsMapEntry` does, and refuses an outpoint the view already holds. No `SanityCheck` op: it asserts, and the shim does not run assertions (D8). | `ccoins_access`, `ccoins_spend`, `ccoins_add` and `ccoins_write`: every row of Core's tables (`coins_tests.cpp:649-879`), through `SingleEntryCacheTest`'s construction. |
| D10 | **The Rust binding holds the pin's lock exclusively** (`Oracle::exclusive`, new) for `coins_ops`: the call writes gArgs, which a concurrent chain call reads. It selects no chain. | `dash-oracle-sys/src/lib.rs` `exclusive`. |
| D11 | **The node-l1 module is the harness skeleton; CH2c registers the target.** `node_l1::coins_ops` provides the script type (`Op`), the fuzz-byte reader (`script_from_bytes`, valid by construction), the Core script (`core_script`) and the comparison (`compare_coins_script` / `compare_coins_ops`). CH2c c3 adds `diff_coins_ops` to `TARGETS` and node-fuzz, and the aligned mode (ENTRY, DynamicMemoryUsage). The public seeds are written now (`examples/coins_ops_seeds.rs`, `node-fuzz/public-seeds/diff_coins_ops`). | `tests/l1_coins_ops.rs`. |
| D12 | **The harness's tip flush is synchronous:** freeze, the harness's own write of F's DIRTY entries in one batch (a spent one as an erase), release. That write stands in for W; CH2's flush writer is not under test here. No F is ever in flight across ops, so DEC-102's flush-point difference (HaveCoinInCache over F) never arises. The database is compared after every tip flush: Core's coins records against the `coins` column family, Core's best block against CH2's `durable()` one (which the release sets), and no head-blocks marker. | `tests/l1_coins_ops.rs`. |
| D13 | **Two by-design differences end a run (or skip one answer) instead of diverging** (`Allowed`). (1) DEC-131: the overlay's add without `possible_overwrite` refuses a coin the tip holds unspent. Core's child adds it FRESH and throws at its flush (`coins.cpp:221`), or never, if the block spends it first. (2) CH2 §2.4.2, O-R6-m3: the overlay's reads (`coin`, `have_coin`) cache nothing. Core's child `FetchCoin` caches the coin in the child and in the tip. So a read through the block's view that finds an unspent coin in the database puts it in Core's tip only. The harness tracks those keys exactly: one leaves the set when CH2's tip gains an entry for it (a tip add of a spendable coin, a tip spend or read, a child spend without a child entry, a commit of the child's entry), on an uncache (which drops Core's clean entry) and at a tip flush. For a key in the set, a tip HaveCoinInCache answer of Core's true against CH2's false is skipped; an add Core refuses and CH2 accepts ends the run; so does a commit only Core refuses, when one of the block's FRESH keys is in the set (Core's tip holds it unspent, and its flush throws FreshMisapplied). See ask A1. | `l1_coins_ops` `seeds_agree`: `block-fresh-at-add` ends by (1), and `block-read-caching` skips a HaveCoinInCache answer by (2), and `block-commit-read-caching` ends at the next block's commit by (2). `random_inputs_agree`: 600 xorshift inputs with no divergence. A one-off run of 20,000 inputs (685,819 ops, 41,121 tip flushes, 22,226 commits) had no divergence either: 3,669 runs ended with both sides throwing the same `logic_error`, 1,190 ended by (1) or (2), and 171 HaveCoinInCache answers were skipped. The commit case of (2) was found by that run (input 388 of the generator). After the exact child-read set (29c77752d), the same 20,000 inputs ran again with no divergence. |
| D14 | **A1 decided: child-read caching stays an allowed difference, handled by CH2c.** CH2's overlay reads stay non-caching (O-R6-m3). The harness keeps classifying the difference as `Allowed::ChildReadCaching` (D13 (2)), and CH2c owns its coverage (hand-off below). | Sol r1 (reviews/O2a-CO-r1-sol.md): PASS WITH CH2c FOLLOW-UP, no blocking finding. |

## Asks

- **A1 (child-read caching, for CH2c's aligned mode). Decided by D14.** D12/DEC-102 cover HaveCoinInCache only across flush points. A second source of difference needs no flush: Core's child reads (`AccessCoin`, `HaveCoin` on the block's view) cache the coin in the tip as well, and CH2's overlay reads cache nothing (O-R6-m3). After a child read, the tip's HaveCoinInCache and its entry flags differ until the next tip flush. A later `possible_overwrite = false` add of that key is refused by Core and accepted by CH2. On the tip, the add itself is refused. In a later block, Core's child adds it FRESH and the block's flush throws FreshMisapplied, where CH2's commit succeeds. The harness classifies these as allowed (D13). CH2c should confirm the classification, or decide to align the overlay's reads with Core's. CH2's coins model already records the same effect (`TwinOnly::read`).

## Hand-off to CH2c

From Sol r1's follow-up:

- `Allowed::ChildReadCaching` can end a run early at a commit. Every op after that point goes uncompared, so the smoke run cannot detect a later error in such a script.
- Before CH2c counts a passing campaign as full parity, it must either run its aligned mode, or keep the scripts that hit this exception in a separate class from fully compared ones.
- CH2c must report allowed exits (`ended_by`) and skipped answers (`skipped`) separately from runs compared to their end.
- `diff_coins_ops` is not registered as a node-fuzz target yet. CH2c c3 adds it to `TARGETS` and node-fuzz (D11).

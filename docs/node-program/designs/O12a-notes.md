# O12a: mixed-network harness, mode A, implementation notes and D-rows

Mixed mode A (A1 §4.8, PLAN M5, NFR-CEQ-09) runs every DashTestFramework (DTF) test of the v24.0 tree with node 0 (wallet funder, `sporkkey`, miner) and every masternode on the reference dashd, and every other node on rdashd. It builds on O11's func-compat runner (`O11-notes.md`) and Core branch.

## Pieces

- **Core** (`~/workspace/dash`, never pushed): `node/o12a-mixed-a` off `node/func-compat-v24.0`:
  - `rust_nodes.py` takes the role mask `non-mn` (`NON_MN`) besides `all` and index lists;
  - `DashTestFramework.start_masternodes` and `dynamically_add_masternode` create their nodes inside `rust_nodes.masternodes()`;
  - slice 2: the observer (D9), kept node 0's alone through links and bulk restarts (D13);
  - DEC-457: `rust_nodes.RPC_FAILURE`, logged by main()'s last handler (D4).
- **Runner:** `contrib/node/func-compat/func-compat.py mixed-a`, with `test_func_compat.py`'s `MixedA` cases.
- **Passlist:** `contrib/node/func-compat/mixed-a.json`.
- **Nightly entry point:** `contrib/node/func-compat/mixed-a-nightly.sh OUT_DIR` (D7). No timer is installed; SB1 owns the nightly.

| D4 | **Failure classes, from the traceback that failed the test.** That is the traceback after `main()`'s last handler message (`JSONRPC error`, `Assertion failed`, `Key error`, `Called Process failed`, `Unexpected exception caught during testing`), not a later one from `stop_nodes()` on the way out. The classes are: `unimplemented-rpc` (the node answers `Method not found (-32601)`; the detail is the RPC named by the frame that calls into the RPC proxy, so `generate` through `TestNode.generate` reads `generatetoaddress`), `unimplemented-option` (rdashd's "`-x` is not supported by rdashd yet" refusal; the detail is the options), `timeout` (`wait_until()`'s `AssertionError: Predicate …`, sync time-outs and `Timeout…`), `harness` (no traceback, no test-script frame in it, or an exception of the process and transport around a node: `INFRASTRUCTURE`, such as `FailedToStartError`, `CalledProcessError`, `OSError`, and the connection and `http.client` errors, `TRANSPORT`, any other `http.client.*` exception included), and `divergence` (any other exception raised through a test line: an `AssertionError`, a `JSONRPCException`, or a `KeyError`, `TypeError`, `ValueError` or `IndexError` on an RPC result; Sol r1 #2). DEC-457: a `TRANSPORT` error is a `divergence`, with or without a test frame, when the Core harness logs that the RPC was to an rdashd node whose process had exited by then (`rdashd RPC failure: node N exited C`, written by main()'s last handler from the traceback's RPC port, after waiting up to 5 s for the process). With the node still running, or on a dashd node's RPC, it stays `harness`; that includes a malformed HTTP reply from a running rdashd (`BadStatusLine`, `IncompleteRead`, `LineTooLong`), which is rdashd's in truth and accepted as `harness` because the flag below keeps it visible. Every `TRANSPORT` error is also flagged in D6's `possible_crashes`, but for `http.client.CannotSendRequest`, which `TestNode.stop_node` logs at an ordinary shutdown after an RPC that timed out. Except for the first two classes, the detail is the innermost test-script line (or "no test frame"). DEC-483: a sixth class, `allowed-diff` with detail `D18`, comes first for a failed test with an rdashd start: when an rdashd node's `debug.log` in the datadir the test left has rdashd's readiness refusal (`rdashd cannot validate block … is not built (ALLOWED-DIFFS D18)`, an abort with exit 1), the run is that declared difference, whatever the test then failed with, an exit 1 at stop included. The brief lists four classes; `unimplemented-option` is the fifth, because a refused option and a missing RPC have different owners and fixes. | Details are names and source lines, never exception types, messages or values. So they are stable from run to run, and they never describe a failure (a crash included) in tracked text. |
| D5 | **A verdict needs an rdashd start; a timeout gets a rerun alone.** A test that started no rdashd node (O11's `RDASHD_STARTS` count per test, BL-356) is a skip, "no rdashd node", whatever its result: mode A left it all dashd, as in DTF tests whose nodes are node 0 and masternodes only. A failure of such a test goes to the untracked run report as `dashd_only_failures` (the first run had two, both `wait_until` time-outs under load). A test the first pass classes as `timeout` runs again alone (`--jobs=1`), and the rerun's entry replaces its own only: test_runner.py also reruns the variants a name prefixes. A rerun (this one or D11's) that starts no rdashd node does not replace a first entry that had one: the first entry stays, and the name goes to the run report's `rerun_without_rdashd` (Sol r1 #1). | A verdict on dashd alone says nothing about rdashd, and a flaky dashd-only test would make the nightly noisy. The box's load (15–190) makes wall-clock waits flaky, so a timeout is only recorded after a quiet rerun. |
| D6 | **Possible crashes stay out of tracked text.** A test is flagged in the run report's `possible_crashes` when its output matches `CRASH` (`panicked at`, an exit code of 101 or a signal, a non-zero exit at stop, a connection refused, reset or dropped under an RPC, a segfault). It is also flagged when its nodes' stderr does; that datadir is moved to `OUT/possible-crashes/` (mode 700) instead of being deleted. A test whose failing RPC was to an rdashd node that had exited (D4), or with a node that exited non-zero at stop, has its datadir kept the same way (DEC-483); in a D18 run (D4), whose abort exits 1, only what that abort does not explain (`CRASH_BEYOND_D18`: a panic, a signal or exit 101, a stop exit or an exited rdashd with a code other than 1, a segfault) keeps and flags it. Its passlist entry is its ordinary class and test line. Known noise: in the observer variant under a full -j 4 run, about half the tests that fail in setup also log a `BrokenPipeError` from a stop RPC during shutdown, after the cause traceback. It matches `CRASH` and flags the test, but no node's stderr matches and it did not reproduce alone or in smaller batches; the matcher is kept as is (DEC-457). | A crash may be security-relevant. It is triaged privately, from the kept datadir, and not described in a committed file. |
| D7 | **Diff and update.** `mixed-a` exits 0 when the regenerated passlist equals `mixed-a.json`, and 1 when it differs (one line per changed test) or when an adaptation is stale (O11 D4 tripwire). It reads the committed file before the run, so a broken file fails before any result is written. `--update` rewrites the file and is refused for a partial run. A partial run (`mixed-a <tests>`) diffs only what it ran. `mixed-a-nightly.sh` builds rdashd and rdash-cli at HEAD (the target directory from `cargo metadata`) and runs `mixed-a`. `mixed-a` exports the checked-in `MIXED_A_CORE_BRANCH` (`node/o12a-mixed-a`; the nightly's `MIXED_A_CORE_BRANCH` env overrides it), records the branch and commit in the run report, and exits 2 with no result when the exported tree is another branch or lacks `MIXED_A_HOOKS` (the role mask, the observer and its r2 rules, `RPC_FAILURE`). It exports beside O11's tree (`v24.0-wallet-node_o12a-mixed-a`), so the two never replace each other's. The adaptations tripwire starts rdashd with `-listen=0`: another node on the box may hold the regtest p2p port, which made the first nightly run fail its observer variant (exit 2): such a tree runs every node on dashd, and every test would come out a skip (Sol r2 #1). `mixed-a` writes its result (`<variant>-<pin>.json` under `--out`) last, after the run report, the diff and any `--update`, and atomically (a `.partial` file renamed). The nightly exits 0 (same) or 1 (differs) only when that result exists; any other outcome, such as a build or harness error, is 2 (Sol r1 #3). `MIXED_A_BIN_DIR` skips the build. | One command for people and for SB1's nightly, which needs to tell "the verdicts moved" from "the run broke". |
| D8 | **Ports and datadirs.** `TEST_RUNNER_PORT_MIN=2700`. A node's p2p, rpc and tor ports are `PORT_MIN + n + (20 × portseed) mod 9979`, +10000 and +20000 (`util.py`). test_runner.py's portseeds count down from the number of tests (39), so mode A uses about 2700–3520, 12700–13520 and 22700–23520. These are below 32768. A run on the default base (11000, O11's) uses about `11000 + 20·N` upward for N tests, so it stays clear of mode A's ranges while it has fewer than about 85 tests; a larger concurrent Core suite can collide, and no base above 1024 avoids that for every N. Each pass runs in a fresh directory under `--tmpdirprefix` and removes it afterwards, except D6's kept datadirs. The runner log keeps each failure's output. | Ports in the ephemeral range collide with client sockets. A nightly must not leak datadirs into /dev/shm. |

## Slice 2: the observer variant and confirming reruns (DEC-451)

Slice 1 (D1–D8) is literal mode A, and it is unchanged. Slice 2 adds the following.

| D | Decision | Why |
|---|---|---|
| D9 | **Observer variant, `RDASHD_OBSERVER=1` (`mixed-a --observer`).** Two Core commits make `DashTestFramework.setup_network` end with `add_rust_observer()`. It adds one rdashd node with a copy of node 0's arguments, starts it, and has node 0 dial it, so rdashd needs no `addnode`. It then finishes the observer's mnsync and waits until the observer has node 0's blocks and sporks, so a setup failure points at setup. Node 0 is the observer's only peer, and no test knows the observer exists. So whenever node 0 starts again (`start_node(0)`, including restarts) or is reconnected after isolation, the framework reconnects the observer, restarting it and finishing its mnsync if a test stopped every node. It uses the base `connect_nodes`, because DTF's pauses every masternode's thread, and the masternodes may be stopped at that point. A test that toggles node 0's network itself (`setnetworkactive`, as `rpc_net` does) is not followed, and leaves the observer disconnected for the rest of the test. `feature_llmq_chainlocks_automatic` unpacks `self.nodes[:2]` instead of `self.nodes`. The variant runs with the same `non-mn` mask. Its passlist is `mixed-a-obs.json`, with `"observer": true`. `mixed-a.json` and its runs are untouched (`RDASHD_OBSERVER=0`, also set for O11's `run`). | DEC-451 (1): in the literal mode, 30 of 39 DTF runner names start no rdashd node. The observer is in `self.nodes`, so every sync, spork, ChainLock and InstantSend wait that iterates the nodes covers it. Without the rejoin, a node-0 restart would strand the observer, and the timeout would be blamed on rdashd. |
| D10 | **The observer's own effects are the harness's.** In the observer variant, a failed `AssertionError` is classed `harness` in two cases. The first is when the innermost test line asserts or waits on a peer count (`getconnectioncount(`, `len(…getpeerinfo())`, `["connections`). The second is when the error is `Error: no RPC connection`, a test calling a node it stopped, which D9's restart should prevent. Other lines that name connections, such as `mine_quorum(expected_connections=…)`, and RPC errors from the count read itself stay divergences. A count wait among masternodes only (`feature_llmq_simplepose`, `feature_llmq_signing`) is also classed `harness` here, rather than `timeout`, although the observer does not change it; that is accepted. The detail stays the test line. The rule covers `AssertionError` only. A test that unpacks or indexes `self.nodes` by count fails with a `ValueError` or `IndexError` once the observer is in the list, and that is classed `divergence` (D4). D9 adapts every such line found at the pin (`feature_llmq_chainlocks_automatic`), so a new one is a harness change to make, not an rdashd verdict. | DEC-451 (1): the observer is one more peer of node 0's, so such an assertion fails because of the variant, not rdashd. Only the failing line is matched, so a quorum failure inside a helper is not hidden. |
| D11 | **BL-392: a changed entry is run again, alone.** After D5's timeout reruns, every test whose entry differs from the committed passlist's runs once more with `--jobs=1`. If the rerun gives the committed entry back, the change was `flaky` and the committed entry stays. Otherwise the rerun's entry stands: `confirmed` if it repeats the first run's, `unstable` if it differs from both. A rerun that starts no rdashd node (D5) is `unconfirmed`, and the first run's entry stands, whatever that entry is, unless the rerun gives back a committed "no rdashd node": then the change is `flaky` (DEC-457, Sol r2 #4). The outcomes go to the run report's `confirm` and are printed. A test the committed file lacks has nothing to confirm against. | One flaky run should not flip the nightly. A test that fails differently on each run is still a change against a pass, so it is reported, not hidden. Both variants and `--update` use it. |
| D12 | **The nightly runs both variants** into `OUT/mixed-a/` and `OUT/mixed-a-obs/`, and exits with the worse of the two (0 same, 1 differs, 2 broken). | One entry point for SB1. |
| D13 | **The observer stays in `self.nodes`, and `DashTestFramework` keeps it node 0's alone (Sol r2 #2, #3).** `connect_nodes` drops a link between the observer and any node but node 0, and makes node 0 dial when a test names the pair either way. `start_nodes` starts the observer, which `num_nodes` does not count, with its own arguments, then rejoins it. `rejoin_rust_observer` (after `start_node(0)`, `start_nodes()` and `reconnect_isolated_node(0, …)`; `start_nodes` also covers masternodes added after the observer) restarts an observer a test stopped, always finishes its mnsync, and connects node 0 to it; when the observer's process has exited while it is still marked running, the test fails (`AssertionError: [node N] the rdashd observer exited with status C`, a divergence and a `possible_crashes` flag) instead of restarting it (`CRASH` matches "the rdashd observer exited"). `stop_nodes` stops it with the rest. A node 0 started with `-connect=0` (`feature_llmq_chainlocks_automatic`'s restart) is meant to stay isolated, so the observer rejoins only when the test reconnects node 0. Audit of the 35 DTF scripts at the pin for calls that build or tear down links: `feature_llmq_chainlocks` (`connect_nodes(i, 1)` over every index) and `feature_llmq_connections` (`connect_nodes(i, 0)` over every index, then `ping()` and a `pingwait` wait on each node, the observer included, which is a fair rdashd check) reach the observer and are handled by the `connect_nodes` rule; every other link-building loop counts to `num_nodes`, which excludes it; `isolate_node`, `disconnect_nodes`, `setnetworkactive` and `addnode` calls name fixed indexes, node 0 or masternodes; every `restart_node(0)` and `stop_nodes` path ends in a rejoin. Loops over `self.nodes` that only query or invalidate (`rpc_net`, `feature_mnehf`, `feature_asset_locks`) reach the observer as any node. An observer that dies while node 0 stays up is noticed at the next rejoin, or as a timeout of the next wait that covers it (and by `RPC_FAILURE` on an RPC to it); its exit message is flagged in `possible_crashes`. Core's `TestRustObserver` covers these over fake nodes. | Taking the observer out of `self.nodes`, as Sol suggested to consider, would keep it out of every node-wide sync, ChainLock and InstantSend wait, and those waits are what make it observe: it would be checked only at setup and at a rejoin. Keeping it in costs these three rules. A dead observer is rdashd's failure, so it is reported, never restarted. Real-node runs of these paths wait for BL-391 (`getnetworkinfo`), which stops every observer at setup today. |

## First passlist

`mixed-a.json` (slice 1) and `mixed-a-obs.json` (slice 2) at this branch's head. The totals and per-class breakdowns are in the commit messages that add them.

At T34 (BL-391 `getnetworkinfo`, BL-394 `addnode`), the observer's setup raced two rdashd gaps: its `mnsync` call (not served yet) and its D18 abort at the first DIP3 block (height 2), which it cannot validate before CH7a. Which came first varied from run to run, so 13 entries flipped between `unimplemented-rpc mnsync`, `divergence` and `harness`. DEC-483's `allowed-diff D18` (D4) made 27 of the 30 observer entries the same in 3 runs: 22 are now `allowed-diff D18`. The other 3 (`feature_governance_objects.py`, `feature_llmq_evo.py`, `feature_llmq_is_retroactive.py`) still race, because the observer is at times stopped before it reaches block 2 and so logs no refusal; they were held at `unimplemented-rpc mnsync`, the class they take without it. On rc.4 (DEC-488), the observer syncs blocks before its `mnsync`, so it always reaches block 2 first: all 25 such entries are `allowed-diff D18`, the same in 3 runs.

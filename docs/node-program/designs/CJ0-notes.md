# CJ0: implementation D-rows

CJ0 (PLAN: `dash-coinjoin` pure: shared validation, session state machines, rounds;
`is_collateral_valid` as a trait that `dashd-coinjoin` implements; FR-CJS-02/05, FR-CJC-02/04)
has no design document. These rows record the implementer's decisions. Core references are to
`v24.0.0-rc.3`. The pinned oracle commit `e610a33e64` has the same `src/coinjoin/`, `src/wallet/coinjoin.cpp`,
`src/masternode/meta.cpp` and the CoinJoin parts of `src/net_processing.cpp`. Every public item in
the crate names its Core function in a `// Core: file:line` comment.

## What the crate is

| Module | Core | What |
|---|---|---|
| `denom` | `coinjoin/common.{h,cpp}`, `coinjoin.h:228` | denominations, collateral amounts, `CalculateAmountPriority`, `MixShape`/`MixSideCounts`, adjacency, `ShouldPromote/DemoteDenoms` |
| `pool` | `coinjoin.h:65-107`, `coinjoin.cpp:237,505` | timeouts, `PoolMessage` (with `GetMessageByID`), `PoolState`, `PoolStatusUpdate`, the `dsa` flag predicates over BS9b's `DsAccept` |
| `inouts` | `coinjoin.cpp:264,654,705,755` | `IsValidInOuts` (entry and final transaction), promotion/demotion entry checks, `ValidateFinalTxComposition`; the coins view trait |
| `collateral` | `coinjoin.cpp:439,458` | `IsCollateralValid`, `ATMPIfSaneFee`'s test-accept half; the `MempoolAccept` trait |
| `queue` | `coinjoin.cpp:49-230`, `server.cpp:129`, `walletman.cpp:243`, `meta.cpp:93-124` | queue bounds and signatures, `CoinJoinQueueManager`, the mixing counters of `CMasternodeMetaMan`, both sides' `dsq` handling |
| `dstx` | `coinjoin.cpp:82-130,583-640`, `net_processing.cpp:3612,3637` | `IsValidStructure`, DSTX signature and expiry, `CDSTXManager` (pure), `ValidateDSTX`, `CanAnnounceDstxTo` |
| `relay` | `net_processing.cpp:2555,2652,2976,4485,6635` | `senddsq`, `RelayDSQ`, the `MSG_DSTX`/`MSG_TX` choice for relay, announcement and `getdata` |
| `server` | `coinjoin/server.cpp` | `CCoinJoinServer`'s session: `dsa`, `dsi`, `dss`, final transaction, fees, timeouts |
| `client` | `coinjoin/client.cpp:127,304,414,464,634` | the client session's transitions and `SignFinalTransaction`'s checks |
| `rounds` | `wallet/coinjoin.cpp:261-420` | `GetRealOutpointCoinJoinRounds`, capped rounds, `IsFullyMixed` |

The node supplies the clock, randomness, chain, coins, mempool, masternode list, InstantSend
locks and the operator key through traits (`CoinView`, `MempoolAccept`, `TipMasternodes`,
`DstxChain`, `ServerEnv`, `ClientQueueSessions`, `RoundsWallet`). Side effects come back as values
(`ServerEffect`, `DsqOutcome`, `DstxValidation`, the client outcomes) that the caller carries out
in order.

## D-rows

| D | Decision | Why |
|---|---|---|
| D1 | `dash-coinjoin` is layer **Pn** (pure, node-only) in `layers.toml`, in the `node-pure` CI group. Its dependencies are base-sdk (B) and `dash-consensus` (P) only. | The PLAN row puts it in the pure node crates. **Conflict to resolve (F1):** FR-CJC-04 and SW-DESK expect the desktop wallet (U-06) and WL6 to use the client side. W may depend only on B, P and W, and L6 bans every Pn crate from the mobile closure. If key-wallet, the FFI or the desktop wallet takes the crate, it has to be P. Every dependency is already B or P, so the change is one `layers.toml` line plus an SB0 amendment, with no code change. |
| D2 | `is_collateral_valid` is generic over `CoinView + MempoolAccept`. `MempoolAccept::test_accept` is Core's `ProcessTransaction(tx, test_accept=true)` and returns the base fee. `dashd-coinjoin` implements it over the mempool (CJ1, m-16). The fee cap (`test_accept_if_sane_fee`) is applied here. | This is the PLAN's trait boundary. The submitting half of `ATMPIfSaneFee` is the node's, and the server asks for it through `ServerEnv::commit_to_mempool` and `ServerEffect::ConsumeCollateral`. |
| D3 | Reuse: the wire types are BS9b's (`dash_p2p_core::{DsAccept, DsEntry, DsQueue, DsTx, DsStatusUpdate, DsComplete, DsSignedInputs}` and their `signature_hash`, plus `COINJOIN_ENTRY_MAX_SIZE` and the protocol versions). BLS is `dash_pkc::bls::core::verify_insecure`, scripts are `dash-consensus`, and the pool sizes are `dash-params`. key-wallet has nothing to reuse: its only CoinJoin code is a classification heuristic with a private denomination list (`transaction_router/mod.rs`). | The brief says to reuse and not duplicate. Neither key-wallet nor base-sdk has rules, sessions or rounds. Replacing key-wallet's list with `dash_coinjoin::denom` waits for F1, because W cannot depend on Pn. |
| D4 | Vectors: `tests/data/core_common.json` comes from `contrib/node/cj0-vectors/gen_common.cpp`, which is compiled against the pinned Core's `src/` and runs Core's own `constexpr` functions in `coinjoin/common.h` over a fixed grid. `core_amount_strings.json` is the pinned dashd's `decoderawtransaction` of each denomination. `core_fully_mixed.json` comes from `gen_fully_mixed.cpp`, which runs `IsFullyMixed`'s hashing lines (`wallet/coinjoin.cpp:416-420`, copied; `regen.sh` refuses to run if the pinned file no longer has them) over Core's `CDataStream`, `COutPoint`/`uint256` serialisation, `CSHA256` (`crypto/sha256.cpp`, compiled) and `ReadLE64`, for a grid of outpoints and salts. `regen.sh` regenerates all three, and each file carries its provenance. Core's CoinJoin unit tests (`coinjoin_queue_tests`, `coinjoin_dstxmanager_tests`, `coinjoin_inouts_tests`, and the rounds cases of `wallet/test/coinjoin_tests`) are ported case by case in `tests/core_ports.rs` and `tests/sessions.rs`. Each test names its Core file and line. | Fixtures come from Core and are never hand-written. The ported tests carry Core's own expectations. |
| D5 | **No oracle entry in CJ0. `diff_coinjoin` is follow-up O2a-CJ (F2) at ABI 20.** | The L1 acceptance needs Core's verdicts on generated inputs, and that means a Core-side shim entry (`oracle_coinjoin_*`). The brief allows recording it as follow-up row O2a-CJ. The coordinator assigned ABI 20, on a branch from `node/train-14-oracle-v24.0`, additive. Until it lands, the evidence is D4's vectors and ports. |
| D6 | P6a hand-off: the relay rules are functions in `relay` and `dstx` (`wants_dsq_after_senddsq`, `dsq_relay`, `relay_inv_kind`, `announce_inv_kind`, `dstx_for_getdata`, `can_announce_dstx_to`, `validate_dstx`, `DstxScore`, and for `MSG_DSQ` `QueueManager::{has_queue, queue_from_hash}`), each tested in `tests/relay_rules.rs`. P6a calls them from its peer manager and owns the per-peer `WantsDsq` state, the inventory queues, object requests, misbehaviour, and `PrioritiseTransaction` with `DstxValidation::Continue::priority_delta`. The `p2p_dstx` relay part of the acceptance runs in P6a, against these functions. | P6a has not started. The brief asks for the rule functions with their tests, and for this hand-off recorded as a D-row. |
| D7 | Core's locks, `TRY_LOCK` variants and their re-checks become single calls. Each handler runs to completion on state the caller owns (`&mut`). `TryHasQueueFromMasternode` and `TryCheckDuplicate` always answer. | The crate is pure: no threads and no locks. Core re-checks state because its scheduler thread can interleave with message handling. Here the caller serialises, so the re-checks are kept as the same predicates (for example, `CreateFinalTransaction` still re-checks live side coverage), but the interleavings they guard cannot occur. The Core tests that seed such an interleaving are ported as the nearest sequence that reaches the same state (`tests/sessions.rs`). |
| D8 | A `dsq` or DSTX read from the wire carries the masternode's ProRegTx hash and no outpoint. The masternode is looked up by ProRegTx hash, and its collateral is filled in from the list. Core then looks it up a second time by that collateral in the same list, which finds the same masternode, so that step is folded. | v24's BS9b types have no outpoint field. The outpoint-only branches of `ValidateDSTX` and `ProcessDSQUEUE` are unreachable from the wire. |
| D9 | `BlsVerdict::Unsupported` is neither valid nor the sender's fault. A queue is `Ignored`, a DSTX is `Stop(None)`, and nobody is penalised. At the base-sdk pin (8382b76, `pkgs/pkc/src/bls/core.rs:77-87,176-179`) `verify_insecure` answers `Unsupported` only for the legacy scheme, and CoinJoin always verifies with the basic one (`coinjoin.cpp:51,84`), so these branches are unreachable today. They are kept because the verdict is part of base-sdk's API. | This avoids banning a peer over a gap in our own BLS. Core would decide, but we cannot know which way. |
| D10 | BIP69 sorting uses Rust's stable sort with Core's comparators. Core's input comparator compares the reversed hash bytes, then the index. Its output comparator compares the value, then `prevector`'s `<`: length first, then bytes. | Core's `std::sort` is unstable. Equal outputs are byte-identical, and equal inputs share a prevout, so for any transaction without a repeated prevout every sort gives the same transaction. The client checks the order with `is_sorted_by` (equivalent to "a stable sort changes nothing"). A repeated prevout is refused either way: Core's `IsValidInOuts` rejects it as a duplicate script (`coinjoin.cpp:350`), and the client's action on both refusals is the same (`client.cpp:489-494` and `:500-506`). |
| D11 | `ChargeFees` picks one uniformly random offender where Core shuffles the list and charges the first. `ChargeRandomFees` keeps Core's per-collateral `GetRand(100) > 10` loop, which stops at the first collateral it spares. The draw order follows Core's: the session id, then `ChargeFees`' 33% gate, then its "nearly all" gate, then the pick. Core makes the pick with a separate `FastRandomContext` (`Shuffle(..., FastRandomContext())`, `server.cpp:530`), not `GetRand`; the port takes one extra `rand_below` draw from the same environment instead, so the two RNG streams do not line up past the gates. | The distribution is the same and the randomness is the node's. Fees are not consensus, so the exact draws need not match Core's RNG stream. |
| D12 | `is_collateral_valid` holds each output, each input coin and both running sums to `MoneyRange` itself, in the loops where Core's `IsCollateralValid` only sums (Core's checks are ATMP's: `consensus/tx_check.cpp:38-45`, `consensus/tx_verify.cpp:188-191`). The sums cannot overflow, whatever `MempoolAccept` does. | Overflow is undefined behaviour in Core's sums. Such a transaction fails Core's test-accept, so the verdict is the same `false`, reached earlier and without relying on the trait impl's range checks. |
| D13 | The rounds cache (`RoundsCache`) does not memoise an unknown transaction (`UNKNOWN_TX`), and it does memoise `IN_PROGRESS` while recursing, as Core does. The wallet clears it when its transactions change. The coin flip in `IsFullyMixed` hashes `outpoint ‖ salt` with SHA-256 and reads the first 8 bytes as a little-endian integer. | This matches `wallet/coinjoin.cpp:261-420`, including the recent fix that stops a miss from being memoised. |
| D14 | Scope against CJ1 and WL6: CJ0 has no I/O, scheduler, persistence, wallet keys or coin selection. CJ1 (`dashd-coinjoin`) wraps `ServerSession`, `DstxManager` and the counters with the node's runtime, and persists the counters (`mncache.dat`). WL6 drives `ClientSession` and owns selection, signing, keys, `dsa` creation and the queue strategy. It calls the session's transitions at Core's points: `enter_queue` (`JoinExistingQueue`/`StartNewQueue`, `client.cpp:1453,1543,1626`), `dsa_sent` (`ProcessPendingDsaRequest`, `:1672`), `entry_sent` (`SendDenominate`, `:378-408`), `signed`, and the handlers for `dssu`, `dsf`, `dsc` and the timeout, so every timestamp that drives `check_timeout` is set here. `FinalTxOutcome::Sign` names the inputs to sign with `SIGHASH_ALL\|ANYONECANPAY`. | This keeps the crate pure and reusable from the desktop wallet (D1). |
| D15 | The server checks a `dss` script against the pooled input's `prevPubKey`, exactly as Core does. For entries read from the wire, `prevPubKey` is empty in Core too. The port keeps Core's behaviour bit for bit (possible security note: see manager). | Parity. The details are with the manager. |
| D16 | The masternode has one queue manager, in `ServerSession`. Received queues go through `ServerSession::process_dsq` (Core's `ProcessDSQUEUE`), which checks for duplicates against, and adds to, the same manager that holds the masternode's own queues. So a session reset clears received queues (`server.cpp:296`), `check_timeout` prunes them (`:626`), and a kept queue of this masternode's answers a `dsa` with ERR_RECENT (`:92`). The free `server_process_dsq` is crate-private. | Core has one `m_queueman` (`server.h:35`). A separate manager would keep refusing a fresh `dsq` after a reset, and would miss ERR_RECENT. Found in review; tested in `sessions.rs::server_dsq_shares_the_session_queue_manager`. |
| D17 | **SB0 amendment: `dash-coinjoin` is layer P**, not Pn (manager ruling on F1, 2026-10-16; the DEC row is the manager's). It supersedes D1's layer. `layers.toml` lists it under P and the `node-pure` group keeps it. Its normal dependencies are B (base-sdk) and P (`dash-consensus`) only, which P allows, and it passes check-pure, check-layers and check-mobile as P. Layer P does not make the client rules usable from an SPV wallet as they stand: the client's final-transaction check and `is_collateral_valid` need a full-node `CoinView` (including the other participants' inputs) and a mempool test-accept (`MempoolAccept`). A mobile SPV wallet cannot provide either, so it would refuse every final transaction. WL6 decides whether the wallet supplies them (for example from a trusted node) or records a deviation. | WL6, the mobile wallet (where CoinJoin users are) and the desktop wallet (U-06) need the client rules. W and the mobile closure may depend on P but not on Pn (L2, L6). |
| D18 | **CJ0 has no Core shim branch and no oracle commits.** Train 15 lists CJ0 as oracle rider ABI 20, but that ABI is reserved for follow-up O2a-CJ (D5, F2), which is not built. So CJ0 follow-merges node/integration 657a28c28 only, not `node/t15-oracle`, and moves no pins. Whoever builds O2a-CJ supplies its own shim branch then. | The branch touches no oracle file (`dash-oracle-sys`, the shim or `pins.txt`). Merging the bundle would tie CJ0's gate to an unrelated rider. |

## Follow-ups

- **F1 (layer).** Closed by D17: `dash-coinjoin` is P. key-wallet's heuristic denomination list can now use `dash_coinjoin::denom` (a W follow-up).
- **F2 (O2a-CJ, ABI 20).** Add the oracle entries for `diff_coinjoin`, branched from `node/train-14-oracle-v24.0` and additive. There are three groups:
  - The pure functions over generated inputs: `IsValidStructure` (both rule sets), `IsValidInOuts` and the promotion/demotion and composition checks (with a coins view from the harness), `IsCollateralValid` (with a test-accept fee), the queue and DSTX signature hashes and verdicts, and `IsTimeOutOfBounds`.
  - The rounds over a harness wallet.
  - A session replay: a `CCoinJoinServer` driven through `dsa`/`dsi`/`dss` with a recorded RNG. `ChargeFees`' offender pick comes from its own `FastRandomContext` (D11), so the replay must record that pick separately from the `GetRand` draws and feed it to the port's extra `rand_below`.
  The node-l1 test `l1_coinjoin` then diffs `dash-coinjoin` against them.
  Group 1 is O2a-CJ1 (ABI 26 as installed in the train-17 bundle; reserved 20, built as 27, under DEC-238, `O2a-CJ1-notes.md`); groups 2 and 3 are O2a-CJ2.
- **F3 (P6a).** Wire D6's functions into the peer manager and run `p2p_dstx`'s relay part.
- **F4 (CJ1).** `ServerEnv` over the node: `commit_to_mempool` is `PrioritiseTransaction(txid, 0.1 COIN)` followed by `ATMPIfSaneFee`, `has_dstx` reads the DSTX manager, and `ServerEffect::AddDstx` and `RelayDstxInv` are carried out in order. `DstxManager::check` runs on `UpdatedBlockTip` and `NotifyChainLock`, and `update_confirmed_height` runs on mempool entry, block connect and block disconnect.
- **F5 (dash-consensus).** Move `inouts::is_pay_to_public_key_hash` (Core's `CScript::IsPayToPublicKeyHash`) next to `dash_consensus::script::is_pay_to_script_hash` and use it from there. It stays local in CJ0 so as not to change a crate other trains build on.

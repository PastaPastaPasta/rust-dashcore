# O9b S6a notes: the `EvoSnapshot` codec

These rows continue O9b-notes' decision log (D1–D16 are on `node/o9b`). They move into O9b-notes
with S6a-2. The parity reference is Core v24.0.0-rc.4. Its `evo/snapshot.{h,cpp}` are byte-identical
to rc.3's.

| # | Decision | Why |
|---|---|---|
| D17 | **Crate and scope.** `dash_dml::snapshot` ports `evo::EvoSnapshot` in full: the encoder, the bounded decoder, `Validate` with `ReconstructHistoricalMNLists` and `CDeterministicMNList::ApplyDiffForSnapshot`, and `GetEvoSnapshotHash` (`EvoSnapshot::hash`). It reuses dash-dml's canonical MN-list and diff codecs, which were already Core's (`codec.rs`), and splits `ValidateCanonicalMNInvariants` and `ValidateMNEncoding` out of the storage encoder. No new dependency edge. Building a snapshot from the node's state is S6b, and the bundle `--evo` wiring is S6a-2. | Core's `Unserialize` ends in `Validate(true)`, which replays the history (`snapshot.h:719`, `snapshot.cpp:263-267`). A Core-exact decoder therefore needs the replay, so reconstruction is in S6a, not S6a-r (manager, 10-29). dash-dml already owns every type the snapshot holds, and dash-evo can't name them. |
| D18 | **The decode domain.** Every refusal is the `what()` of the `std::ios_base::failure` Core throws; Core throws nothing else on this path. The LLMQ bounds come from Core's static table (`AVAILABLE_LLMQS`, as `SnapshotLLMQParams` reads it, `snapshot.h:104`), never the running chain's overrides. Masternode network info is checked with the caller's `NetInfoValidity` (Core's `netInfo->Validate()` under `Params()`). | Snapshot bytes are untrusted input. A decoder more lenient than Core's would accept what Core refuses, and a stricter one would refuse Core's own snapshots (but see D20). |
| D19 | **Vectors and verdicts come from Core.** `contrib/node/o9b-evo-snapshot` builds a fresh, blob-verified rc.4 `test_dash` and links one more file, with `evo_snapshot_tests.cpp`'s fixtures verbatim, into a copy of it. Dump mode gives 26 vectors, including Core's `populated_v3_golden_value` hash. Judge mode gives Core's verdict on 142 crafted inputs: every decode bound at its limit and one past it, the replay's record budget (kind `reconstruct:<budget>`, on the populated snapshot), and Validate's matrix, including each term of the diff chain's check alone. The inputs are defined once, in `crafted()`, and checked by kind and hash; the corpus is in `dash-dml/tests/data/evo_snapshot` with its PROVENANCE.md. Every vector and verdict matches, except the D20–D22 cases, which are compared as those rows say. | Only Core's code decides what a valid snapshot is. Core's own fixture has identical historical lists, so its `mndiff_*` vectors are all the same empty diff; the crafted cases carry the diff decoding. |
| D20 | **A deliberately stricter domain.** dash-dml refuses a masternode state holding a field its version can't store, as `MnCold::version_hidden_field` defines it (EV2a D17). Core accepts a snapshot whose diff gives one: the field is invisible to its serializer, and so to every hash. Crafted case `history_update_hidden_port` gives a version-3 masternode a platform port; Core says `ok`, dash-dml says `… cannot store its platformP2PPort`, and `stricter_domain_refuses_what_core_accepts` pins both verdicts. The refusal comes first in `add_mn`, so on an input Core also refuses for a later reason (a hidden port and a duplicate key, say) the two texts differ; that is the same divergence. **No real Core node can produce such a snapshot.** A snapshot's base list and its additions come through the canonical reader, which only reads what the version stores. Each replayed state is a state Core wrote: `CDeterministicMNStateDiff(a, b)` captures every differing member (`dmnstate.h:250-283`), with `netInfo` compared deeply and by type (`util/helpers.h:40-46`, `netinfo.h:306`) and the operator key captured on any scheme change (`dmnstate.h:266-267`), and it serializes every masked field whatever the version (`:290-316`). And no rc.4 write site leaves a state outside the domain:<ul><li>Post-v24 targets are `max(old, payload)`: ProUpServ `specialtxman.cpp:114`, `:488`, ProUpReg `:538-539`, ProUpRev `:602-606`; ProUpSharedReg restores the old version, `:675`.</li><li>An upward `SetStateVersion` moves `scriptPayout` into `payouts` and clears the platform ports (`:57-60`, `:96-97`), and re-encodes the operator key under the target's scheme (`:68-71`).</li><li>ProUpReg sets exactly one of `payouts` and `scriptPayout` for the target version (`:570-577`). ProUpServ clears the scalar ports from ExtAddr (`:126-134`).</li><li>`ResetOperatorFields` (`dmnstate.h:127-135`) leaves the default key and a version-1 netInfo. Pre-v24 it can only go from v2 to v1, where nothing is hidden, since ExtAddr payloads are refused before v24.</li><li>The payload readers read only what their version stores (`providertx.h:178-218`).</li></ul> | A refusal of valid Core data would not be acceptable. This one is reachable only by crafted input, where refusing is safe and keeps one state domain for the list type everywhere (EV2a D17). |
| D21 | **AddMN key text.** For four AddMN refusals, Core prints the key's value, and dash-dml's messages leave it out (`MnListError::core_message`). The verdict test drops only the value (everything after the `=`) from Core's text; the rest must match exactly. The four messages: `… with a duplicate keyIDOwner=<Base58>`, `… duplicate share ownerKeyID=<Base58>`, `… duplicate pubKeyOperator=<key>`, `… duplicate platformNodeID=<hex>`. `mnlist_duplicate_owner` covers the first. Collateral (`mnlist_duplicate_collateral`) and address messages match in full. | Manager ruling 1 (10-29). The values are log text; the refusal and its reason are what must agree. |
| D22 | **Update order.** `ApplyDiffForSnapshot` walks `updatedMNs`, an `unordered_map` with a salted hasher, filled in ascending id order (`deterministicmns.cpp:418-435`). That order decides which refusal Core reports when several updates fail, and which masternode an AddMN refusal names when two updates collide. libstdc++ puts a node inserted into an empty bucket at the front, so absent bucket collisions and rehashes Core walks the updates in descending order; dash-dml applies them in descending order. Inputs whose text depends on that order (`CLASS_ONLY`: `history_updates_two_missing`, `history_updates_duplicate_owner`) compare only accepted versus refused. Single-failure cases (`history_update_missing_id`) stay exact. | Manager ruling 3 (10-29), extended to the colliding-update case the review found (S6a r1). Core's order is not deterministic across processes (the salt) or for larger maps (rehashing), so no order can always match it; descending matches it for small maps. |
| D23 | **Messages after two normalizations.** libstdc++'s `ios_base::failure` appends `: iostream error` to `what()`, twice where `Validate` rethrows a replay error (`snapshot.cpp:266`). Core's end-of-data text names its stream (`DataStream::read(): end of data`). The test strips the suffix, however many times it appears, and reads that text as `end of data`. So it can't tell a replay refusal from a Validate refusal with the same text: three checks (the hash-prefix run, the internal id over the counter, the nested-collection rules) run in both. The input is refused with the same reason either way. dash-dml's codec now renders read errors with Core's text (`ReadErrorKind`'s `Display`), where it used to print their debug names. | Mechanical; no information is lost. |
| D24 | **One mutant per bound and per check.** `contrib/node/o9b-evo-snapshot/mutants.py` patches 41 env-gated mutants (`O9B_MUT=<name>`) into a reflink copy, never the worktree. Each loosens one bound by one, drops one check, or (`-T`) tightens a bound by one. Each fails the named test, which is `crafted_verdicts_match_core` on the named case unless it says otherwise:<ul><li>Decode counts: M-QTYPES `quorum_count_over`, M-HISTORY `history_count_over`, M-MODIFIERS `modifier_count_over`, M-RANGES `ranges_over`, M-SIGNALS `signals_over`.</li><li>Commitments: M-SIGNERS `commitment_signers_over`, M-SIGNERS-T `commitment_signers_at_limit`, M-VALID `commitment_valid_members_over`, M-VALID-T `commitment_full_size`, M-ACTIVE `active_over`, M-SAFETY `safety_over`, M-INDEX `commitment_index_out_of_range`.</li><li>`ReadFixedBitSet`: M-BITSET-REMAIN (remaining-bytes check dropped) `commitment_signers_at_limit`, M-PADDING `commitment_padding_bit`.</li><li>Rotation: M-ROTSNAPS `rotation_snapshots_over`, M-SNAPCOUNT `rotation_snapshot_on_plain_type`, M-ROTBITS `rotation_bitset_over`, M-SKIP `rotation_skip_list_over`, M-ROTFLAG `quorum_rotation_flag_2`, M-ROTORDER `rotation_snapshots_swapped`, M-ROTWORK `rotation_work_not_a_target`. M-CYCLEDUP is killed by `validate_refuses_constructed_repeated_cycle`.</li><li>History chain, one term each: M-CHAIN-PREV `history_previous_unlinked`, M-CHAIN-NULL `history_target_null`, M-CHAIN-BASE `history_target_is_base`, M-CHAIN-REPEAT `history_target_repeated`, M-CHAIN-NEGATIVE `history_height_negative`, M-CHAIN-LISTHASH `history_list_hash_null`.</li><li>History budgets and replay: M-OPS `history_operations_over_budget`, M-RECORDS `reconstruct_over_record_budget`, M-REUSE `history_addition_reuses_identity`, M-POSTINV `history_addition_over_counter`, M-POSTENC `history_update_over_budget`.</li><li>Masternode lists and diffs: M-MNSECTION `mn_count_over`, M-MNBUDGET `mnlist_script_over_budget`, M-PREFIX `mnlist_prefix_run_over`, M-PAYOUTS `mnlist_payouts_over`, M-ADDORDER `mndiff_additions_descending`, M-ADDORDER-EQ `mndiff_addition_id_repeated`.</li><li>Validate: M-SIGNAL-BIT `signal_bit_29`. M-SIGNERS-V, Validate's own commitment-size ceiling, is killed by `validate_bounds_constructed_commitment_sizes`.</li></ul>With no mutant, the whole dash-dml lib suite passes (217 tests). | The manager's rule: one refusal test per bound, with a named mutant it kills; the S6a r1 review added each Validate and replay check. Two checks repeat others that decoded input meets first: Validate's commitment-size ceiling (the decode bounds) and a repeated rotation cycle (strict canonical order). Constructed snapshots reach them, since `validate` is public; Core's tests reach neither. The record budget's 8,000,000 is cited from Core (`snapshot.h:84`), not crafted: a Core-judged case at it needs about 160 replays of a 50,000-masternode list. |

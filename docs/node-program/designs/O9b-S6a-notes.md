# O9b S6a notes: the `EvoSnapshot` codec

These rows continue O9b-notes' decision log (D1–D16 are on `node/o9b`). They move into O9b-notes
with S6a-2. D25–D27 are S6b-0's: the two pure helpers beside the codec (DEC-746). The parity
reference is Core v24.0.0-rc.4. Its `evo/snapshot.{h,cpp}` are byte-identical
to rc.3's.

| # | Decision | Why |
|---|---|---|
| D17 | **Crate and scope.** `dash_dml::snapshot` ports `evo::EvoSnapshot` in full: the encoder, the bounded decoder, `Validate` with `ReconstructHistoricalMNLists` and `CDeterministicMNList::ApplyDiffForSnapshot`, and `GetEvoSnapshotHash` (`EvoSnapshot::hash`). It reuses dash-dml's canonical MN-list and diff codecs, which were already Core's (`codec.rs`), and splits `ValidateCanonicalMNInvariants` and `ValidateMNEncoding` out of the storage encoder. No new dependency edge. Building a snapshot from the node's state is S6b, and the bundle `--evo` wiring is S6a-2. | Core's `Unserialize` ends in `Validate(true)`, which replays the history (`snapshot.h:719`, `snapshot.cpp:263-267`). A Core-exact decoder therefore needs the replay, so reconstruction is in S6a, not S6a-r (manager, 10-29). dash-dml already owns every type the snapshot holds, and dash-evo can't name them. |
| D18 | **The decode domain.** Every refusal is the `what()` of the `std::ios_base::failure` Core throws; Core throws nothing else on this path. The LLMQ bounds come from Core's static table (`AVAILABLE_LLMQS`, as `SnapshotLLMQParams` reads it, `snapshot.h:104`), never the running chain's overrides. Masternode network info is checked with the caller's `NetInfoValidity` (Core's `netInfo->Validate()` under `Params()`). | Snapshot bytes are untrusted input. A decoder more lenient than Core's would accept what Core refuses, and a stricter one would refuse Core's own snapshots (but see D20). |
| D19 | **Vectors and verdicts come from Core.** `contrib/node/o9b-evo-snapshot` builds a fresh, blob-verified rc.4 `test_dash` and links one more file, with `evo_snapshot_tests.cpp`'s fixtures verbatim, into a copy of it. Dump mode gives 26 vectors, including Core's `populated_v3_golden_value` hash. Judge mode gives Core's verdict on 145 crafted inputs: every decode bound at its limit and one past it, the replay's record budget (kind `reconstruct:<budget>`, on the populated snapshot), its 8,000,000 constant (80 and 81 zero-operation diffs over 100,000 masternodes, `record_budget_cases()`, about 20 MB each, so checked by an ignored test in release), and Validate's matrix, including each term of the diff chain's check alone. The inputs are defined once, in `crafted()`, and checked by kind and hash; the corpus is in `dash-dml/tests/data/evo_snapshot` with its PROVENANCE.md. Every vector and verdict matches, except the D20–D22 cases, which are compared as those rows say. | Only Core's code decides what a valid snapshot is. Core's own fixture has identical historical lists, so its `mndiff_*` vectors are all the same empty diff; the crafted cases carry the diff decoding. |
| D20 | **A deliberately stricter domain.** dash-dml refuses a masternode state holding a field its version can't store, as `MnCold::version_hidden_field` defines it (EV2a D17). Core accepts a snapshot whose diff gives one: the field is invisible to its serializer, and so to every hash. Crafted case `history_update_hidden_port` gives a version-3 masternode a platform port; Core says `ok`, dash-dml says `… cannot store its platformP2PPort`, and `stricter_domain_refuses_what_core_accepts` pins both verdicts. The refusal comes first in `add_mn`, so on an input Core also refuses for a later reason (a hidden port and a duplicate key, say) the two texts differ; that is the same divergence. **No real Core node can produce such a snapshot.** A snapshot's base list and its additions come through the canonical reader, which only reads what the version stores. Each replayed state is a state Core wrote: `CDeterministicMNStateDiff(a, b)` captures every differing member (`dmnstate.h:250-283`), with `netInfo` compared deeply and by type (`util/helpers.h:40-46`, `netinfo.h:306`) and the operator key captured on any scheme change (`dmnstate.h:266-267`), and it serializes every masked field whatever the version (`:290-316`). And no rc.4 write site leaves a state outside the domain:<ul><li>Post-v24 targets are `max(old, payload)`: ProUpServ `specialtxman.cpp:114`, `:488`, ProUpReg `:538-539`, ProUpRev `:602-606`; ProUpSharedReg restores the old version, `:675`.</li><li>An upward `SetStateVersion` moves `scriptPayout` into `payouts` and clears the platform ports (`:57-60`, `:96-97`), and re-encodes the operator key under the target's scheme (`:68-71`).</li><li>ProUpReg sets exactly one of `payouts` and `scriptPayout` for the target version (`:570-577`). ProUpServ clears the scalar ports from ExtAddr (`:126-134`).</li><li>`ResetOperatorFields` (`dmnstate.h:127-135`) leaves the default key and a version-1 netInfo. Pre-v24 it can only go from v2 to v1, where nothing is hidden, since ExtAddr payloads are refused before v24.</li><li>The payload readers read only what their version stores (`providertx.h:178-218`).</li></ul> | A refusal of valid Core data would not be acceptable. This one is reachable only by crafted input, where refusing is safe and keeps one state domain for the list type everywhere (EV2a D17). |
| D21 | **AddMN key text.** For four AddMN refusals, Core prints the key's value, and dash-dml's messages leave it out (`MnListError::core_message`). The verdict test drops only the value (everything after the `=`) from Core's text; the rest must match exactly. The four messages: `… with a duplicate keyIDOwner=<Base58>`, `… duplicate share ownerKeyID=<Base58>`, `… duplicate pubKeyOperator=<key>`, `… duplicate platformNodeID=<hex>`. `mnlist_duplicate_owner` covers the first. Collateral (`mnlist_duplicate_collateral`) and address messages match in full. | Manager ruling 1 (10-29). The values are log text; the refusal and its reason are what must agree. |
| D22 | **Update order.** Core keeps a diff's updates in `updatedMNs`, a `std::unordered_map` with `StaticSaltedHasher` (`deterministicmns.h:635`), whose salt changes with every process (`saltedhasher.cpp:8-10`). The decoder fills it with `emplace` in ascending id order (`snapshot.h:362-368`); `CanonicallySortedCopy` copies and moves it before the replay (`snapshot.h:552-557`, `snapshot.cpp:167`), and libstdc++'s copy and move keep node order. `ApplyDiffForSnapshot` walks it (`deterministicmns.cpp:420`), as do the two encoding loops around the apply (`snapshot.cpp:199`, `:204`). libstdc++ links each new node directly after its bucket's "before" node, and the map has 13 buckets until its 14th element. So:<ul><li>Up to two updates are always walked in descending order, whatever the salt.</li><li>From three to 13, descending unless ids share a bucket mod 13, which the salt decides.</li><li>From 14, the map rehashes.</li></ul>The order decides which refusal Core reports when several updates fail, and which masternode an AddMN refusal names when two updates collide. dash-dml walks updates in descending order in all three loops. `history_updates_two_missing` (`id=4`) and `history_updates_duplicate_owner` compare exactly, and the M-ORDER mutant (ascending) fails them. `history_updates_three_missing` is the one `CLASS_ONLY` input; it compares only accepted versus refused. Single-failure cases (`history_update_missing_id`) stay exact. The oracle is the libstdc++ Linux build. libc++'s copy constructor likely re-inserts in iteration order, which would reverse a two-update map, so a macOS Core could report `id=3`; that is not verified (no libc++ here). | Manager ruling 3 (10-29), narrowed in S6a r1 (DEC-731): Opus-h's probe (g++ 15.2.0, 20,000 salts) found one walk order for two updates and two for three, and 40 judge processes gave the recorded verdicts. |
| D23 | **Messages after two normalizations.** libstdc++'s `ios_base::failure` appends `: iostream error` to `what()`, twice where `Validate` rethrows a replay error (`snapshot.cpp:266`). Core's end-of-data text names its stream (`DataStream::read(): end of data`). The test strips the suffix, however many times it appears, and reads that text as `end of data`. So it can't tell a replay refusal from a Validate refusal with the same text: three checks (the hash-prefix run, the internal id over the counter, the nested-collection rules) run in both. The input is refused with the same reason either way. dash-dml's codec now renders read errors with Core's text (`ReadErrorKind`'s `Display`), where it used to print their debug names. | Mechanical; no information is lost. |

| D25 | **`reconstruction_heights` is `EvoSnapshotReconstructionHeights` (`snapshot.cpp` rc.4:128-148), except where Core's arithmetic overflows.** For each type, in the caller's order: a negative base refuses with "invalid reconstruction base height" (:131); a DKG interval or active count of 0 or less refuses with "invalid reconstruction LLMQ parameters" (:135-137); `H` = the base rounded down to the interval; a rotated type gives H-C..H-4C, any other `SnapshotCommitmentCount(params, false)` heights from H; each work height is `WORK_DIFF_DEPTH` (8) below. Heights below genesis are kept, as in Core. Core computes `h - i * dkgInterval` and `- WORK_DIFF_DEPTH` in `int`. For an interval whose multiple, or that multiple's work height, leaves `int`, which is undefined behaviour there, ours refuses with the parameters text. `h - back` itself can't overflow, since both are non-negative. Core throws `std::invalid_argument` here, not `ios_base::failure`; `CodecError` carries the text alone. | No table interval comes close to overflow; refusing is the defined answer where Core has none. S6b-1 calls it with the chain's enabled types. |
| D26 | **`EvoSnapshot::verify_cbtx` is `VerifyEvoSnapshotCbTx` (`snapshot.cpp` rc.4:349-382), in Core's order.** `validate(false)`, its text passed through; then the CbTx height against the list's (`GetHeightForSnapshotCodec`); then `merkleRootMNList` against the list's simplified-list root (`merkle_root_mn_list_full`, EV4-serve's `CalcCbTxMerkleRootMNList` reference); from CbTx version 2, `merkleRootQuorums` against the root of every type's active commitments' `SerializeHash`, byte-sorted (`merkle_root_quorums_from_hashes`); from version 3, the balance against the pool's `locked`. A field the CbTx's version lacks reads as zero, which is what Core's struct holds. Each root's "mutated" arm (`mutated \|\| root != …`) is kept as Core has it, but nothing past `validate` reaches it: the simplified list's leaves are distinct entries keyed by distinct proTxHashes, and two equal commitment hashes would need two commitments with one quorum base, which `validate` refuses ("duplicate evo quorum base hash"). Without a SHA256d collision no inner level has an equal pair either. So no mutant drops either arm; it could not die. | The roots and the commitment hash are the ones the node's block checks use (dash-evo's SML and quorum roots, dash-consensus's `SerializeHash(qc)`). Only their composition is new, and Core's `cbtx_cross_checks` pins that on `SyntheticSnapshot()`. |

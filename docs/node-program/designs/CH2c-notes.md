# CH2c: coins performance evidence and L1 (implementation plan and D-rows)

CH2c is PLAN row CH2c (`CH2-coins-flush.md` §7.3). It covers c1 (wall clock and tuning), c2 (W-MC and the DEC-43
proxy) and c3 (L1 `diff_coins_ops`). The base is integration `479ca9905`, before merge train T27. The design is CH2
at that commit: §5.5 (ruling 6), §5.7, §5.8, §5.9 and §6.2, read with DEC-43, DEC-94 Q2/Q3, DEC-95, DEC-96 Q2,
DEC-99, DEC-100, DEC-102, DEC-164 (BL-75), DEC-184 and DEC-186. Core references are `v24.0.0-rc.3`. Where this file
and the design disagree, the D-row says why.

## D-rows

| Row | Decision | Why |
|---|---|---|
| D1 | **Bases.** Every measurement records the integration commit it ran on. Merge train T27's P5a changes the default mempool headroom (DEC-322/DEC-365), and with it the coins cache's budget whenever the mempool allowance is lent. The DEC-43 cells lend no allowance (`max_mempool = 0`, CH2 §5.5), so their B is the coins share alone and P5a does not move it. Only the W-MC `p300` cell (allowance on) depends on the headroom, and it is rerun after the follow-merge. | The proxy's B must not silently change between rotations. |
| D2 | **The L1 op alphabet.** These are O2a-CO's ops, which both sides run. On the tip: `Add(key, coin, possible_overwrite)`, `Spend`, `Access`, `Have`, `HaveInCache`, `Uncache`, `SetBest(h)`, `GetBest`, `Flush`. With a block's view open: `Push`, `ChildAdd`, `ChildSpend` (moveout), `ChildAccess`, `ChildHave`, the tip's `HaveInCache`, `Commit(h)` and `Drop`. CH2c adds two Core-side reads: **`Entry(key)`** (Core's `GetCoinsMapEntry` flags on the tip; a test-only op) and **`Usage`** (the tip's `DynamicMemoryUsage()` and `GetCacheSize()`). It also adds three **node-only scheduling ops**, which Core never sees. They are allowed only with no block's view open, because CH2 never freezes mid-block (DEC-95). `Freeze` freezes active at the tip's best block as F, if no F is in flight and a best block is set. `WStep(n)` writes F's next `n` DIRTY entries to the database in one Buffered batch, in F's dirty order. `Release` writes F's remaining entries and releases it. A tip `Flush` is the ALWAYS flush: it finishes an in-flight F (writing the rest, then releasing), then freezes active, writes it and releases it. The database is compared after it, as now. | §6.2's "freezes and W steps at random points, then ALWAYS at each FlushTip". The scheduling ops are bytes of the same script, so one corpus covers both modes and the fuzzer chooses the flush points. |
| D3 | **Two modes, chosen by the input's first byte** (bit 0). **Aligned:** the script has no scheduling ops (the reader drops them), so F is never in flight across ops. Every op is compared. That includes `HaveInCache` and `Entry`: active's DIRTY/FRESH must equal Core's flags, and an entry absent from active must be absent from Core's map. `GetCacheSize` must equal active's entry count, tombstones included. This is D12's "equal" case (CH2 §2.4.5), checked. **Hidden:** the scheduling ops are kept. Values, errors (the `logic_error` text), `GetBest` and the database after each tip `Flush` are compared. `HaveInCache`, `Entry` and `GetCacheSize` are not compared **with CH2**, because D12 (DEC-102) and D2 (the flags in F) allow them to differ across our flush points. Core's `Entry` and its size are still checked against the twin. CH2's answers are counted as `uncompared`, apart from O2a-CO's `skipped`. **Re-spend (rev1, the smoke's first cluster):** a tip spend of a coin that neither Core's view nor CH2's holds unspent returns whether a spent entry is still cached (`SpendCoin`, `coins.cpp:129-150`). That depends on each side's own flush history. Core erased a FRESH coin that CH2 froze first, which leaves CH2's non-FRESH tombstone over F; or Core keeps a DIRTY tombstone that CH2 already released. So in hidden mode CH2's boolean is uncompared. Core's boolean is checked against the twin, which shares Core's history (rev2, review L2: `SpendCoin` finds an entry in the tip, or an unspent coin in its database). The op runs on both sides. A valid chain never reaches this, because inputs are checked first. The seed is `hidden-respend`. | §6.2, DEC-102. |
| D4 | **`DynamicMemoryUsage` checks the proxy's Core model, not CH2.** DEC-102 removed CH2's Core-model meter, and CH2's native ledger is not Core's memusage (DEC-99, O2a-CO D3). So the L1 compares Core's per-op `DynamicMemoryUsage()` (USAGE) with **`CoreUsage`**, the arithmetic model the proxy's Core-model arm uses for its flush trigger and its memory (D9, D10), and not with CH2's Σ. The comparison is exact, in both modes, after every tip op (Core's side does not depend on the mode). `CoreUsage` covers four things: (1) the map's nodes in v24's `PoolResource` (256 KiB chunks; the free list reused; chunks kept until `ReallocateCache` at a flush); (2) libstdc++'s bucket array, `MallocUsage(8 × bucket_count)` under `_Prime_rehash_policy` with load factor 1; (3) `cachedCoinsUsage`, each coin's script `MallocUsage(capacity)` above prevector's 28 inline bytes; (4) the child's caching reads into the tip (`FetchCoin`). The node size and the chunk size are measured from the oracle (provenance in the test), not assumed. CH2's own memory is gated at the proxy instead (D8: native Σ ≤ B, peak coins usage, `rss_anon_peak`). | The brief asks for `DynamicMemoryUsage` per op. Under DEC-102 the only consumer that needs Core's exact number is the proxy's Core model. An exact per-op check certifies that arm's flush points and memory, which is what the DEC-43 gate leans on. |
| D5 | **Run classes** (O2a-CO's hand-off). Each run reports `full` (compared to its end, or both sides ended at the same `logic_error`), `ended_by: FreshAtAdd`, or `ended_by: ChildReadCaching`, and separately the counts of `skipped` and `uncompared` answers. The target asserts only "no divergence". The campaign's report (`examples/coins_ops_classes.rs` over the certified corpus) gives the class counts per mode. Only `full` aligned runs count as full parity. O2a-CO D14's classification of child-read caching stays (CH2's overlay reads stay non-caching, O-R6-m3). | O2a-CO Sol r1 follow-up. |
| D6 | **Proxy cells.** `coins-replay-{wm,wt}-dec43`: ST1's traces (mainnet-453371, testnet-435990) at Core's DEC-43 numbers: `-dbcache=300` with txindex, so **B = 252.75 MiB** (the block tree 2, txindex 37.25, coins DB 8, coins 252.75; `CacheSizes::calculate`), with no allowance. Both traces peak below Core's LARGE at that B (1,187,399 and 579,988 live coins, ≈ 131 MiB and ≈ 64 MiB at 115.67 B), so this literal cell flushes only at the end and measures cache-resident connect, the final flush and memory. It is gated as the design names it. CH2c adds **`coins-replay-{wm,wt}-dec43p`**: the same cell pressure-matched as ST1's P300 (ST1 §3.4). Here B = 252.75 MiB × U / 6,422,912, which is 46.7 MiB for mainnet and 22.8 MiB for testnet. The engine budgets keep their literal sizes (ST1's caveat; both arms alike). It is gated too, because it is the cell where misses and flushes happen. | The literal cell alone would leave the flush and miss paths unexercised. The pressure-matched cell is the evidence for them. |
| D7 | **The common cap.** Each arm runs in its own `systemd-run --user --scope` with `MemoryMax = B + 74 MiB (E) + 37.25 MiB (txindex) + O + A` and `MemorySwapMax = 0`, on CPUs 24–31 (ST1 §5). Here A = 0.5 × U × 75 B (ST1's page-cache allowance) and O = the larger of the two arms' measured fixed overhead: `rss_anon_peak` of a run over the trace's first 1,000 blocks, which has no flush, minus its peak coins usage, rounded up to 1 MiB. The cap counts anonymous memory and page cache together (CH2 §5.5). Traces are copied to tmpfs outside the arms' cgroups first, so the arms are not charged for them. | CH2 §5.5's regime, the same number for both arms. |
| D8 | **Pairing and gates.** 5 rotations per cell. In each rotation both arms run back to back, the order alternating (R-L, L-R, …), each from an empty datadir under `/work/scratch/ch2c/db`. The gate needs every pair: ours ≤ Core's in 5/5, ties included. The reported `sign_p` is ST1's two-sided exact sign test without ties, so 5/5 gives p = 0.0625. In each rotation the arms run with Core in the middle (`rdashd, core, rdashd-split`, then reversed), so each of our arms is adjacent to Core (rev2, review L4). A rotation is kept whole. A failed run (an OOM kill under the cap) loses all of that pair's gated metrics and is never retried alone. A failed Core run voids its pair. Every result records the binary's sha256 and commit, and resuming across a different binary is refused (rev2, review M1). **Gated** (CH2 §5.5): total time (replay + quiesce + close); V-stall time (ours: V's waits on W; Core: the synchronous flushes' whole time); `rss_anon_peak` (RssAnon sampled every 5 ms from `/proc/self/status`, together with the peak at the end); peak coins usage (max native Σ over block boundaries ≤ max `CoreUsage` over the Core arm's block boundaries, DEC-95/96); native Σ ≤ B at every block boundary (DEC-99/100); and 0 DMAX flushes. **Reported:** `memory.peak`, RssFile, flushes by cause, flushed bytes, puts and deletes, misses, miss-read p99, and RocksDB's stall counters. | CH2 §5.5 and §5.9; DEC-94 Q2 gates stall and bytes, not the flush count. |
| D9 | **The Core-model arm** (a new `--arm core-dec43` beside ST1's `leveldb` engine). The cache is a map with Core's DIRTY/FRESH semantics (ST1 §3.1). It accounts `CoreUsage` (D4) and runs Core's `FlushStateToDisk` arithmetic after each block (`core_size_arith`: CRITICAL, LARGE). It flushes as Core's `Flush()` does, in **Core's order**. The block-index batch goes first, synced (`WriteBatchSync`, `-blockindex` LevelDB, 2 MiB cache, ≈ 120 B per dirty block). Next, the coins: the head-blocks marker, then the map in its iteration order with no sort, in `-dbbatchsize` (16 MiB) unsynced sub-batches, the tip last (chainstate LevelDB, 8 MiB cache). The evo stand-in follows (a separate LevelDB, 64 MiB cache; its best-block record). Then the map is emptied and reallocated (`ReallocateCache`). The txindex-shaped LevelDB (37.25 MiB cache) takes one unsynced batch per block from its own thread: 8 + 12 B per transaction (CH2 §5.9 rev2), and its locator at each flush. Misses read synchronously (`FetchCoin`). | CH2 §5.5's Core-model arm, with Core's own write order rather than ST1's sorted one, and Core's usage rather than ST1's 80 B per entry. |
| D10 | **Usage-matched memory** (rev1). ST1's map preallocates 80 B per entry, which is neither Core's resident memory (≈ 115.67 B per P2PKH coin, CH2 §5.2) nor its growth shape. The Core-model arm's map is therefore a **replica of `CCoinsMap`'s layout** (`core_map.rs`): 104-byte nodes carved from 256 KiB chunks and reused through a free list (v24's `PoolResource`), and an 8-byte-per-bucket array that grows by libstdc++'s `_Prime_rehash_policy` (`core_usage.rs`, its prime table taken from libstdc++.so.6). Chunks and buckets live until the flush's `ReallocateCache`. Its allocation equals `CoreUsage` except for the scripts above 28 bytes that Core keeps on the heap (`cachedCoinsUsage`). At every block boundary the arm also holds a **ballast** of touched anonymous memory equal to that remainder (`CoreUsage − the map's allocation`, never negative), released with the map at each flush. The arm's `rss_anon_peak` therefore holds what Core's formula says Core holds at block boundaries, as Core's `UpdateTip cache=` does (DEC-96 Q2). The per-block child view (ConnectBlock's `CCoinsViewCache view(&CoinsTip())`) is a second `CoreMap`, emptied after its `BatchWrite` into the tip. The JSON reports the peak ballast. | rev0's ballast for the whole map gap would have been gigabytes of untouched-shape memory standing in for chunk growth. The replica keeps Core's shape (chunk steps, bucket doublings) and needs a ballast only for the script heap, checked per op by D4's `CoreUsage` against the oracle. |

Both arms instead run the same txindex-shaped writer thread (8 + 12 B per transaction, from each block's distinct created txids): one unsynced batch per block, its locator at each flush, on its own engine (RocksDB here, LevelDB in the Core arm, as each node has it).

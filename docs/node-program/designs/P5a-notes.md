# P5a: overlay intake for a following node — implementation notes and D-rows

P5a (PLAN §4.5, rev1 M-10.1) gives a following node Core's object intake and relay for the two
overlay objects it must follow before LK1a: `spork` and `clsig`. It is plumbing, not ChainLock
semantics: the object-request tracker, inventory relay, the `PostProcessMessage` applier, the
`clsig` branch up to `ProcessNewChainLock`, and the seam LK1a fills. This file records the
implementer's choices where the sources leave one (IMPLEMENTER: "decide, record a D-row,
continue"). Core lines are v24.0.0-rc.3's (`np:` = `src/net_processing.cpp`); extracts are in
`/work/scratch/p5a/core`.

## What Core does for a following node

- **Intake.** `inv` (np:4507-4611): every non-block entry gets `AddKnownInv` (the peer's
  `m_tx_inventory_known_filter`), then, if `!AlreadyHave(inv)`, `AddObjectAnnouncement` — in IBD
  only for `MSG_SPORK` (np:4567-4577). `AlreadyHave` (np:2351-2460) asks the spork manager for
  `MSG_SPORK` (np:2421-2423) and `ChainlockHandler::AlreadyHave` for `MSG_CLSIG` (np:2438-2439;
  chainlock/handler.cpp:76-87: the seen map, then the stored chainlocks).
- **Requests.** `m_object_request` is one `TxRequestTracker` for every object type
  (np:1117-1122; txrequest.{h,cpp}). `AddObjectAnnouncement` (np:1635-1664) caps a peer at
  `MAX_PEER_OBJECT_ANNOUNCEMENTS` = max(5000, 2·`MAX_INV_SZ`), passes `fPreferredDownload` as
  `preferred`, and delays `MSG_TX` from non-preferred peers on a non-masternode by 2 s and every
  type by 2 s when the peer has ≥ 100 requests in flight. `SendMessages`' last section
  (np:6841-6897) asks the tracker for this peer's requestable invs, forgets those `AlreadyHave`
  now covers, appends the rest to `vGetData`, records GETDATA-only types in
  `m_recent_object_requests`, and marks them `RequestedTx` with expiry now + `GetObjectInterval`
  (np:1595-1609: clsig 5 s, spork 60 s). `notfound` completes known types (np:5744-5765);
  `FinalizeNode` drops the peer (np:1816).
- **spork** (np:5688-5711): `ReceivedResponse` for every decoded spork, `Misbehaving(100)` for a
  malformed or invalid one, and `ForgetTxHash` + `RelayInv` when `ProcessSpork` changed the store.
  SP0 implements everything but the tracker and the relay (SP0 D4).
- **clsig** (np:5794-5819), inline in `PeerManagerImpl::ProcessMessage` after the fallthrough
  handlers, before `m_handlers`: nothing at all unless `m_chainlocks.IsEnabled()`
  (`SPORK_19` active, chainlock/chainlock.cpp:33); then read, hash (`::SerializeHash`),
  `PeerConsumeGetDataResponse` (np:6925-6957) and `+10 "unrequested clsig"` when unrequested
  (P2P-12, PRD behaviour 23); otherwise `PostProcessMessage(ProcessNewChainLock(...))`.
  `ProcessNewChainLock` (chainlock/handler.cpp:133-183) dedups on `seenChainLocks`, inserts the
  hash before anything else, returns empty at or below the best ChainLock height, verifies
  against the quorum set (`MisbehavingError{10}` when invalid), updates the best ChainLock and
  returns `CInv(MSG_CLSIG, hash)`, which `PostProcessMessage` (np:3819-3836) forgets and relays.
  The handler exists on every node (init.cpp:2152); only signing needs a masternode.
- **Relay.** `RelayInv(inv)` (np:2546-2553) calls `PushInv` (np:1228-1257) for every peer in
  `m_peer_map` whose `GetInvRelay()` is non-null — in Dash every peer, because `TxRelay` is
  always constructed (np:446) and only `GetTxRelay()` is gated. `PushInv` skips an inv the
  peer's known filter has and queues non-tx types on `vInventoryOtherToSend`. `SendMessages`
  section 8 (np:6723-6747) sends that queue at once (no trickle), skipping types that violate
  blocks-only when `!m_relay_txs` (protocol.cpp:185-211), known ones, and `MSG_ISDLOCK` without
  `fSendIS`, and inserts each sent hash into the known filter.
- **Serving.** `ProcessGetData` (np:2935-3111) serves `MSG_SPORK` from the spork manager
  (np:3017-3022) and `MSG_CLSIG` from `m_chainlocks.GetChainLockByHash` (np:3041-3047); anything
  not pushed goes into one `notfound`.

# BL-155: sharded gate selftest, implementation notes and D-rows

`contrib/node/selftest-checks.sh` ran its planted-violation cases (323 at integration 3a6e02f82) one after another, about 1.3 min each under the box's usual load, so 6–7 h. Every train gate forces it (DEC-216). BL-155 makes it shardable and runs it as parallel shards in the gate. Correctness and isolation must not change. BL-155 has no design of its own; this file records the implementer's decisions, per the IMPLEMENTER contract ("decide, record a D-row, continue").

## Interface

- `selftest-checks.sh --shard I/K`: runs the cases it owns, plus every clean-tree case.
- `selftest-checks.sh --shards K`: the driver. It runs K shards in parallel, waits for all of them, and prints one merged report.
- `selftest-checks.sh --list`: prints `<n>\t<description>` for every case without running a check.
- With no flag, the script behaves and prints as before.

## D-rows

| D | Decision | Why |
|---|---|---|
| D1 | Case *n* is the *n*-th `expect` call the script reaches, counted from 1. It belongs to shard `(n − 1) % K + 1` (round robin). | The order is a function of HEAD alone: loops and conditionals read only the tree. So the assignment is deterministic and stable for a given commit. Adjacent cases share a section and a check, so they cost about the same. Round robin spreads every expensive section (pure, shared and products, the clippy builds) over all shards, which contiguous blocks would not. A hash of the description is unstable under rewording, and six cases are called "clean tree". |
| D2 | Every shard runs all the planting code between cases and every `reset`. It skips only the check call of a case it does not own. | Plants are cheap file edits. Some plants build on state that outlives `reset` (the fork checkout in the private `CARGO_HOME`, directories under `$base`), so every shard must walk the same sequence of trees as a serial run. `--list` (no check at all) reaching the end with the same 323 cases shows that no plant depends on a check having run (after D4). |
| D3 | The clean-tree cases (description `clean …`, optionally after a `label: ` prefix; 11 cases) run in every shard. In the merge, such a case is ok only if it is ok in every shard, and it is printed once. | The brief requires the clean-tree pass per shard. Each shard has its own worktree, cargo home and target, so each must show that the unmodified tree passes before its plants count. The canary needs nothing extra: each shard's `reset` checks its own `target/` canary on every case, owned or not. |
| D4 | The fork checkout that the `in_home` plants edit (`$home/git/checkouts/base-sdk-*/<rev>`) is now made by an explicit `in_home cargo metadata`. Before, it was a side effect of the preceding clean-tree check. | That was the one plant that depended on a check: `--list` stopped there with `set -e`. Sharded runs would have been fine, since the check is a clean case (D3), but the dependency should not rest on that. The call is offline and takes seconds. |
| D5 | The driver gives each shard `TMPDIR=$run/<i>/tmp`, under its own `mktemp -d` in the caller's `TMPDIR`. The shard's worktree base, private `CARGO_HOME`, `target/` (inside its worktree) and every `mktemp` the checks make (check-shared, check-loom, check-public-api, check-release-refs) live there. Paths shared with other shards are only those a serial run already shares with every concurrent gate: the repo's object store and `.git/worktrees/`, the real `CARGO_HOME` for the checks not run `in_home`, and the fork repository (read only: `rev-parse` and `archive`). | Git names a new worktree's admin directory with `mkdir` and retries on `EEXIST`, so concurrent `worktree add`s do not race. Cases that commit do so on their own worktree's detached HEAD, and objects are content-addressed. The real `CARGO_HOME` is written only by cargo, under its package-cache lock. The private home's `registry` and `git/db` are symlinks used offline, so they are read only, as before. `/tmp` and `/dev/shm` are untouched whenever `TMPDIR` is set; the gate sets it under `/work/scratch`. No check writes a fixed path: every grep hit is relative to the worktree or under `TMPDIR`. |
| D6 | Merged report: the verdict lines exactly as serial prints them (`ok    pass: …`, `ok    fail: …`, `FAIL  wanted …`), one per case and in case order. Then any problem lines (`FAIL  shard i/K did not finish …`, with the last 15 lines of its log). Then `shard i/K: a ok, b FAIL, c run, exit s` for each shard, `total: X ok, Y FAIL, N cases (union of K shards)`, and finally serial's last line (`N selftest(s) failed` on stderr with exit 1, or `all selftests passed`). Section headers and `skip  …` notes appear only in the shard logs. | Anything that judges the serial output (the step's exit status, counts of `^ok`/`^FAIL` lines, DEC-220's six `[size]` lines) reads the merged output the same way. The count lines start with `shard`/`total`, so they do not change those counts. |
| D7 | The merge fails closed. Each shard appends `<n>\t<ok/FAIL/skip>\t<description>\t<line>` per case and `end\t<failures>` at its very end. A shard counts as finished only with an `end` record and an exit status that matches it (0 if no failures, else 1). The finished shards must list identical cases (number → description), numbered 1..N, and a shard that died must agree on the cases it reached. Every case needs its owner's verdict, and every clean case needs a verdict from every shard. Anything missing is a `FAIL  case n was not run: …` line. No finished shard at all is a FAIL. | A shard that crashes, is killed or stops early can never pass silently: its owned cases have no verdict. The list agreement catches a shard that walked a different case sequence. |
| D8 | (Superseded by D21 in f1.) Shards are started with `setsid setpriv --pdeathsig TERM`. `setsid` does not fork here (a background job of a shell without job control is not a group leader), so each shard's PID is its process-group ID. After a shard is reaped with a non-zero status, and on the driver's exit, the driver sends SIGTERM to that shard's group, once. A shard that exited 0 is left alone, since its children are done. The driver removes the worktrees under `$run` that a killed shard left registered, and deletes each shard's `tmp/`. The logs and results stay in `$run` (the gate's `TMPDIR` is removed when the gate exits). If the driver is SIGKILLed and its traps never run, the parent-death signal ends each shard; its EXIT trap removes its worktree, and any child it has running finishes its current check. Shown: all four shards and their worktrees were gone 15 s after a driver SIGKILL. | Only our own process groups, never a command-line pattern. Signalling a group once, right after its leader is reaped, keeps the PID-reuse window to the moment between `wait` and `kill`. A crashed shard's `target/` (about 22 GB) does not stay on disk. |

| D21 | f1, Sol r1 major 1. A shard's parent-death signal killed the shard's shell, but not a check it had started in the foreground, and the shell's EXIT trap then removed the worktree under that check. The shards now run under a supervisor: a Python process that the driver starts with `setpriv --pdeathsig TERM`. It also checks `getppid()` every second, in case the driver died before the signal was armed. It starts each shard with `posix_spawn(setsid=True)`, so the shard leads its own session and process group, and restores the SIGPIPE and SIGXFSZ dispositions Python ignores. Shards are handled in the order they finish, polled once a second with `waitid(WNOHANG|WNOWAIT)`. When a leader exits other than 0, its group gets SIGKILL, repeated until `/proc` shows no live process with that group id (D25 changes the exit-0 case). On SIGTERM, SIGINT or SIGHUP, or once the driver is gone, every running group gets SIGKILL and then the same sequence. The driver only waits for the supervisor; on its own TERM or INT it sends the supervisor SIGTERM and waits for it. A supervisor exit other than 0 fails the run. | Groups, not cgroup scopes.

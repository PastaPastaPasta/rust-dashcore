# O2a-GV: oracle payments and credit-pool entries, implementation notes

Decision rows taken while implementing O2a-GV: the Core entries `oracle_block_value_payee` and
`oracle_credit_pool_step` (ABI 18, Core branch `node/o2a-gv-oracle-v24.0`), their `dash-oracle-sys` bindings
(`Oracle::block_value_payee`, `Oracle::credit_pool_step`, module `payments`), the live harness
(`scripts/payments-check.py` and the `payments_check` example) and the fixture test (`tests/payments.rs`). The byte
formats are in `O2a-GV-context.md`. Program decisions live in DECISIONS.md. Line numbers cite Core v24.0.0-rc.3 files
that the pin leaves unchanged.

| Row | Decision | Evidence |
|---|---|---|
| D1 | **Two stateless entries, v24 only.** Each call builds its state (a `SuperblockManager`, a `CCreditPoolManager`) from the call's contexts and drops it on return. A non-v24 build returns `ORACLE_E_UNSUPPORTED` (DEC-82). ABI 18 is additive over train 14's ABI 17. | `oracle.h` "block payments and the credit pool (ABI 18)"; `tests/smoke.rs` ABI 18. |
| D2 | **The check level is transcribed, not called.** ConnectBlock's level comes from `CChainstateHelper::IsSuperblockValidationRequired()` (`evo/chainhelper.cpp:41-52`): NoCheck if `best_chainlock_height >= height` or not synced, else DisallowDuplicates with V24 after the parent, else AllowDuplicates (`validation.cpp:2841-2843`). A `CChainstateHelper` cannot be built next to the shim's EHF stand-in, so the shim evaluates the same two conditions from the payments context. Everything after the level is Core's own code: `IsBlockValueValid`, `IsBlockPayeeValid`, `GetBlockTxOuts`, `IsSuperblockTriggered`, `GetSuperblockPayments`. An empty `CChain` is passed: on these paths `CSuperblock::GetPaymentsLimit()` is the only reader, and it ignores it (`governance/superblock.cpp:145-163`). | `tests/payments.rs` `regular_block_masternode_payment` (chainlocked at its height → NoCheck), `superblock_strings` (a chainlock one below does not exempt). |
| D3 | **No spork in v24's payment path.** v23.1's `SPORK_9_SUPERBLOCKS_ENABLED` gate is gone in v24. The PLAN row's "spork values" applied to the dropped v23.1 pin (DEC-82), so SP0's semantics do not enter the context. | `masternode/payments.cpp:313-448` reads no spork. |
| D4 | **The tip's masternode list is the chain context's list.** `GetListAtChainTip()` reads the list after `CDeterministicMNManager::UpdatedBlockTip(tip)`. The shim calls that with the context's tip, as a synced node does when it connects a block at its tip. A reorg is outside this model: until the new branch's work beats the old tip, `ActivateBestChain` does not notify `UpdatedBlockTip` (`validation.cpp:3843`), so new-branch blocks connect against the old tip's list. EV3 must not assume "tip list = parent list" there. Pre-DIP3 heights have no list, so a synced node sees no trigger there: a pre-DIP3 superblock's verdict under synced mode is "no triggered superblock detected" (whenever it pays more than the reward). | Live mainnet runs; `superblock_strings`. |
| D5 | **Triggers are not validated as governance objects.** The payments code never reads a trigger's signature, collateral or masternode outpoint. The shim decodes each object whole, seeds its funding votes into `mapCurrentMNVotes` under the object's lock, and passes it to `SuperblockManager::AddTrigger(obj, tip height)`, which parses the `CSuperblock` as Core does (a failed parse is not added; an expired trigger is still added). `IsSuperblockTriggered()` counts the votes against the tip's list, weighted by type. | `superblock_strings`: unfunded, one vote short, a NO vote, another height → "no triggered superblock detected"; `Trigger::superblock` builds the object bytes. |
| D6 | **The refusal set (ORACLE_E_ARG): undefined behaviour in Core, or a state no chain produces** (the wording `CheckListState` uses). The undefined-behaviour guards are exact: the payee's masternode reward times its operator reward, but only with an operator payout script, then the reward left after the operator's times an owner payout's reward, for all but the last payout (`masternode/payments.cpp:164-187`; validator r2 m1′: the first fix multiplied the reward before the operator's); a trigger's event height plus `min(576, nSuperblockCycle)`, the expiry of the Valid status `AddTrigger()` gives (`governance/superblock.cpp:345-357, :461`); a trigger's payment total, or that total plus the reward (`:281-292`). The states no chain produces: a fee outside the money range; an operator reward above 10000, owner payouts above `MAX_REWARD`, or share amounts outside the money range or summing to 0 (no ProRegTx carries them); output values outside the money range and a first transaction that is not a coinbase (CheckBlock and CheckTransaction reject them first); a repeated trigger or vote; a vote signal or outcome out of range. Validator r1 m1: the first cut refused subsidy + fee above `INT64_MAX / 10000` always, which also refused fees Core answers. | `payments_context_refusals`; `fees_up_to_max_money_get_a_verdict` (fee = MAX_MONEY, 50% operator reward). The owner-payout guard: D17. |
| D7 | **"old budgets are no longer active" is unreachable.** `IsBlockValueValid()` calls `IsOldBudgetBlockValueValid()` only below `nSuperblockStartBlock` (`masternode/payments.cpp:329`), and that string fires only at or above it (`:272`). The other old-budget strings are covered. | `old_budget_and_pre_budget_strings`. |
| D8 | **One block-read seam, two clients.** `build-oracle.sh` allows a single `--wrap` per symbol, and `oracle_llmq.cpp` already wraps `node::ReadBlockFromDisk(CBlock&, const CBlockIndex*, const Params&)`. Its wrap now asks `oracle_internal::ReadStepBlock()` (`oracle.cpp`) when no LLMQ context is reading. During a credit-pool step, that call serves the step context's blocks and fails any other read as missing context; otherwise it returns `nullopt`, and Core's own function runs. Every block the step serves must match its header (merkle root, not mutated): `GetCreditDataFromBlock()` caches per-block data process-wide by block hash. | `credit_pool_refusals` (a reordered block is refused); the archive links one `__wrap_` definition. |
| D9 | **The credit-pool window start is context on the accepting path.** When `CheckCreditPoolDiffForBlock()` accepts, V20 is active at the block and DIP0003 is active at height − `CreditPoolPeriodBlocks()`, the shim refuses with `ORACLE_E_CONTEXT` when the step context lacks that block, whether Core reads it or not, just before `GetCreditPool(block)`, whose `ConstructCreditPool()` reads it (`evo/creditpool.cpp:167-203`). A rejecting check needs no window block: the diff reads only the parent's pool, which the shim seeds in the cache (`GetCreditPoolDiffForBlock()`, `evo/creditpool.cpp:376-381`), so Core's reject (e.g. `failed-creditpool-unlock-too-much`) stays a verdict (Sol r1 Medium: the first cut required the block before the diff). Otherwise a block an earlier call cached in `GetCreditDataFromBlock()`'s static LRU (`evo/creditpool.cpp:69-72`) would be answered from the cache, and the refusal would depend on call history. The test found this: the refusal passed alone and failed after the accepting step. When the headers do not reach the window start, the ancestor there is the context's placeholder, whose block the context cannot hold, so the same rule refuses. A first cut also refused short headers outright, which over-refused where DIP0003 is not active at the window start (validator r1 m4). | `credit_pool_refusals` runs the accepting step first, then both refusals; `credit_pool_unlock_block` rejects an unlock above the limit with no window block. |
| D10 | **v24's rules are reachable only off mainnet at the pin.** Mainnet's `DEPLOYMENT_V24` has `nStartTime = NEVER_ACTIVE` (`chainparams.cpp:213`), so `VersionBitsConditionChecker` returns FAILED before it reads the context's seeded state (`versionbits.cpp:47-49`). On mainnet, `strict` and `DisallowDuplicates` never apply, whatever the context says. The acceptance's "strict_multiplicity with V24 on" therefore runs on testnet (V24 STARTED there at the reference node's tip), with V24 seeded ACTIVE. | `strict_multiplicity` and `superblock_duplicate_payments` (testnet fixture samples). On a mainnet context, ACTIVE gave `strict = false` (found while writing the test). |
| D11 | **Live harness: what each sample checks.** `payments-check.py` reads pure RPC (`getblock`, `getblockheader`, `getblockstats totalfee`, `protx listdiff 1 h-1`, `getcreditpoolinfo`) at concurrency 1, mainnet ≤ 2,090,000. The example runs these legs per sample: not synced (accept, NoCheck); synced (accept; superblocks with the trigger rebuilt from the coinbase and funded by the first valid masternodes by registration up to the threshold → triggered, `GetSuperblockPayments()` equal to the coinbase's payments); the expected masternode outputs are a sub-multiset of the coinbase; crafted rejects per string at real blocks. Miners order outputs differently: the miner's output is the one paying reward − masternode payments, else the only one within it. The superblock payments are the rest, in coinbase order, because `CSuperblock::IsValid()` scans forward (`governance/superblock.cpp:300-318`). | `/work/scratch/o2a-gv/runs/mainnet-payments.jsonl` (see the final report). |
| D12 | **Credit-pool chained run.** The run starts from `getcreditpoolinfo(from − 1)` (the empty pool at V20's height). Each later step's prev is the previous step's pool, compared with `getcreditpoolinfo(h)` on `balance`, `currentlimit` and `window.unlocked`. The RPC prints no unlock indexes, so a run started mid-chain begins with none. Mined blocks never repeat an index, so no verdict changes. `getcreditpoolinfo` is a pure read: its only write, the snapshot, happens inside a block-scoped evodb transaction (`evo/creditpool.cpp:140-150`). | Live runs. |
| D13 | **Fixture lists are trimmed.** The fixture keeps the masternodes the coinbase pays plus the first 12 valid ones by registration (the voters). `GetMNPayee()` takes the minimum under its order, so a subset that holds the real payee picks the same one. The derived variants: `banned` (every masternode PoSe-banned → no payee, R4 F6) and testnet `strict` (each paid masternode gets a 50% operator reward to its own payout script). | `tests/data/PROVENANCE.md`; the fixture samples pass the example's legs, like the live ones. |
| D14 | **Fees come from `getblockstats totalfee`** (duffs), not from summing `getblock 2` fee fields. | `payments-check.py`. |
| D15 | **Disk blocks are refused where no node has them** (validator r1 M1, m5). A disk block without a coinbase would make the shim's amount checks read `vtx[0]` out of bounds (an empty block's merkle root is zero, and context headers are not proof-of-work checked). An asset unlock whose payload does not decode would make `GetCreditDataFromBlock()` throw (`ORACLE_E_EXCEPTION`). Both are `ORACLE_E_ARG` now. | `credit_pool_refusals`: an empty disk block, a block that is no context header's, a repeated block, a prev amount out of range. |
| D16 | **Without a list, only Core's reads can need one** (validator r1 m2). The shim checks the payee's reward fields only when DIP0003 is active at the tip (validator r2 nit): before it, `GetListForBlockInternal()` returns the empty list without a read (`evo/deterministicmns.cpp:830-832`). ConnectBlock reads the parent's list only from DIP3 enforcement, and the tip's only at a superblock height being checked. When DIP0003 is active at the tip and the context holds no list, the shim skips its own reads (`GetBlockTxOuts`, `GetListAtChainTip`, `IsSuperblockTriggered`) and reports them as not computed. A verdict that Core can give without the list stays a verdict. | `oracle.h`; the context note. |
| D17 | **The owner-payout overflow guard has no fixture test.** Several owner payouts exist only in ExtAddr (version 3) states, and `ProTxVersion::GetMax()` allows version 3 only with V24 active (`evo/specialtxman.cpp:1135`). No chain at the pin holds one: V24 is NEVER_ACTIVE on mainnet and STARTED on testnet. The fixture tooling (`dml-listdiff-check.py`) encodes state versions 1 and 2 only. The guard (`CheckPayeeRewards`) is checked by review against `masternode/payments.cpp:164-187`. Follow-up: cover it with a crafted ExtAddr list once a Core-produced one exists (EV3 or node-fuzz). | Validator r2 m1′ (fixed in code). |
| D18 | **Live harness `skipped` result.** Testnet miners split their reward across outputs and some testnet superblocks pay scripts with no address, so the example cannot always tell the superblock payments from the miner's outputs. Such a sample records `skipped` with the reason; the legs that ran before (`ibd`, `masternode`, `payee_missing`) still count. Real oracle errors stay `error`. | Testnet heights 30048 and 53088 (`runs/testnet-payments-recheck.jsonl`). |
| D19 | **The value check short-circuits, as ConnectBlock does** (Sol r1 High). `ConnectBlock()` returns `bad-cb-amount` before `IsBlockPayeeValid()` (`validation.cpp:2846-2849`). The first cut ran the payee check, the payee reward refusals and the outputs whatever the value verdict, so a post-DIP3 overpaying coinbase with no list in the context got `ORACLE_E_CONTEXT` (the payee check reads the tip's list, `GetBlockTxOuts()` → `GetListForBlock()`, which the context lacks) where Core has a definite `bad-cb-amount`. Now nothing after a failed value check runs: the record's `payee_valid` is 0 (`None` in Rust) and `outputs_computed` is 0. | `regular_block_masternode_payment` (overpay without a list: `bad-cb-amount`; the accepted block without one: `ORACLE_E_CONTEXT`); `reject_value` asserts the fields are not computed. |
| D20 | **The live runs check fidelity to mined coinbases, not to the reference nodes' governance** (Sol r1 scope note). The harness builds a synthetic trigger from each superblock coinbase's outputs, funded by the first valid masternodes. A match shows that Core's trigger and payment rules, applied to that trigger, give the mined block's verdict and payments. It does not show that the shim, given the reference node's real trigger set (competing triggers, real votes, expired or executed ones), picks the same trigger. EV3/GV1b must cover that with real trigger sets. | `payments-check.py`, the `payments_check` example. |

## Deviations and follow-ups

- The step runs only `CheckCreditPoolDiffForBlock()` and `GetCreditPool()`. `CheckCbTx`, each unlock's
  `CheckSpecialTxInner` (`oracle_check_special_tx_block` covers it) and the quorum block processor are not run (the
  context note says so).
- EV3 owns the native `dash_evo::payments` / `dash_dml::creditpool` and the L1 `diff_credit_pool` target. This row
  provides the oracle side only.

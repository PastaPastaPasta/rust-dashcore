# MN0-3: implementation notes

These rows record slice decisions that are not design changes. The plan is PLAN-MN0 §11, in node-program-docs. Core citations are at `v24.0.0-rc.5`.

## C0: the template's reads (OD-CP-125 R1, OD-CP-126, OD-CP-127)

| Row | Decision | Why |
|---|---|---|
| 3-D1 | **Read surface added by C0, and the template's fault boundary.** Every item is in `dashd-chainstate`; `EvoReads` and `dash-evo` are unchanged. (1) `RuntimeRows::snapshot_unstamped` (pub(crate), `llmq/rows.rs`): the cached row, unstamped (the LRU's `peek`), else the disk row, not inserted. One section, as `snapshot_for_block`. (2) `TemplateRows` (pub(crate), `llmq/members.rs`): one answer per key per turn over (1). A store lands in its memo only: no write, no effect, no ledger record. (3) `MembersFacade::template_rows` (pub(crate)): (2) over the facade's rows, with no gate, members cache or attempt. (4) `template_members` (pub(crate)): Core's `GetAllQuorumMembers` over (2), without the members caches, which only memoise the same answer. `EvoView::with_qc` lends it as the members. Its precompute is `TemplateMembers`' `NotBuilt` refusal: the assembler never precomputes, only `ProcessBlock` and `UndoBlock` do (`dash-dml/src/blockprocessor.rs:371`, `:518`). A node without the facade refuses both. (5) `BlockConnector::with_tip_coins` and `EvoView::with_tip_coins`: the active coins through a `BlockOverlay` dropped unwritten. It reads the child, then the tip's cached entries, then the engine without inserting (`coins/overlay.rs` `resolve`), so nothing is written, dirtied or flushed. `DigestTap` forwards it. (6) The pub `dashd-chainstate` API the assembler takes: `EvoView::with_template` (`chain/command.rs:464`) runs `with_llmq` once at V's tip and lends its LLMQ context (the index, the mined rows, (4)) with a `ParentChainlock` reader; `ParentChainlock` (`:518`) reads the tip's coinbase facts (`coinbase_facts`), the tip header's height and V20 at the tip, and answers the tip CbTx's non-null ChainLock, `None` before a tip or below V20 (a parent coinbase `BlockDataUnavailable` is `None`, `evo/cbtx.cpp:192-195`); `BlockConnector::with_tip_coins` (`chain/seams.rs:1037`, default `Ok(None)`) takes the connector's coins cell, then calls the `TipCoinsCall` (`:1123`) over (5); `EvoView::with_tip_coins` (`chain/command.rs:416`) wraps it for one call. (7) `ChainHandle::query_or_stop` (`chain/actor.rs`, OD-CP-135): a class R read whose `Err(Fatal)` V answers first, then reports unless the latch shows it reported, and stops, as after a command's `Fatal` (`stop_serving`, `:2044-2071`). Only for a fault of V's own reads in the turn, under connect's class policy; never a refusal, a readiness answer or a caller's error. An `Ok` turn is `query`'s. The template's reads map as connect's `store_failure` does (`evo/node.rs:691-703`; dashd-mining `read_fault`): a capability not built is NotReady, any other store error V's fault. That covers the tip list (`GetListForBlock`), the credit pool (`GetCreditPool`), the LLMQ view's own error (`with_template`) and the list build's store errors (`BuildNewListFromBlock`: its member computation, the snapshot rows, the historical lists, the coins). `list_after` checks the builder's precondition first (`dml-prev-list-mismatch`, a list at the tip), a `Failed` refusal, so no store error the build returns is that refusal. Kept as before: the credit pool's `PoolError` (`Failed`, Core's throw); the parent ChainLock's store error (`Failed`; ambiguous, its connect counterpart is the CbTx check's); the tip facts' reads (`Failed`; ambiguous); the quorums root's `qc_hashes` errors (`Failed`; a corrupt mined row is reported and latched by the guarded engine, which the template's reads test shows); coins `None` (NotReady); and a poisoned coins cell, reachable only after a V panic poisoned it (`Failed`, as gettxout's read of the same cell answers an RPC error, `rpc.rs:539-549`; OD-CP-134 OPUS-R1-9). On a node an engine read error never reaches the boundary: the guarded engine ends the process first (`CoreAbortSink::read_failed`, Core's `dbwrapper_error`). Route B (`InlineRows`, `llmq/capability.rs`) is not used. Lock order is the connect's. Connect: the coins cell (`connect/connector.rs:319`), held across `core.connect` (`:338`), and under it the rows section, a leaf taken per read (`llmq/rows.rs:154`). Template: the view pin, the pool copy (a leaf, released: dashd-mining `source.rs:260`), then the coins cell (`source.rs:276` → `chain/command.rs:425` → `connect/connector.rs:657`), held across the build, and under it `with_template` (`source.rs:277` → `chain/command.rs:464`) → `TemplateRows::get` (`llmq/members.rs:97`) → the rows section (`llmq/rows.rs:192`) | OD-CP-125 R1, OD-CP-127, Q2, OD-CP-134 M2 m5, OD-CP-135 |
| 3-D2 | **Pinning for rows: one answer per key per turn.** Rows are a raw keyed store, as Core's evoDb rows are. Route C writes them on V's thread from an attempt's log, never mid-turn. Route B writes them inline from other threads, so a row written between a turn's start and its first read of that key is seen. Its value is the deterministic one for that key, so the only change it can make is absent → present. Core is exposed the same way: `GetSnapshotForBlock` takes only `snapshotCacheCs` (`llmq/snapshot.cpp:301-317`), and `CreateNewBlock`'s `cs_main` does not exclude `StoreSnapshotForBlock` on other threads (`:320-328`). On a synced chain each previous-cycle snapshot was stored when its own cycle connected, so the window is not expected to be reached. Row versioning is out of scope | OD-CP-127 (b) |
| 3-D3 | **C0 plants**, run in a reflink copy against `-- template with_qc`, all killed. p1 (`TemplateRows` reads through the stamping `snapshot_for_block`) is killed by `a_template_read_leaves_the_cache_as_it_was`, `a_failed_template_read_keeps_nothing` and `a_templates_rotated_members_leave_the_facade_and_rows_as_they_were`. p2 (route-B rows: the stamping read plus a store that writes runtime rows) is killed by those three and `a_template_store_reads_back_and_writes_nothing`. p3 (no memo) is killed by `a_template_reads_each_key_once`. p4 (store dropped) is killed by `a_template_store_reads_back_and_writes_nothing`. The members-cache leg of route B can't be planted (the capability is sealed), so the E-wire test asserts the facade's members caches unchanged instead | OD-CP-125 E-wire, OD-CP-127 |

## C1 to C4: the template's list, ChainLock and commitments (OD-CP-124, OD-CP-125, OD-CP-128)

| Row | Decision | Why |
|---|---|---|
| 3-D4 | **Two phases, two rules.** (a) The assembler (`create_new_block`): the list after the block is `build_new_list_from_block` over C0's read-only members, rows and coins, its effect log a dropped `Vec`, so the turn changes no stored value (Core's `CMNListBuilder`, `node/miner.cpp:221-237`, `:299-303`). (b) The validity pass (`TestBlockValidity`): V's proposal path as merged (D33): the attempt's log is applied on every outcome (`connect/connector.rs:622-623`). Its persistent writes are (1) at a cycle base, the snapshot row keyed by the proposed block, the value its connect computes, and (2) on a member-cache miss, historical snapshot keys rewritten with the bytes already stored; nothing else (OD-CP-128 as OD-CP-134 M3 amends it). Core does the same: `ProcessBlock` runs `PreComputeQuorumMembers` before any `fJustCheck` return (`llmq/blockprocessor.cpp:34-40`, `:212-223`), and a commitment's check computes its members (`llmq/commitment.cpp:301`, `blockprocessor.cpp:267-277`); the rotated `GetAllQuorumMembers` stores the snapshot (`llmq/utils.cpp:458-462`, `:701-707`) through `GetRawDB().Write` (`llmq/snapshot.cpp:320-328`), outside the evo transaction the pass rolls back (`validation.cpp:4960`). The stop rule does not fire: each row is the one a later read of that key finds (`snapshot.cpp:301-317`), equal to the connect's. Tests: (i-a) E-wire, `a_templates_rotated_members_leave_the_facade_and_rows_as_they_were`: every engine row and the evo layer byte-equal around the template's reads, the members caches and rows cache unchanged, and the list after block 300 built as `list_after` builds it, equal to the recorded root; (i-b) `a_proposal_at_a_cycle_base_keeps_the_row_its_connect_computes`; (i-c) `a_proposal_off_a_cycle_base_changes_no_stored_value`: at 300 one write, the 288 cycle's key with its stored bytes; (i-d) `a_proposal_at_a_cycle_base_adds_only_its_snapshot_row`: at 312 one write, the proposed block's key, the only row added; (ii) (a) `every_rotated_snapshot_is_dashds`: V's rows at the ten rotated cycle bases 144 to 360, with templates' validity passes run at every tip, equal dashd's `quorum rotationinfo` snapshots field for field; (ii) (b) `a_proposed_cycle_base_row_is_never_read`: a proposed 312 under another nonce stores its row, and connecting the recorded chain to its end never asks for it; (iii) the cold baseline in (i-b): 312 connected cold with no proposal stores the same row | OD-CP-128 (A), OD-CP-134 M3 m1 m4, corrects OD-CP-125 R2 (b) |

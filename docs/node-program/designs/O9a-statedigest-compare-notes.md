# O9a: StateDigest comparator, dump and recorded decisions: implementation notes and D-rows

O9a's design is O8's spec §7.2–§7.3 and §10 (`O8-statedigest-v1.md`), with the checkpoint-1 plan's rulings (manager, 2026-10-12). This file records the implementer's decisions where those sources leave a choice, per the IMPLEMENTER contract.

What O9a-1 adds:
- `dash-statedigest::compare`: linear projection, the field-class comparator, coverage and the verdict.
- `dash-statedigest::decisions`: `RecordedDecisions`, with keyed and strict lookup and `final_connect`.
- `dash-conformance digest compare`: the CLI, the text report and the first-mismatch dump (`conformance/src/digest/{store,compare,dump}.rs`).
- `conformance/tests/digest_compare.rs`: the tests over Core's regtest v24 recordings.

What O9a-2 adds (built on `node/integration` with CH1-node, db025b8be):
- `dash-statedigest::emit`: records from plain values, for emitters that are not Core.
- `dashd-chainstate::chain::digest_tap`: `DigestTap`, a `BlockConnector` decorator behind the `statedigest` feature.
- `dash-conformance digest replay`: a stored node's `blocks.dat` through V with the tap around `NullConnector` (`conformance/src/digest/replay.rs`).
- `conformance/tests/digest_replay.rs`: `feature_dip3_deterministicmns` node0 replayed and compared with its golden.

| D | Decision | Why |
|---|---|---|
| D1 | The comparator core and `RecordedDecisions` are in `dash-statedigest` (Pn). File IO, zstd, the CLI, the dump and the replay driver are in `dash-conformance` (T). O8's spec §12 now says so (48d899320). | Ruling 5: O9b, O15 and N-layer code reuse the pure halves. Pn takes no file or decompression dependency. |
| D2 | Exit codes: 0 clean, 1 diverged, 2 error, 3 incomplete. Diverged means a key differs, or a `--require` key is absent from a pair. Otherwise the comparison is incomplete if nothing was compared, if the range stops short of `--from`/`--to`, if any key of the mode was absent from some pair (uncovered), or if a linear input skips heights inside the range (D4). An inverted range (`--from` above `--to`) is an error. `--require` turns a named key's absence into a divergence; it never makes another key's absence pass. Clean means every key of the mode was present and equal in every pair. As a result, a digest never compares clean: digests lack the six golden-only `C.s` keys (§5.3), so digest-vs-digest and digest-vs-golden comparisons of Core's own records end at exit 3. The tests assert that verdict, with exactly those six keys uncovered. Linear mode refuses `--org`, and refuses a `--require` naming only observation keys. A dump that fails after a divergence is a warning, and the exit stays 1. | Ruling 1. O8 §10.3 carries the erratum (48d899320), so an uncovered key cannot read as a pass. Review finding B1: an earlier version let `--require` narrow the clean check to the named keys. |
| D3 | zstd is decoded by the `zstd` crate 0.14 (`zstd-safe` 8.0.0) over the `zstd-sys` 2.1.0 that RocksDB already brings in. The lockfile change is additive. `Cargo.lock` holds `zstd-safe` at 8.0.0, so `zstd-sys` does not move; the manifest does not pin it. Only `dash-conformance` depends on it. libzstd decodes every frame to the end of the file, skips skippable frames and checks content checksums and declared sizes; `store.rs` unit tests pin each of these. A file is decoded when it starts with a zstd or skippable frame magic, whatever its name. `cargo deny check` passes. `node-fuzz` depends on neither crate. | Ruling 2: one decoder implementation in the tree. A pure-Rust decoder (`ruzstd`) was tried in the Sol r1 round on a misquoted ruling and reverted: it needed its own multi-frame and checksum reader, the code libzstd already provides. |
| D4 | Linear mode compares only projections. A record's height decides its slot. A run's first tip `C` may rewind the stack (reindex). It may also jump forward over blocks no run recorded: the projection keeps the jump as a hole. The comparison reports the skipped heights inside the range for each side (`Report::skipped`, "unrecorded heights" in the text report, `skipped` in `mismatch.json`) and never calls such a run clean: a hole on one side is also a gap mismatch (exit 1), and a hole both inputs share is incomplete (exit 3). A run that stops at the first mismatch lists the holes read up to it. Stream mode compares the attempts each input recorded and does not detect heights both inputs skip: two recordings that share a roll-forward can compare clean there. Coverage claims therefore come from linear mode (manager ruling, Sol r1 round). When `D` records pop the whole stack, the last popped block stays as a floor, and the next `C` must link to it. Within a run, a gap, an overlap, an unlinked `prev`, or a `D` of a block that is not the tip is an error, not a mismatch. A `D` pops the stack only with `res:"ok"` from `tip`, or with `ok`/`unclean` from `replay`. A file's `H` records must all name the chain of its first. | §10.2 defines the projection, not its failure cases. An input that is not a chain has no linear meaning, so a planted `prev` change fails projection in linear mode and is reported in stream mode (tested). |
| D5 | A linear comparison of two nodes that started recording at different heights gaps at the low end unless `--from`/`--to` give the common range. The tool does not narrow the range by itself. | Narrowing it would hide a node that lost its early records. The tests pass the common range explicitly. |
| D6 | Core against Core: linear mode is clean on 228 of the 230 same-test node pairs, golden against golden and digest against digest (with `--require` on every patch key). The two exceptions are `rpc_invalidateblock` node2, which mines its own chain. Stream mode on `org:"tip"` is gated on the 112 measured clean pairs; it checks attempt order, while the coverage claim rests on linear mode (D4). The module docs of `conformance/tests/digest_compare.rs` list each excluded pair with its reason: node-local rejects, isolated forks and reorgs, and `ban_reset` results from node-local PlatformBan metadata. | Ruling 4. Stream mode compares every attempt in order, so any attempt only one node made diverges. |
| D7 | The origin gap: until CH3a/CH7a give V's connector the origin, rdashd's records are all `org:"tip"`. Comparisons against Core therefore run in linear mode, or in stream mode with `--org tip`. No key depends on the origin except through the projection. | Accepted at checkpoint 1. `BlockConnector` receives no origin (CH1-node bf90eef84). |
| D8 | On mainnet and testnet, stdout names keys and never shows values. `DASH_EMBARGO_DIR` must be an absolute path to an existing directory; anything else is refused. The dump goes under `$DASH_EMBARGO_DIR/statedigest` (a `--dump-dir` must resolve inside it), and the tool refuses to run without that variable, before it compares anything. The mainnet/testnet refusal now applies with `--no-dump`. Regtest and devnet print values and dump to `--dump-dir` (else the private corpus). Directories are 0700 and files 0600, created new. | Ruling 6, PLAN §7.5. |
| D9 | The dump's optional RPC detail refuses the shared oracles' RPC ports (27998, 37998), whatever the URL's path, and any cookie that resolves under `/work/chains`. The dump never contacts the oracles: its `quorum *` calls are not pure reads. | The oracles are pure-read and shared (IMPLEMENTER). |
| D10 | Keyed lookup: a `(name, args)` recorded k times returns its k answers in order. Asking it again repeats the answer if all k answers were the same; otherwise it is a miss. Strict lookup needs the next recorded entry. `finish` fails under strict on queries never asked, and under keyed returns them for the caller to report. | §7.2 leaves open what happens after the k-th ask. Repeating one stable answer is safe, and guessing between different answers is not. |
| D11 | `RecordedDecisions::load` builds its own run join instead of calling `recording::join`, which O8 made `pub(crate)` for it (d8af6c543). Runs are matched by their `run` string. Every orphan is collected with its file and line, and a digest run with no decisions run is accepted. A seq may appear once per run, across `C`, `R` and `D` records. `final_connect(b)` names the attempt behind the digest's last tip `C` of `b` over every run (the `C` the golden keeps, §9.2). It is `None` when that `C` is in a run without decisions; it never falls back to an earlier run's attempt. An attempt's `#n` counts the joined attempts of its `(b, org)` only. | `join` is a pass/fail check: it needs equal run counts and stops at the first problem. §7.3 lets `-statedigestlog` be set without the decisions flag, and a replay needs every orphan listed. O8 can return `join` to private. |
| D12 | `Node::verify` checks each stored file against `extract.json`: the digest, decisions and golden by `<name>.sha256`, and `blocks.dat` by `blocks_dat_sha256`. All four must be stored and hashed: a missing file, a missing hash or a differing hash fails. O8's store (bc3fa7831, merged here) binds and carries all four for every node. | A set with a file or hash missing is not verified, so it cannot pass as one. `store.rs` is the only code that knows the layout. |
| D13 | The `dash-statedigest` unit tests use synthetic records, labelled as such. Every test over Core's records is in `dash-conformance`, which can read zstd. The planted-mutation tests change one value of a Core record. They leave out the `S` records, which no comparison reads, except in the case that checks the dump's sparse excerpt. | D1 keeps zstd out of Pn. `S` records are 86% of a golden's bytes, and keeping them made the debug-build tests take minutes. |
| D14 | O8 made `recording::join` `pub(crate)` (d8af6c543) for O9a, and O9a does not call it (D11). | O8 owns that change (ruling 7) and can return it to private. |
| D15 | `dash-conformance` depends on `dashd-chainstate` with `statedigest` and without `rocksdb`: the replay runs V on `MemBlockFiles`, `NullMempool`, `NoFlush` and `NoUi`, with CS3's `CoreChecks` and `check_block_index` on. V needs no feature of its own. `DigestTap` sits behind `statedigest`, so a node build without it carries no digest code. | The replay checks what V decides (acceptance, the active chain, the header keys), not storage. RocksDB would add a C++ build to every conformance build for nothing the replay reads. |
| D16 | What the tap can record is what V hands its connector (`digest_tap.rs` module docs): a `C` has the header keys of §5.1 only, `fx` is absent, every record is `org:"tip"`, and `D.res` folds Core's `unclean` into `failed`. The replay log is therefore compared in linear mode, with `--require` on the header keys; it is incomplete (exit 3), with the other `C.s` keys uncovered, until CH3a's `ConnectBlock` fills them. | The seam's `bool` and its missing origin (D7) are CH1-node's; the derived and golden keys need the real connector. An absent key stays uncovered rather than claimed (D2). |
| D17 | The params come from the node's `extract.json`: regtest at Core v24 with each `chain_args` entry passed to `ChainParamsBuilder::arg` by its option name. A node whose `other_params_runs` is not empty is refused, as is an unknown option or a missing `chain_args`. | The recording ran under those options; the store already carries them. A node restarted with other options needs per-run params, which no regtest v24 node needs yet. |
| D18 | The mock clock: before each block, the replay sets it to `A.t` of the attempt behind the block's final-chain connect (`RecordedDecisions::final_connect`); a block without one keeps the previous time. V starts at genesis's recorded `A.t`, else at that of the first block that has one, else at genesis's header time. | Core's checks read adjusted time (the future-time limit); the recorded attempt's clock is the one the node used. A node that ran on mock time needs the per-block clock: `p2p_invalid_block` node0's last block is past the future-time window of the earlier attempts, and the tests replay it. |
| D19 | The replay is linear only: `blocks.dat` holds the node's active chain in height order (§13.1), with no side branches, invalid blocks or proposals. Each block after genesis must be accepted and leave a valid state, and V must stop without an `AbortNode` or a tripped fail-stop latch; either is reported ahead of the reply V never sent, the latch with its first reason. Acceptance does not prove a connect, so V's final tip must also be the file's last block at the height of a chain of every block handed in. A repeated or duplicated block other than genesis reaches V and fails the acceptance check (a block before its parent) or that tip check (fewer distinct blocks than handed in); a second genesis never reaches V (D22). The output digest is created new and never overwritten; a replay that fails removes it, and if removing it fails (other than the file being gone already) the error names both failures and the file left. The tests replay every stored regtest v24 node that ran one parameter set (77 of 81) and compare it with its golden from the golden's first height (D5). What the replay must end on comes from the corpus (D21), not from the golden: V ends on that tip, the golden's last block is that tip, and every header key is equal at every height. | The store records no other block bytes. Replaying attempts in stream order needs the side blocks, which O8's store does not keep. A partial log is not a digest of what V did. |
| D20 | The replay runs with SPORK_19 (ChainLocks) off, as `StaticSporks::for_network(&p, Some(false))` sets it. | The replay feeds V no ChainLock and no spork message, so the value decides nothing yet. A replay that feeds recorded ChainLocks needs the node's recorded spork state. |
| D21 | The replay is bound to the `extract.json` beside the node's files. It parses that file once and, before it reads anything else, checks the hashes against it (`Node::verify_against`, the check `Node::verify` runs), so `blocks.dat`, the digest and the decisions (and the golden, which `verify` also checks) must be the files `extract.json` hashed; a mismatch is exit 2, before V starts. After the replay, V's tip height must be the tip of `extract.json`'s summary and V's tip the golden's last block (the golden is hashed too). There is no `--no-verify`: a test that edits an input writes the edited files' hashes into its copy's `extract.json`. The all-node test takes the tip height and the golden's block count from the summary and the tip hash from the hashed `blocks.dat`, independently of the golden. The check trusts `extract.json`, which nothing hashes. For the git-tracked vectors the tests and the gate use, git is the provenance and the replay is bound to the corpus. The CLI also takes any other node directory; there the replay proves only that the files agree with that directory's `extract.json`, and the `digest replay` help says so. | Sol r1 F1: a `blocks.dat` cut to genesis with its golden cut to match replayed and compared without a mismatch. With the hashes it is refused; with rewritten hashes the summary tip still refuses it. A chain of the same height in `blocks.dat` with only its hash rewritten fails on the golden's last block. What is left needs `extract.json` itself rewritten: Sol r2 rewrote the hashes and the summary of an untracked shortened copy together, and it replayed at exit 0. The summary carries no tip hash, so the hash comes from the hashed `blocks.dat`. |
| D22 | `blocks.dat` must hold genesis as block 0 and nowhere else: an empty file, a block 0 that is not genesis and a later genesis are each exit 2 with a named reason, before V starts. The replay hands V every block after block 0. | Sol r1 F2: an empty file replayed to a genesis-only digest, and a second genesis was skipped silently, so a malformed input replayed clean. |

Review nits left open in O9a-1:
- `RecordedDecisions::load` takes each file as one byte slice. The regtest files are small; streaming the input is for O9a-2, if mainnet replay needs it.
- The dump checks that `DASH_EMBARGO_DIR` is absolute and exists. It does not check the directory's group or world permissions; the files it creates are 0600 and its directories 0700.

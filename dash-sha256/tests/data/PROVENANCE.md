## NIST CAVP

Downloaded on 2026-10-08 from
<https://csrc.nist.gov/CSRC/media/Projects/Cryptographic-Algorithm-Validation-Program/documents/shs/shabytetestvectors.zip>
(zip sha256 `929ef80b7b3418aca026643f6f248815913b60e01741a44bba9e118067f4c9b8`). The three
`SHA256*.rsp` files are copied with their CRLF line ends converted to LF (the repository's
`.gitattributes` and pre-commit policy); nothing else changes. The originals' sha256 (CRLF):
ShortMsg `75e1cb83994638481808e225b9eb0c1ebd0c232d952ac42b61abce6363be283c`, LongMsg
`6fac36f37360bcf74ffcf4465c18e30d6d5a04cc90885b901fc3130c16060974`, Monte
`29ea30c6bb4b84e425fb8c1d731c6bb852dac935825f2bd1143e5d3c4f10bfb9`. The table gives the LF
files' hashes. CAVS 11.1, generated by NIST in May 2011: 65 short messages (0 to 512 bits), 64
long messages (up to 51,200 bits), and the 100-checkpoint Monte Carlo test.

## `core-crypto-tests.json`

```
dash-sha256/contrib/extract-crypto-tests.py ~/workspace/dash 0364ed626ec2eaa518bf1ae4a0566ce638c7fe18 \
    > dash-sha256/tests/data/core-crypto-tests.json
```

The script reads `crypto_tests.cpp` from git at the commit and records each `TestSHA256(input,
digest)` call of `sha256_testvectors` with its line. Two inputs are generated, not literal:
`std::string(1000000, 'a')` (stored as a repeat) and `test1` (Core's `LongTestString()`, which
`tests/vectors.rs` ports). The v23.1.8 file has the same 11 vectors, one line earlier.
`tests/vectors.rs` runs them through a port of Core's `TestVector` (whole input, then random
pieces with a copy of the hasher finished near the end).

## `core-fixture.json`

```
dash-sha256/contrib/core-harness/build.sh ~/workspace/dash 0364ed626ec2eaa518bf1ae4a0566ce638c7fe18 <harness>
echo fixture | <harness> > dash-sha256/tests/data/core-fixture.json
```

`build.sh` compiles Core's unmodified `sha256.cpp`, `sha256_sse4.cpp`, `sha256_sse41.cpp`,
`sha256_avx2.cpp` and `sha256_x86_shani.cpp` (taken with `git archive` at the commit) with the
per-file flags of Core's build, next to `harness.cpp`. The `fixture` command hashes inputs from a
splitmix64 generator seeded by the case: SHA-256 of every length 0 to 320 bytes and 15 longer
ones (to 100,003 bytes), each whole and in random pieces; `SHA256D64` of 0 to 33 inputs. Before
writing a line it checks that every implementation Core selects on the CPU (`SHA256AutoDetect`
with STANDARD, USE_SSE4, USE_SSE4_AND_AVX2, USE_SSE4_AND_SHANI and USE_ALL) gives the same
digest, whole and in pieces.

Produced on the node program's build machine (Xeon E5-2687W v4: SSE4.1, AVX2, no SHA-NI). The
same command gave a byte-identical file (md5 `577cceec1c7d299d1fafe73edc57d2aa`) from:
- the v23.1.8 build;
- the v24.0.0-rc.3 build under `qemu-x86_64 -cpu max` (QEMU 10.2.1), where Core selects
  `x86_shani(1way,2way)`;
- the v24.0.0-rc.3 aarch64 build (`build.sh … aarch64`, `aarch64-linux-gnu-g++`) under
  `qemu-aarch64 -cpu max`, where Core selects `arm_shani(1way,2way)`.

`tests/core.rs` regenerates the inputs with the same generator and checks every implementation
of this crate against the file.

## `core-long.json`

```
echo long-fixture | <harness> > dash-sha256/tests/data/core-long.json
```

The same harness hashes a 1 MiB block from the splitmix64 generator (seed 2^29), repeated and cut
at seven lengths around 2^29 bytes, where the message's bit length passes 2^32 and the high word
of Core's length field is first non-zero. The lengths end at 63, 0, 1, 55, 56, 63 and 0 mod 64, the
padding cases. Every implementation Core selects on the CPU must agree before the file is
written. The v23.1.8 build gave the same file. Python's `hashlib` gave the same seven digests,
as an independent check.
